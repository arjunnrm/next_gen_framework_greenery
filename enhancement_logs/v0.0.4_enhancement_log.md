## Why this release exists

Assets for UC3, UC6 and UC7 were spread across `docs/`, `onboarding/`, `flowx_testing/`,
`resources/` and the repository root, so provisioning a use case meant gathering files from
five places and knowing which of two similarly-named UC6 directories was current. This
release puts each use case's documents, onboarding specs and source data in one folder, so a
setup script copies one tree per use case into that use case's Volume.

The defects in E1–E3 were not the goal. They surfaced while checking the documentation
against the code, which is the point of doing that check.

## E1 — `asn1_pdu_name` was marked required and is not

| | |
|---|---|
| **Previous** | `onboarding_spec.schema.json` listed `asn1_pdu_name` in the `required` array for ASN.1 `source_config`. The Spec Builder enforced the same in `registry.js` (`req:1`) and `config/registry/ingestion.json` (`"required": true`). `attribute_knowledge.json` told users "Required — onboarding rejects the flow if this is missing." |
| **Current** | Optional in all four places, described as: leave blank to auto-detect the root PDU, supply a name only to override detection. |

The decoder has auto-detected a module's root PDU since 0.0.2. An absent or blank
`asn1_pdu_name` *is* the documented request to auto-detect
(`asn1/decoder.py:35-40`), and `spec_validator.py:1597-1603` implements exactly that —
it type-checks the value only when one is present.

So the two validation gates disagreed. Per the repo's own rule that a spec must pass the
JSON schema **as well as** `spec_validator.py`, every valid auto-detect ASN.1 spec passed the
validator and was rejected by the schema. `UC7_cdr_asn_bronze.json` has four flows, all
relying on detection, and failed on all four — which is why UC7 could not be onboarded from
its own spec.

The app carried the same phantom requirement, so the Spec Builder blocked specs the framework
accepts, and its attribute inspector stated the opposite of the framework's behaviour.

## E2 — `destination_config.compressed` is not an attribute

| | |
|---|---|
| **Previous** | Five specs set `"compressed": true` on a `DATABRICKS_VOLUME` observability destination. |
| **Current** | `"compression": "GZIP"` — the real attribute, a string. |

The runtime reads `destination_config.compression`, validated against
`ALLOWED_OBSERVABILITY_COMPRESSION = {"GZIP", "gzip", "none", ""}`
(`spec_validator.py:2033`, `observability/destination_dispatcher.py:139`). There is no
`compressed` key anywhere in the framework.

The boolean was therefore inert. It read as "gzip is on" while the exporter applied its own
default — the exact failure mode the "removals are rejected, never ignored" rule exists to
prevent, arriving through a typo rather than a removal. It was corrected to
`"compression": "GZIP"` rather than dropped, preserving the evident intent.

`onboarding_spec_full_reference.json` was one of the five. It is what spec authors copy from,
so leaving it would have kept minting new specs with a dead key.

## E5 — use-case docs staged into mkdocs, not duplicated

mkdocs can only include files beneath `docs_dir`, and the use-case documents now live outside
it. Keeping a second copy under `docs/` would reintroduce exactly the drift
`build_docs_reference.py` exists to prevent, so that script now stages
`BT_Usecase/<UC>/docs/*.md` — and the `.csv`/`.sql` assets those pages link to as siblings —
into `docs/UC*/` at build time, alongside the reference trees it already derives.
BT_Usecase is the source of truth; `docs/UC*/` is derived output and gitignored.

## E7 — data classified before anything was deleted

Every data asset was classified by provenance trace — which generator writes it, which loader
reads it — and recorded in `docs/DATA_PROVENANCE_CLASSIFICATION.md`.

An initial estimate put ~45 files up for deletion. Building the reference set
programmatically instead (every basename searched across `notebooks/ scripts/ src/ tests/
resources/` plus the in-tree generator scripts) showed `bt_group`, `asn1_cdr_*` and
`zip_ingestion` **are** referenced. The real orphan count was **10**.

## E8 — raw JSON debug viewer

A `raw` button beside the preview pane's copy control opens a modal with the complete
unparsed spec and a one-click "copy all". Always JSON and always unfiltered regardless of the
preview pane's JSON/YAML toggle — a debugging copy-paste should never be a half-rendered view
of the thing being debugged. Payload size is displayed so a truncated paste is obvious.

## E9 — new documents

`docs/SCRIPTS_GUIDE.md` (every active script: purpose, prerequisites, command line) and
`docs/DATA_PROVENANCE_CLASSIFICATION.md` (every data asset, **[Customer-Provided]** vs

## Known gaps

1. **Not deployed.** No `bundle deploy` was run. `databricks bundle validate -t metaflow_v7`
   passes, but validation is not deployment, and deploying while a pipeline or test wave is
   running prunes `<artifact_path>/.internal/` and kills the run. Deploy deliberately, when
   nothing is in flight.
2. **`dev_flowx` does not validate** — `volume flowx.config.wheels does not exist`. This is a
   pre-existing bootstrap condition in that workspace, unrelated to this release
   (`bootstrap_workspace.py` must run first); `metaflow_v7` validates clean.
3. **Full `tests/unit` not re-run end to end.** The suite takes ~1h45m and the sandbox has no
   local Java, which produces a large pre-existing failure baseline. The tests touching the
   moved fixtures and changed schema were run and pass. Compare by failing-test-ID, never by
   count, when the full suite is next run.
4. **UC3 test data is not in the tree.** `build/` is gitignored, so `build/uc3_test_data/**`
   is regenerated on demand via `scripts/generate_uc3_test_data.py --out-dir
   build/uc3_test_data`. Deliberate — it is [Simulated] output derived from the
   [Customer-Provided] DDL sheets, which are in the tree.
5. **`docs/UC*/` is derived.** Editing it directly is wasted work; the next
   `build_docs_reference.py` run overwrites it. Edit `BT_Usecase/<UC>/docs/`.
