# v1.7.09 — UC3 streaming lane reads the real Debezium CDC feed

**Date:** 2026-09-11
**Scope:** UC3 streaming-CDC onboarding spec, its pipeline/job resources, docs and unit tests.
**Framework source changed:** **none.** `pyproject.toml` stays at `0.0.4` and `databricks.yml`'s
`framework_version` with it — no wheel behaviour changed, so no rebuild is required for these
changes to take effect (the spec reaches the engine through the control tables).

---

## 1. Scope

| ID | Enhancement |
|---|---|
| E1 | Point the three UC3 streaming flows at the real multiplexed Debezium landing table `<catalog>.staging.oracle_excalibur_cdc`, replacing three staging tables that do not exist |
| E2 | Parse the Debezium envelope out of the `value` JSON string column with an explicit per-table `schema_ddl` |
| E3 | Split the multiplexed table into three Bronze targets with `dq_config` drop rules, while keeping a single physical read |
| E4 | Sequence CDC by the Oracle SCN instead of `sys_update_date` |
| E5 | Make the pipeline `continuous: true` for seconds-level latency, and move observability to continuous mode |
| E6 | Nine new unit tests pinning E1–E5 and the three silent parsing traps found while building them |

## 2. Previous vs current

### E1 — the source table

| | Previous | Current |
|---|---|---|
| `source_config.source_table` | `physical_device_stream` / `customer_stream` / `subscriber_stream` — three **different** tables, written by the Job 1 simulator | `oracle_excalibur_cdc` — the **same** table on all three flows |
| Shape | Pre-split (one table per Oracle table) and pre-flattened (one column per Oracle column) | One multiplexed landing table; all three Oracle tables interleaved, row image nested in a JSON string |
| Reality | Those three tables do not exist in `bt_digital_poc.staging` | The table exists, is fed by Debezium Server through the Zerobus gRPC sink, and held 196 rows across 4 topics when this was built |
| `starting_version` | absent | `0`, so Debezium's initial snapshot (`op='r'`, 150 of the 196 rows) is ingested as the Bronze initial load rather than skipped |

### E2 — envelope parsing

| | Previous | Current |
|---|---|---|
| `json_string_columns` | absent (source was already flat) | `[{column: "value", schema_ddl: "struct<payload:struct<before:…,after:…,source:…,op:…>>"}]` per flow — 1939 / 5138 / 7252 chars, generated from the live Connect schema |
| `data_standardization_sql` | 2 / 3 / 0 expressions (`CAST(NULL AS STRING)` for `Null(DF)=Y` columns) | 35 / 94 / 135 expressions: 3 CDC control columns + one `CASE WHEN op='d' THEN before.<COL> ELSE after.<COL> END` per payload column + `src_deleted_flg`, then the unchanged `Null(DF)=Y` blanks |
| Column count verified | — | 31 / 90 / 131, matching `BT_Usecase/UC3/data/uc3_oracle_source_schema.sql` **column-for-column and in order** |

### E3 — the fan-out

| | Previous | Current |
|---|---|---|
| Row filtering | none needed — each flow had its own table | `dq_config.rules` with `action: "drop"`: `only_<table>_topic` on `destination`, plus `cdc_op_recognised` to drop the heartbeat topic |
| Physical reads | 3 (one per staging table) | **1.** All three flows share one `ReadIdentity`, so `engine/source_plane.py` emits a single base streaming read consumed by three `bind()` calls |
| `dq_config` | absent on all three flows | present on all three |

`data_standardization_sql` **cannot** be used for the split: it is projection-only (one
`withColumn` per entry, `ingestion/standardization_sql.py`). `source_config.filter_condition`
does not exist for ingestion flows — it is reconciliation-only. The DQ `drop` action is the
framework's row filter, and it is applied to the staged view *before* `apply_changes`.

### E4 — sequencing

| | Previous | Current |
|---|---|---|
| `sequence_by_column` | `sys_update_date` | `__cdc_scn` — `CAST(COALESCE(payload.source.scn,'0') AS DECIMAL(38,0))` |
| Ordering guarantee | none within a second: two changes committed in the same second share `sys_update_date`, so `apply_changes` ordered them arbitrarily | monotonic per redo stream; also the column the landing table's own comment names for dedup |
| At-least-once delivery | unaddressed | handled by the sequencer: `apply_changes` discards a replayed row whose sequence is equal or lower. `source_config.remove_dups` is deliberately **not** set — it is *full-row* dedup with **unbounded** streaming state, and the per-row `idempotency_key` would make every replay unique to it anyway |
| `columns_to_exclude` | `[sys_creation_date, sys_update_date]` | `+ [__cdc_op, __cdc_source_table]`. `__cdc_scn` is **not** excluded — `apply_changes` must be able to read its own `sequence_by` column |

### E5 — latency

| | Previous | Current |
|---|---|---|
| `uc3_streaming_cdc_pipeline` | `continuous: false` — latency = trigger interval, minutes at best | `continuous: true` — each micro-batch commits as new CDC rows land |
| `event_log:` on the pipeline | absent | `<catalog>.observability.uc3_excalibur_streaming_cdc_event_log` |
| `observability[].mode` | `triggered` | `continuous`, with `destination_config.event_log_tables` naming that table |
| `uc3_streaming_cdc_job` | `run_pipeline_update` (pipeline_task) → `observability_export` (`depends_on`) | pipeline task **removed**; holds only an on-demand export taking `pipeline_task_run_id` as a job parameter |
| How the lane is started | `bundle run uc3_streaming_cdc_job` | `bundle run uc3_streaming_cdc_pipeline` |

The job split is forced, not stylistic: a continuous update never reaches a terminal state, so
the old `depends_on` chain meant `observability_export` waited on a task that never finished and
therefore never ran. The triggered observability engine *hard-requires* `pipeline_task_run_id`
(`observability/runtime_params.py::REQUIRED_TRIGGERED_PARAMETERS`) resolved from an upstream
pipeline task; a standing pipeline has none. The framework already anticipates exactly this —
`spec_validator.py` requires `event_log_tables` for, and only for, `mode: "continuous"`, because
"the continuous observability pipeline has no upstream task to resolve a pipeline from".

Pattern precedent: `resources/observability/observability_otel_streaming_pipeline.yml` is the
bundle's existing `continuous: true` pipeline, and likewise has no wrapping job.

## 3. Defects found

Three of these produced a spec that passed **both** validation gates and would still have
written a wrong Bronze table. All three were found by querying the live table — not by
validation, not by review — which is why each now has a unit test.

| # | Defect | Symptom | Root cause | Fix |
|---|---|---|---|---|
| D1 | Lowercase `schema_ddl` | **Every** payload column parsed to NULL — all 31/90/131, primary keys included. Row counts, op codes, SCN and delete flags all looked perfect. | `from_json` field matching is **case-sensitive**; Debezium emits Oracle's UPPERCASE names | Declare and reference the row-image fields uppercase; lowercase only in the `AS` alias |
| D2 | Connect `Timestamp` declared as `TIMESTAMP` | `sys_creation_date` came back as year **+58664** instead of 2026 | Connect `Timestamp` is epoch **milli**seconds in an int64; Spark reads a `TIMESTAMP`-typed number as **micro**seconds — a silent 1000x error | Declare those fields `BIGINT`, convert with `timestamp_millis()` in the projection |
| D3 | Duplicate projection aliases | `AMBIGUOUS_REFERENCE` when the projection was replayed as SQL; at runtime `withColumn`'s last-wins silently picked a winner | The `Null(DF)=Y` `CAST(NULL …)` entries were carried forward *and* the payload loop also extracted those columns | Skip a column in the payload loop when a carried-forward entry already aliases it |
| D4 | Delete rows would have been all-NULL | `apply_as_deletes` could never match a target key | A Debezium delete carries its row image in `before`; `after` is null | Every payload column branches: `CASE WHEN op='d' THEN before.<COL> ELSE after.<COL> END` |

### Pre-existing framework defect found, not fixed

`target_config.columns_to_exclude` is **self-contradictory** in the framework as it stands:

* `cdc/comparison_columns.py` (module docstring) and `onboarding/spec_validator.py` (line ~1196)
  both state it is comparison-only in v2 and "never drops it from the target table";
* `cdc/scd.py::_build_except_column_list` still passes it into `dlt.apply_changes`'s
  `except_column_list` for SCD1/SCD2/SCD3, which **does** drop the column.

So `sys_creation_date`/`sys_update_date` are **absent from Bronze**, not merely excluded from the
value hash — contradicting `UC3_MASTER_DOCUMENT.md` §8's attribute table. Left as-is (out of
scope, and changing it would alter the shape of every existing SCD target); documented in
§3a.8 and corrected in the §8 row. Harmless for CDC correctness here because sequencing moved
to the SCN.

## 6. Known gaps

1. **Not deployed and not run.** Every gate above is offline or read-only. The pipeline has not
   been deployed or started, so the row counts in §5 are *predicted* from replaying the spec's
   SQL, not observed in Bronze. Deploying requires the operator decision in gap 2.
2. **Continuous billing is an operator decision.** `continuous: true` keeps serverless compute
   up for as long as the pipeline runs. That is the cost of seconds-level latency and should be
   confirmed before the first start on a shared workspace.
3. **The landing table is a point-in-time sample.** 196 rows, 4 topics, one `destination`
   value per Oracle table. Schema evolution is unproven: `schema_ddl` is explicit and
   deterministic, so a **new** Oracle column is silently ignored until the DDL is regenerated
   (which is the correct trade against the inferring `from_json`, whose inferred schema lives
   only in a streaming checkpoint — but it is a maintenance obligation).
4. **`columns_to_exclude` framework contradiction is unfixed** — see §3, "Pre-existing framework
   defect". Two audit timestamps are dropped from Bronze where the docs said they were kept.
5. **Deleted keys in SCD1 with no `before` image would be unmatchable.** The 3 live deletes all
   carry a full `before` image, so this is theoretical here, but a Debezium connector configured
   without full row-image capture on delete would break the delete path.
6. **Recommended table tags still missing** (`cost_center`, `classification`, `sla`) on all
   three flows — the 9 validator warnings. Pre-existing; not introduced here.
7. **A one-time full refresh may be required.** The flows now stream a *different* source table
   than the control-table rows were onboarded with. Per this repo's own experience, changing what
   a DLT flow streams from fails the next *incremental* update; the first run after re-onboarding
   should be a full refresh, and any auto-retry loop stopped first.
