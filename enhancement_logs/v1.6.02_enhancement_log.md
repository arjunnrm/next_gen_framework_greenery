# v1.6.02 Enhancement Log

**Release date:** 2026-09-02
**Progress Tracker:** `Completed — implemented and verified LIVE on the arjun target
(dbc-aa517a4b-be89). The retention copy was proven end-to-end: a wheel was archived, a subsequent
bundle deploy PRUNED it from .internal/, and the archived copy survived. --prune-keep, idempotent
re-run, and the missing-archive-folder bootstrap were each exercised against the live Volume.`

**Theme:** wheel retention, and the correction of a false belief the repo had written down.

The framework publishes its wheel to `<artifact_path>/.internal/` on a UC Volume, and every deployed
job/pipeline is pinned to a **fully-resolved absolute filename** — e.g.
`/Volumes/flowx/config/wheels/.internal/flowx-0.0.1788286445689-py3-none-any.whl`.
Because `scripts/bump_and_build.py` stamps a unique epoch-millis version per deploy, nothing is ever
overwritten in place. The exposure is the opposite one: **DABs prunes `.internal/` down to the current
deploy's wheel**, deleting the exact file an earlier-deployed resource still points at.

**The load-bearing finding.** `scripts/build_and_upload_wheel.py`'s module docstring asserted that a
UC Volume "has none of that behaviour … nothing removes an older wheel just because a newer one
appeared". That is **false**, and it is the kind of false that is trusted precisely because it is
written down next to the code. Re-confirmed live on 2026-09-02: three consecutive deploys to the
`arjun` workspace left `.internal/` holding exactly one wheel. The narrower true statement is that
DABs manages *only* `.internal/` — anything elsewhere in the Volume is never pruned. Retention is
therefore an explicit copy OUT of `.internal/`, not a property the Volume gives for free.

**What this release does NOT claim.** The archive is a rollback/forensics net, not a fix for the
mid-run kill. Deployed resources remain pinned to the `.internal/` path, so an archived copy does not
repair a pin whose target was pruned while a pipeline was installing it — recovery means repointing
the resource at the archived path by hand. **Prevention** stays the operational rule, and is now
mechanically enforceable with `databricks bundle deploy --fail-on-active-runs`, which refuses to
deploy while any job or pipeline in the bundle is running.

## 6. Known Gaps

- **The archive does not protect a running pipeline.** Resources stay pinned into `.internal/`;
  recovery from a mid-install prune is a manual repoint. Closing this properly would mean pointing
  resources at a stable, never-pruned path — a larger change that reintroduces the pin-vs-upload
  drift class that deploy-built-and-published was adopted to eliminate.
- **The script is a separate post-deploy step, not automatic.** DABs has no post-deploy hook, and
  `artifacts.*.build` runs *before* upload, so it cannot archive what has not been published yet.
- **`--fail-on-active-runs` is documented, not defaulted.** It cannot be set in `databricks.yml`; it
  must be typed on each deploy.
