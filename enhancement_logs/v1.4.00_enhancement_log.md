# v1.4.00 Enhancement Log

**Release date:** 2026-08-30
**Progress Tracker:** `Completed (offline)` — code, JSON schema, validation, docs, agent skills, app registry and the app frontend bundle are all complete and verified locally. **Live pipeline/job execution against `dev_metaflow` has NOT been run** for this release; see §4c and §7.

**Theme:** subtraction. Five spec attributes and one CDC strategy removed, one attribute added, one execution model narrowed, and one runtime contract made explicit. Nothing in this release adds a new capability to the data plane — the goal was to delete the framework's remaining non-native machinery (a hand-rolled surrogate-key engine, a duplicate normalization switch, a reconciliation mode that could not run on the compute this framework uses) and to replace derived/optional runtime inputs with declared, validated ones.

**The load-bearing decision — every removed attribute is REJECTED at onboarding, never ignored.**
An ignored key is the worst of the three possible behaviours: the spec still onboards, the control
table still gets its row, the pipeline still runs — and it quietly does something other than what
the document says. For `normalize_column_names` and `generate_surrogate_key` specifically, ignoring
would flip a data-shaping behaviour from ON to OFF with no signal at all: columns silently stop
being renamed, rows silently stop carrying the key their target table is diffed on. So each removed
key maps to its own migration sentence, named per spec path, and **presence is the trigger, not
truthiness** — `"generate_surrogate_key": false` is rejected too.

**Delivery method:** implemented in a single session, primarily hands-on rather than by multi-agent
orchestration — the work was one connected refactor across a shared set of files (`spec_validator.py`
alone is touched by five of the seven enhancements), so file-disjoint parallel streams were not
available without a merge problem larger than the edits themselves. Two independent agents were used
at the end for the genuinely disjoint documentation sweeps (test plans + seed notebooks; reference
`.md` + app docs site). Both were verified afterwards against the code on disk, which is how the
`ts_ref_full_snapshot_cdc` id collision in §6 was caught. See §5.

## 2. Previous State vs. Current (Target) State

### E14 — Artifact packaging path
- **Previous:** `dev_metaflow` set `workspace.artifact_path` to `/Volumes/metaflow/framework/wheels/${workspace.current_user.short_name}` — a dynamic, per-target, per-user Unity Catalog Volume path. `dev` set nothing and used the workspace default, so the two targets disagreed on where artifacts live.
- **Current:** **No target sets `artifact_path`.** Both fall back strictly to the DABs standard `${workspace.root_path}/artifacts`. Three reasons, in order of how often they bit: (1) **deployment conflicts** — a per-user path forks the artifact location by whoever ran the deploy, so two engineers deploying the same target published to two places and each rewrote `../dist/*.whl` to their own; (2) the `dev` target **cannot** have a Volume path at all (metastore at its volume ceiling, 52 estimated vs. a limit of 50; `metaflow` catalog at 51 schemas), so the divergence was permanent; (3) it did not buy what it was adopted for — **verified false on 2026-08-30**: DABs prunes superseded artifacts from `<artifact_path>/.internal/` on a UC Volume exactly as it does in the workspace (`.internal/` went from two wheels to one across a deploy).
- **Consequence:** the in-flight-update hazard (`ENVIRONMENT_PIP_INSTALL_ERROR`, seen 2026-08-29 on TC-ING-004/TC-ING-005) was never actually mitigated by the Volume, so the operational rule is the only mitigation and is unchanged: **never `bundle deploy` while a test wave or pipeline is running.** Wheels published by the older manual `scripts/build_and_upload_wheel.py` still sit in the Volume root outside `.internal/`; DABs never managed or pruned those, so any pipeline still pinned to one keeps working.

### E15 — Column normalization: one switch (BREAKING)
- **Previous:** two ways to enable the same thing. `source_config.column_normalization` `{enabled, case}` layered over the legacy boolean `source_config.normalize_column_names`, adjudicated by a three-level precedence ladder, a *presence*-vs-truthiness test on `enabled`, and a contradiction WARNING — roughly forty lines in `resolve_column_normalization` whose only job was deciding which of two synonyms won.
- **Current:** `column_normalization.enabled` is the only switch, read with a plain `.get("enabled", False)`. Absent object, absent key and explicit `false` all mean off. `normalize_column_names` is removed and **rejected** at onboarding.
- **Subtle migration case, called out because it silently changes behaviour:** before v1.4.0 an object that *omitted* `enabled` deferred enablement to the legacy boolean, so `{"case": "preserve"}` on its own was **on**. It now reads as written: **off**. A spec relying on that deferral must add an explicit `"enabled": true`. (This is the exact deferral added as the E05 remediation fix in v1.3.0 — it existed only to make the two-synonym world safe, and goes away with the second synonym.)
- **Naming note that will confuse a future reader if not stated:** the Python *function* `normalize_column_names(df, source_config)` still exists and is still what `notebooks/03_engine/` calls. Only the **config key** is gone.

### E16 — Surrogate-key engine removed (BREAKING)
- **Previous:** `crypto/hashing.py` generated `__framework_surrogate_key` — a SHA-256 over every payload column of every row — gated by `target_config.generate_surrogate_key` and scoped by `surrogate_key_columns` / `surrogate_key_exclude_columns`, with a parallel `reconciliation_flows[].generate_surrogate_key`. It was mandatory for `FULL_SNAPSHOT_CDC_NO_PK` (forced on over an explicit `false`, per v1.3.0's E10) and optional elsewhere.
- **Current:** the module is **deleted**, the column is no longer generated by any flow, and all four spec attributes are removed and rejected. Row identity is `primary_keys` and nothing else; change detection is `columns_to_check`/`columns_to_exclude`. `dq/quarantine.py::_apply_hash_and_surrogate_key_columns` is renamed `_apply_hash_columns` and now only produces `__framework_hash_key`/`__framework_hash_value`.
- **Why it went:** three costs, none small. **Compute** — a full-width hash per row per snapshot on top of the CDC diff. **Fragility** — row identity depended on the exclusion list staying correct; a single volatile column leaking into the basis re-keyed the entire table and `apply_changes_from_snapshot` read that as a delete-and-reinsert of everything. That is not hypothetical: the framework shipped exactly that defect (`__framework_source_file_name` in the basis, so re-delivering a byte-identical snapshot under a new filename churned every row) and fixed it in v1.3.0's E08. **It did not model the data** — two rows identical in every column were one row to the hash, so a snapshot with genuine duplicates could not be represented at all.
- **Legacy data is left alone.** A table materialized before the upgrade still physically carries `__framework_surrogate_key`. It is not dropped; `cdc/comparison_columns.py` still names it in `EXCLUDED_TECHNICAL_COLUMNS` (deliberately — a comparison set that picked it up would compare a stale payload-wide hash against nothing); and `storage/column_ordering.py` no longer front-loads it, so it drifts to the end of the schema on the next rewrite.

### E17 — `FULL_SNAPSHOT_CDC_NO_PK` removed (BREAKING)
- **Previous:** two snapshot strategies. `FULL_SNAPSHOT_CDC` diffed on `target_config.primary_keys`; `FULL_SNAPSHOT_CDC_NO_PK` diffed on the generated `__framework_surrogate_key` when the source had no natural key.
- **Current:** one. Full-snapshot ingestion relies strictly on the [Databricks-native CDC pattern](https://docs.databricks.com/aws/en/ldp/cdc) — `dlt.apply_changes_from_snapshot` over a real key. `dlt.apply_changes_from_snapshot` **requires** `keys`; the withdrawn strategy existed only because the framework was willing to manufacture one.
- **Migration:** a source whose key was simply never declared moves to `FULL_SNAPSHOT_CDC` + `primary_keys`; a genuinely keyless source moves to `TRUNCATE_AND_LOAD`, which replaces the target wholesale and needs no key — an honest full refresh instead of a synthetic diff.
- **Behavioural improvement worth stating:** under the payload hash, a Day-2 field change was reported as a *delete of the old row plus an insert of a new one* — the same entity under two identities. With a declared key it is reported as the `UPDATE` it always was. Expect the first post-migration snapshot to diff as a full delete-and-reinsert (the diff key itself changed), then correct behaviour thereafter.
- **New guard replacing the old one:** `cdc/snapshot.py` used to check inside the snapshot-input dataset that `__framework_surrogate_key` was present. It now checks that the configured `primary_keys` are present — the same defect class one layer earlier. With no generated key to fall back on, a `primary_keys` entry that never reached the clean upstream (renamed by `column_normalization`, projected away by `data_standardization_sql`) *is* the failure, and it is reported with the available columns and the two usual causes rather than as a generic missing-key error from `apply_changes_from_snapshot`.

### E18 — Reconciliation is triggered-only (BREAKING)
- **Previous:** `recon_mode` (`"triggered"` default / `"continuous"`) as a `reconciliation_flow_spec` field, plus a per-run override widget on `05_reconciliation_engine.py`, plus `continuous` and `processing_time` parameters on `run_streaming_target_reconciliation`.
- **Current:** all of it removed, from spec, JSON schema, DDL, validator, notebook widgets and function signatures. Every run is a bounded job task: batch reads, and `trigger(availableNow=True)` for a `read_mode: "streaming"` side, draining the backlog and stopping. **Both** former values are rejected — `"triggered"` included, because it is removed as an *attribute*, so a spec asserting the surviving behaviour still names a field that does not exist.
- **Why `"continuous"` went:** it wrapped a standing stream around a **batch-shaped** unit of work. `run_target_reconciliation` writes one `reconciliation_run_log` row per invocation and checks a batch fingerprint for idempotency, so a never-ending query produced a log row per micro-batch whose fingerprint could never repeat, and counts describing an arbitrary slice of wall clock rather than a comparison anyone asked for. It also **never ran where this framework runs** — a standing trigger on serverless job compute raises `INFINITE_STREAMING_TRIGGER_NOT_SUPPORTED`, which is precisely why scenario 004's continuous task was already blocked in the v1.3.0 test status. Reconciliation answers *"do these two datasets agree as of now"* — a question with a boundary in it. To ask it more often, schedule the job more often.
- **Simplification that falls out:** `task_run_id` narrowing of a side declaring `task_run_id_column` used to be gated on the mode. Every run is bounded now, so the narrowing is unconditional whenever both are configured. One asymmetry is retained deliberately: in a mixed batch/streaming comparison only the **static** side is narrowed, because the streaming side's own micro-batch offsets already are the batch boundary and filtering it would silently discard offsets the checkpoint then advances past for good.

### E19 — Observability runtime parameter contract
- **Previous:** the triggered engine took `run_pipeline_update_run_id` (required) and `catalog` (optional, defaulted to `"poc"`). `dataflow_group_id` was **derived** from the upstream pipeline's `dataflow.group.id`. Environment labelling was an **optional** `deployment_environment` widget. Validation was ad-hoc and per-widget.
- **Current:** four required task parameters — `dataflow_group_id`, `catalog`, `env`, `pipeline_task_run_id` — validated together by the new `observability/runtime_params.py` **before** a `WorkspaceClient` is constructed and before any API call, table read or dispatch. Every missing parameter is reported in one message, so an operator fixing a job definition learns everything wrong with it in one run instead of one per redeploy.
- **Rename:** `run_pipeline_update_run_id` → `pipeline_task_run_id`. The old name baked one convention — a task literally called `run_pipeline_update` — into the parameter name, so it read as a lie in every job whose pipeline task is called something else.
- **`dataflow_group_id`: derived → declared, with the derived value kept as a cross-check.** A derived value cannot detect the most likely wiring mistake there is — `depends_on` pointing at the wrong `pipeline_task`, or a copy-pasted observability block still pointing at the job it came from — because whatever pipeline the task lands on reports *its* group id quite happily and the export succeeds while describing the wrong dataflow. A disagreement now raises and names both. A pipeline that declares no `dataflow.group.id` at all is **not** an error: the cross-check logs at INFO and the declared value stands, so this stays an optional safety net rather than becoming a new hard requirement on every pipeline in the estate.
- **`env` replaces the optional `deployment_environment`.** Optional environment labelling is worse than none — telemetry that omits it is silently merged with every other environment's in the consumer, and nobody notices until a prod alert fires on dev data.
- **New failure mode caught explicitly:** a mistyped task key does **not** fail loudly on its own. When `<key>` in `{{tasks.<key>.run_id}}` does not name a task in the job, the Jobs service substitutes nothing and passes the literal template text through as the parameter value. `runtime_params.py` detects exactly that and names the cause; without it, the symptom is a confusing "must be numeric" complaint about a value nobody typed.

### E20 — `encrypted_columns[].source_data_type`
- **Previous:** encryption replaced a column's physical type with ciphertext binary, and the pre-encryption type was captured **implicitly** from whatever Spark reported at that moment, then persisted as the Unity Catalog `original_data_type` column tag. `_validate_encrypted_columns`'s own docstring stated the field was "never user-supplied".
- **Current:** an optional `source_data_type` may be **declared** per encrypted column (`"string"`, `"decimal(18,2)"`, `"timestamp"`, …). **Omitting it is safe and is the documented default path** — the observed type is used, exactly as before, so no existing spec needs editing and none is invalidated.
- **What declaring it buys:** the captured type is what a downstream `source_inputs[].decrypted_columns[].cast_to_type` is validated against. With no declaration, whatever the source delivers today becomes the tag — so a source column that quietly changes from `string` to `int` silently re-tags, and the **decrypt** side starts failing later, far from the cause. With a declaration, the disagreement is caught at encryption time, naming both types, and raises `CryptoError` rather than picking a winner. Comparison is case-insensitive and whitespace-trimmed, so an author does not have to match Spark's own casing to be believed.
- **Validation split, deliberately:** onboarding type-checks it only (non-empty string). The declared value is a Spark type string that the validator has no Spark session to parse and no source schema to check against; the meaningful comparison is declared-vs-observed, and that can only happen where both exist.

## 6. Defects Found and Fixed

Three defects were introduced during this release's own implementation and caught before completion. All three are recorded because each is an instance of a *class* worth not repeating.

1. **[MAJOR — introduced by this release] Duplicate `flow_step_id` / `target_table` / `input_name` across four spec documents.** Renaming the `_no_pk` demonstration flows onto their non-`_no_pk` names collapsed each onto an id that already existed (`ts_ref_full_snapshot_cdc` in both `onboarding_spec_full_reference.json` copies; `ts_template_full_snapshot_cdc_example` in both `pipeline_onboarding_template.json` copies). `input_name` must be unique across the **whole** spec — one of the cross-array-element constraints JSON Schema cannot express — so these documents would have failed real onboarding validation while remaining schema-valid. Found by an independent agent reading the JSON. **Fixed:** the second flow of each pair is now `*_minimal` (the strategy-plus-keys permutation, distinct from the full form with a delete-marker column). **Follow-up shipped with the fix:** a repo-wide cross-flow uniqueness audit, now part of §4a and reporting 0 violations.
2. **[MAJOR — introduced by this release] Unescaped braces in an f-string DDL comment.** The new `column_normalization ({enabled, case} -- ...)` text was added to `ddl_definitions.py`'s `get_ingestion_flow_spec_ddl`, which is an f-string; `{enabled, case}` was evaluated as an expression and raised `NameError`, breaking every control-table DDL. Caught by `test_observability_config_ddl.py`. **Fixed** by escaping to `{{enabled, case}}`, matching every other literal brace in that file.
3. **[MAJOR — introduced by this release] JSON/YAML template divergence.** `pipeline_onboarding_template.json` and `.yaml` are asserted equivalent by `test_spec_loader.py`; the defect-1 fix was applied to the JSON only. The YAML also carried the same duplicate-id collision, and a naive text replace hit **both** occurrences instead of the second. **Fixed** by editing the second flow positionally. Caught by the existing test.

Also worth recording, from the same session, because it is the second occurrence of a pattern already documented in this repo's memory:

4. **[Process] A non-greedy DOTALL regex used to delete three field definitions from `databricks-app/web/src/Builder.jsx` over-matched and swallowed ~650 lines**, surfacing only at `npm run build`. This is the same class as v1.3.0-era's blanket-`sed` identifier mangling. **Rule adopted:** for structured JS/JSX/Python deletions, anchor on exact line prefixes and delete by index — never `re.sub(r'...\.*?\}\),', '', s, flags=re.S)` — and always run `node --check` / `npm run build` after touching that tree.

Three further stale references were found by the documentation agents in files outside their edit scope, all confirmed real against the source and fixed: `observability/agent_tools.py`'s failure-matrix message still naming `run_pipeline_update_run_id`; three `ddl_definitions.py` column comments still listing removed values; and `sample_data/generate_sample_datasets.py`'s docstring claiming "1 update" for a fixture pair that in fact contains **2** (verified by diffing the committed CSVs: John Smith `ACTIVE`→`INACTIVE` **and** Fatima Ali `Dallas`→`Fort Worth`).
