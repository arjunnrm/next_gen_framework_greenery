## E1 — `materialize` defaults to `"always"`

**Previously.** `plan_source_plane(materialize="auto")`, with the decision expressed as
`share = materialize == "always" or (materialize != "never" and fanout >= 2)`. A single-consumer
external read stayed `inline`: the consumer issued its own physical scan of the origin, preserving
its predicate pushdown. Materializing was framed throughout the docs as a real cost to be spent
only when fan-out amortized it.

**Currently.** `plan_source_plane(materialize="always")`, decision
`share = materialize != "auto" or fanout >= 2`. Every external read identity that is not already
produced in-graph becomes its own materialized base node — N distinct source identities produce N
base ingestion nodes — and every consumer binds via `dlt.read`/`dlt.read_stream`.

**Why the argument in the docs had to be rewritten, not just the value.** Three separate documents
(`docs/01` §7, `docs/13` L1237ff, `docs/07`) made the affirmative architectural case for the old
default, ending on sentences like "this is why `source_plane.materialize` defaults to `auto`
rather than `always`". Flipping the default while leaving those in place would have left the repo
actively justifying the opposite of what it now does — the stale-description failure mode
`AGENTS.md`'s Definition of Done exists to prevent.

**`inline` is retained, not retired.** It remains a declared `Binding.kind` and remains in
`describe_plan` output, but it is **no longer reachable for any external identity** — `share` is
unconditionally true, so the branch survives only as dead-code defence. Deleting it would have
churned `docs/01`'s binding table, `Binding.kind` and several tests for no behavioural gain.

## E2 — `materialize: "never"` is hard-rejected

**Previously.** Accepted silently. There was no validator for the block at all (see E4).

**Currently.** Rejected at onboarding with the approved message, verbatim:

> `materialize='never' is deprecated and prohibited under the Single-Read architectural mandate. Remove this setting to default to 'always', ensuring base tables are read once and reused via dlt.read().`

**The one design decision worth recording.** `AGENTS.md`'s "Removals are rejected, never ignored"
convention points at `reject_removed_keys()`, which triggers on **key presence**. That helper is
the *wrong* pattern here and using it would have been a defect: `materialize` is a **surviving**
key — `"always"` and `"auto"` are both legal — so a presence trigger would reject the default
value. The rejection is **value-scoped**, so it follows `REMOVED_CDC_LOAD_STRATEGIES`
(a withdrawn *value* of a key that still exists) via a new
`REMOVED_SOURCE_PLANE_MATERIALIZE_VALUES` registry, checked **before** the allowed-values test so
the author gets the migration sentence rather than a generic `not one of [always, auto]` listing
that reads as a typo.

**`"auto"` survives deliberately.** The requirement prohibited `"never"` and changed the default;
it did not prohibit `"auto"`. It is weaker than `"always"`, not unsafe, and groups onboarded before
this release set it explicitly. Rejecting it would break those specs for no guarantee the new
default does not already deliver. See "Known gaps" for the honest counter-argument.

## E3 — the runtime raise (the migration hole)

Onboarding validation runs **once**. `notebooks/03_engine/03_lakeflow_declarative_pipeline.py`
reads `dataflow_group_spec.source_plane_config_json` straight from the control table and passes it
into `plan_source_plane` on every pipeline update; those rows are never re-validated. A group
onboarded before this release carrying `{"materialize": "never"}` would therefore have kept running
the prohibited policy forever, silently — precisely the "still runs the pipeline while quietly
doing something other than what the document says" failure `AGENTS.md` forbids.

`plan_source_plane` now raises `FrameworkConfigError` on `"never"` itself. The message lives in one
module constant, `MATERIALIZE_NEVER_REJECTION`, imported nowhere and duplicated nowhere, so the
onboarding-time and runtime errors cannot drift apart. The notebook's fallback literal also moved
from `"auto"` to `"always"` for the case where the persisted JSON is silent.

## E4 — `source_plane` gains its first validator

**Previously.** The string `source_plane` appeared **exactly once** in the 2,600-line
`spec_validator.py`: inside `ALLOWED_ROOT_KEYS`. The block was accepted in any shape, with any
keys, persisted verbatim by `metadata_upsert.py`, and interpreted only at pipeline runtime — where
an unrecognised `materialize` value silently behaved as `"auto"`. `onboarding_spec_full_reference.md`
documented this honestly as a caveat, which meant the repo was telling readers and agents that the
block was unchecked.

**Currently.** `_validate_source_plane` runs whenever the block is supplied: `check_dict` on the
container, `reject_unknown_keys` against a new `ALLOWED_SOURCE_PLANE_KEYS`
(`catalog`/`materialize`/`schema`), the by-name value rejection above, an allowed-values check on
what survives, and string checks on `catalog`/`schema`. The full-reference caveat has been replaced
with a description of the enforcement.

`ALLOWED_SOURCE_PLANE_KEYS` is pinned to the JSON schema's `$defs.sourcePlane` by extending
`test_allowed_key_sets_match_json_schema` — the existing root-keys assertion could not see inside
the block, so without that extension the new allowlist would have been the one allowlist free to
drift from the schema.

## E5 — node names now discriminate on the options fingerprint

Found while updating tests, not reported: `stable_node_name` digests the **locator only**. Two
reads of one locator under different base-read options (`format`, `schema_location`,
`file_pattern`, `reader_options`, `starting_version`) are two distinct `ReadIdentity` values and
therefore, under E1, two nodes — which would have received the **identical** dataset name and
failed the entire Lakeflow update with "Cannot redefine dataset".

This was **unreachable before this release**: such a pair sat at fan-out 1 apiece and stayed
`inline`, so neither was ever named. E1 is what made it reachable.

`stable_node_name` gained an optional `discriminator` argument defaulting to `""`, which reproduces
the previous locator-only digest byte-for-byte, so its own collision-matrix tests are unaffected.
`plan_source_plane` passes the identity's `options_fingerprint`.

## D1 — defect found: `NameError` in `register_source_plane`

A concurrent refactor in this same release re-keyed `plan.nodes` from `ReadIdentity` to
`(ReadIdentity, mode)` and renamed the loop variable `identity` to `node_key`, but left one
reference to the old name inside the node's `dlt.table` comment f-string:

```python
f"L0 source-plane node -- one shared read of '{identity.locator}' "
```

This raised `NameError: name 'identity' is not defined` in `register_source_plane` — i.e. on
**every pipeline update**, for every group, before any dataset was registered. It was caught by
`tests/unit/test_read_once_wiring.py`, which is the only test that exercises registration rather
than planning. Fixed to `node.identity.locator`.

## Known gaps

1. **`"auto"` is accepted but inert — deliberately not a downgrade.** The requirement prohibited
   only `"never"`, so `"auto"` stays a legal value; but it is resolved to `"always"` rather than
   kept as a live fan-out>=2 threshold. Keeping it live would have reintroduced exactly what the
   mandate removes (a topology whose shape depends on fan-out) and would have made a spec saying
   `"auto"` plan differently from a spec that says nothing, while the schema documents the default
   as `"always"`. The cost of this choice: a pre-v1.7.3 group that set `"auto"` explicitly to get
   inline fan-out-1 reads silently gains base nodes on its next update. That is the intended
   direction of the mandate, but it is a real behaviour change for such a group, not a no-op.
2. **Cost of the new default is unmeasured.** Every fan-out-1 source now gets a full materialized
   copy and an extra DAG step. This is the intended trade, but no benchmark accompanies it, and the
   docs no longer contain the counter-argument that used to quantify the cost qualitatively.
3. **Per-mode identity means a dual-mode locator is scanned twice.** Deliberate — a materialized
   view is not a legal streaming source — but it does mean "read once" is now literally "read once
   per execution mode", and `test_every_external_locator_is_physically_read_once_per_execution_mode`
   had to be renamed to say so rather than quietly loosening its assertion.
4. **No integration run.** Verified offline only (validator + `plan_source_plane` + wiring stubs).
   The geneva `e41a47ba` topology test pins a real production pipeline's shape, and its far-side
   binding changed from `inline` to `shared_node` — a genuine behavioural signal that has not been
   confirmed against a live pipeline update.
