# v1.5.00 Enhancement Log

**Release date:** 2026-08-31
**Progress Tracker:** `Completed — LIVE VERIFIED (S1 only)` — framework code, control-table DDL, Python validation, JSON schema + templates, the app attribute delta, the Databricks App registry + rebuilt bundle, docs, agent skills and the unit suite are complete and verified locally, **and a reconciliation flow in `execution_mode: "pipeline"` has now been run end-to-end against `dev_flowx`**: job `flowx_test_recon_dag_job` (id `854232399214818`) SUCCESS on 2026-08-31, pipeline `be78d88d-6064-414d-a10c-2aacd900fa86` registering ingestion + L3 + L4 + L5 (including the `foreachBatch` heal sink) in one update. §4c's "NOT RUN" is superseded by **§4e**. Getting there took **seven post-build defect fixes, D1–D7** (§1, §2, §5b) — one of which (D1) meant the feature could not turn on at all. Scenarios S2/S4/S5 remain **not live**; see §6.

**Theme:** one graph. Reconciliation stops being a job task that races the pipeline and becomes a third first-class flow type *inside* the dataflow group's own Lakeflow Declarative Pipeline update — with a source plane underneath it that makes every physical read in that update happen exactly once.

The release exists to satisfy three requirements, stated in the user's own terms:

- **R1 — one DAG.** Ingestion, transformation and reconciliation all run inside **one** Lakeflow pipeline update per dataflow group.
- **R2 — read once.** Every physical source table/path is read **exactly once** per update and reused across every consumer.
- **R3 — observability unchanged.** Observability stays a normal Lakeflow job task, downstream of the update. It is not moved, not wrapped, and not made a graph node.

**The load-bearing decision — `execution_mode` defaults to `"job"`.** Four DABs job resources still run reconciliation tasks against onboarded rows. Defaulting to `"pipeline"` would run those flows twice per cycle: once in the pipeline, once in the job. So nothing already deployed changes shape until an author opts in, one flow at a time, and `"pipeline_audit_only"` exists as a first-class middle setting (in-DAG comparison, job-mode healing) rather than as a fallback nobody documented.

**The second load-bearing decision — the fingerprint ledger is KEPT, verbatim.** Two replacements were designed and both were rejected against the code: Delta `txnAppId`/`txnVersion` keyed on `batch_id` is *sequence*-addressed and silently drops legitimate new corrections after a full refresh restarts `batch_id` at 0 (silent data loss, in the healing path); and a content-addressed anti-join of the miss set on `(__framework_hash_key, __framework_hash_value)` provably matches nothing, because `matcher.py` strips `__framework_hash_value` from the append projection. The ledger matters *more* in pipeline mode, not less — a full refresh re-runs an `@dlt.append_flow` with no cleanup of prior writes, and `foreach_batch_sink`'s `batch_id` restarts at 0 while the target table is untouched.

## 2. Previous State vs. Current (Target) State

### E21 — Source plane (R2)

- **Previous:** every consumer read its own source directly and independently. Three violations were verified in shipped code, not hypothesised. **Intra-flow:** `dq/quarantine.py` reads the staged view at `_clean_upstream` and again at `_quarantine_table`, and `engine/sink_registration.py` reads it a third time — so TC-DQ-004 (streaming Auto Loader + 2 quarantine rules) opened **two independent `cloudFiles` streams over one path sharing one `cloudFiles.schemaLocation`**. **Cross-flow:** `dfg_ea_flood_autoloader_v2` declares 9 transformation inputs over 6 distinct tables, including two byte-identical streaming reads of `flowx.silver.ea_affected_customers`. **Cross-side:** a reconciliation flow re-read its source once per `target_configs[]` entry, and `streaming.py` re-read the static side per micro-batch.
- **Current:** `plan_source_plane(...)` then `assert_acyclic(plan)` then `register_source_plane(spark, plan)` then `bind(plan, consumer_id, want_stream)`. The plan pass is pure — no `dlt`, no Spark action, unit-testable with zero workspace. `bind` is keyed on a **consumer id string**, never on a caller-recomputed identity, so plan and bind structurally cannot disagree about what a read *is*. It returns `in_graph_sibling` (a real producer to consumer edge), `shared_node` (one materialized node — a streaming table if *any* consumer streams, an MV otherwise, never the reverse) or `inline` (today's exact code path).
- **Identity:** `ReadIdentity(locator_kind, locator, options_fingerprint)`. The locator is **casefolded** — `flowx_testing/003` writes `{{catalog}}.Excalibur_usecase.zerobus_source_bus` with a capital E, and a case-sensitive miss would silently fall through to a duplicate read. Only **base-read** options (which bytes are scanned) are in the fingerprint; every shaping overlay (`schema_config`, `column_normalization`, `filter_condition`, dedup, standardization SQL, decryption, watermark, DQ columns) is applied per consumer *after* the read, so two consumers with different shaping share one read. `read_mode` is deliberately **not** in the key: one materialized streaming table legally serves `dlt.read_stream` and `dlt.read` consumers in the same update.
- **Collisions:** `stable_node_name` **always** appends `sha256(locator)[:8]`, never only on truncation — sanitizing alone collides `flowx.bronze.a_b` with `flowx.bronze_a.b`, and `Cannot redefine dataset` fails the whole update. A streaming/batch collision is **resolved** by collapsing to a streaming table, never split into two nodes, and never papered over with `pipelines.incompatibleViewCheck.enabled=false` (pipeline-wide, and it silences the check without making a streaming plan batch-readable — recorded as known-and-rejected in `docs/13`).
- **Consequence:** `materialize` defaults to `"auto"` (a node only at fanout >= 2). Materialization is a full physical copy, an extra DAG step, a checkpoint in the streaming case — and it destroys predicate pushdown of a consumer's `filter_condition` into the origin, which `matcher.py` relies on. `"never"` is the documented escape hatch for a huge, heavily-filtered table.

### E22 — Reconciliation inside the DAG (R1)

- **Previous:** `notebooks/05_reconciliation/05_reconciliation_engine.py` ran as a standalone job task against whatever the pipeline had most recently materialized — structurally the same anti-pattern `common_pitfalls.md` entry 22 already forbids for sink egress. The comparison itself was Python inside a job: not queryable, not lineage-tracked, not gate-able.
- **Current:** `execution_mode` selects the host. In pipeline mode the flow registers a layered node set. **L3** publishes the prepared source and prepared target as real datasets, so the read/filter/standardize/hash chain is paid **once** per update instead of once per target, the whole run is internally consistent for the first time, and `target_record_count` is structurally pinned to the pre-append instant. **L4** publishes `recon__<rid>__<tid>__classified` / `__metrics` / `__mismatch` as real, queryable, lineage-tracked UC tables. **L5** is the heal lane. The comparison algebra is unchanged — the same full-outer join, the same when-chain, and the same `groupBy` + `F.max_by(priority)` per-key collapse, which is the framework's hardest-won correctness property.
- **The imperative half stays imperative.** The fingerprint-ledger-guarded append and the three control-table writes are re-hosted **verbatim** inside one `dlt.foreach_batch_sink` handler per flow — keeping notebook 05's sequential per-target loop, its `try/except` and its `break`. `.collect()` is legal there, so the Phase-1 two-tier short-circuit genuinely still skips the join.
- **`on_failure: "fail"` blast radius, restated.** Because all targets stay in **one** handler, `"fail"` still stops the remaining targets of that `reconciliation_id` via the existing `break` — semantics preserved. What changes: re-raising fails that flow and therefore the pipeline **update**, whereas today it fails one job task, so sibling reconciliation flows in the same group may already have run. Deliberately **not** mapped onto `dlt` expectations: expectations are per-row predicates, there is no row-level predicate meaning "this target's reconciliation raised", and an expectation cannot be attached to a sink at all.

### E23 — `publish_schema` and `dq_config`

- **Previous:** a reconciliation flow had no way to say where its results should live (there were no published results), and no declarative way to fail anything on a **finding**. `error_handling.on_failure` gates *exceptions*, and a mismatch is not an exception.
- **Current:** `publish_schema` names the schema (within the hosting pipeline's own catalog) for the three published datasets, defaulting to the pipeline's own schema; without it, pipeline `e41a47ba` would put geneva reconciliation results in `bronze_excalibur`, which an operator may not want. `dq_config` is a `$ref` to the **existing** `$defs/dqConfig`, attached to the one-row `__metrics` dataset — e.g. `{"name": "no_value_drift", "expr": "value_drift_count = 0", "action": "fail"}`. `action: "quarantine"` is rejected for a reconciliation flow (there is nothing to quarantine on a one-row metrics table). Both keys are rejected **on presence** when `execution_mode` is `"job"`. `dq_config` is **additive** — it does not repurpose `on_failure`, which keeps its exception-level meaning.

### E24 — The engine notebook becomes a thin loop

- **Previous:** `03_lakeflow_declarative_pipeline.py`'s own header claimed it was a thin registration loop, while roughly 170 lines of ordering-critical flow-construction logic lived in the notebook itself — importable by nothing, and therefore covered by no test.
- **Current:** `generate_ingestion_flow` / `generate_transformation_flow` moved **verbatim** into `engine/flow_generators.py`, joined by the new `generate_reconciliation_flow`. The notebook resolves rows, plans the source plane, and calls three generators. An AST test now asserts the notebook contains no `dlt.*` call and no framework logic, so the claim in its header cannot rot again.

### E25 — Control plane

- **Previous:** `load_active_group_metadata` returned three values, and reconciliation rows were invisible to the engine notebook.
- **Current:** it returns a 4-field `GroupMetadata` NamedTuple — `(group_row, ingestion_rows, transformation_rows, reconciliation_rows)`. Four new **nullable** columns: `dataflow_group_spec.source_plane_config_json` and `reconciliation_flow_spec.{execution_mode, publish_schema, dq_config_json}`. Every read goes through `getattr(row, "<column>", None)` and NULL means the documented default (`execution_mode` NULL means `"job"`).
- **Superseded on this point by D4.** This section originally read "**No migration script is required or provided**" — that was wrong, and it was wrong in a way that made pipeline mode unusable on every workspace provisioned before v1.5.0. The `getattr` default protects a *read* from a missing column; it does nothing for the **write**, which is a MERGE naming the column and fails with `UNRESOLVED_COLUMN`. An additive migration now exists and is described in D4 below. The `getattr` reads stay as the second layer.

### E26 — Observability stays a job task (R3)

- **Previous:** `reconciliation_run_log` / `reconciliation_mismatch_log` rows existed only because the standalone job task wrote them.
- **Current:** `observability/reconciliation_export.py::export_reconciliation_control_rows(spark, control_catalog, group_id, pipeline_update_id)` reads the `__metrics` / `__mismatch` datasets an update published and writes the corresponding control rows, de-duplicated per `(pipeline_update_id, target)` so re-running the task is idempotent. It runs as an ordinary **downstream job task**, exactly like the rest of `observability/`. Nothing about the observability engine's own architecture, task wiring or destination dispatch changed.

### E27 — Placement and cycle validation

- **Previous:** nothing checked whether a flow's source was a table the same group publishes, or whether a heal target fed back into an ingestion source. Validate-only probes confirmed that a `dlt.create_sink` writing into the pipeline's own published streaming table **and** into the table its own ingestion streams from **both** `bundle validate` clean. Lakeflow will never warn. A sink makes a loop invisible; it does not make it safe.
- **Current:** `assert_acyclic` runs a Kahn topological sort over the whole edge set and raises a named `FrameworkGraphCycleError` listing the ring — strictly stronger than a list of pairwise rules, and it catches multi-hop rings nobody enumerated. `V-CYC-1..8` are enforced **twice**, at onboarding *and* at plan time, because a control-table row can be hand-edited past the validator. The one cross-*pipeline* case (`dfg_geneva_tariffs_recon` and `dfg_zerobus_tariffelementband_cdc`) is a **WARNING** naming both groups, not an error: the loop is real at the data level but legal today.
- **Mode-scoped rejections, all presence-based per AGENTS.md:** `read_mode: "streaming"` (a stream-static join supports only inner and left_outer, which cannot express `MISSING_IN_SOURCE`), `task_run_id_column` (`resolve_pipeline_run_id` returns the *pipeline* id, which is constant across every update and is the same value stamped into `__framework_pipeline_run_id` — narrowing by it would match every row that pipeline ever wrote, i.e. a **silent no-op**), and a missing `dataflow_group_id` are each errors in pipeline mode. `dataflow_group_id` stays globally optional: the DDL allows NULL and notebook 05 explicitly handles the group-less case today.

### D1 — The pipeline-mode columns were declared but never written

- **Previous:** `onboarding/metadata_upsert.py::upsert_reconciliation_flow_spec` declared
  `two_tier_verification`, `execution_mode`, `publish_schema` and `dq_config_json` in
  `_RECONCILIATION_FLOW_SPEC_SCHEMA` — and its `Row(...)` literal **never set any of them**. A spec
  declaring `execution_mode: "pipeline"` therefore onboarded cleanly, persisted `execution_mode` as
  NULL, was read back as `"job"` by `load_active_group_metadata`, and was filtered straight out of
  the DAG. **The feature could not be turned on at all**, by anybody, and it failed silently: no
  error, no warning, a SUCCESS onboarding run and a pipeline that simply contained no reconciliation
  nodes.
- **Current:** all four are written. `None` is left as a genuine SQL NULL rather than being
  defaulted in Python, so the DDL-documented defaults stay authoritative in exactly one place
  (`execution_mode` NULL means `"job"`; `two_tier_verification` NULL means `true`).
- **Class:** the *identical* root cause as §5 defects 1 and 2 — an attribute the validator accepts
  that does not survive the round trip to the control table. Those two were found in pre-existing
  code and a round-trip regression test was added for them; this release then reintroduced the same
  bug in the same function for the new columns. The lesson is that the round-trip test has to be
  extended with every attribute, not written once.

### D2 — `V-CYC-8` was unreachable for the specs it exists to protect

- **Previous:** `_validate_landing_side_effect_collisions` (V-CYC-8) was invoked from **inside**
  `_validate_reconciliation_pipeline_placement`, which early-returns when a spec declares no
  reconciliation flows. V-CYC-8 guards ordinary Auto Loader landing-path side effects, so the specs
  it matters for are precisely the ones with no reconciliation flow — i.e. the rule was dead
  everywhere it applied.
- **Current:** `validate_spec` calls `_validate_landing_side_effect_collisions` directly, so it runs
  for every spec regardless of whether reconciliation is present.
- **Class:** a validation rule nested under an unrelated guard. A rule's reachability is part of the
  rule; a test that only ever feeds it reconciliation-bearing specs proves nothing about it.

### D3 — The cycle rules broke backward compatibility for shipped job-mode specs

- **Previous:** the `V-CYC` append-loop rules (`V-CYC-2`, `V-CYC-3` same-group, `V-CYC-5`, and the
  `target_configs` self-/cross-append checks) were emitted as hard **errors** unconditionally. They
  describe a Lakeflow **graph** cycle — which does not exist in job mode, where the standalone engine
  runs after the update has finished. Firing them on a job-mode flow was therefore a real
  backward-compatibility break: the shipped, pre-v1.5.0, purely job-mode spec
  `flowx_testing/038_rec_003_precomputed_hash.json` stopped validating, and
  `02_onboarding_engine.py` raises on any non-empty errors list, so it could no longer be onboarded
  **at all**.
- **Current:** a new `_append_cycle_finding(pipeline_mode, execution_mode, message, errors)` routes
  each such finding to `errors` in pipeline mode and to a **warning** in job mode. Pipeline-mode
  strictness is unchanged; job-mode specs onboard exactly as they did before v1.5.0.
- **Class:** a new rule applied outside the execution context that makes it true. Every finding this
  release added had to be asked "is this still a defect under `execution_mode: 'job'`?" — for the
  graph-cycle family the answer is no.

### D4 — New control-table columns reached new installations only

- **Previous:** every statement in `get_all_control_table_ddls` is `CREATE TABLE IF NOT EXISTS`, a
  no-op against an existing table. A column added to a `CREATE` statement therefore reaches **new
  installations only**. Verified live, not inferred: `flowx.config.reconciliation_flow_spec` on
  the test workspace had **none** of `execution_mode` / `publish_schema` / `dq_config_json`, and
  pipeline-mode onboarding failed with `UNRESOLVED_COLUMN`.
- **Current:** `control_plane/ddl_definitions.py` gained `ADDITIVE_CONTROL_TABLE_COLUMNS` (bare table
  name → list of `(column_name, sql_type, comment)`) and `get_add_column_ddl()`;
  `control_plane/schema_provisioner.py` gained `ensure_control_table_columns(spark, control_catalog)`,
  called at the end of `ensure_control_schema_exists`. Strictly **additive** — never a drop, never a
  retype.
- **Deliberately not `ADD COLUMNS IF NOT EXISTS`:** Databricks SQL rejects that spelling with
  `PARSE_SYNTAX_ERROR` (verified live). Idempotence is therefore caller-side — skip columns already
  present — plus a narrow duplicate-column race swallow (`_DUPLICATE_COLUMN_CONDITIONS` /
  `_is_duplicate_column_race`), the same shape as the existing `is_already_exists_race()` predicate.
- **CRITICAL OPERATIONAL POINT:** `databricks bundle deploy` does **not** apply this migration. Only
  **running** the `setup_control_tables` task (`01_setup_control_tables.py`) does. An operator who
  deploys v1.5.0 and goes straight to onboarding a pipeline-mode flow gets `UNRESOLVED_COLUMN`.
- **On a brand-new workspace the migration is a no-op** — the three columns are in the `CREATE` DDL
  too, so `CREATE TABLE IF NOT EXISTS` already produces them. It matters only for workspaces
  provisioned before v1.5.0.

### D5 — `TRUNCATE_AND_LOAD` is not an append-only source

- **Previous:** `engine/source_plane.py`'s `_NON_APPEND_ONLY_CDC_STRATEGIES` (the `G-STREAM` guard)
  listed `SCD1`/`SCD2`/`SCD3`/`FULL_SNAPSHOT_CDC` but not `TRUNCATE_AND_LOAD`. A `TRUNCATE_AND_LOAD`
  target is a `@dlt.table` fed by a **full recompute**, so every update replaces its contents and
  Delta refuses to stream from it. A reconciliation flow whose source is an in-graph
  `TRUNCATE_AND_LOAD` target therefore passed every plan-time check under `execution_mode:
  "pipeline"` and then failed at pipeline **runtime** with `DELTA_SOURCE_TABLE_IGNORE_CHANGES`.
- **Current:** `TRUNCATE_AND_LOAD` is in the set, so the rejection happens at plan time, and the
  error message names `execution_mode: "pipeline_audit_only"` as the correct setting.
- **Where it bites:** this is exactly the live geneva topology — `dfg_geneva_tariffs_recon`'s recon
  source `geneva_admin.stg_tariffelementband` is that same group's own `TRUNCATE_AND_LOAD` ingestion
  target — which is why `flowx_testing/053_geneva_e41a47ba_recon_in_pipeline.json` uses
  `pipeline_audit_only`. Pinned by `tests/unit/test_geneva_e41a47ba_topology.py`.
- **Class:** a guard enumerated by listing the cases someone thought of rather than derived from the
  property that matters ("does this target get rewritten in place?").

### D6 — `PIPELINE_SCHEMA` had no fallback chain

- **Previous:** in `notebooks/03_engine/03_lakeflow_declarative_pipeline.py`, `PIPELINE_CATALOG` had
  a three-step resolution chain and `PIPELINE_SCHEMA` was a bare `= _CURRENT_SCHEMA`. During graph
  **definition** `spark.catalog.currentDatabase()` is not the pipeline's target schema, so
  `PIPELINE_SCHEMA` was `None` even for a pipeline explicitly declaring `schema: bronze_excalibur` —
  and the first `_node_name()` call in `reconciliation/graph_registration.py` died with
  `ValueError: Unsafe or malformed target_schema: None`.
- **Current:** it resolves `spark.conf` `"pipelines.schema"` → `"pipelines.target"` →
  `currentDatabase()` → `GROUP_ROW.target_schema`, warning if all four miss.
- **Blast radius:** any reconciliation flow that sets no explicit `publish_schema` — which is the
  documented default, so this hit the common case rather than an edge one.

### D7 — Reconciliation would have run twice for scenario 003

- **Previous:** `resources/flowx_test_002_003_job.yml` still defined the standalone
  `run_003_reconciliation` task, even though the file's own header claimed it had been removed. With
  scenario `003` flipped to `execution_mode: "pipeline"`, reconciliation would have run **twice** per
  cycle — once inside the pipeline update, once as the job task — risking a double append into
  `Excalibur_usecase.zerobus_source_bus`.
- **Current:** the task is deleted. Its absence is part of `TC-R2-001`'s pass criteria.
- **Class:** exactly the double-run this release's `"job"` default exists to prevent, arriving via
  the one route the default cannot cover — a spec deliberately opted in while its job resource was
  left behind. A file header asserting a change is not evidence the change was made.

## 5. Defects Found

### 5a. Six defects found in pre-existing code while designing the release

Six defects were found in **pre-existing shipped code** while designing this release. Each is recorded because each is an instance of a *class* worth not repeating.

1. **[MAJOR — pre-existing] `reconciliation_flows[].two_tier_verification` was never persisted.** `metadata_upsert.py`'s reconciliation schema had no such `StructField` and the `Row` literal never set it, so `"two_tier_verification": false` **onboarded cleanly and was silently discarded**. The live `dfg_geneva_tariffs_recon` row is NULL and the runtime defaults it to `True` — a silent behaviour **inversion**: the author asked for the full comparison on every run and got the fingerprint short-circuit instead. Fixed here (DDL column, upsert schema, `Row` kwarg and `whenMatchedUpdate`).
2. **[MAJOR — pre-existing] `spark_config` had exactly the same defect** — accepted by the validator, never written to `dataflow_group_spec`. Fixed the same way. Both defects share one root cause: **there was no test asserting that every attribute the validator accepts survives a round trip through the control table.** That regression test now exists, per flow kind, and is what would have caught both long ago.
3. **[MAJOR — pre-existing] `two_tier_verification`'s documented semantics were wrong in one respect.** A Phase-1 fingerprint match skips the **join and the append** and **never** the log writes — `_complete_phase_1_match` exists precisely to write the same run-log/result rows a Phase-2 run would. Corrected in the DDL comment, `docs/07` and the app knowledge base.
4. **[MAJOR — pre-existing] `apply_transform_sql` rested on a void premise.** Its design assumed a sequential, single-threaded execution context. That premise does not hold in a pipeline update, where flows are registered into one graph and Lakeflow decides the schedule. Re-checked against the code and corrected/annotated rather than left resting on an assumption nothing enforces.
5. **[MAJOR — pre-existing] `spark.catalog.tableExists` is unusable in the graph-execution context.** It raises `py4j.protocol.Py4JError` and **took down TC-CDC-002's entire update on 2026-08-29**. Every remaining call on a graph-reachable path was removed. The consequence is documented rather than worked around: **`append_target_table` must pre-exist.** Creating it on demand would race sibling flows (Lakeflow rule 7 — `CREATE OR REPLACE` in Unity Catalog is idempotent in intent but not atomic), and a newly created append target gets no `CLUSTER BY (__framework_hash_key)`, so pre-create it with clustering where that matters.
6. **[MINOR — pre-existing, but it corrupted a rule] `dq/quarantine.py` carried a false docstring** claiming a code path runs "outside the pipeline graph". It does not: it runs inside a `@dlt.table` closure at graph-**execution** time, which is exactly what makes its eager `.agg(...).collect()[0]` on the **batch** branch legal, and what makes the same call illegal on the streaming branch (a streaming DataFrame cannot be eagerly aggregated or collected). The docstring is corrected, and the correction is now written up as `common_pitfalls.md` **entry 23**, because the over-broad "never put an eager action inside a dataset query definition" rule as previously circulated in this repo is **falsified by the framework's own shipped code** — and writing this release's AST guard to the blanket rule would have failed against `quarantine.py` on the first run. The original bug that produced the over-broad rule (v1.3.0's E09 `isEmpty()` guard) is real, but it is a **freshness** problem, not an eagerness one.

    flowx.bronze_excalibur.bronze_tariffelementband TO \`flowx@nrmanalytix.com\`;`

**Operational, and easy to get wrong:**

- **`bundle deploy` does not apply the D4 control-table migration.** On any workspace provisioned
  before v1.5.0, pipeline-mode onboarding fails with `UNRESOLVED_COLUMN` until the
  `setup_control_tables` task is **run**. On a brand-new workspace the migration is a no-op, because
  the three columns are in the `CREATE TABLE IF NOT EXISTS` DDL as well. Setup order on a new
  workspace: `setup_control_tables` → onboard via the generic `onboarding_job` → run the pipeline.

**Recorded decisions, not oversights:**

- **Reconciliation `governance_tags` are deferred to v1.6.0.** The three published recon datasets do not carry governance tags in v1.5.0. A recorded decision, taken to keep the Definition of Done finishable — not an oversight.
- **Healing is source-change-triggered in pipeline mode** — the one genuine capability narrowing. The L5 handler fires per micro-batch of the pulse, which streams the reconciliation source; an update in which the source advances no offsets does not invoke the handler, so no append happens **that update**. **The comparison answer is unaffected:** `classified` / `__metrics` / `__mismatch` are batch MVs recomputed every update regardless, so target-side drift or deletion is always **detected** and the `dq_config` expectation always evaluates. This is a deferred fix, never an undetected breach. Two first-class remedies: keep `execution_mode: "job"` for a flow whose source is static or low-change, or use `"pipeline_audit_only"` for in-DAG reporting with job-mode healing. Moot for the concrete case — `TRUNCATE_AND_LOAD` into a streaming table is pure append and the Auto Loader source appends on every update. **No heartbeat is fabricated:** Lakeflow offers no construct that emits one row per update into a streaming table, and inventing one would be a lie.
- **Convergence takes one update per correction round** — inherent, not a defect, and unchanged from today. The topological sort orders the ingestion read strictly *before* the recon node that produces the corrections (that ordering is exactly what makes the recon source same-update fresh), and a sink write is outside the graph entirely, so this update's corrections cannot be consumed by this update's read. The only shape that would close it in-update is precisely the self-read cycle Lakeflow forbids. Read the run-log row as "appended N, expect convergence next update".
- **The per-run log-silencing widget override is lost in pipeline mode.** `pipelines start-update` accepts only `--full-refresh`, so the `recon_run_log_capture` / `recon_mismatch_log` widget tri-state moves to the `dataflow.recon.run_log_capture` / `dataflow.recon.mismatch_log` **pipeline configuration** keys (tri-state preserved: absent or `""` defers to `logging_config`), read at notebook top level exactly as `dataflow.group.id` is. `resolve_log_capture_flags` is pure and survives verbatim; only its input source changes. **The loss is real:** an operator firefighting a flow that is flooding the log tables now needs a pipeline settings edit that takes effect on the **next** update, not the current one.
- **Merging the engines collapses two run-as identities into one.** Today the recon job task and the pipeline can run as different principals; afterwards **one** identity must simultaneously hold SELECT on every external far-side table (often another team's), MODIFY on every `append_target_table`, and MODIFY on the four `{catalog}.config` reconciliation tables. The gap is live today: the CLI user lacks USE SCHEMA on `flowx.geneva_admin` and SELECT on `flowx.bronze_excalibur.bronze_tariffelementband`, while pipeline `e41a47ba` runs as `arjun@`. Without a precheck this surfaces as an opaque mid-update abort, and the far-side read moving under the pipeline's identity is a genuine security-posture change.
- **A cross-pipeline feedback loop is invisible to Lakeflow, and the framework only warns.** The landing → zerobus → bronze → recon → landing loop spans `dfg_geneva_tariffs_recon` and `dfg_zerobus_tariffelementband_cdc`; `flowx_testing/003`'s append target is group 002's zerobus ingestion source. Merging two such groups into **one** dataflow group would make it a hard cycle plus, for a streaming Delta source with no `ignoreChanges`, a live `DELTA_SOURCE_TABLE_IGNORE_CHANGES` offset race.
