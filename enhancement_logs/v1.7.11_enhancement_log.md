## 2. E1 — the batch source is now the Lakeflow Connect Oracle snapshot

### Previous vs current

| | Previous | Current |
|---|---|---|
| Flow kind | 3 `ingestion_flows` | 3 `transformation_flows` |
| Source | `source_type: autoloader`, CSV under `/Volumes/{{catalog}}/staging/uc_3/batch/<table>/` | `source_inputs[].table = {{catalog}}.oracle_excalibur_batch.<table>` with `is_streaming: false` |

| Target | `{{catalog}}.staging.<table>_batch`, `streaming_table`, `cdc_load_strategy: APPEND`, `partition_columns: ["batch_date"]` | `{{catalog}}.staging.<table>_batch`, `target_type: materialized_view`, `cdc_load_strategy: TRUNCATE_AND_LOAD`, `liquid_clustering_columns` |
| Semantics | an accumulating append of dated CSV batches | a **full snapshot recompute per update** — which is what a reconciliation against a CDC twin needs |
| `pipeline_parameters` | `{"landing_root": "/Volumes/{{catalog}}/staging/uc_3/batch"}` | **gone** — no path is referenced any more |

The three connector tables are `bt_digital_poc.oracle_excalibur_batch.{customer,physical_device,subscriber}`.

### Why transformation flows and not ingestion flows

This is the load-bearing technical point of this release and it was settled empirically, not by
reading.

**The Lakeflow Connect destinations are MERGE-written.** Verified live: their Delta history shows
`MERGE` at version 2, and their table properties carry `__ingestion_connector_primary_key` and
`__ingestion_connector_cursor_columns = ["SYS_UPDATE_DATE"]`. That is the connector's default
`scd_type: SCD_TYPE_1`, not `APPEND_ONLY`. Delta refuses a streaming read of a MERGE-written table
(`DELTA_SOURCE_TABLE_IGNORE_CHANGES`), and this framework refuses `skipChangeCommits` outright.

**No ingestion flow of any `target_type` can read such a table.** This is not a matter of picking a
different `source_type` or a non-streaming target:
`engine/source_plane.py::_requests_from_ingestion_rows` plans **every** ingestion source request
with `want_stream=True` unconditionally, on the stated grounds that "there is no batch ingestion
reader to fall back to", and `_execute_reader` hard-rejects a batch bind of an ingestion identity.

A first attempt used `source_type: zerobus` with `target_type: materialized_view`. It passed both
spec gates and then failed at pipeline runtime on every update with
`Failed to resolve flow: '_<table>_batch_staged'`.

A transformation flow has none of that: `source_inputs[].is_streaming: false` is honoured verbatim
by the source plane, the reader origin is `"table"`, and the result is a real
`spark.read.table(...)`. The Single-Read DAG mandate is unaffected — one external identity, one
base node, one read per table.

## 3. E2 — reconciliation heals into the Debezium landing table

### Previous vs current

| | Previous | Current |
|---|---|---|
| `execution_mode` (all 3 flows) | `pipeline` | **`pipeline_audit_only`** |
| `append_target_table` | `{{catalog}}.staging.<table>_stream` — the obsolete simulator tables, which do not exist | `{{catalog}}.staging.oracle_excalibur_cdc` — the multiplexed Debezium CDC landing table the 004 streaming lane consumes |
| `transform_sql` | absent | present on all three: 12,043 / 22,380 / 31,955 characters |
| `filter_condition` on the target side | absent | `__END_AT IS NULL` on the customer flow only (see D1) |

### What the generated `transform_sql` does

It reshapes the miss set into a **complete Debezium envelope row**, so a healed row re-enters
through the same CDC engine as any real change. There is exactly one implementation of "how a
change is applied". Each SQL emits the 9 landing columns in order — `destination`, `target_table`,
`key`, `value`, `operation`, `source_position`, `idempotency_key`, `partition`, `headers` — and
within them:

- the verbatim Kafka-Connect `schema` block for the key and for the payload;
- **UPPERCASE** Oracle field names, because `from_json` field matching is case-sensitive (the D1
  trap of v1.7.09);
- `unix_millis()` for Connect `Timestamp` fields, which are epoch **milli**seconds;
- `before: null` and `op: 'r'`, the snapshot-read operation;
- `source.scn` set to `MAX(existing scn) + 1`, read from the landing table itself, so a healed row
  outranks everything already delivered and `apply_changes` cannot discard it as stale;
- `idempotency_key` as `sha256` over `destination | key | value`;
- `__flowx.*` headers recording the originating `target_id`, the heal SCN and the heal timestamp.

## 4. E3 — job `005` gains three heal tasks

`pipeline_audit_only` registers the comparison (L3 prepared sides and L4 `__classified` /
`__metrics`) **inside** the pipeline update, and then returns before registering any heal lane
(`reconciliation/graph_registration.py`, `if not needs_heal: return`). Healing must therefore run
as the standalone engine.

| | Previous | Current |
|---|---|---|
| Task graph | `run_pipeline_update` → `observability_export` | `run_pipeline_update` → `heal_physical_device` / `heal_customer` / `heal_subscriber` (parallel) → `observability_export` |
| Heal task shape | n/a | `notebooks/05_reconciliation/05_reconciliation_engine.py`, one task per `reconciliation_id`, `base_parameters` = `catalog`, `reconciliation_id`, `task_run_id: "{{job.run_id}}"`, `environment_key: framework_env` |

Without these three tasks the lane would compare and report forever and never heal anything. The
three run in parallel with each other — different `reconciliation_id`, different source, different
target, no shared state — but all after the pipeline update, because each re-reads the prepared
sides that update has just published. `observability_export` was re-pointed to depend on all three,
and remains the only writer of this group's `reconciliation_run_log` rows on an update that
produced no heal pulse.

`continuous: false` on pipeline `006` is deliberate and unchanged: the query-based connector is
scheduled rather than continuous, and a reconciliation compares two settled states.

## 5. E4 — framework fix: V-CYC-7 narrowed to `execution_mode == "pipeline"`

`docs/v1.7.11_json_attribute_delta.json` carries the verbatim new rejection messages and the full
rationale. In summary:

| | Previous (≤ v1.7.10) | Current (v1.7.11) |
|---|---|---|
| Rule scope | fired for **both** pipeline modes (the `pipeline_mode` boolean) | fires for `execution_mode == "pipeline"` only |
| What it rejects | a reconciliation source produced by SCD1/SCD2/SCD3/FULL_SNAPSHOT_CDC, or by TRUNCATE_AND_LOAD into a `materialized_view` | unchanged, but under `pipeline` alone |
| What the message says | "Set execution_mode to 'job' to keep the standalone engine for this source." | now also names `pipeline_audit_only` as the fix, and says why: `pipeline` streams the source for the L5 heal pulse |

The rule exists because `pipeline` **streams** the reconciliation source: the L3 `_src` node and
the L5 heal pulse are bound with `want_stream=needs_heal`, and `needs_heal` is only ever true under
`pipeline`. `pipeline_audit_only` binds the same node with `want_stream=False`, a batch `dlt.read`,
and registers no heal lane, so the hazard does not exist for it.

The framework already said this in three places — `engine/source_plane.py`'s G-STREAM message,
`docs/07_reconciliation_engine.md` §11.7 and `docs/13` R7 all name `pipeline_audit_only` as the
fix — while the validator rejected exactly that fix. A MERGE-written source therefore had **no
legal in-pipeline setting at all**.

**This is a relaxation. Nothing that validated before is now rejected**, and no onboarded
control-table row changes shape. Every other V-CYC rule keeps its existing mode scoping: V-CYC-1
and V-CYC-6 stay on both pipeline modes; the append-loop rules V-CYC-2/3/5 stay
error-in-pipeline-modes / warning-in-job.

## 6. E5 — framework fix: `append_schema` defers to `transform_sql`

| | Previous | Current |
|---|---|---|
| What the preflight compared | the **source** table's columns against `append_target_table`'s columns, always | the same, **unless** the flow declares a non-blank `transform_sql` |
| Status reported with `transform_sql` | `SCHEMA_MISMATCH` | the new advisory `SHAPE_DEFINED_BY_TRANSFORM_SQL` |
| Status reported without it | `SCHEMA_OK` / `SCHEMA_MISMATCH` | unchanged |

The old check assumed the appended rows carry the source table's own columns. That holds only when
`transform_sql` is absent: `reconciliation/appender.py::apply_transform_sql` runs the SQL over the
miss set **before** `append_missing_records` writes it, so with `transform_sql` the appended shape
is that SQL's SELECT list. The check therefore reported `SCHEMA_MISMATCH` for every correctly
written reshaping flow — UC3's batch lane reshapes a 31 / 90 / 131-column staging row into the
9-column Debezium landing row, so it would have been flagged as missing every business column.

The new status is advisory and never affects `valid` (only `MISSING_REQUIRED` does). Its note says
plainly that the shape cannot be compared statically and that the append runs with `mergeSchema`,
so a misspelt alias **adds** a column rather than failing. Any consumer switching on
`existence_checks[].status` must tolerate the new value and render it as informational.

## 7. Defects found

An adversarial multi-agent review confirmed each of these.

| # | Severity | Defect | Disposition |
|---|---|---|---|
| D1 | Blocker | `bronze.customer` is SCD2 and the recon target had **no current-row filter**, so closed history versions took part in matching. `matcher.py` collapses duplicate keys MATCHED > VALUE_DRIFT > MISSING — "a key counts as matched as soon as *any* target row matches" — so a stale closed version could mask real drift, and that now drives live heal writes. | **Fixed.** `"filter_condition": "__END_AT IS NULL"` added to the customer flow's `target_config` only; the other two tables are SCD1 and hold no history. |
| D2 | Blocker | The Lakeflow Connect tables are MERGE-written, and no ingestion flow of any `target_type` can read them (§2). The first draft failed at pipeline runtime with `Failed to resolve flow: '_<table>_batch_staged'` on every update. | **Fixed.** The three flows became transformation flows with `is_streaming: false`. |
| D3 | Major | The first draft set `sequence_by_column` to a struct whose tiebreaker was `current_timestamp()`. Spark evaluates that **once per query**, so it is constant within a micro-batch and broke no tie at all. | **Fixed before deployment.** Removed entirely when the flows became `TRUNCATE_AND_LOAD` materialized views, which need no sequencing. |
| D4 | Major, operational | The three `staging.<table>_batch` tables still existed as `STREAMING_TABLE`s (100 / 41 / 141 columns, partitioned by `batch_date`, 120 rows each of obsolete simulated CSV data, last written 2026-09-08). Lakeflow cannot convert a streaming table into a materialized view in place. | **Resolved as a one-time step.** The three tables were DROPPED before the first update on the new spec, with the user's explicit approval. |
| D5 | Major, operational | After changing a flow's **type** (ingestion → transformation), the old `ingestion_flow_spec` rows stay `is_active = true` and keep driving the graph. | **Resolved as a one-time step.** Re-onboarded through the generic onboarding job with `prune_missing_flows=true`, which deactivated all three. |

## 10. Known gaps

1. **Not yet verified end to end at the time of writing.** The batch pipeline run was still being
   validated when this was written. Row counts in `staging.<table>_batch`, the reconciliation
   `__metrics`, the heal tasks' `reconciliation_run_log` rows and the resulting Bronze changes must
   all be confirmed after a successful update. **A green `bundle run` exit does not mean the
   pipeline succeeded** — this repo has been bitten by exactly that, and the run's own state must be
   read, not the CLI's exit code.
2. **Definition of Done steps 5 to 7 are not complete.** `BT_Usecase/UC3/docs/UC3_MASTER_DOCUMENT.md`,
   `BT_Usecase/_shared/delivery/04_consolidated_rollout_runbook.md`, `agent_skills/SKILL.md` and its
   synced `.claude/skills/` copy were updated alongside the code. Still outstanding: the `docs/*.md`
   prose for the V-CYC-7 narrowing (`docs/07_reconciliation_engine.md` §11.7 and `docs/13` R7 now
   agree with the validator but do not yet record that the validator was the side that moved), the
   regenerated mkdocs trees, and the whole Databricks App change listed under `app_update_status` in
   the attribute delta — the `execution_mode` help sentence in
   `config/registry/reconciliation.json`, both `attribute_knowledge*.json` files and
   `web/src/registry.js`, plus tolerating `SHAPE_DEFINED_BY_TRANSFORM_SQL` in any status-rendering
   path. **The App then needs `npm run build` in `databricks-app/web` before deployment**, because
   Databricks Apps does not build at deploy time and an un-rebuilt `web/dist/` keeps serving the
   stale text.
3. **The connector cursor is `SYS_UPDATE_DATE`, and rows whose cursor column is NULL are never
   ingested** (per the Databricks Lakeflow Connect documentation for the query-based Oracle
   connector). Today there are zero such rows, so the snapshot is complete. But an Oracle row that
   was never updated would be permanently absent from the batch lane and would report as a permanent
   `MISSING_IN_SOURCE`. This is a precondition to monitor, not a one-off check.
4. **The job-mode heal's restart-idempotency fingerprint is key-only and unbounded in time.**
   `reconciliation/appender.py::compute_batch_fingerprint` computes the fingerprint from the miss
   set's **match keys only**, not its values, and checks it against **all** prior `SUCCESS` runs with
   no time bound. A second, genuinely different drift on the same key set is therefore silently
   skipped as `SKIPPED_ALREADY_PROCESSED`. Remediation when it bites: supersede the
   `reconciliation_run_log` row carrying that fingerprint, or re-onboard under a new
   `reconciliation_id`. **Not fixed here** — it is framework-wide behaviour affecting every existing
   flow, and changing it is a separate piece of work.
5. **The full comparison runs twice per cycle.** `pipeline_audit_only` computes it inside the
   pipeline update, and the heal job task computes it again. That is the documented shape for
   audit-only healing, but the compute cost is real and doubles with the width of these tables.
6. **The heal writes into another dataflow group's raw ingestion source, and no gate checks it.**
   `staging.oracle_excalibur_cdc` is the 004 streaming group's source. V-CYC-3 and V-CYC-4 only
   inspect the **same** spec document, so this cross-spec loop gets neither an error nor the warning
   those rules exist to emit. The loop is deliberate and is the whole point of E2, but it is
   unguarded: nothing would stop a future edit turning it into a real cycle.
7. **Deletes are asymmetric, and this is an open design question.** Bronze applies CDC deletes, but
   a batch snapshot has no delete concept and the heal envelope hardcodes `op='r'`
   (`src_deleted_flg='0'`). A key deleted in Oracle but still present in the batch snapshot would be
   re-healed back into Bronze. Nothing in the current design detects or prevents that.
8. **The `006` pipeline YAML header is partly stale.** Its v0.0.7 paragraph still describes the
   abandoned `zerobus` ingestion approach ("Three `zerobus` ingestion flows STREAM the three
   append-only streaming tables …"), which D2 replaced with transformation flows. The `heal`
   paragraphs and the `continuous: false` rationale are current. The header should be corrected;
   it is comment text only and does not affect deployment.
