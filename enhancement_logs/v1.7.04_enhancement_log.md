**Theme:** the first deploy to a new workspace stopped being a documented hand-edit and became a
flag — plus the step-by-step runbook that was missing entirely.

Bringing FlowX up on a brand-new workspace was a known chicken-and-egg with a known workaround,
and the workaround was *edit `databricks.yml`, deploy, edit it back*. That is a bad shape for a
first-run procedure: it is three manual steps on a shared, version-controlled file, the
half-finished state is committable, and it was described in prose in two places rather than being
a runbook anyone could follow top to bottom. This release replaces the edit with a `--var`
override, wraps the whole sequence in a script, and writes the runbook.

## E1 — `wheels_root`

**Previously.** Every target hardcoded

```yaml
artifact_path: /Volumes/${var.catalog}/config/wheels/${var.framework_version}
```

On a workspace where that Volume did not exist yet, `bundle validate` *and* `bundle deploy` refused
outright:

```
Error: volume flowx.config.wheels does not exist
  at workspace.artifact_path
     resources.volumes.framework_wheels_volume
```

The Volume is declared by this same bundle, but the check runs during **config resolution, before
any resource is created** — so the deploy that would create it is the one being rejected. The
documented workaround was to comment the `artifact_path:` line out, deploy
`--select schemas.config_schema,volumes.framework_wheels_volume`, then uncomment it.

**Currently.** A `wheels_root` variable holds the parent directory, and every target composes:

```yaml
artifact_path: ${var.wheels_root}/${var.framework_version}
```

The bootstrap overrides it for exactly one command:

```bash
databricks bundle deploy -t <target> -p <profile> \
  --select schemas.config_schema,volumes.framework_wheels_volume \
  --var="wheels_root=/Workspace/Users/<you>/.bundle/flowx/<target>/artifacts"
```

No file is edited, so there is no half-finished edit to commit by mistake.

**This is not a bypass of the check — that was verified explicitly.** An early hypothesis was that
routing the path through a variable defeats the pre-check altogether, which would have made this
"fix" a silent hole rather than a bootstrap. It does not. Isolated on a scratch bundle against a
genuinely absent Volume, the literal path and the `${var…}` path both produce `Found 1 error`.
Earlier probes that appeared to pass had pointed at Volume *names* the bundle did not declare —
the guard keys on the declared resource, not on the syntax of the path. The guard is fully intact;
only an explicit, per-command override moves the path out of its way.

**The default stays inside the Volume**, so an override is a bootstrap-only argument and every
ordinary deploy still publishes to the fixed, shared path the v1.6.0 decision record requires.

## E2 — `scripts/bootstrap_workspace.py`

Runs the sequence end to end: catalog pre-flight → phase 1 bootstrap deploy → full deploy →
optionally `bundle run` for the app.

- **Idempotent.** It runs `bundle validate` and matches the pre-check's error text, so phase 1 is
  *skipped* on a workspace that is already bootstrapped rather than assumed. Safe to re-run.
- **`--dry-run`** prints the exact commands and changes nothing.
- **Catalog pre-flight.** `${var.catalog}` cannot be a bundle resource on UC Default Storage
  accounts, so the script checks it exists and stops with instructions rather than failing later
  and less clearly.
- **Windows encoding.** `subprocess` is pinned to `encoding="utf-8", errors="replace"`. Found by
  running it: the CLI emits UTF-8, Python on Windows decodes a pipe as cp1252 by default, and the
  first em-dash in bundle output raised `UnicodeDecodeError` inside a reader thread.

## E4 — Structural guards

Two tests in `tests/unit/test_resource_layout.py`:

| Test | Catches |
|---|---|
| `test_every_target_composes_artifact_path_from_wheels_root` | a target hardcoding the literal path, which silently opts out of the one-command bootstrap |
| `test_wheels_root_defaults_into_the_declared_wheels_volume` | a bootstrap override committed as the default, which would publish every wheel outside the managed Volume with no error anywhere |

**Both were mutation-tested.** Each was confirmed to fail against a deliberately broken
`databricks.yml` and pass against the real one. Worth recording: the first mutation attempt
*passed*, which looked like a useless test — the mutation had silently not applied, because the
`str.replace(..., 1)` anchor matched an earlier occurrence than intended. Re-running it with the
edit verified to have landed produced the expected failure.

## D2 — App re-deploy fails on an invalid update mask

**Found:** the second and subsequent `bundle deploy` runs against `metaflow_v7` fail with

```
Invalid update mask … Supplied update mask: …, forward_user_access_token, …
(400 INVALID_PARAMETER_VALUE)
```

**Diagnosed as external, not ours.** `forward_user_access_token` appears nowhere in
`resources/` or `databricks-app/` — the CLI sends it. The Apps API accepts it on **create** and
rejects it on **update**, which is exactly why the *first* deploy to this workspace succeeded and
every later one fails. Reproduced with `--select apps.flowx_onboarding_app` alone, so it is
unrelated to `wheels_root`; all other resources deploy normally alongside it.

**Handled, not hidden.** The script recognises the message, reports it as the known CLI issue it
is, and exits 0 with the `bundle run` command that rolls the app's code forward regardless — while
any *other* deploy failure still exits 1. Also recorded in the runbook's troubleshooting table.

## Known gaps

- **`dev_flowx`, `arjun_2` and `arjun_3` do not currently validate** — all three report
  `volume flowx.config.wheels does not exist`. This is **pre-existing and unrelated**: the same
  failure reproduces on the stashed original `databricks.yml`. Those workspaces need the Step 3
  bootstrap for the current `framework_version`, which this release now makes a one-liner. Not
  done here because it means deploying to three workspaces that were not in scope.
- **`test_every_group_folder_is_included_by_databricks_yml` fails** in the working tree because
  several `include:` lines are commented out. Note that `AGENTS.md` and
  `docs/09_developer_guide_and_recipes.md` both warn that a commented-out `include:` makes DABs
  **delete** those resources from the target on the next deploy — `--select` is the safe way to
  scope a deploy. Left as-is because restoring them is the operator's call, not this release's.
- **The `forward_user_access_token` update-mask failure (D2) is worked around, not fixed** — it
  needs a newer Databricks CLI. The app's *code* still updates correctly via `bundle run`; only
  its definition (description, scopes, resources) cannot be changed until the CLI is upgraded.
