**Theme:** storage the bundle writes into belongs *in* the bundle — and the limits of that idea.

A deploy to a fresh workspace failed on its first resource:

```
Error: cannot create resources.volumes.framework_wheels_volume:
       Schema 'flowx.config' does not exist
```

The bundle declared its two UC **Volumes** but nothing declared the schema holding them. On the
three established workspaces `flowx.config` had been created by hand at some point in the past,
so the gap was invisible — the bundle only ever deployed where a human had already run the CREATEs.
`arjun_2` was the first workspace without that history, and it surfaced an undocumented manual
prerequisite sitting in front of every deploy.

**The load-bearing finding — and the one that reversed a decision mid-release.** The natural fix is
to declare the whole hierarchy: catalog → schema → volume. Declaring the **schema** is correct and
fixes the bug. Declaring the **catalog** is not merely unnecessary, it is *actively harmful*, and it
took a live deploy to find out:

```
Error: cannot create resources.catalogs.flowx_catalog:
       Metastore storage root URL does not exist. Default Storage is enabled in your account.
       You can use the UI to create a new catalog using Default Storage, or please provide a
       storage location for the catalog (400 INVALID_STATE)

Error: cannot create resources.schemas.config_schema:
       dependency failed: resources.catalogs.flowx_catalog
```

Note the **second** error. The unbuildable catalog did not fail in isolation — DABs propagated the
failure down the dependency edge it had just created and took `config_schema` with it. The catalog
resource therefore blocked the very fix it was added to complete: with it present, the deploy failed
*and* the schema was never created; with it absent, the schema deployed cleanly. **A resource that
can only ever fail is strictly worse than no resource.**

Why it can only ever fail, two independent reasons:

1. **UC Default Storage.** These accounts have no metastore storage root URL, so `CREATE CATALOG`
   without a `MANAGED LOCATION` is rejected. Supplying one is not an escape: a Default-Storage
   catalog's `storage_root` is an **account-managed** path carrying metastore and catalog UUIDs
   generated at create time — verified on `arjun_2`:
   `s3://dbstorage-prod-ycljl/uc/9acb37d2-a3c9-4ebc-9d3a-75e6705cc467/3c07299f-.../`. It cannot be
   committed to version-controlled YAML and differs per workspace. (`hoonartek` reports no
   `storage_root` at all.)
2. **The catalog already exists on every target** — checked on all three: `dev_flowx`, `arjun_2`
   and `hoonartek` all have `flowx`, each created outside this bundle via the UI.

So `${var.catalog}` is a documented **prerequisite**, not a resource. A unit test keeps it that way.

**The other thing not to conflate.** Declaring the schema does **not** remove the `artifact_path`
bootstrap; they are different mechanisms:

| | Mechanism | Fixed by this release? |
|---|---|---|
| `Schema 'flowx.config' does not exist` | **Resource creation order** at deploy time | **Yes** — and structurally, via a real dependency edge |
| `volume flowx.config.wheels does not exist at workspace.artifact_path` | **Config-resolution pre-check**, runs *before* any resource is created | **No** — a Volume declared in the same bundle cannot satisfy it |

Re-verified on CLI v1.13.0 against `arjun_2` **with the schema resources in place**: uncommenting
that target's `artifact_path` before the bootstrap deploy still fails validate. The one-time
comment-out/deploy/uncomment dance survives — but the SQL that used to precede it is gone.

**Why the ordering fix is structural, not incidental.** DABs rewrites the literal strings in each
volume body into resource references. `bundle validate -o json` on `arjun_2` shows:

```
volumes.framework_wheels_volume -> catalog_name: ${var.catalog}
                                   schema_name:  ${resources.schemas.config_schema.name}
```

That is a real edge in the deployment graph, not a comment. Create order schema → volume is
enforced by DABs itself; the original error cannot recur while the declarations stand. (It is also
exactly the mechanism that made the catalog resource so damaging — the same edge that guarantees
correct ordering guarantees failure propagation.)

### Deliberately NOT declared

The ~40 `bronze_*` / `silver_*` schemas named by the feature-test and BT-fixture pipelines are left
out. A Lakeflow pipeline creates its own target schema on first update, so their absence fails a
*pipeline run* at worst, never a deploy — and declaring 40 of them would consume the schema quota
the `dev` target has already nearly exhausted (51 schemas, 50-Volume metastore ceiling; see
`databricks.yml`'s LIVE CAVEAT). The declared set is exactly the set whose absence **fails a
deploy**.

## 6. Known Gaps

- **`dev_flowx` and `hoonartek` need a one-time schema bind, and it is not automated.**
  `flowx.config` already exists on both, created outside this bundle, so DABs does not own it and
  a deploy attempting a create fails with `Schema 'config' already exists`. Bind once per workspace:

  ```
  databricks bundle deployment bind schemas.config_schema flowx.config -t dev_flowx -p dev_flowx
  ```

  `bundle deployment unbind` reverses it without deleting anything. Documented in the group's
  `README.md` and the schema file header. **Nothing enforces it** — the failure is a clear upfront
  error, not silent, but it will happen on the next deploy to either workspace if skipped. Not
  needed on `arjun_2`, where this bundle created and owns the schema.

- **`dev_flowx` / `hoonartek` `working_schema` and `sample_suite_schema` are untested.** Only
  `arjun_2` has been deployed. `flowx.dev` almost certainly already exists on `dev_flowx`, so
  expect the same bind requirement for `schemas.working_schema` there.

- **The `dev` target's quota is untouched by this and still a live risk.** Adding four sample
  Volumes raises the bundle's Volume count on any target it deploys to. `dev`'s metastore is
  already at its 50-Volume ceiling, so a full deploy there will fail on the sample Volumes as it
  already did on `framework_wheels_volume`. Deploys from this machine target `dev_flowx`, not
  `dev`.

- **The catalog remains a manual, undeclarable prerequisite.** This is not fixable in the bundle
  while the accounts use Default Storage. If a workspace is ever created with a metastore storage
  root, a `catalogs.*` resource with an explicit `storage_root` becomes possible there — but it
  would be per-workspace config, not a portable resource, and pitfall 40 should be re-read first.

- **The ~40 pipeline-created `bronze_*`/`silver_*` schemas remain undeclared** — deliberate (§2),
  but it means a *pipeline* can still be the first thing to create a schema. Only deploy-blocking
  containers are declared.
