**Theme:** the sample suite stops seeding itself. Every one of the five reference jobs carried its own
three `seed_iteration<N>` notebook tasks, interleaved with three pipeline updates — the same seeding
machinery re-expressed five times, in five files, with the fixture-generation story for the whole

ordered chain per sample behind a single serial provisioning root. A sample job is now four tasks:
onboard, run, publish its spec, done.

The suite also gains its sixth member, and it is the one that finally puts a **real** telecom wire
format through the framework: `flowx_sample_06_asn1_tap3_job` decodes BER payloads against the
genuine GSMA TAP release 3.10 module already sitting in this repo
(`BT_Usecase/UC7/data/asn_schema/TAP.310.asn1` — 1597 lines, 375 types), not a five-field module written
to make a test pass.

**The load-bearing finding.** Picking `asn1_pdu_name` on a real ASN.1 module is not the formality the
existing toy fixture makes it look like. `derive_asn1_field_defs` requires a **top-level `SEQUENCE`**
and rejects `CHOICE` **anywhere in the resolved member tree** — and every genuine telecom module is
built the opposite way round, with a root `CHOICE` selecting between message kinds. On TAP.310 the
module's own top-level PDU `DataInterChange` is a `CHOICE` (rejected), and `TransferBatch` *is* a
`SEQUENCE` but reaches `CallEventDetail`, also a `CHOICE` (rejected one level deeper — the version of
this that wastes an afternoon). 70 of the module's 93 top-level `SEQUENCE` types do resolve.
`Notification` is the one this sample uses, and it is not a contrivance: it is the real TAP3
file-level PDU a roaming partner sends when it has no chargeable events to transfer. The way to find
the workable set is to ask the framework's own resolver, not to read the module — now written down in
`common_pitfalls.md` **37**, `SKILL.md` §4, and `docs/02`.

## 2. Previous State vs. Current (Target) State

### E47 — Seeding was five copies of the same machinery

- **Previous:** each of the five sample jobs declared three `seed_iteration<N>` notebook tasks,
  interleaved with three `run_pipeline_iteration<N>` pipeline tasks — 8 tasks per job, 30 seed-related
  tasks across the suite, and no single place that answered "what data does this suite need?".
- **Current:** one job, `flowx_sample_seed_job`:

```text
provision_sample_schema                       (serial root)
  |-- seed_sample_01_iteration1 -> _iteration2 -> _iteration3
  |-- seed_sample_02_iteration1 -> _iteration2 -> _iteration3
  |-- seed_sample_03_iteration1 -> _iteration2 -> _iteration3
  |-- seed_sample_04_iteration1 -> _iteration2 -> _iteration3
  |-- seed_sample_05_iteration1 -> _iteration2 -> _iteration3
  `-- seed_sample_06_iteration1 -> _iteration2 -> _iteration3
```

- **Why the root task is serial, and is not redundant with the notebooks' own `IF NOT EXISTS`.** Every
  `04_seed_sample_*` notebook still issues its own `CREATE SCHEMA/VOLUME IF NOT EXISTS` — it must, so
  each stays runnable standalone. But `IF NOT EXISTS` is idempotent in *intent*, not *atomic*: Unity
  Catalog lets two concurrent creates of the same object race and the loser fails outright. That is
  not theoretical here — it is pitfall 7, discovered live on 2026-08-29 when three concurrent
  `setup_control_tables` runs made the losers fail with `[ROUTINE_ALREADY_EXISTS]`. Six chains
  starting at the same instant is the same race with six entrants. `provision_sample_schema` creates
  the schema and all four Volumes first, so every downstream `IF NOT EXISTS` is a no-op that cannot
  lose one.
- **Why iterations stay ordered inside a chain but chains run in parallel.** Several seeds are
  cumulative by construction — Sample 01's `FULL_SNAPSHOT_CDC` parts feed is strictly additive across
  iterations, Sample 03 layers replica drift on top of the previous slice — so iteration 2 landing
  before iteration 1 produces fixtures that do not match what the specs describe. Nothing couples one
  *sample* to another, so the six chains are independent, and a failing chain does not block the rest
  (proved live: §4b).
- **`catalog` is a job parameter** (default `flowx`, matching every other resource in
  `resources/sample_jobs/`), so a run can be retargeted without editing the file.

### E48 — A sample job is now four tasks

- **Previous:** `setup_control_tables -> seed_iteration1 -> onboard -> run_pipeline_iteration1 ->
  seed_iteration2 -> run_pipeline_iteration2 -> seed_iteration3 -> run_pipeline_iteration3 ->
  store_sample_config`.
- **Current:** `setup_control_tables -> onboard_sample_NN -> run_pipeline -> store_sample_config`
  (Sample 03 keeps its `observability_export` between the last two).
- **Why three pipeline updates became one, and what that costs.** With every iteration seeded before
  the sample job starts, the first update ingests all three; updates 2 and 3 would find no new files
  and do nothing. Keeping them would be two wasted serverless starts per sample and a job header that
  no longer described what the job did. **The end state is unchanged** — `apply_changes` sequences the
  SCD1/SCD2 versions within the single batch, so Sample 01's SCD2 history is still built. What is
  genuinely lost is the update-by-update *progression*: Sample 03's reconciliation counters now land
  on their final `value_drift_count 6` / `missing_in_target_count 14` instead of stepping
  0 → 6 → 14. That is a real reduction in what the sample demonstrates, it is a direct consequence of
  seeding up front, and it is called out in the job headers, `docs/09` §6.2 and
  `flowx_testing/README.md` rather than left for someone to discover. The staged behaviour is still
  available: run the seed job's chain one iteration at a time with the sample's pipeline in between.

### E49 — The suite had no ASN.1 case, and the repo's real ASN.1 modules had no consumer

- **Previous:** five samples, none exercising `source_type: "asn1"`. The four genuine GSMA/telecom
  modules in `BT_Usecase/UC7/data/asn_schema/` (`EMSC`, `GGSN`, `PSGW`, `TAP.310`) were referenced by
  exactly one file in the whole repo — a sentence in `v1.5.01_enhancement_log.md` explaining why
  `bt_tests/` is only six files. Nothing read them. The only ASN.1 coverage anywhere was TC-ING-004
  against `sample_data/asn1_schema/gsm_cdr.asn`, a five-field module written for that test.
- **Current:** `flowx_sample_06_asn1_tap3_job` + pipeline + spec + seed notebook. The seed copies
  `TAP.310.asn1` verbatim into `/Volumes/flowx/flowx_sample/landing/sample06_asn1/schemas/` and
  then compiles **that landed copy** to encode its fixtures — so the schema identity the seed encodes
  with is byte-identical to the one the spec's `asn1_schema_path` points the pipeline at, not merely
  a copy of the same file. Every encoding is round-trip-decoded in the seed before it is written: an
  unreadable fixture fails in the seed, not three tasks later as a mystery quarantine row.
- **What the sample actually demonstrates**, beyond "asn1 works": `Notification` yields all three
  Spark output shapes the decoder can produce, in one PDU — scalars, a nested `SEQUENCE` → `struct`
  (the three `DateTimeLong` timestamps), and a `SEQUENCE OF` → `array` (`operatorSpecInformation`).
  Verified live in §4c.
- **Deliberate decode failures.** 2 truncated payloads per iteration (a valid encoding cut to 40% and
  25%). `asn1tools` raises `MissingDataError`; `asn1/decoder.py` captures it per row into
  `_asn1_decode_error` instead of failing the micro-batch; the spec's `asn1_decode_ok` rule
  quarantines them. Their `fileSequenceNumber` — the quarantine table's `record_id_column` — is NULL
  by construction, because nothing decoded. That is the correct and intended shape, not a defect.
- **No manual prerequisite.** `asn1tools` is already a declared dependency of the framework wheel
  (`pyproject.toml`), so `../../dist/*.whl` installs it into both the job tasks and the pipeline.
  Samples 01, 02, 03 and 06 need nothing provisioned by hand.

### E53 — `FULL_SNAPSHOT_CDC` asked the source plane for a consumer that was never planned

- **Previous:** `_build_ingestion_dataframe` called
  `bind(plan, f"{dataflow_id}:source", want_stream=is_streaming)` for **every** ingestion flow.
  `source_plane.py::_plan_ingestion_consumers`, meanwhile, skips `FULL_SNAPSHOT_CDC` rows outright.
  So the plan held no consumer under that id and `bind` — which raises rather than guessing — killed
  graph analysis for every snapshot pipeline in the repo.
- **Current:** the generator branches on the strategy and reads directly for snapshot flows:

```python
if is_snapshot_cdc:
    staged_df = read_ingestion_source(spark, flow_row.source_type, source_config)
else:
    staged_df = bind(plan, source_consumer_id, want_stream=is_streaming)
```

- **Why direct reading is correct and not a shortcut.** The plane's purpose is to make a locator
  *shared between consumers* read once (R2). A snapshot source has exactly one consumer by
  construction — that is precisely what the exclusion in `source_plane.py` asserts. Bypassing the
  plane here loses no read-once guarantee because there was never a second reader to deduplicate.
- **Why the strategy name is now an exported constant.** Both sides must branch on the same literal.
  `source_plane.SNAPSHOT_EXCLUDED_FROM_SOURCE_PLANE` is the single spelling, imported by the
  generator; two independent string copies drifting apart would plan a consumer on one side and not
  the other, and that mismatch is invisible until a live pipeline update.
- **What the tests pin.** Both directions. The snapshot flow must not reach `bind`; every other
  strategy (`APPEND`/`SCD1`/`SCD2`/`SCD3`/`TRUNCATE_AND_LOAD`) and an *absent* `cdc_load_strategy`
  must still bind. A fix that quietly routed all ingestion around the plane would break R2 while
  every snapshot test passed.

### E54 — a pure helper lived in a module that requires a pipeline

- **Previous:** `observability/reconciliation_export.py` and `reconciliation/appender.py` imported
  `_is_table_not_found` from `dq/quarantine.py`, which does a module-level `import dlt`. Both are
  reached from plain **job** notebook tasks, where importing `dlt` calls into a notebook entry point
  that has no id to return and raises `NoSuchElementException: None.get` — at import time, before a
  line of framework code runs.
- **Current:** `dq/table_errors.py` holds `is_table_not_found` / `TABLE_NOT_FOUND_CONDITIONS` and
  imports **nothing at all**. The two job-context modules import from it; `dq/quarantine.py` keeps
  `_is_table_not_found` / `_TABLE_NOT_FOUND_CONDITIONS` as aliases so pipeline-side callers and
  existing tests are untouched.
- **Why the alias carries a warning comment.** A job-context module importing the *alias* imports
  `quarantine.py`, which imports `dlt` — reintroducing the bug in full while looking like it used
  the fixed API. The comment says so at the definition site, which is where someone will be looking.
- **Why the guard is static, not an import test.** `databricks-dlt` is a dev dependency, so
  `import dlt` succeeds under pytest and proves nothing about the serverless job runtime. The
  failure is environment-specific; the *import edge* that causes it is not.
  `tests/unit/test_job_context_has_no_dlt_import.py` walks the real graph with `ast` and asserts the
  edge is absent — transitively, because the original bug was two hops out and no direct-import
  check would have caught it. `dq/quarantine.py` is asserted to *still* import `dlt`, so the other
  assertions cannot pass vacuously.

### E50 — The `CHOICE` constraint was one sentence, and the sentence was not enough

- **Previous:** `SKILL.md` §4 said *"`CHOICE` types are not yet supported."* True, and useless at the
  moment it matters — it does not say that the constraint applies to the **whole resolved tree**, nor
  that the natural PDU of a real module is exactly the thing it forbids.
- **Current:** the failure mode is stated with the module that produces it, both rejection points
  (top-level and one-level-deep), and a runnable probe that enumerates the usable PDUs of any module
  in about a second. Two adjacent constraints that bite the same person are stated in the same place:
  one ASN.1 module per file (no `IMPORTS` across files), and nested constructs become
  `struct`/`array` columns rather than being flattened.

### D2 — every `FULL_SNAPSHOT_CDC` ingestion flow failed at graph analysis  *(blocked Sample 01 — **FIXED**, E53)*

```
FrameworkConfigError: source_plane.bind: unknown consumer_id 'df_sample_01_part_snapshot_ingest:source'.
Known consumer ids: ['df_sample_01_customer_scd1_ingest:source', 'df_sample_01_order_events_ingest:source',
'df_sample_01_supplier_scd2_ingest:source', 'ts_sample_01_customer_order_scd3:input:sample01_customer_dim_src',
'ts_sample_01_customer_order_scd3:input:sample01_order_events_src']
```

`engine/source_plane.py::_plan_ingestion_consumers` **deliberately skips** `FULL_SNAPSHOT_CDC` rows
("its 'source' is consumed by `apply_changes_from_snapshot`'s own path-based lambda, never through
the plane"). But `engine/flow_generators.py::_build_ingestion_dataframe` called
`bind(plan, f"{dataflow_id}:source", ...)` **unconditionally** to build the staged view — and the
staged view *is* in the graph for a snapshot flow (`_staged` → `_clean` → `_snapshot_input` →
target). The plane never planned a consumer for it, so the bind could not resolve.

The exclusion comment is right about the *lambda* and wrong about the *staged read*. Affected
`flowx_testing/samples/sample_01_multi_scd.json`, `024_cdc_006_snapshot_pk.json` and
`025_cdc_007_snapshot_nopk.json` — i.e. every snapshot-CDC spec in the repo.

**Fix (applied in this release as E53):** `_build_ingestion_dataframe` branches on the strategy —
through the shared `source_plane.SNAPSHOT_EXCLUDED_FROM_SOURCE_PLANE` constant, so both sides spell
the same literal — and calls `read_ingestion_source(spark, ...)` directly for snapshot flows. That
matches `source_plane.py`'s documented intent and leaves the R2 read-once contract untouched for
every other strategy (§2 E53). **Verified live:** `flowx_sample_01_multi_scd_job` SUCCEEDED on its
first post-fix run and the `FULL_SNAPSHOT_CDC` target holds 80 rows (§4c). Pinned in both directions
by the 10 new tests in `tests/unit/test_flow_generators.py` §6.

### D3 — the observability **job** could not import its own module  *(blocked Sample 03's export task — **FIXED**, E54)*

```
Py4JJavaError: An error occurred while calling o36.get.
: java.util.NoSuchElementException: None.get   (at entry_point.getNotebookId().get())
```

Raised at **import time**, not run time:
`observability/reconciliation_export.py:69` did
`from ...dq.quarantine import _is_table_not_found`, and `dq/quarantine.py:50` does a module-level
`import dlt`. `notebooks/08_observability/08_dlt_observability_engine.py` runs as a plain **job**
notebook task, not inside a Lakeflow pipeline, and importing `dlt` there fails immediately.

`_is_table_not_found` is a pure exception-inspection helper with no DLT dependency whatsoever — it
just happened to live in a module that requires a pipeline context. Beyond Sample 03 this affected
`resources/observability/dlt_observability_job.yml` and every job task that exports observability.

**Fix (applied in this release as E54):** `is_table_not_found` / `TABLE_NOT_FOUND_CONDITIONS` moved
to the import-free `dq/table_errors.py`; both job-context modules import from it, and
`dq/quarantine.py` keeps the historical `_`-prefixed names as warning-commented aliases (§2 E54).
**Verified live:** Sample 03's `observability_export` task SUCCEEDED where it previously raised the
error above, and `store_sample_config`, previously skipped `UPSTREAM_FAILED`, runs (§4c). Guarded by
`tests/unit/test_job_context_has_no_dlt_import.py` (13 tests), which walks the real import graph with
`ast` and asserts the `dlt` edge is absent **transitively** — the original bug was two hops out.

### D1 — no non-UI path exists to create the Unity Catalog secret  *(blocks Samples 04 & 05 — **OPEN**)*

Samples 04 and 05 share `flowx.flowx_sample.sample_zip_passkey`. Provisioning it was attempted
on the first workspace and could not be completed; v3 has the same gap:

* `databricks secrets put-secret flowx.flowx_sample sample_zip_passkey` →
  *"Scope flowx.flowx_sample does not exist!"* — the `databricks secrets` CLI manages **legacy
  workspace scopes only**, and `dbutils.secrets.get(catalog=, schema=, key=)` cannot read one (see
  `crypto/secrets.py`'s module docstring: the two systems are three generations apart).
* `POST /api/2.1/unity-catalog/secrets` (the documented create endpoint) → **404 Not Found**. So do
  `PUT`/`POST` on `/api/2.1/unity-catalog/secrets/{catalog}/{schema}/{name}` and `GET` on the by-name
  path. Only the **list** route is served: `GET /api/2.1/unity-catalog/secrets?catalog_name=…&schema_name=…`
  returns `{}` normally.
* Not a permissions problem: the CLI principal **owns** `flowx.flowx_sample`.

The remaining supported path is the Catalog Explorer UI: **Catalog → `flowx` → `flowx_sample`
→ Create → Secret**, name `sample_zip_passkey`, any non-empty value (`pyzipper` derives the AES key
from the passphrase), then grant the running principal `READ SECRET`. The "manual, admin-audited,
external to the bundle" framing in `flowx_testing/README.md` is therefore not merely a policy
preference — it is currently the only mechanism that works. That path is now being walked — the
operator is creating the secret manually in Catalog Explorer; until it exists, Samples 04/05 stay
blocked (§6).

### D4 — the v1.6.0 fixed `artifact_path` only ever validated by coincidence  *(resolved by E52)*

On v3, `bundle validate` failed with:

```
Error: artifact_path should contain the current username or ${workspace.current_user.short_name}
       to ensure uniqueness when using 'mode: development'
```

The same config validated clean on the first workspace. The reason is a coincidence, not a
configuration difference: that workspace's deploying user was `flowx@nrmanalytix.com`, whose
`short_name` is literally **`flowx`** — and the path is `/Volumes/flowx/config/wheels`, which
contains it. DABs' development-mode uniqueness check was satisfied by the catalog name happening to
equal the user name. v3's user is `flowx_v3@nrmanalytix.com`; the coincidence is gone and the
check bites.

Satisfying the check by re-adding a `${...short_name}` path component is exactly the per-user fork
`databricks.yml` records as tried and **reverted on 2026-08-30**. `mode: development` was therefore
dropped from the target instead (E52), keeping the fixed shared path. Cost: deployed resources lose
the `[dev <user>]` name prefix and schedules are no longer auto-paused — nothing in this bundle
declares a schedule, so the second point is inert today. The reasoning is written into
`databricks.yml` beside the change.

**No defect was found in anything this release changed.** The seed job, the five rewritten sample
jobs and Sample 06 all behaved as specified on their first live run, on two independent workspaces —
and the E53/E54 fixes behaved as specified on *their* first post-deploy runs (§4c).

## 6. Known Gaps

The two gaps this section previously opened with — Sample 01 unverified behind D2, Sample 03's
`observability_export` unverified behind D3 — are **closed**: both defects are fixed here (E53/E54)
and both runs are verified live (§4c). The stale-profile gap is also gone: the operator renamed the
`.databrickscfg` profile to `dev_flowx`, matching the target, and a bare
`bundle validate -t dev_flowx` passes (§4b). What remains:

1. **Samples 04 and 05 are unverified**, blocked by D1, not by anything in this change. Both seeds
   preflight the secret and fail fast with a message naming it, so the blocked state is loud rather
   than silent. The operator is creating the secret manually in Catalog Explorer — the only mechanism
   that works (§5, D1). Once it exists, re-run `flowx_sample_seed_job` (chains 01/02/03/06 are
   idempotent and simply re-land the same bytes) and then the two jobs.
2. **The staged, update-by-update narrative is no longer what the suite shows by default.** Deliberate
   (§2 E48) and documented in three places, but a reader who wants to watch SCD2 history accumulate or
   Sample 03's drift counters step 0 → 6 → 14 must now drive the seed job one iteration at a time.
   §4c confirms the *end state* is right: 6 drift, 14 missing, on the single update — and, since the
   E53 fix, 40 current + 17 history SCD2 rows out of the one collapsed update.
3. **Only `Notification` is exercised of TAP.310's 70 resolvable PDUs.** The other 69 — including
   `BatchControlInfo`, `AuditControlInfo`, `ChargeDetail` — are reachable with a spec change and no
   framework change, but none is covered.
4. **`CHOICE` support in `derive_asn1_field_defs` remains unimplemented**, which is why the real
   top-level TAP3 PDU (`DataInterChange`) and the batch PDU (`TransferBatch`) cannot be ingested at
   all. Supporting it would mean a union-typed Spark output or a discriminator-plus-nullable-arms
   shape; neither is designed. This release documents the constraint rather than lifting it.
5. **The other three BT modules (`EMSC`, `GGSN`, `PSGW`) still have no consumer.** TAP.310 now has
   one; they do not.
