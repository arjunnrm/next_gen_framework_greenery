## 2. E1/E2 — the governance notebook

**File:** `notebooks/04_governance/04_apply_governance_and_egress.py`

### Previous

```python
GROUP_ID = dbutils.widgets.get("dataflow_group_id").strip()
if not GROUP_ID:
    raise ValueError("The 'dataflow_group_id' widget is required.")
...
try:
    if APPLY_ABAC:
        apply_all_governance_tags(spark, CATALOG, GROUP_ID)
    ...
except Exception as exc:
    logger.error("Governance pass failed for group '%s': %s", GROUP_ID, exc)
    raise
```

One group per task. Tagging N groups meant N chained tasks.

### Current

`dataflow_group_id` is split on `,`, stripped, blanks dropped, de-duplicated order-preserving.
The execution block iterates `GROUP_IDS`, records each failure into `_failures`, and raises a
single `RuntimeError` at the end naming every failing group and the `N of M` count.

`GROUP_ID` is retained as `GROUP_IDS[0]` for log messages.

### Why accumulate-then-raise rather than a bare `raise` in the loop

Stopping at the first failure would make **one task carrying N groups strictly worse than N
separate tasks**: with separate tasks a failing group fails only its own task, whereas a loop
that re-raises immediately would silently deny every group listed *after* the failure its tags,
while reporting a single failure naming only the first. That is the same class of silent-gap
failure as the pre-v1.7.5 `target_type: "sink"` bug, which took an entire group's tags down with
it (`docs/04_data_quality_and_governance.md` §3 item 4).

This mirrors the accumulate-then-raise contract `governance/tags.py::apply_governance_tags`
already uses per statement within a single table.

### Backward compatibility

A single id is the one-element case of the list, so **no existing job definition needed editing**.
Verified callers that still pass a single id and keep working:

- `archive/resources/feature_tests/flowx_test_gov_001_tagging_job.yml`
- `archive/resources/feature_tests/flowx_test_gov_002_idempotent_tag_job.yml` (3 tasks)
- `archive/resources/feature_tests/flowx_test_obs_001_json_log_job.yml`

**Limitation (unchanged):** isolation is at the **group** level only. Within one group,
`apply_all_governance_tags` still has no per-flow isolation — the first failing table aborts the
remaining flows of that group (`governance/tags.py:200` has no per-flow guard).

## 5. E5 — in-graph mismatch append: investigated and rejected

**Objective:** bring UC3's mismatch/quarantine append inside the declarative pipeline, removing
the three `heal_*` notebook tasks from `005_lfj_uc3_excalibur_batch_recon`.

**Blocker.** The in-graph L5 heal lane (`__pulse` → `heal_flow` → `heal_sink`) registers only when
`execution_mode == "pipeline"` (`reconciliation/graph_registration.py:400`, early return at
`:691`). That mode **streams** the reconciliation source: the same `needs_heal` flag is passed as
`_want_stream` to the L3 `_src` node (`:478`) and the pulse binds with a hard-coded `True`
(`:706`), because `dlt.foreach_batch_sink` accepts streaming queries only.

UC3's recon source `staging.<table>_batch` is a `TRUNCATE_AND_LOAD` materialized view over
`oracle_excalibur_batch.<table>`, which the Oracle Lakeflow Connect connector MERGE-writes.

**Two bridge designs were built and tested this session (both rejected):**

| Variant | JSON schema | `validate_json` | `plan_source_plane` | Verdict |
|---|---|---|---|---|
| A — APPEND mirror reading the snapshot MV | PASS | PASS | **FAIL** | Rejected at plan time |
| B — APPEND mirror reading `oracle_excalibur_batch.<t>` directly | PASS | PASS | **PASS** | **Fails at runtime** |

Variant A raises `FrameworkConfigError` from the G-STREAM guard
(`engine/source_plane.py:529-549`), naming `cdc_load_strategy='TRUNCATE_AND_LOAD' /
target_type='materialized_view'`.

**Variant B is the dangerous one: it passes all three offline gates.** G-STREAM only inspects
*in-graph siblings*, and `oracle_excalibur_batch.<t>` is external to the pipeline, so the guard
never sees it. It still fails at runtime with Delta's `DELTA_SOURCE_TABLE_IGNORE_CHANGES`.
Confirmed directly against the live `hoonartek` workspace:

```
DESCRIBE HISTORY bt_digital_poc.oracle_excalibur_batch.customer
  v3  MERGE   (matchedPredicates: update; numTargetRowsInserted 1)
  v2  MERGE   (numTargetRowsInserted 30)
```

A third design — an APPEND streaming-table copy bridging the two — was already proven to fail at
runtime on 2026-09-11 (`flow_generators.py` derives `is_streaming` from target type *or* any
streaming input, producing `AnalysisException: View '_<t>_batch_events_staged' is not a streaming
view and must be referenced using read`).

**Conclusion.** With a MERGE-written source there is no configuration that yields an in-graph
sink. `pipeline_audit_only` + one `05_reconciliation_engine.py` job task per `reconciliation_id`
remains the only working shape. The three `heal_*` tasks stay.

**Offline reproduction recipe** (no deploy, no Spark, ~10 minutes): drive
`engine/source_plane.py::plan_source_plane` directly with fake control-table rows — a `dict`
subclass exposing `__getattr__` — built from the spec JSON. This exercises the G-STREAM guard,
which neither the JSON schema nor `spec_validator.py` covers.

**Standing warning.** For this source shape, three green offline gates are *not* evidence.
Check `DESCRIBE HISTORY <source>` for `MERGE` operations before trusting any streaming design.

## 6. E6 — in-pipeline tag sync: investigated and rejected

**Objective:** run the tag add/update/prune/no-op reconciliation inside the pipeline lifecycle.

**Blocker.** `ALTER TABLE ... SET TAGS` is Unity Catalog DDL. DDL from inside a dataset query
definition is prohibition #3 of the three real prohibitions in
`agent_skills/reference/common_pitfalls.md` §23 ("side-effecting writes — any
`.write`/`saveAsTable`/DDL from inside a query definition"). The only legal graph terminal is
`dlt.create_sink` + `@dlt.append_flow` / `dlt.foreach_batch_sink`.

Nor is there a legal non-closure execution point: the pipeline notebook's top level runs at
graph-**definition** time, *before* any target table is materialized, so DDL there would target
tables that do not yet exist. This is documented in three independent places —
`governance/tags.py:10-16` and `:156-161`, and
`notebooks/03_engine/03_lakeflow_declarative_pipeline.py:66` and `:438`.

Post-update tagging therefore remains the only working shape, which is what E1–E3 improve.

### Premise correction, and the defects that are real

The brief stated that column tags "are failing to apply". **On `hoonartek` they are applying.**
Live Unity Catalog at the time of this work:

| Table | column-tag rows | distinct columns |
|---|---|---|
| `bronze.customer` | 231 | 33 |
| `bronze.subscriber` | 133 | 18 |
| `bronze.physical_device` | 51 | 8 |
| `staging.customer_batch` | 18 | 3 |
| `staging.physical_device_batch` | 12 | 2 |

plus table tags on all three `bronze` and all three `staging.*_batch` tables. Job `009` works.

Two genuine defects **remain open** (not addressed by this release, since the requested scope
became the multi-group widget):

1. **No diffing.** `apply_governance_tags` issues `SET TAGS` unconditionally for every column on
   every run; it never reads `information_schema.column_tags`/`table_tags` first. The only
   `spark` calls in the module are the two `spark.sql(statement)` at `governance/tags.py:123`
   and `:137`. `information_schema` appears in that module only inside docstrings.
2. **No pruning.** There is **no `UNSET TAGS` anywhere in the repository** — `grep -rn "UNSET"`
   over `src/` returns nothing. A tag removed from a spec and re-onboarded stays live in Unity
   Catalog permanently. This contradicts the "removals are rejected, never ignored" principle in
   `AGENTS.md`, at the governance layer.

Both are self-contained changes to `governance/tags.py` and are recommended as the next
enhancement.
