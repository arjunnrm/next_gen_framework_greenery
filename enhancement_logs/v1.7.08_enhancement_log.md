**Theme:** Deploying the three BT use cases to a *second* workspace exposed a class of defect the
first workspace could never surface: configuration that was correct only because of where it ran.
A source schema that existed on one host and not another, a Genie space naming a catalog no other
target has, a Volume every spec writes to that no target declares. None of these are logic bugs
and none would fail a unit test; each one fails at pipeline runtime on the first workspace that
does not happen to match. This release fixes the four that blocked UC3/UC6/UC7 on `hoonartek` and
records the two that remain open.

items below were found only by querying target tables after a run reported SUCCESS.

**UC2 does not exist in this repository.** `BT_Usecase/` contains UC3, UC6 and UC7 only; there is
no `resources/uc2/` and no file matching `*uc2*`. It is recorded here as requested-but-absent
rather than silently dropped.

## E1 — UC7 read from a schema that does not exist on this workspace

**Previous:** `BT_Usecase/UC7/onboarding/UC7_cdr_asn_bronze.json` addressed all four ingestion
flows at `/Volumes/{{catalog}}/landing/uc_7/...`. On `metaflow_v7` that was correct.

**Current:** all 12 occurrences are `/Volumes/{{catalog}}/staging/uc_7/...`, matching UC3 and UC6,
which already used `staging`.

**How it presented.** The pipeline failed `INTERNAL_ERROR` and auto-retried six times, each update
reporting:

```
Failed to resolve flow: 'bt_digital_poc.bronze._src___volumes_bt_digital_poc_landing_uc_7_raw_sgsn__f51e7bd6__stream'
Update 07fc5d has failed. Failed to analyze flow '...' and 3 other flow(s).
```

The generated flow name embeds the resolved path, which is what identified the cause — the error
itself never says "schema does not exist".

**Why the spec was wrong in a way no test could catch.** `BT_Usecase/UC7/docs/UC7_CDR_ASN_Test_Report.md`
§8.2 records the reason explicitly: on `metaflow_v7` the whole `uc_7` tree was **copied**
`landing` → `staging` (112,148,054 bytes, 28 files, verified byte-for-byte), and the group was
then deliberately **not** repointed, because re-onboarding would have abandoned the Auto Loader
checkpoints and re-ingested every file. That was a correct decision for that workspace and left
the spec carrying a `landing` assumption that held in exactly one place. `hoonartek` has a
`staging` schema and no `landing` schema at all, so the assumption failed on first contact.

**Verified after the fix:** re-onboarded `action_type: UPDATE`; the control table's
`source_config_json.path` now reads `staging` for all four flows; the pipeline ran green and
decoded **175,498** CDRs (`sgsn_cdr_raw` 175,048, `emsc_cdr_raw` 353, `psgw_cdr_raw` 93,
`tap310_raw` 4) with **0 rows** in all four `*_quarantine` tables — so every record passed both
the BER decode and the CHOICE-arm DQ rules.

**Lesson recorded:** a use-case spec path is workspace-coupled configuration. A spec that has only
ever run on one workspace has not been shown to be portable, and the doc that explains why a path
was left alone is the first place to look when it breaks elsewhere.

## E2 — UC3's simulator lost the fixtures it derives its schema from

**Previous:** `BT_Usecase/UC3/data/` was deleted in commit `cb40c22` ("Push"). The directory held
`CUSTOMER_DDL.csv` (128 lines), `PHYSICAL_DEVICE_DDL.csv` (48) and `SUBSCRIBER_DDL.csv` (161).

**Current:** all three restored from `cb40c22~1`; line counts match the deletion diff exactly.

**Why it mattered.** `uc3_streaming_simulator_job`'s `delta_table_setup` task does not hand-type
the three staging tables' column lists — BUILD_CONTRACT 6 forbids that. It derives them at run
time from these CSVs via `src/uc3_simulator/uc3_ddl_schema.py`, applying the contract's
header-quirk fallbacks, the `Feed column name` ingestibility test and the Oracle→Spark type map.
Without the files the task fails, so the three `*_stream` zerobus tables are never created — and
those are precisely what `dfg_uc3_excalibur_streaming_cdc` reads (`source_type: zerobus`,
`source_table: {customer,physical_device,subscriber}_stream`). `bt_digital_poc.staging` contained
**zero** tables before this was fixed, so the CDC group was unrunnable, not merely degraded.

**Verified after the fix:** simulator SUCCESS; all four tables created (three `*_stream` plus
`uc3_simulator_offsets`, the producer's cursor); a full drain of **exactly 100 rows per table**,
matching the design's ~7 ticks × `chunk_size: 15`.

## E3 — UC6 and UC7 jobs cut to pipeline + observability

**Previous:** UC7 ran `setup_control_tables -> onboard_uc7 -> run_pipeline_update ->
observability_export`. UC6 ran the same plus `apply_governance_uc6` between the pipeline and the
export. UC3's `004`/`005` were already two-task (v1.7.07 E5), so **only UC6 and UC7 changed**;
UC3's `uc3_seed_job`, `uc3_streaming_simulator_job` and `uc3_governance_job` are separate jobs
already and were left alone.

**Current:** both jobs are exactly `run_pipeline_update -> observability_export`. UC6's
`observability_export` was rewired from `apply_governance_uc6` to `run_pipeline_update`, which
would otherwise reference a deleted task.

**Three consequences, each documented in the job file's own header rather than left to be
rediscovered:**

1. **Onboarding no longer runs with the job.** The pipeline reads control-table rows, not the spec
   file, so a spec edit has no effect until `onboarding_job` is run separately. UC6 keeps
   `prune_missing_flows: "true"` in the documented command — it is the only owner of
   `dfg_uc6_ea_flood_warning`, so rows for flows it no longer declares are stale by definition.
2. **Control-table provisioning is external.** `bundle deploy` does not apply the additive
   migration, and `01_setup_control_tables.py` is also what installs the
   `preflight_check_onboarding_spec` UC function and the `<catalog>.observability` semantic layer.
   The onboarding engine's `ensure_control_schema_exists` covers only the `CREATE ... IF NOT EXISTS`
   path.
3. **UC6 governance tags are now inert until run by hand.** This is the sharpest edge. Unity
   Catalog tag DDL (`ALTER TABLE ... SET TAGS`) runs against an already-materialized table and is
   illegal inside a pipeline's graph-definition code, so the step cannot be absorbed into the
   pipeline — removing the task removes the behaviour. Phase C of the UC3 build already proved the
   cost: a pipeline succeeded end to end with **zero** tags in `information_schema.column_tags`
   because no task ever invoked the notebook.

**Method note.** The edits were made by deleting verified line ranges with an assertion on every
anchor line, never by regex — this repo has twice been damaged by a broad pattern (a blanket `sed`
mangled Python identifiers; a non-greedy DOTALL `re.sub` swallowed ~650 lines of `Builder.jsx`).
One assertion fired on an off-by-one and stopped the edit before it did anything. Verified after:
`yaml.safe_load` reports exactly two tasks per job with no orphaned `depends_on`;
`test_resource_layout.py` passes; the deployed job definitions read back as
`['observability_export', 'run_pipeline_update']`.

## E4 — UC3 reconciliation output moved out of the working schema

**Previous:** all three UC3 batch-recon flows set `publish_schema: "staging"`, so nine generated
objects sat alongside the six real data tables — six `_recon__*` internals (`__src`, `__tgt`) and
three `recon__*__metrics`.

**Current:** `publish_schema: "reconciliation"` on all three flows, pointing at a new
`bt_digital_poc.reconciliation` schema. `logging_config.run_log_capture` stays `true`.

**The requested change was to blank `publish_schema`, and that is rejected.** Since v1.7.07
`publish_schema` is the only thing that publishes (v1.7.07 E9), and `_validate_logging_config`
rejects a pipeline-mode flow with a capture flag set and no `publish_schema`:

> run_log_capture/mismatch_log_capture is true but the flow has no publish_schema ... the
> reconciliation_run_log / reconciliation_mismatch_log rows are exported from the PUBLISHED copies.

So blanking it forces `run_log_capture: false` too, which silently costs the entire recon audit
trail: the reconciliation still *runs* as a pipeline-scoped temporary dataset but becomes
unauditable. Moving the schema achieves the same visible outcome — no `_recon` objects in
`staging` — at no cost to the audit. A separate rule rejects a blank `publish_schema` on a flow
with a healing target regardless of the capture flags; UC3 has none, so that one did not fire.

**Changing `publish_schema` leaves orphans.** Lakeflow does not move a published object, it
creates a new one, so after re-onboarding and re-running, all nine existed in *both* schemas and
`staging` still showed `_recon` tables — the decluttering appeared to have failed. The old copies
are out of the pipeline graph and never refresh again. They were dropped only after the live
copies and the audit trail were confirmed working, and only with explicit sign-off: six
`DROP MATERIALIZED VIEW IF EXISTS` and three `DROP TABLE IF EXISTS` (the `_recon__*__src` nodes are
STREAMING_TABLEs). The keep-list was printed and checked first — `staging` legitimately holds
seven objects that must not match the filter (three `*_batch`, three `*_stream`, and
`uc3_simulator_offsets`).

**Verified after the fix:** nine objects in `reconciliation`, zero `_recon*` in `staging`, seven
data tables untouched, and fresh `SUCCESS` rows in `reconciliation_result` for all three flows
(e.g. `rf_uc3_customer_batch_vs_bronze`: 96 matched, 52 missing-in-source, 0 missing-in-target).

**On reading those numbers.** `status: SUCCESS` means the reconciliation ran, **not** that the data
agreed — UC3's batch and streaming feeds are independently generated synthetic datasets and are
not expected to match. `reconciliation_mismatch_log` is empty by configuration
(`mismatch_log_capture: false` on all three flows), not by defect; aggregates still land in
`reconciliation_result`.

## E5 — every UC spec writes to an observability Volume no target declares

**Previous:** all four specs declare an observability destination under
`/Volumes/{{catalog}}/observability/app_logs/`. The bundle declares an `observability` Volume only
in the **`flowx_sample`** schema (`resources/flowx_bootstrap/flowx_sample_volumes.yml`) — never in
the `observability` schema the specs actually address. No target has ever provisioned it.

**Current:** `bt_digital_poc.observability.app_logs` created as a MANAGED Volume, deliberately
**not** a bundle resource — same reasoning as `staging.uc_7` in the UC7 test report: a
bundle-managed MANAGED Volume is deleted along with its data by `bundle destroy` or by removing
the YAML and redeploying, and this one accumulates exported logs.

**How it stayed hidden.** Every earlier run in this session was scoped `--only run_pipeline_update`
to onboard without triggering data processing, so `observability_export` never executed. Trimming
the jobs (E3) is what surfaced it: the task that had sat behind `apply_governance_uc6` now ran
directly, and failed loudly on all three groups:

```
ObservabilityDispatchError: All 1 destination(s) failed for dataflow_group_id='dfg_uc7_cdr_asn':
[('dest-uc7-volume', "[Errno 95] Operation not supported: '/Volumes/bt_digital_poc/observability/app_logs'")]
```

It failed rather than degrading because the task sets `fail_task_on_dispatch_error: "true"`, which
is the correct design — a silently-skipped observability export is worse than a failed task. Note
the per-task split: `run_pipeline_update` **SUCCESS**, `observability_export` **FAILED**, on all
three. The data pipelines were never affected.

**Verified after the fix:** all three jobs green on both tasks, and
`/Volumes/bt_digital_poc/observability/app_logs/` now holds `dfg_uc7_cdr_asn/`, `uc6/` and
`streaming_cdc/`.

**Still open — this is a latent defect for every workspace, not just this one.** The durable fix
is to declare the Volume in `resources/flowx_bootstrap/` so a fresh workspace provisions it
automatically. That was offered and the manual route was chosen to unblock the runs; the root
cause is unchanged.

## E6 — repairing a pre-rename stash popped onto the current tree

**Previous:** the working tree carried 31 files in `UU` (unmerged) state with 73 conflict hunks.
The markers read `>>>>>>> Stashed changes:src/NextGen_Metadata_Framework/...` — the pre-FlowX-rename
path — identifying `stash@{0}` ("baseline-check-singleread", 46 files) as the source.
`src/flowx/lakeflow_framework/onboarding/spec_validator.py` had 33 marker lines and raised
`SyntaxError: unterminated string literal`.

**Current:** zero conflict markers repo-wide; all 7,542 `.py` files parse; `bundle validate -t
hoonartek` OK.

**The deployed wheel was never affected.** `dist/flowx-0.0.4-py3-none-any.whl` was built at 15:27
and `spec_validator.py` was corrupted at 15:35 — eight minutes later. The wheel was unzipped and
checked: zero markers, `spec_validator.py` parses. Every run recorded in this log was therefore
executed against clean framework code.

**How the resolution was decided, rather than guessed.** A dry run compared the "ours" side of
every conflict against the committed `HEAD` content: 13 files matched exactly, 17 did not. So
blanket-taking either side was unsafe. Inspecting the 17 showed the extra content was almost
entirely **prose describing already-committed behaviour** — for example `appender.py` gained
docstring text about the v1.7.3 "silent by default" flip, while `_DEFAULT_LOG_CAPTURE = False`
and `resolve_log_capture_flags` were *already* in HEAD. Only three lines looked like executable
code, and each proved to be a duplicate: the stash side re-declared the `materialize` rejection
registry under a second name (`REMOVED_SOURCE_PLANE_MATERIALIZE_VALUES`) with an inlined copy of a
message that HEAD imports from `engine/source_plane.py` specifically to stop the two drifting.

Two merge artifacts survived the first pass and were removed:

* a **duplicated `_validate_source_plane` call**, which made every `source_plane` error appear
  twice — caught by `test_materialize_never_is_rejected_with_the_migration_message` asserting an
  exact one-item list ("Left contains one more item");
* an **orphaned `_LOG_CAPTURE_DEFAULT = False`**, defined once, referenced nowhere, absent from
  HEAD, and duplicating the documented and test-asserted `_DEFAULT_LOG_CAPTURE`.

Two test files (`test_recon_logging_gates.py`, `test_read_once_wiring.py`) were reset to their HEAD
content: since the source resolution took HEAD's side, stash-side tests asserted behaviour that
was never committed (`"is set to false"` appears in neither HEAD's validator nor HEAD's test).
HEAD's `test_recon_logging_gates.py` then passed **46/46** against the resolved source, which is
the evidence that the source resolution is right.

## Known gaps

* **D4 forces every deploy on a non-`flowx` catalog to be `--select`-scoped.** All deploys in this
  release were scoped to the schemas, wheels Volume, `onboarding_job`, the specs Volume + publish
  job, and the UC jobs/pipelines; each reported `0 deleted`. Never scope by editing `include:` — a
  commented-out include *destroys* the resources it declared.
* **E5 is unfixed at the root.** A new workspace will hit the same missing Volume.
* **SCD2 versioning is untested** on this workspace (see above).
* **The UC3 governance job was not run**, so `dfg_uc3_*` governance tags are not applied here; and
  per E3, UC6's tags now need `04_apply_governance_and_egress.py` run by hand.
* **No attribute delta ships with this release** — nothing about the spec contract changed. See
  Scope.
