## Why this release exists

UC6 replaces a ~10-year-old Ab Initio ETL that matches Environment Agency flood-risk postcodes
against EE mobile customer addresses to find the MSISDNs to warn. The supplier is changing from
Fujitsu to Leidos, and the output contract cannot change during the parallel run.

The brief proposed four framework enhancements. **Three of them already existed** — glob
filename matching (`source_config.file_pattern`), a configurable delimiter
(`reader_options.delimiter`, already a shipped reference example), and archive-on-ingest
(`landing_retention_policy.clean_source: "archive"`). The three that genuinely did not exist
were **not** in the brief's list, and all three sat on the encryption/compression boundary:

| Gap | Why UC6 could not be expressed without it |
|---|---|
| Symmetric PGP | `crypto/pgp.py` was asymmetric-only. UC6's EA feed and two of its four outputs are `gpg --symmetric` AES256. |
| gzip landing members | `source_zip_handling` extracts ZIP archives via pyzipper. UC6's inbound file is a `.csv.gz.gpg` — decrypt to disk and what remains is a bare gzip stream, which pyzipper cannot open. |
| gzip + dialect egress | The `pgp_zip` sink wrote comma-only, always-headered, CRLF CSV inside a ZIP. UC6 must emit pipe-delimited, LF-terminated `.csv.gz` and `.csv.gz.gpg`. |

## E1 — Symmetric PGP

**Previous:** `crypto/pgp.py` exposed `pgp_encrypt` / `pgp_decrypt` / `pgp_verify`, all taking
ASCII-armored public/private key material. An OpenPGP message protected by a Symmetric-Key
Encrypted Session Key packet — no keypair, just a passphrase and an S2K derivation — could not
be read or written at all.

**Current:** `pgp_decrypt_symmetric(data, passphrase)` and
`pgp_encrypt_symmetric(data, passphrase, cipher="AES256")` alongside them, sharing the module's
conventions: armored output, `bytearray` normalised to `bytes`, `CryptoError` on every failure.

**Why a separate function rather than an optional argument:** the two schemes are mutually
exclusive at the message level. A key-encrypted message is not passphrase-decryptable and vice
versa — both directions are asserted in `tests/unit/test_crypto_pgp.py`. One function taking
either would leave "which one applies" ambiguous when a caller supplied both.

**Verification that matters:** round-tripped against the **real GnuPG 2.4.9 CLI in both
directions** with a gzip payload — the framework decrypts what `gpg --symmetric` wrote, and
`gpg --decrypt` reads what the framework wrote. This is deliberately not a self-round-trip:
`pgp_encrypt`'s own source comment records a shipped bug where internal round-trips passed while
external recipients could not decrypt, because `bytes(PGPMessage)` emits binary rather than
armored output.

## E2 — gzip landing members and symmetric pre-extraction

**Previous:** `source_zip_handling` assumed a ZIP archive throughout. `pre_extraction_decryption`
supported only `type: "pgp"`.

**Current:** `member_format` selects the container (`"zip"` default, `"gzip"` new) orthogonally
to the decryption layer, and `"pgp_symmetric"` joins the decryption-type registry.

**Note for spec authors:** an *unencrypted* `.gz` needs no `source_zip_handling` whatsoever —
Spark's codec layer decompresses it transparently on read, and adding a handling block only buys
a pointless staging copy. `member_format: "gzip"` exists for the *encrypted* case.

**A real bug this caught.** The first implementation derived the landed filename by stripping
only `.decrypted`, so `EE_2026-08-20-REQUEST_1OF1.csv.gz.gpg.decrypted` landed as
`...csv.gz.gpg.decompressed` — the `.gz` test missed because the name still ended `.gpg`. That
landed name is what Auto Loader's `file_pattern` glob matches, so the result would have been a
**silent zero-row ingest**, not a visible failure. Found by running against UC6's own fixture
rather than a synthetic one. Envelope suffixes are now stripped too, with a regression test.

## E3 — gzip archives, CSV dialect and symmetric PGP on the sink

**Previous:** `sink_config.format: "pgp_zip"` produced exactly one shape — a ZIP of
comma-delimited, always-headered, CRLF-terminated CSV, optionally encrypted to a recipient's
public key. The CSV was written by `csv.DictWriter` with no dialect arguments at all.

**Current:** three additive keys, each defaulting to the previous behaviour.

- `sink_config.staged_file_options` — `delimiter`, `include_header`, `line_terminator`
  (`crlf`/`lf`, spelled as names because JSON cannot carry a bare control character). Rejected
  for JSON-Lines staging, which has no delimiter or header to configure.
- `post_export_archive.archive_format: "gzip"` — concatenates the micro-batch's staged partition
  files into one gzip stream (a gzip holds exactly one member) and names the export
  `<stem>.<csv|jsonl>.gz`, or `....gz.gpg` when encrypted. The CSV header is emitted per staged
  file, so all but the first are dropped on concatenation.
- `pgp_encryption.passphrase_secret` — symmetric egress, mutually exclusive with
  `recipient_public_key_secret` and incompatible with signing (which needs a sender keypair).

**Verification:** the emitted `EE_2026-08-20-TELEPHONE_1of1.csv.gz.gpg` decrypts with the real
`gpg` CLI, gunzips cleanly, and contains pipe-delimited LF-terminated rows with exactly one
header across two partitions.

## E4 — Two JSON-schema defects

Both were reachable only by validating against the schema *as well as* the Python validator.
Since v1.7.2 the schema's `additionalProperties` is what actually rejects unknown keys at
onboarding, so a spec can pass `validate_spec` and still be refused.

1. **`reconciliationTargetConfig` rejected its own keys.** It composes
   `reconciliationDatasetConfig` via `allOf` and adds `target_id` / `comparison_direction` /
   `append_target_table`. The base def set `additionalProperties: false`, and that keyword
   cannot see properties declared in a *sibling* `allOf` branch — so those three were always
   "additional". **Every reconciliation spec in `flowx_testing/` failed the schema.** Moving the
   keyword to the target branch merely inverts the bug. `unevaluatedProperties` is the keyword
   that evaluates across `allOf` branches, and is what now closes the composed def. Confirmed to
   still reject an invented key.
2. **`transformationFlow` omitted `source_description`**, which has been in
   `ALLOWED_TRANSFORMATION_FLOW_KEYS` since the v2 schema and becomes the table's UC COMMENT.

After the fix, 53 of 58 `flowx_testing/` specs validate; the remaining 5 are an unrelated
pre-existing `asn1_pdu_name` issue, deliberately untouched.

## E5 — UC6 as configuration

`007_lfj_uc6_ea_flood_warning` (orchestration only) drives
`008_ldp_uc6_ea_flood_warning` (all data engineering). One spec: 6 ingestion flows, 6
transformation flows, 4 export sinks, 6 source-presence gates. **No UC6-specific pipeline code
exists.**

Findings that changed the build, each evidenced in `docs/UC6/FRAMEWORK_CAPABILITY_MAP.md`:

- **Excalibur is comma-delimited** (43 fields, no pipes at all), not pipe as the brief states for
  every source. Pipe would yield a one-column table and break the EE/TMUK path silently.
- **`CSS_account_*.dat.gz` also matches `CSS_account_address_*.dat.gz`** — 56-field and 19-field
  schemas into one table. The spec uses `CSS_account_[0-9]*.dat.gz`; a test pins the trap.
- **The file-presence DQ gate is not expressible on an ingestion flow.** Those rules are per-row
  predicates, so zero rows means zero evaluations and a missing file passes silently — the exact
  failure the requirement exists to prevent. Implemented as reconciliation flows asserting
  `source_record_count > 0` on the one-row `__metrics` dataset. Configuration, not a framework
  change.
- **`observability.appl_logs` does not exist** anywhere in the framework; it appears only in the
  supplied design document. UC6 routes to the real volume-export destination.
- **Asset naming** follows the repo's number-first lowercase convention, not the brief's
  `007_uc6_lfj_EA`, per the brief's own instruction to prefer what the repo does.

**Match strength is a documented assumption.** The legacy Ab Initio scoring algorithm is in none
of the supplied documents. It is one parameterised SQL expression so it can be replaced wholesale
when the real one surfaces.

## E6 — Fixture and business-rule harness

**The supplied POC bundle proves nothing about the business rules**, for two independent and
verified reasons: no postcode overlap between the EA request and any of the five EE sources, and
no join-key overlap across the three CSS files under any candidate column. A run yields zero
matches, and every OSAPR row lands `Bad OSAPR` or `Single Addr` — so the brief's own acceptance
test ("spot-check Found / Not Found / Bad OSAPR / Single Addr") cannot pass on it.

The bundle is kept **unmodified** and its no-match behaviour is pinned as an assertion.
`scripts/generate_uc6_test_data.py` builds a second fixture that exercises all four branches plus
the telephone privacy safeguard and the age filter.

`scripts/verify_uc6_business_rules.py` executes **the spec's own `transformation_sql`** — parsed
with sqlglot's Spark dialect, then transpiled to DuckDB — against both fixtures. It lives in
`scripts/` rather than `tests/unit/` because this repo's `tests/conftest.py` eagerly builds a
`DatabricksSession` and databricks-connect patches pyspark to refuse a local session, which is
why the offline unit baseline sits at ~126 failures.

**It earned its place immediately:** it caught an under-17 customer reaching the telephone list.
The cause was a sqlglot bug that mis-parenthesises `months_between(...) / 12`, not a defect in
the Spark SQL — but the spec now parenthesises the expression explicitly (semantically identical,
immune to that class of bug) and a test pins it.

## E8 -- `export_trigger`: exporting an aggregating target

**Previous:** impossible. Not "unimplemented" -- structurally impossible, and only discoverable
at pipeline runtime. Two facts collided:

1. A Lakeflow sink is **streaming-only** (Databricks: *"Only streaming queries are supported."*),
   enforced by `require_streaming_source`.
2. Delta **refuses to stream from a fully-recomputed table** (`DELTA_SOURCE_TABLE_IGNORE_CHANGES`),
   enforced at plan time by the G-STREAM guard. `skipChangeCommits` is refused framework-wide.

So a `materialized_view` -- or any `TRUNCATE_AND_LOAD` flow -- could be computed and published,
and then had **no way to leave the platform as a file**. UC6 hit exactly this: four export
sinks reading two `GROUP BY`-heavy GOLD tables. Neither validation gate catches it; the spec
onboards cleanly and the pipeline update fails.

**Current:** `sink_config.export_trigger: "per_update"` separates the **trigger** from the
**payload**. The default uses one stream for both -- the staged view's rows both schedule the
write and *are* the write -- which is why a non-streamable payload takes the trigger down with
it. Under `per_update`:

- the **trigger** is a one-row `rate-micro-batch` *pulse* (`_flowx_export_pulse`, temporary, registered **once per pipeline** and shared by every `per_update` sink — four sinks are four edges from one stream, not four streams),
  independent of every business feed, carrying no data. It makes the append flow genuinely
  streaming -- satisfying Lakeflow's constraint honestly rather than by relabelling metadata;
- the **payload** is the staged view read as a batch `dlt.read`, which is what makes an
  aggregation legal.

They are joined on a constant literal; the gate column is dropped before any row reaches the
sink.

**The design decision worth recording.** An earlier version pulsed off an upstream *business*
stream. That fires per **micro-batch**, not per **update** -- so an update in which the
upstream advanced no offsets would recompute the aggregate and write **no file at all**. Silent
missing output on a contractual feed is worse than the error being removed. Six independent
adversarial reviews rejected that design, and they were right to. A `rate-micro-batch` pulse is
update-scoped instead. **The plain `rate` source was the first implementation and was wrong**: it counts rows as
wall-clock seconds since checkpoint creation, so under `AvailableNow` it is a race. Found live — UC6's first green
update produced correct gold tables and four EMPTY sinks — then isolated with a side-by-side probe:

| Pulse source | Fresh checkpoint | Incremental update |
|---|---|---|
| `rate` | 1 row | **0 rows** |
| `rate-micro-batch` (`rowsPerBatch=1`) | 1 row | 1 row |

`rate-micro-batch` (`rowsPerBatch=1`, no `.limit()`) is
update-scoped instead.

**Verified on the live runtime BEFORE implementation**, not asserted from reading docs:

| Update | New business data | Handler invocations |
|---|---|---|
| 1 (full refresh) | yes | 1 |
| 2 | **none** | 1 |
| 3 | none | 1 |

The same probe also read a sibling aggregating MV batch-side successfully, and established that
`dlt.foreach_batch_sink` **is** available on this runtime -- contradicting a code comment whose
"confirmed absent" refers to the local `databricks-dlt` pip stub, where even `create_sink`
reports False.

**Backward compatibility.** Opt-in, default-off. A sink without the key takes the byte-identical
pre-v1.7.5 path, asserted directly: `test_default_path_still_rejects_a_non_streaming_payload`
and `test_default_path_registers_no_pulse_table`.

**Not a spec restructure.** One optional key in `sink_config`. No flow is re-typed, no
`cdc_load_strategy` changes, nothing is removed.

## Known gaps

- ~~Not deployed~~ **Deployed and green** on `metaflow_v7`: run 583025937928399, all five tasks SUCCESS, real-data
  validation ALL 26 PASSED. It took five failed pipeline updates to get there -- every defect passed both offline
  gates and surfaced only at graph planning or execution (defects 8-15 above). That gap -- no pre-flight that
  exercises Lakeflow planning -- is the framework's most expensive missing capability and the next thing to build.
- **Match strength is an assumption**, not a recovered requirement (E5).
- **The Databricks App is updated but not redeployed.** E7 landed the registry, rules,
  knowledge base, `registry.js` and the mandatory `npm run build`. Deploy remains two steps —
  `bundle deploy` then `bundle run` — and `bundle deploy` alone leaves the app on its previous
  code. `server/settings.py` was checked and needs no change: it carries no attribute coupling.
- **`Builder.jsx` was deliberately not modified.** It is a generic renderer driving off
  `registry.js` field descriptors; every new field renders through the existing widgets
  (`select`, `text`, `boolean`) and its `visible_when`/`w` predicate. Editing it would have added
  per-attribute special-casing to a file whose whole design avoids that — and which this repo has
  twice damaged with broad regexes.
- **No schedule** is declared on the job. The legacy cadence is weekly, but an unattended
  schedule would fire against an empty `raw/` and fail the presence gates by design.
