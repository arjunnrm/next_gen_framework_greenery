## Previous vs current

### E1/E2 — the version means something again

**Previous.** `scripts/bump_and_build.py::stamp_version()` rewrote `pyproject.toml`'s patch
component to `int(time.time()*1000)` on every build, producing e.g.
`flowx-0.0.1788350054326-py3-none-any.whl`. Two builds of identical source
got different versions and no deployed artifact traced back to a release.

**Current.** `read_version()` only reads and validates. It raises when the patch component
exceeds 6 digits, so a stale checkout cannot silently reintroduce the old scheme. Releasing is a
deliberate edit to `pyproject.toml` plus the matching `framework_version` bump.

### E3 — per-version artifact directories

**Previous.** All four targets shared `artifact_path: /Volumes/${var.catalog}/config/wheels`.
The repo's own comments claimed unique wheel filenames made this overwrite-safe.

**Current.** `/Volumes/${var.catalog}/config/wheels/${var.framework_version}`.

**Why the previous reasoning was wrong.** `bundle deploy` prunes superseded artifacts from
`<artifact_path>/.internal/` by scanning the directory, **not** by filename collision. A unique
filename never prevented a new release's deploy from deleting the wheel a still-running pipeline
of the previous release was resolving (`ENVIRONMENT_PIP_INSTALL_ERROR`). Separate directories make
that structurally impossible. The never-deploy-mid-run rule still applies *within* one version.

### E4 — auto-detection was implemented but unreachable

**Previous.** `asn1/decoder.py` shipped `detect_root_pdu_name`, and
`decode_asn1_binary_stream(..., pdu_name=None)` already defaulted to detection — but
`spec_validator.py` had `check_string(..., required=True)` on `asn1_pdu_name`, and
`ingestion/readers.py` read `source_config["asn1_pdu_name"]` by subscript inside a
`except KeyError -> FrameworkConfigError` wrapper. Omitting the key failed onboarding AND runtime.

**Current.** Both layers accept an absent/null/blank value as a request to auto-detect. A supplied
value is still type-checked and still wins as an explicit override. Verified end-to-end: TC1's
spec carries no `asn1_pdu_name` and the pipeline resolved PSGW's `CallEventRecord` CHOICE root
unaided, decoding 10 records with 0 quarantined.

### E5 — five live test cases

Each job and pipeline carries `v0.0.2` in its name so a run traces to a release. Onboarding is
delegated to the generic `onboarding_job` via `run_job_task` in all five — none inlines
`02_onboarding_engine.py`.

## Defects found

1. **TC3 streamed from a MERGE-written target (spec authoring, not framework).** Its second
   transformation read an SCD1 target with `is_streaming: true`, which raises Delta's
   `DELTA_SOURCE_TABLE_IGNORE_CHANGES` at execution time. `source_plane.py`'s G-STREAM guard
   rejected it at *plan* time with a message naming the fix, and explicitly refused
   `skipChangeCommits` because it silently drops changed rows. Fixed to a batch read.
2. **`psgw_synthetic.ber` would have produced a false pass (fixture, not framework).** It holds 10
   records concatenated as back-to-back TLVs in one file; `asn1tools` returns only the FIRST from
   such a buffer with no error — 1 row ingested, 9 silently dropped, reported SUCCESS. The seed
   notebook lands one record per file and asserts each decode consumes the whole file.
3. **Auto-detection unreachable from a spec** — see E4.
4. **TC3, defect 3 (spec authoring, caused by fixing defect 1).** Making the SCD1 input batch left
   `tf_tc3_order_enriched` with all-batch inputs but a `streaming_table` target; Lakeflow raised
   *"View `_tc3_order_enriched_staged` is not a streaming view and must be referenced using read"*.
   Target changed to `materialized_view` (legal here: the append-only rule rejects an MV only for
   `TRUNCATE_AND_LOAD`, and this flow is `APPEND`).
5. **TC3, defect 4 — a real constraint conflict, not a typo.** `execution_mode: "pipeline"` FORCES a
   streaming read of the reconciliation source (it registers the L5 heal lane, and
   `dlt.foreach_batch_sink` accepts streaming queries only), but TC3's source had to be a batch-only
   MV. The batch-source alternative `pipeline_audit_only` is rejected when both capture flags are
   false — the mode exists solely to produce `__metrics`/`__mismatch`. TC3's objective is both flags
   off, so an in-pipeline reconciliation was genuinely incompatible with it. The flow never healed
   anyway (no `append_target_table`, direction `target_to_source`), so `"pipeline"` bought it
   nothing. **Operator decision: the reconciliation flow was removed from TC3.** CDC record-state
   resolution is still exercised by the SCD1 `apply_changes` flow, which is what the test case's
   step 3 actually describes; in-pipeline reconciliation with metrics on/off is covered by TC4/TC5.
6. **FRAMEWORK GAP — a flow removed from a spec is never deactivated.** `metadata_upsert.py` only
   ever writes `is_active=True`, and there is no deactivation path in `onboarding/` (`action_type`
   accepts only `CREATE`/`UPDATE`/`VALIDATE_ONLY`). After TC3's reconciliation flow was deleted from
   the spec and the group re-onboarded, the pipeline **still** failed on
   `Consumer 'recon_tc3_enriched_vs_status_metrics_off:source' requested a streaming read ...` —
   driven entirely by the stale control-table row. This is the same class as AGENTS.md's "removals
   are rejected, never ignored", except a removed flow is not rejected but silently *retained*, so
   the spec and the running system disagree with no signal. Clearing it requires
   `UPDATE <catalog>.config.reconciliation_flow_spec SET is_active = false WHERE reconciliation_id = ...`,
   which could not be issued here: CLI v1.13.0 returns `Error: Not Found` for
   `/api/2.0/sql/statements` in this workspace. **TC3 therefore remains RED pending that manual
   UPDATE.** Left as an open decision rather than silently changing onboarding semantics, since
   auto-deactivating absent rows would affect anyone onboarding a partial spec.
