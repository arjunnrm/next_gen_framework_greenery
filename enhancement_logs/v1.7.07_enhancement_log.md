**Theme:** A thirteen-point architecture review of UC3 (Excalibur) and UC6 (Flood Warning)
found that the two use-case specs, the framework's onboarding gates and the App had drifted in
small, silent ways: a catalog that no bundle target deploys to, a validation rule the runtime

path that deleted the value it was about to render. This release closes each one and pins it.

## Why this release exists

The review (published 2026-09-08, "UC3 & UC6 Architecture Review") answered thirteen questions
from the framework source rather than the docs. Most answers were rationale — the design was
right and the question was really "why". Five were defects, and two more were hardening items
the review surfaced along the way. Every change below is one of those seven.

## E1 — `data_standardization_sql` must name its output column

**Previous:** `_validate_standardization_expression` checked the forbidden-keyword list and the
`;` ban. The runtime (`ingestion/standardization_sql.py`) additionally requires every entry to
end in `AS <column_name>` — it is the alias that tells `withColumn` which column to write — and
raises `FrameworkConfigError` without it. So `"trim(customer_name)"` onboarded cleanly, wrote its
control row, and killed the pipeline at graph definition.

**Current:** the validator applies the runtime's own regex (`_STANDARDIZATION_ALIAS_PATTERN`) and
reports `must end with 'AS <column_name>' naming the output column`. The JSON-schema
`dataStandardizationSql` item pattern now also requires the alias, so both gates agree
(`test_unknown_key_rejection.py` still passes). The review also corrected two docs that said a
column could be "projected away by `data_standardization_sql`" — impossible, since it is a
`withColumn` loop that only adds or replaces.

Corpus impact: none. Every shipped spec (including `flowx_testing/`, `BT_Usecase/`, the golden
specs) already ends each entry with an alias.

## E2 — `TRUNCATE_AND_LOAD` on a `streaming_table` is rejected

**Previous:** no `target_type` × `cdc_load_strategy` matrix existed. Both `APPEND` and
`TRUNCATE_AND_LOAD` are in `engine/flow_registration.py::_NO_OP_CDC_STRATEGIES`, so on a
streaming target `TRUNCATE_AND_LOAD` was realised as `dlt.read_stream` → plain append: identical
to APPEND, never truncating, with the spec claiming a full reload it never performed.

**Current:** `_reject_incompatible_target_type_strategy` rejects the pair on ingestion and
transformation flows with a message naming the fix (`materialized_view` / `batch_table`, or say
`APPEND`). Only this one pair is listed; `materialized_view` + `FULL_SNAPSHOT_CDC` and friends
are legitimate and untouched. The App gets the same rule in `config/validation/rules.json`.

Corpus impact: one archived spec (`archive/old_json/053_geneva_*`) carries the pair; nothing
under `flowx_testing/` or `BT_Usecase/` does.

## E3 — UC3 batch-recon spec no longer names a catalog

**Previous:** `target_catalog`, `pipeline_parameters.landing_root`, three `schema_location`s,
every reconciliation `source_config.table` / `target_configs[].table` /
`append_target_table`, and the observability `volume_path` all said `br_digital_poc`. The bundle
targets set `catalog` to `bt_digital_poc` (`hoonartek`) and `flowx` (`metaflow_v7`); the job
onboards with `catalog: ${var.catalog}`. The pipeline resource and control tables therefore
lived in one catalog while the batch flows and reconciliations wrote to another.

**Current:** all 19 literals are `{{catalog}}`. `spec_loader.py::substitute_environment_placeholders`
is a raw-text replace before parsing, so the placeholder is legal in every one of those positions
(the `${landing_root}` runtime parameter inherits it). `test_uc3_specs.py` pins that no
functional string mentions either catalog literal.

## E4 — Governed tag values

**Previous:** `domain: "crm"`, and `info_type` carried both `EIN Number` and `EIN number`. The
governed `info_type` policy allows only the former, so `SET TAGS` would fail the group's tagging.

**Current:** `domain: "Customer 360"` on all six flows; both `EIN number` occurrences corrected;
`uc3_governed_tags.sql` lists `'Customer 360'` and records the `ALTER TAG POLICY ... ADD
ALLOWED_VALUES` needed where the policy pre-exists with `'crm'`. The three zerobus flows drop
`capture_technical_metadata: true` (the default; on a Delta-table source the four
file-provenance columns land NULL, and `sequence_by_column` is explicit so CDC does not need the
ingestion timestamp). Tags are applied from control-table rows, so the change takes effect after
re-onboarding and re-running the governance job.

## E5 — UC3 jobs: run jobs run, seed job seeds, governance job tags

**Previous:** `004` and `005` each ran `setup_control_tables -> onboard -> run_pipeline_update ->
apply_governance -> observability_export` on every trigger. The YAML comments claimed setup
"applies the additive control-table migration"; it does not — `ensure_control_table_columns` is
called from `ensure_control_schema_exists` inside the onboarding engine.

**Current:** `004` and `005` are `run_pipeline_update -> observability_export` (the shape the
sample-suite layout test pins). `uc3_seed_job.yml` (`003b_lfj_uc3_excalibur_seed`) runs setup
then onboards both specs in series; `uc3_governance_job.yml` (`009_lfj_uc3_excalibur_governance`)
tags both groups. Job-level `dataflow_group_id` tags stay: they are the system-table join key.
Run order for a fresh workspace: seed → 003 → 004 → 005 → governance.

## E6 — UC6: retain the EA archive; publish recon output to `staging`

**Previous:** `delete_source_after_extract: {"action": "delete_now"}` consumed the EA `.gpg` on
every run (the run-book step "re-upload before each run"). The six `pipeline_audit_only` recons
had no `publish_schema`, so their `recon__*__metrics` views landed in the pipeline's declared
schema — `bronze`, beside the business tables (known limitation R9).

**Current:** `delete_source_after_extract: false`; the extractor writes a
`.<archive>.__framework_extracted__` sidecar and skips the archive until a newer copy lands. The
marker matches neither this flow's `zip_file_pattern` nor the five sibling `file_pattern`s on
`raw/`. `publish_schema: "staging"` on all six recons, matching UC3. The UC6 master document's
wrong attribution of the loud failure to `error_handling.on_failure` (inert in audit-only mode)
is corrected.

## E7 — App: `source_inputs[].table` rendered empty on import

**Previous:** `Builder.jsx::absorbItem` split any `table` value with exactly three dot-parts into
`target_catalog/target_schema/target_table` and deleted `table`. That decomposition exists for
reconciliation `target_configs`, whose registry row renders those three boxes; `source_inputs`
renders a single `table` box, so every `{{catalog}}.schema.table` input (all 17 in UC6) came up
blank. The server-side twin (`server/core/deserializer.py`) had the correct
`flow_kind == "reconciliation"` guard; the client copy had lost it.

**Current:** both the import split and the save-side recomposition (`itemObj`, which also injects
the framework-rejected `type` key) are gated on the repeat declaring the three fields.
`npm run build` rebuilt `web/dist` (`index-CG1V1kHH.js`); Databricks Apps does not build at
deploy time.

## E9 — `publish_schema` is the only thing that publishes

**Previous:** `register_reconciliation_flow` resolved `effective_publish_schema = row.publish_schema
or publish_schema`, the second being the hosting pipeline's own schema. So every pipeline-mode flow
published its `recon__<rid>__<tid>__metrics` (and `__mismatch`) as real materialized views even when
it never asked for a schema — UC6's six presence gates landed six MVs in `flowx.bronze` beside the
business tables, while UC3's landed in `staging` only because that spec said so. Two guards made
the shape worse: `dq_config.rules` *required* `run_log_capture: true`, and `run_log_capture: true`
is what published the view. A pure gate therefore could not exist without publishing.

**Current:** `publish_schema` is the sole publish decision.

| Situation | Before | After (v1.7.07) |
|---|---|---|
| `publish_schema` absent, `dq_config` rules | rejected unless `run_log_capture: true`, then published to the pipeline schema | accepted; `_recon__<rid>__<tid>__metrics` registered **temporary**, gate fires, nothing published |
| `publish_schema` absent, `run_log_capture`/`mismatch_log_capture: true` | published to the pipeline schema | **rejected** (onboarding and graph definition): the control-table rows are exported from the published copies, so the flag promised a row that could never be written honestly |
| `publish_schema` absent, `execution_mode: pipeline` with `append_target_table` | `_src`/`_tgt` published to the pipeline schema | **rejected**: the heal handler reads them back through the metastore, so they must be published, and nothing is published without `publish_schema` |
| `publish_schema` set | published there | unchanged |
| `pipeline_audit_only`, both flags false, no rules | rejected (no output) | still rejected |
| `pipeline_audit_only`, both flags false, rules present | rejected | accepted (the gate is the output) |

Mechanics: a new `_audit_node()` helper returns `(name, temporary)` for `__metrics`/`__mismatch`;
`_node_name()` raises rather than name a published node without a schema; `registers_metrics =
run_log_capture or dq_rules`. `observability/reconciliation_export.py::_publish_location_candidates`
returns no candidates for an unpublished flow and the export loop logs at INFO and moves on. The
`publish_schema` argument the pipeline notebook passes is retained for call-site compatibility and
documented as unused. `spec_validator.py::_validate_logging_config` gained `publish_schema` and
`heals` parameters and the two new rejections; the old `dq_config`-needs-`run_log_capture`
rejection is gone.

Corpus impact: none. Every pipeline-mode flow shipped in the repo (UC3, UC6, the golden spec, the
full reference) sets `publish_schema`. Live impact: none until re-onboarding; a pre-v1.7.07
workspace keeps its already-published views until the flow's next update drops them.

Tests: `test_recon_logging_gates.py` — five new graph-layer tests (temporary metrics for a gate,
capture without publish rejected, pipeline-conf override caught, healing without publish rejected,
audit-only gate accepted) and four new validator tests; the two pre-v1.7.07 "dq rules need
capture" tests are inverted to assert acceptance.

## E10 — UC6 tables are named for the business, not the project

**Previous:** every UC6 target table carried the technical `uc6_` prefix (`uc6_css_account`,
`uc6_osapr_output`, `uc6_export_leidos_telephone`), and the platform naming standard prescribed
`uc<N>_<entity>` for bronze.

**Current (user decision, 2026-09-08):**

| Layer | Rule | Before → after |
|---|---|---|
| Bronze | the source table's own name (`source_table_name`) | `uc6_ea_request → ea_request`, `uc6_css_account → css_account`, `uc6_css_account_address → css_account_address`, `uc6_css_subscription → css_subscription`, `uc6_jt_customer → jt_customer`, `uc6_excalibur_address → excalibur_address` |
| Silver | the business subject | `uc6_ea_base → ea_request_base`, `uc6_ea_address → ea_request_address`, `uc6_ee_address_paf → ee_customer_address_paf`, `uc6_matched_address → flood_area_matched_address` |
| Gold | subject + output | `uc6_osapr_output → flood_warning_osapr`, `uc6_telephone_output → flood_warning_telephone` |
| Sinks | the export | `uc6_export_leidos_telephone → leidos_telephone_export`, `uc6_export_leidos_osapr → leidos_osapr_export`, `uc6_export_telephone → telephone_export`, `uc6_export_osapr → osapr_export` (staging paths follow) |

Flow ids, rule ids, `input_name` aliases and `source_database` keep `uc6` — they are identifiers,
not table names, and an alias equal to a table name would collide in the pipeline namespace.
`tests/unit/test_uc6_spec.py::test_every_table_is_uc6_prefixed` is inverted to
`test_no_table_carries_the_technical_uc6_prefix`, plus a new assertion that every bronze table
equals its `source_table_name`. `scripts/validate_uc6_pipeline_output.py` and
`scripts/verify_uc6_business_rules.py` follow the new names; the delivery naming standard §3.3 now
prescribes the source-table / business-subject rule and records UC6 and UC3 as its users.

**Operational consequence:** renaming a Lakeflow table is a new table. On the next update the
pipeline creates the new names, re-ingests bronze from `raw/` (fresh Auto Loader checkpoints — the
six raw files must be present), recomputes silver/gold, and drops the `uc6_*` datasets it no longer
defines. Re-onboard first; `apply_governance_uc6` then tags the new names. Any external consumer of
`gold.uc6_osapr_output` / `gold.uc6_telephone_output` must move to `flood_warning_osapr` /
`flood_warning_telephone`.

## E11 — UC6: one COUNT(*) gate replaces six self-reconciliations

**Previous:** six `pipeline_audit_only` reconciliation flows, each comparing a bronze table against
itself so that `source_record_count > 0` could be asserted on the recon engine's one-row `__metrics`
dataset. It worked — a groupBy-less aggregate is one row even over an empty table — but at the cost
of 24 graph nodes, a full-outer self-join and collapse per source, six published `recon__*__metrics`
views, and **no dependency edge** to the flows it protected: Lakeflow could recompute `ea_request_base`
to zero rows before the gate failed the update.

**Current:** `reconciliation_flows` is gone from the UC6 spec (user decision, 2026-09-08). One
transformation flow, `ts_uc6_source_presence_gate`, publishes `silver.flood_warning_source_presence`:
`SELECT '<source>' AS source_name, count(*) AS row_count FROM <bronze alias> UNION ALL …` over the six
bronze tables, with `dq_config` rule `uc6_every_source_present` = `row_count > 0`, action `fail`. The
three flows that read bronze directly (`ts_uc6_ea_base`, `ts_uc6_ea_address`,
`ts_uc6_ee_address_paf`) gain the gate as a `source_inputs[]` entry and wrap their SQL in
`SELECT u.* FROM (<sql>) u CROSS JOIN (SELECT count(*) AS present_sources FROM <gate alias> WHERE
source_name IN (...) AND row_count > 0 HAVING count(*) = N) g`: a one-row broadcast that changes no
cardinality but makes the gate upstream of every consumer. The gate is first in
`transformation_flows` so `scripts/verify_uc6_business_rules.py`, which materialises flows in array
order, has it before its readers; Lakeflow orders by lineage.

What is lost: the `reconciliation_run_log` row per source per update — written only by the export
task, only on passing updates, never on the failing one. The expectation's pass/fail counts in the
pipeline event log, already exported by `observability_export`, are the audit trail. Tests:
`test_uc6_spec.py` gains three assertions (no recon flows; the gate counts every bronze source once
with a fail rule; every bronze reader depends on the gate). `scripts/verify_uc6_business_rules.py`
passes unchanged on the new shape.

## E12 — `prune_missing_flows`: removed flows no longer stay active

**Previous:** `metadata_upsert.py` only ever wrote `is_active = true`. Deleting a flow from a spec
and re-onboarding left its row active, and `load_active_group_metadata` kept handing it to the
pipeline — the removed flow kept registering datasets and kept running (observed 2026-09-03 on a
deleted recon flow; would have recurred on E11's six rows). The only remedy was a hand-written
`UPDATE ... SET is_active = false`.

**Current:** new module `onboarding/spec_pruning.py`. `build_flow_deactivation_statements()` is a pure
function returning, per flow table (`ingestion_flow_spec.dataflow_id`,
`transformation_flow_spec.flow_step_id`, `reconciliation_flow_spec.reconciliation_id`), a count and
an `UPDATE ... SET is_active = false, updated_at = current_timestamp() WHERE dataflow_group_id = '<g>'
AND is_active = true [AND <id> NOT IN (<declared ids>)]`; an empty declared list deactivates every
active row of that kind for the group. `deactivate_flows_absent_from_spec()` executes them and logs
a WARNING per table that had stale rows. `02_onboarding_engine.py` gains the `prune_missing_flows`
widget (`false`/`true`, default `false`) and calls it after the upserts; `onboarding_job.yml` exposes
it as a job parameter; the UC6 job's `onboard_uc6` passes `"true"`.

**Why opt-in, not default:** a `reconciliation_flows[]` entry may carry a *different*
`dataflow_group_id` than the spec that declares it (the supported cross-group case). Pruning by group
cannot tell that row from a removed one, so re-onboarding group X would deactivate a flow spec Y still
declares. Groups owned by exactly one spec — every BT_Usecase group — can turn it on. Rows are never
deleted; a flow re-added to the spec is reactivated by the next upsert. Tests:
`tests/unit/test_spec_pruning.py` (6).

## E13 — UC6 spec: simpler to read, provably the same

**Previous:** 47 KB. Every flow restated `storage_format: "delta"`, every ingestion flow restated
`capture_technical_metadata: true` and `reader_options.mode: "PERMISSIVE"` (all defaults), seven
flows carried an empty `dq_config`, input aliases mixed roles and names (`uc6_ea_request_base` was
an alias for *bronze* `ea_request` while the *silver* table is `ea_request_base`), and the two
address-normalising statements repeated
`nullif(trim(regexp_replace(regexp_replace(upper(coalesce(x, '')), '[^A-Z0-9 ]', ' '), ' +', ' ')), '')`
about thirty times — eight of them inside a `PARTITION BY`.

**Current (41 KB):**

| Change | Detail |
|---|---|
| Defaults dropped | 17 × `storage_format`, 6 × `capture_technical_metadata`, 6 × `reader_options.mode`, 7 × empty `dq_config` |
| Aliases renamed | `<table>_in` for a plain read, `<table>_for_<consumer>` where one table feeds several flows, `gate_<source>` for the gate; asserted unique and never equal to a table name (aliases share the pipeline namespace) |
| `ts_uc6_ea_base` | one `ranked` CTE, then `WHERE rn = 1` |
| `ts_uc6_ea_address` | `ea` → `normalised` → `deduped` CTEs: the address is assembled with `concat_ws` first and normalised **once**; the dedupe key is the three named columns, not a repeated expression |
| `ts_uc6_ee_address_paf` | one CTE per source (`css`, `jt`, `excalibur`) selecting raw `postcode / address_raw / town_raw / po_box`, a `customers` UNION ALL, and one normalising SELECT at the end |
| `ts_uc6_telephone_output` | reuses the OSAPR decision (`o.count = 1`) instead of restating `count_of_osapr > ${min_addresses_per_area}`; drops the msisdn null filter the PAF flow already applies |
| `_about` | describes the current shape and points at §13 of the master document |

**Equivalence.** `scripts/verify_uc6_business_rules.py`'s DuckDB harness was used to materialise all
11 transformation outputs on both fixtures before and after; every one of the 22 tables is
byte-identical (NULL and empty string treated alike, which no consumer distinguishes). The
normalise-once rewrite is equivalent because `concat_ws` skips NULLs and the collapse of `' +'`
removes the gaps that empty or punctuation-only components leave; the Excalibur record-variant
fallback still decides emptiness *after* normalisation. The telephone rewrite is equivalent because
`count = 1` is exactly `best_match_strength > threshold AND matched_osapr_count > min`, and a row
with `match_strength > threshold` implies `best_match_strength > threshold`.

**One trap found and pinned.** The first rewrite wrote `floor(months_between(a, b) / 12)`. In Spark
that is unambiguous; sqlglot's DuckDB rendering of `MONTHS_BETWEEN` expands to `a + CASE … END` with
no parentheses, so `/ 12` bound to the CASE alone and every age came out around 140 — the under-17
customer passed the offline check. The spec keeps the original `floor((months_between(a, b)) / 12)`
form, which is Spark-neutral and transpiles faithfully; `test_uc6_spec.py` now asserts it.
