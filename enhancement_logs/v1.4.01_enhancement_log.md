# v1.4.01 Enhancement Log

**Release date:** 2026-08-30
**Progress Tracker:** `Completed — deployed and onboarding-verified against dev_metaflow.` All ten
corrections implemented and tested locally, then deployed: wheel, 88 bundle resources and the
Databricks App to `dev_metaflow`, followed by `framework_config_onboarding_job` — **43/43 specs

release listed as blocking. **No Lakeflow pipeline has been run**, so v1.4.00 §4c's pipeline-level
gap is narrowed, not closed — see §4d.

**Theme:** verification against the enforcer, not against the plan. v1.4.00 propagated a spec
change into the Databricks App by working through a hand-written checklist. This release checks the
result the only way that actually proves anything — by driving the app's own output through
`onboarding/spec_validator.py` and comparing. Ten disagreements surfaced. One of them was written
into the checklist itself.

**The load-bearing finding.** `docs/v1.4.0_json_attribute_delta.json`'s entry for
`cdc_operation_column` stated its applicability correctly in the `after` field — `{SCD1, SCD2,
FULL_SNAPSHOT_CDC}` — and then instructed the app to *"simplify the predicate to
`isCdc(strategy)`"*, which is `{SCD1, SCD2, SCD3, FULL_SNAPSHOT_CDC}`. The app implemented the
instruction rather than the fact, so the Spec Builder offered a delete-marker field on SCD3 and
onboarding rejected every spec that used it. A checklist an agent follows is code; a contradiction
inside one propagates exactly like a bug, and reading the checklist back to itself cannot find it.

## 2. Previous State vs. Current (Target) State

### E21 — `cdc_operation_column` offered on SCD3 (BUG)
- **Previous:** `Builder.jsx` gated both `target_config.cdc_operation_column` and
  `target_config.cdc_operation_mapping.delete_values` on `isCdc(strategy)`, i.e. all four
  CDC-dispatched strategies. `spec_validator.py`'s `strategies_supporting_delete_marker` is
  `{SCD1, SCD2, FULL_SNAPSHOT_CDC}`.
- **Current:** a new `hasDeleteMarker(s)` helper in `registry.js`, exported and used by both
  fields. The server-side registry's `visible_when` lists the same three.
- **Why it is worth its own entry:** this is the *only* failure direction that actually costs an
  author anything. The builder narrowing the framework is a deliberate UX choice made in several
  places — `partition_columns` on a CDC strategy is accepted by the validator and then silently
  ignored at runtime, so the builder hides it rather than offering an inert field. The builder
  *widening* the framework has no upside: the author fills the field in, saves, and onboarding
  refuses the spec with an error about a field the UI told them to set.
- The app's own `attribute_knowledge.json` already carried the correct rule in prose — *"A
  validation error on SCD3, which has no delete path at all"* — while the predicate beside it said
  otherwise. Curated prose and executable predicate disagreed, and only the predicate ran.

### E22 — A one-argument predicate is always-False (BUG)
- **Previous:** removing the `FULL_SNAPSHOT_CDC_NO_PK` guard from `shared.cdc.json` deleted the
  operand and left the operator: `{"ne": ["target_config.cdc_load_strategy"]}`.
- **Current:** deleted. Both delete-marker fields are visible again in the registry-driven surface.
- **The mechanism, because it will recur:** `evaluate_predicate` reaches every binary comparison
  behind `if isinstance(args, (list, tuple)) and len(args) >= 2:` and falls through to a bare
  `return False` otherwise. A malformed predicate therefore does not raise, does not warn, and does
  not degrade to true — it evaluates to *false for every input*, so the `and` containing it is
  false for every input, and the field it guards is invisible for every strategy. Verified directly:
  `evaluate_predicate({'ne': ['target_config.cdc_load_strategy']}, {...}) is False`.
- **Guard added:** `test_no_binary_predicate_is_missing_its_operand` walks every predicate in
  `config/registry/*.json` and fails on any binary operator with fewer than two operands. This is
  the cheapest possible check for an entire class of silent registry corruption.

### E23 — `primary_keys` not required for `FULL_SNAPSHOT_CDC` in the app's rules (BUG)
- **Previous:** `rules.json`'s `scd_requires_primary_keys` fired on `[SCD1, SCD2, SCD3]`. The
  registry's `visible_when` had been updated to include `FULL_SNAPSHOT_CDC` in v1.4.00; the
  validation rule beside it had not.
- **Current:** `[SCD1, SCD2, SCD3, FULL_SNAPSHOT_CDC]`, with a message that names the migration.
- This is `modified[0].app_action` of the v1.4.0 delta — *"The visibility/required predicate for
  primary_keys must now include FULL_SNAPSHOT_CDC"* — applied to the visibility half and missed on
  the required half. A keyless snapshot flow passed the app's validator and failed onboarding.

### E24 — `columns_to_exclude` scope stated by enumeration rather than complement
- **Previous:** the rule fired when the strategy was in `[APPEND, TRUNCATE_AND_LOAD]`. The framework
  rejects the attribute for anything outside `{SCD1, SCD2, SCD3}` — three strategies, not two.
  `FULL_SNAPSHOT_CDC` fell through.
- **Current:** `nin [SCD1, SCD2, SCD3]` — the complement of the strategies that have a comparison
  concept at all. A strategy added later cannot silently fall through it, which enumerating the
  rejected side guarantees it eventually will.
- The registry's own field description had said *"Validation error with APPEND, TRUNCATE_AND_LOAD or
  FULL_SNAPSHOT_CDC"* since v1.4.00. Prose right, rule wrong — the same shape as E21.

### E26 / E27 — The app could not author a Kafka sink (BUG)
- **Previous:** `sink_config.format` offered `"kafka"`, and `sink_config.path` was correctly hidden
  for it. Nothing replaced it. `kafka_options` — required by `_validate_sink_config`, and required
  to contain both `kafka.bootstrap.servers` and `topic` — existed nowhere in the app. Selecting
  Kafka produced a spec rejected with `sink_config.kafka_options: is required but was missing`.
- **Current:** `kafka_options` is a `kv` field visible when `format == "kafka"`, seeded with the
  three documented keys, plus a `kafka_sink_requires_options` rule.
- **E27 fell out of E26 and matters on its own.** Flow rule contexts were built as
  `{"v": ..., "root": ..., "@__flow_kind": ...}`, and `resolve_path_value` searches `v` only. `kv`
  and `repeat` widgets are stored under `kvs`/`reps`, so *any* rule referencing one resolved to
  `None` whether it was populated or not — an `empty` guard would have fired on a correctly-filled
  flow. `resolve_path_value` now falls back to `context["kvs"]`/`context["reps"]`, checked before
  the root fallback so a flow-scoped kv wins over a same-named root scalar. Both flow contexts pass
  them. Two tests cover it: the missing case *and* the populated case, since a rule that always
  fires passes a missing-field test.
- **Deliberately not done:** `kafka_secret_options` — a map of option name to Unity Catalog secret
  reference — is still unauthorable. The serializer has no repeat-to-map-of-secret-ref shape, and
  inventing one for the rarer of two Kafka credential paths is a worse trade than saying so. The
  field's help text now names it as hand-edit-only rather than leaving an author to discover the
  gap at onboarding.

### E28 — Three optional attributes the framework validates and the app could not express
`post_export_archive.export_file_name_format`,
`post_export_archive.pgp_encryption.sign_passphrase_secret`, and
`pre_extraction_decryption.passphrase_secret`. The last is worth naming precisely: it is the
passphrase on the **PGP private key**, and it sits beside `secret_passphrase`, which is the AES
password on the **ZIP archive**. The two are independent, combinable, and differ by word order
alone. Both now carry help text saying which is which and pointing at the other.

### E29 — `templates/reconciliation/blank.json` shipped the builder's internal shape
- **Previous:** `target_configs[0]` carried `target_catalog` / `target_schema` / `target_table`. A
  reconciliation target in the spec has none of those — the framework reads a three-part `table`.
  The three keys are the *builder's* decomposed edit form, which `serializer.py` recomposes on save
  and `deserializer.py` decomposes on import.
- **Current:** `{"type": "table", "table": "..."}`, matching `full.json` and `warn.json`, which
  already shipped the canonical shape.
- **Why this survived v1.4.00:** it round-trips. Loaded through the builder it works, because
  `absorbItem` accepts the decomposed keys directly. It fails only when used the way a template file
  invites — saved or read as a spec. Nothing in the app's own test suite validates a template as a
  spec, which is precisely the gap the new test closes.

### E30 — `transform_sql` pointed at a view that does not exist
- **Previous:** `onboarding_templates/pipeline_onboarding_template.{json,yaml}` read
  `SELECT ... FROM missing_records`.
- **Current:** `FROM _reconciliation_unmatched_records` — `appender.py::UNMATCHED_RECORDS_VIEW_NAME`,
  the fixed temp view the reconciliation appender actually registers the miss set as.
- The app's copy of the same template, `onboarding_spec_full_reference.json`, and the agent skill's
  copy of that were all already correct. Only this pair was stale, and the two copies of the
  canonical template had therefore silently forked. A test now asserts they are identical, which is
  the cheaper way to notice than reading both.

### E31 — Agent skill overstated CDC field applicability
- **Previous:** *"Common optional `target_config` fields across every CDC-dispatched strategy:
  `sequence_by_column`, `columns_to_check`/`columns_to_exclude`,
  `cdc_operation_column`/`cdc_operation_mapping.delete_values`, `generate_hash_columns`."* Two of
  those five are narrower than "every".
- **Current:** a per-field **valid for / rejected on** table naming both enforcing sets in
  `spec_validator.py` (`strategies_supporting_comparison_exclusion`,
  `strategies_supporting_delete_marker`), so a reader can check the claim against the code.
- **Also added — §9.1**, on the encrypt → decrypt type contract. `encrypted_columns[].source_data_type`
  is the one attribute v1.4.0 *added*, and the skill had not mentioned it, `original_data_type` or
  `cast_to_type` anywhere. The section states the thing an agent most needs: **omitting it is the
  documented default path**, so the key should be emitted only when asked for, and never as `""`.

### 4e. Method note — how these were found

Not by re-reading the checklist. Three mechanical sweeps, each comparing an app surface to the
framework rather than to a document:

1. **Every shipped template through the real `validate_spec`.** Found E29, E30.
2. **A (strategy × optional attribute) matrix**, asking for each cell whether the builder shows the
   field and whether the framework accepts it. Found E21. Its "app hides / framework accepts" cells
   were reviewed individually and all confirmed deliberate — the framework's validator is
   permissive about attributes that are merely inert at runtime, and the builder is right to hide
   those.
3. **A bidirectional path audit** — every path the app can emit against every path the JSON schema
   defines, in both directions. The app→framework direction was clean. The framework→app direction
   found E26 and E28.

`spark` is stubbed throughout: no Java is installed on this machine, so no local Spark session is
available. The stub returns exactly the plan text this workspace's serverless environment returns
for an unresolved reference, which `_validate_sql_syntax` tolerates by design — so the SQL path is
exercised and only *attribute* problems can fail. SQL grammar validation remains a live-run
concern, unchanged from v1.4.00.

## 5. Defects Found and Fixed

All ten are listed in §1–§2 and, machine-readably, under `app_surface_corrections` in
`docs/v1.4.0_json_attribute_delta.json`. Three are worth calling out as *classes* rather than
instances:

1. **A checklist entry that contradicted its own factual field** (E21). The delta's `after` said
   `{SCD1, SCD2, FULL_SNAPSHOT_CDC}`; its `app_action` said `isCdc(strategy)`. The app implemented
   the action. **Rule adopted:** an `app_action` must restate the set literally, never name a helper
   whose membership is defined elsewhere. The corrected entry now says so explicitly, and keeps the
   old text under `app_action_superseded` rather than erasing it.
2. **A silent-false predicate** (E22). Deleting an operand and leaving the operator produces a
   guard that is false for every input, with no error anywhere. This is the structural-edit hazard
   already recorded in this repo's memory — the blanket `sed` and the DOTALL `re.sub` — in a new
   medium: JSON predicates rather than source text. The new hygiene test is the counterpart to
   `node --check`.
3. **Prose and predicate disagreeing, with only the predicate running** (E21, E24). In both cases
   the app's own curated knowledge base and field descriptions stated the correct rule while the
   executable predicate beside them did not. Curated prose is not a check; it reads like one.

## 6. Known Gaps / Follow-Ups

- **`sink_config.kafka_secret_options` is still unauthorable in the app.** It needs a
  repeat-widget-to-map-of-secret-ref serializer shape that does not exist. Documented in the
  `kafka_options` help text as hand-edit-only; recorded as APP-C5 in the JSON delta.
- **The app↔framework applicability matrix in `test_framework_spec_agreement.py` is a hand
  transcription of `Builder.jsx`'s `w:` predicates.** It cannot drift silently in the direction
  that matters — if the transcription says a field is shown and the framework rejects it, the test
  fails — but a predicate loosened in `Builder.jsx` without updating the transcription would not be
  caught. Deriving it by executing `registry.js` under node, as
  `build_attribute_knowledge.py` already does, would close that.
- **`databricks-app/web/dist/` is not actually tracked by git, and never has been — needs a
  decision.** `.gitignore` carries a global `dist/` on line 3 and `!databricks-app/web/dist/**` on
  line 4, so the intent to track the built bundle is explicit. It does not work: git never descends
  into an excluded *directory*, so a negation for files beneath it can never match. `git ls-files
  databricks-app/web/dist` returns 0 files, while both the v1.4.00 log and
  `test_canonical_spec_and_features.py`'s docstring describe `web/dist/` as "committed Vite output".
  Two consequences: a fresh clone has no bundle, so `conftest.py::frontend_text` fails its own
  "frontend build is missing" assertion and takes several tests with it; and DABs `sync` honours
  `.gitignore`, so a deploy from a clean checkout would ship an app with no frontend at all. The
  minimal fix — unignoring the directory before its contents — is applied here and verified with
  `git check-ignore -v`:

  ```
  dist/
  !databricks-app/web/dist/
  !databricks-app/web/dist/**
  ```

  **The bundle itself has deliberately not been `git add`ed.** Committing ~315 KB of generated
  output on every frontend change is a repo-policy call, not a defect fix. The alternative — build
  at deploy time — is closed off by Databricks Apps, which does not build. Whoever owns that call
  should either add the tree or drop the negation and replace it with a documented pre-deploy build
  step; leaving a negation that silently does nothing is the one option that should not stand.

- **The v1.4.00 live-run gap is untouched.** TC-CDC-007, TC-CDC-006, TC-SEC-001/TC-TRF-003,
  scenario 004 and TC-OBS-001/003 all still need a real run before v1.4.0 can be called
  live-verified. See v1.4.00 §4c.
- **`columns_to_exclude`'s effect on the target schema remains genuinely undecided** between the
  validator and the SCD registrar — carried forward, and stated as such in the app's own attribute
  knowledge. Not touched here.
