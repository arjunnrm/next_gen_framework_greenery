# v1.5.01 Enhancement Log

**Release date:** 2026-08-31
**Progress Tracker:** `Completed — implemented and verified offline. NOT deployed.` The regrouping
is verified the only way that actually proves it: the fully-resolved bundle config is **byte-identical**
to v1.5.0 (§4a). No `bundle deploy` was run, deliberately — see §4c.

**Theme:** a resource tree you can scope a deploy against. `resources/` held 95 YAML files in one
flat directory, loaded by a single `resources/*.yml` glob. Finding the app among 83 test resources
meant knowing its filename, and "deploy just the app and the config jobs" had no expression at all
in the layout. The files are now grouped one folder per purpose, each with its own `include:` line.

**The load-bearing finding.** The obvious way to scope a deploy — comment out
`resources/feature_tests/*.yml` — is *destructive*, and silently so. DABs treats a resource that is
absent from the configuration as one to **delete from the target**, so an include line commented out
"just for this deploy" tears down the 83 jobs and pipelines it used to declare. The non-destructive
mechanism is `--select` (Databricks CLI ≥ v1.13.0), which leaves unselected resources untouched.
Grouping the tree is what makes that command short enough to actually use; it is not itself the
scoping mechanism. Both facts are now written into `databricks.yml`'s own header, `docs/09` Step 8,
and `common_pitfalls.md` 34, because the destructive reading is the intuitive one.

## 2. Previous State vs. Current (Target) State

### E32 — Flat `resources/` (95 files, one glob)
- **Previous:** `include: [resources/*.yml]`; 95 YAML files in `resources/` root.
- **Current:** six folders, six include lines:

| Folder | Holds | Resources |
|---|---|---|
| `resources/metaflow_app/` | the Onboarding App + the UC Volume it stores authored specs in | 2 |
| `resources/metaflow_config_jobs/` | `onboarding_job` (one spec per run) + `framework_config_onboarding_job` (a whole `spec_dir` per run) | 2 |
| `resources/observability/` | DLT observability export job + the OTEL streaming pipeline | 2 |
| `resources/bt_tests/` | tests driven by real BT fixtures: geneva tariff recon replay, ASN.1 decode, PGP decrypt | 6 |
| `resources/feature_tests/` | the `TC-*` feature/regression corpus — one job + one pipeline per case | 83 |
| `resources/stability_tests/` | reserved for `STABILITY_TEST_PLAN.md` A1–G4 | 0 |

- **Why the BT split is only 6 files:** the boundary drawn is *"consumes a real BT artefact"* —
  `metaflow_testing/BT_Testing/{EMSC,GGSN,PSGW,TAP.310}.asn1`, the PGP-encrypted
  `EE_2026-08-20-REQUEST_1OF1.csv.gz.gpg`, or the live `dfg_geneva_tariffs_recon` pipeline replayed
  by `051`/`053`. The `Excalibur_usecase`/zerobus scenarios (`002`/`003`/`004`, `ing_003`,
  `recon_dag`) stay in `feature_tests/` because they are the framework's own verification path —
  `003` is `TC-R2-001`, the scenario whose live pass is v1.5.0's §0b evidence — and moving them
  would have pulled the read-once regression proof out of the feature suite.
- **Why an empty include pattern is fine:** `resources/stability_tests/*.yml` matches nothing today
  and `bundle validate` accepts it (verified). The line is in place so adding the first stability
  resource needs no `databricks.yml` edit.

### E33 — Relative paths were one level short
- **Previous:** `notebook_path: ../notebooks/...`, `- ../dist/*.whl`,
  `source_code_path: "../databricks-app"` — correct while the file sat in `resources/`.
- **Current:** `../../` in all 296 occurrences (93 wheel globs, 202 notebook paths, 1 app source
  path). DABs resolves a relative path against the **declaring file**, so every one of them would
  otherwise have resolved into `resources/<group>/../notebooks`, i.e. `resources/notebooks`.
- **Why it needed a test, not just care:** `databricks bundle validate` checks configuration shape,
  not that a notebook exists at the path. A stale `../` validates clean and fails at deploy — or,
  for the wheel glob, uploads nothing and fails at pipeline install with
  `ENVIRONMENT_PIP_INSTALL_ERROR`, several minutes into a run.
- **Two false positives the rewrite deliberately skipped:** `/Workspace/.../test_specs/...` in
  `onboarding_job.yml`'s usage comment and `.../landing/2026-08-28/` in
  `metaflow_test_prm_001_path_param_job.yml`'s header are prose **ellipses** whose last three
  characters are `../`. A regex anchored on `../` alone rewrites both into nonsense; the applied
  rewrite matched only the literal directory names `../dist/`, `../notebooks/` and
  `"../databricks-app"`.

### E34 — Scoping a deploy had no documented mechanism
- **Previous:** nothing in the repo said how to deploy a subset. The reachable-by-intuition method
  (edit `include:`) destroys resources.
- **Current:** documented in three places, always with the trap attached:

```bash
databricks bundle deploy -t dev_metaflow -p dev_metaflow \
  --select apps.metaflow_onboarding_app,jobs.onboarding_job,jobs.framework_config_onboarding_job,volumes.onboarding_specs_volume
```

- The wheel is still built and uploaded, because the selected jobs declare `../../dist/*.whl` in
  `environments[].spec.dependencies` — `--select` scopes *resources*, not artifacts.
- `jobs.onboarding_job` and `volumes.onboarding_specs_volume` stay in the list even for an app-only
  change: the app resolves `${resources.jobs.onboarding_job.id}` into `METAFLOW_ONBOARDING_JOB_ID`
  and binds the spec Volume to its service principal with `WRITE_VOLUME`.
- Unchanged and restated: deploying the app is **two steps**; the running app serves its previous
  code until `databricks bundle run metaflow_onboarding_app`.

### E35 — `stability_tests/` exists before its first resource
- **Previous:** `STABILITY_TEST_PLAN.md` (created 2026-08-30) defines A1–G4 with no resources built.
- **Current:** the folder and its `README.md` record the three settings §1.1 makes non-negotiable
  (`pipelines.maxFlowRetryAttempts: "0"` — the default of **5** turns a transient flow failure into
  a reported SUCCESS; `max_retries: 0` per task; `development: true` + `continuous: false`), the
  fixed 4-schema/4-volume footprint from §2, and a naming convention
  (`metaflow_stab_<case>_<slug>_{job,pipeline}.yml`) that keeps a stability resource distinguishable
  from a `TC-*` one in the Jobs UI.

## 4. Test Case Execution & Verification Status

### 4a. The load-bearing verification — resolved config is byte-identical

`databricks bundle validate -t dev_metaflow -o json` was captured from a detached
`git worktree` at `HEAD` (pre-move) and from the working tree (post-move), normalised for the
worktree's own absolute path, and compared: **identical**. Every notebook path, wheel dependency,
app source path, job name, pipeline name, task, parameter and environment spec resolves to exactly
what v1.5.0 deployed. This is the assertion that the `../` → `../../` rewrite was complete and
correct; a single missed path shows up as a diff.

Resource census after the move — `apps 1, jobs 50, pipelines 43, volumes 1` = **95**, one per file,
matching the 95 files moved.

### 4c. Deliberately NOT run

**No `bundle deploy`.** Two independent reasons, and the second is the binding one:

1. Nothing in this release changes deployed behaviour — the resolved config is identical (§4a), so a
   deploy would produce a new wheel filename and no other difference.
2. `bundle deploy` prunes superseded artifacts from `<artifact_path>/.internal/`, which kills an
   in-flight Lakeflow update with `ENVIRONMENT_PIP_INSTALL_ERROR`
   (`metaflow_testing/TESTING_PLAN.md` §0). Whether a test wave is running is not knowable from
   here, so the deploy is left to the operator.

**No `npm run build`.** See §3a step 5 — no app-serving file changed.

## 6. Known Gaps

1. **Not deployed.** The layout is verified equivalent offline, not observed equivalent in a
   workspace. The first `bundle deploy` after this release should be a full one (no `--select`) so
   DABs reconciles all 95 resources at their new declaration sites in a single pass.
2. **`--select` is documented, not exercised.** The command's resource keys are asserted to exist by
   `test_resource_layout.py::test_usual_deploy_selection_names_real_resources`, but no scoped deploy
   has been run against a workspace, so the claim that the wheel is still built and uploaded under
   `--select` rests on the DABs artifact contract rather than on an observed run.
3. **`stability_tests/` is empty.** A1–G4 remain unbuilt; the folder documents the constraints a
   future resource must satisfy but enforces none of them. `test_resource_layout.py` asserts the
   folder exists and is included, not that anything is in it.
4. **The BT/feature boundary is a judgement, not a rule the tests enforce.** `test_resource_layout.py`
   checks that every resource is in *some* group, not that it is in the *right* one. A new
   geneva-shaped test dropped into `feature_tests/` will pass every check here.
