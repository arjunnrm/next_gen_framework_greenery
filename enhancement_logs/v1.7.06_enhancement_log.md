## Why this release exists

FlowX's runtime observability is **export-oriented**. Every number it computes — per-flow
`num_output_rows`, per-expectation pass/fail counts, DQ quarantine counts, SCD upsert and delete
counts — is computed and then shipped *out*: OTel `ResourceLogs` to a collector, JSONL/GZIP to a
Volume, structured JSON to the driver log. That is the correct architecture for alerting. It is the
wrong architecture for a question, because **almost none of it lands in a queryable Delta table**.

Meanwhile the platform had been recording the operational half all along — run durations, result
states, retries, DBU cost, observed lineage — in `system.lakeflow`, `system.billing` and
`system.access`. Nobody was joining the two.

| Half | Knows | Does not know |
|---|---|---|
| System tables | A pipeline ran for 94 seconds, cost 0.7 DBUs, and read three tables | That it is `dfg_uc6_ea_flood_warning`, 11 flows, 5 DQ rules, 2 reconciliations |
| Control tables | Exactly that | Anything about the 94 seconds |

The join turned out to need **no framework change on the pipeline side at all** — the key was
already being written (E2). Only the job side needed anything, and that was one tag.

## E1 — The observability semantic layer

**Previous:** nothing. There was no `<catalog>.observability` schema, no view joining a
`dataflow_group_id` to a pipeline run, and no queryable record of per-flow row counts, per-rule DQ
outcomes, or cost. A question like "what did this dataflow group cost last month" had no answer at
any price, because cost was never in the telemetry export in the first place.

**Current:** `src/flowx/lakeflow_framework/control_plane/observability_views.py` (1147 lines) —
pure string-building functions, no `spark.sql` execution, exactly like `ddl_definitions.py` —
producing 11 views in dependency order:

| View | Grain | Reads |
|---|---|---|
| `v_dataflow_group_catalog` | group | control tables |
| `v_flow_inventory` | flow (all 3 kinds, `UNION ALL`) | control tables |
| `v_pipeline_registry` | pipeline | `system.lakeflow.pipelines` + `information_schema` |
| `v_pipeline_updates` | update | `pipeline_update_timeline` ⋈ registry |
| `v_job_runs` | job run | `jobs`, `job_run_timeline` + control |
| `v_dataflow_cost` | group × date × workload × SKU | `system.billing.*` ⋈ registry |
| `v_flow_metrics` | update × flow | UC event logs ⋈ registry |
| `v_dq_results` | update × flow × expectation | UC event logs ⋈ registry |
| `v_reconciliation_health` | recon run | `reconciliation_flow_spec` ⟕ `reconciliation_run_log` |
| `v_dataflow_lineage` | source→target edge | `system.access.table_lineage` ⟕ registry |
| `v_group_health_summary` | group | views 1, 4, 6, 7, 8, 9 |

**Three design decisions worth recording.**

- **Views, not materialized tables.** The system tables are already materialized on the platform's
  cadence. Copying them into FlowX-owned tables buys a refresh job to keep green, a storage cost
  and a staleness window, in exchange for nothing at dashboard scale. A view is also cheap to fix —
  a corrected `has_cdc` predicate is one `CREATE OR REPLACE VIEW`, no backfill. (Four of the six
  defects below were exactly that fix.)
- **A separate schema, not `<catalog>.config`.** This is a **grant boundary**, not tidiness. The
  control tables carry `*_json` and `raw_spec_payload` columns holding connection strings and
  credential-shaped config. Putting the views in their own schema means
  `GRANT SELECT ON SCHEMA <catalog>.observability` hands a BI user or a Genie space the entire
  derived surface **without** granting read on the secrets-adjacent columns. Views in `config`
  would have required exactly that.
- **Column `COMMENT`s are the semantic model, not decoration.** Genie reads them. They are
  written for an LLM: what a column means, what to join on, what to `SUM`, and — the part that
  matters most — **what not to conclude**. `has_run_history`'s comment says outright that absence
  of rows is not evidence of health; `attribution`'s says to treat `name_match` figures as
  indicative; `dbus`'s says to compare DBUs rather than dollars across regions.

**`v_group_health_summary` is a view over the other views**, not a re-derivation from base tables,
so a fix to duration or attribution arithmetic propagates instead of being reimplemented and
diverging. Its `health_status` `CASE` order is itself a decision: `INACTIVE` before `NO_RUNS`
before `FAILING` before `DEGRADED`, so a group disabled *after* a bad run is not reported as
`FAILING` for runs that predate its disabling, and "nothing ran" stays distinct from "it ran badly".

## E2 — The join key, and the one thing that needed a tag

**Previous:** there was no way to attribute a platform run, or a dollar, to a FlowX dataflow group.

**Current, pipeline side — free.** `system.lakeflow.pipelines.configuration` is a
`MAP<STRING,STRING>`, and **every FlowX pipeline resource already sets `dataflow.group.id` in its
`configuration:` block** — it has to, because that is how a pipeline finds its own control rows at
graph-definition time. So `p.configuration['dataflow.group.id']` recovers the FlowX identity of any
pipeline with **no change to any pipeline, resource file or spec**. `v_pipeline_registry` computes
it once; ten other views join through that view rather than re-deriving it.

**Current, job side — one tag, and an honesty column.** The job side looked like it should work the
same way. It does not. The framework passes `dataflow_group_id` as a notebook task
**`base_parameter`**, and those do **not** surface in
`system.lakeflow.job_task_run_timeline.task_parameters` — **verified empty on a live workspace**,
not inferred from documentation. So a `dataflow_group_id` **job tag** was added to
`resources/{uc3,uc6,uc7}/*_job.yml`, and `v_job_runs` reports which path produced each row:

| `attribution` | Mechanism | Quality |
|---|---|---|
| `'tag'` | `system.lakeflow.jobs.tags['dataflow_group_id']` | Exact, declarative |
| `'name_match'` | Case-insensitive containment of a known group id in the job name | Heuristic — correct by convention, not contract |
| `NULL` | Neither matched | Row still returned, group `NULL` |

**Why `attribution` is a column and not a filter.** Blending an exact attribution with a heuristic
one into a single number is how a dashboard becomes untrustworthy: the reader cannot tell which
figures are guaranteed. And dropping unattributable runs would hide every framework job predating
the tag — a *silent* undercount, which is worse than a visible one. `v_dataflow_cost` takes the
stricter line for money: **job cost is attributed by tag only**, never by name match, because a
name-matched dollar figure invites arithmetic nobody should do.

**Event log location is discovered, not constructed.** `system.lakeflow.pipelines.settings` exposes
only `photon`, `development`, `continuous`, `serverless`, `edition`, `channel` — there is **no**
`catalog` and no `target` field, so the event log's location is not derivable from the pipeline row
(this cost a `FIELD_NOT_FOUND`; defect 5). The name is matched against
`system.information_schema.tables` on the id-derived suffix instead, joined back to live
FlowX-tagged pipelines so it never picks up an unrelated `event_log_*` table.

## E3 — Provisioning, deliberately non-fatal

**Previous:** `01_setup_control_tables.py` created control tables and stopped.

**Current:** a new section 5 creates the `observability` schema and all 11 views. It is wrapped in
**two nested guards**, because the two failure modes are different and both must degrade rather
than fail:

- **Inner** — event-log discovery fails or returns nothing. `event_log_tables` becomes `[]`, and
  `v_flow_metrics` / `v_dq_results` are created over a **typed empty relation**
  (`SELECT CAST(NULL AS ...) ... WHERE FALSE`) so every dependent dashboard dataset, Genie data
  source and `v_group_health_summary` still resolves against a real object with the right column
  types. An empty chart is a correct answer; a broken dashboard is not.
- **Outer** — the schema or any view DDL fails. Nothing is re-raised.

**Why non-fatal is the right call and not laziness.** `SELECT` on the `system` catalog is a
*workspace* grant the deploying principal may legitimately not hold, and observability is not a
prerequisite for onboarding a pipeline. Making section 5 fatal would mean a missing system-table
grant blocks every onboarding in the workspace. The warning names the likely cause and the fix:
*"Most often this means the deploying principal lacks SELECT on the system catalog — grant it, then
re-run this notebook."*

Re-running `01_setup` is idempotent (`CREATE SCHEMA IF NOT EXISTS`, `CREATE OR REPLACE VIEW`) and is
also how you pick up **newly-published event logs**, since `event_log_tables` is resolved at
DDL-build time. Onboard a group, run its pipeline once, re-run `01_setup`.

## E4 — The AI/BI dashboard

**Previous:** `flowx_control_dashboard` covered the control metadata. Nothing covered runs, cost,
throughput, DQ outcomes or lineage.

**Current:** 13 datasets, 9 pages, 103 widgets, 15 charts — Overview, Pipeline Performance, Data
Flow & Throughput, Quality & Reconciliation, Cost & Efficiency, Framework & Lineage, AI Forecast,
Job Orchestration, Global Filters. Deployed and published live.

**`dataset_schema: observability`, not `config`** — and the mechanism to keep straight is that
`dataset_catalog`/`dataset_schema` **only fill in what a query omits**. All 10 view-backed datasets
use bare names; the 2 forecast datasets that need raw hourly usage use three-part `system.billing.*`
names, which pass through unchanged. **No dataset currently uses a two-part `config.<table>` name** —
it is the available escape hatch for reaching a control table from this dashboard, and
`v_dataflow_group_catalog` already surfaces the onboarding-audit facts that would have needed one.
Two unit tests reject a hard-coded catalog or an unknown object.

**The three forecast datasets are deliberately not filter-bound.** A forecast fitted to a filtered
subset of hours forecasts a different series than the chart claims to show, and `AI_FORECAST` will
not tell you that.

## E5 — AI_FORECAST, and the ten-billion-DBU lesson

This is the one part of the release that produces a *confidently absurd* number if used naively,
so it is worth the space.

**The first implementation forecast a DAILY series.** On this workspace only **4 days** of billing
history existed, so `AI_FORECAST` was fitting to **3 usable daily points** — and projected
**10,257,538,803 DBUs by day 14**.

Ten billion DBUs. It did not error. It did not warn. It returned a well-formed number with a
confidence band in a chart that looked exactly like a working forecast. **An under-fed forecast
fails plausibly, not loudly** — which makes it more dangerous than one that fails.

**The fix is grain.** `date_trunc('HOUR', ...)` over the same 14-day window gives **73 points**
instead of 3, and a credible forecast. The four rules now encoded in the dashboard SQL, in the
Genie instruction block, and in doc 17 §6:

| # | Rule | Why |
|---|---|---|
| 1 | **Hourly, never daily** | A daily series on a young workspace has single-digit points |
| 2 | **Exclude the current, partly-elapsed bucket** (`< date_trunc('HOUR', current_timestamp())`) | 5 minutes of usage in a 60-minute bucket is the *most recent* point; left in, it reads as a collapse and the model extrapolates a decline that is purely an artefact of when you looked |
| 3 | **Always pass `parameters => '{"global_floor": 0}'`** | Without a floor the lower band goes **negative** — negative DBUs, negative dollars. Cost is non-negative by construction; the model does not know that unless told |
| 4 | **Report the band and the hours of history, not just the point** | A point forecast with no interval and no "fitted on N hours" is indistinguishable from a measurement |

Plus the framing rule: **say it is list price, and say it is a projection, not a commitment.**

Two implementation details that are easy to lose in an edit: `horizon` is an absolute timestamp
anchored to `MAX(actual hour) + MAKE_DT_INTERVAL(0,48,0,0)` — the last *observed* point, not
`current_timestamp()`, so a gap in billing ingestion shortens the horizon rather than silently
forecasting across it; and a `bridge` CTE re-emits the final actual point with its value copied
into the forecast columns, without which the actual and forecast lines do not touch and the chart
shows a one-hour hole at the join.

**Live verification** (~30 hours of history at time of writing): $23.19 observed, **$18.94**
next-48h, **$290.08** projected 30-day run rate. Sane, mutually consistent, and still wide — which
is what rule 4 exists to make visible.

## E6 — The Genie space, and its format contract

**Previous:** no Genie space over framework metadata.

**Current:** 15 data sources, 1 instruction block, 12 example question/SQL pairs, 12 sample
questions, 4 benchmarks. It answers "show me details of every dataflow group and what features they
use", "explain/document dataflow group X", and "forecast our spend".

**Only two raw system tables are exposed** — `system.billing.usage` and
`system.billing.list_prices`, and only because `AI_FORECAST` needs the raw hourly grain that
`v_dataflow_cost` has already aggregated to a day. The other thirteen are the 11 views plus two
control tables for row-level detail. That restraint is the design: a Genie space pointed at raw
`system.lakeflow.*` has to rediscover the `configuration['dataflow.group.id']` join, the
slowly-changing-jobs deduplication, the cumulative-event-count trap and the terminal-status
ordering **on every question**, and will get at least one of them wrong. Pointed at commented
views, it mostly reads the answer off.

**The serialized format was reverse-engineered** via `databricks bundle generate genie-space`, and
three of its requirements are **API-enforced, not stylistic**:

1. `version: 2` at the top level.
2. **Every human-readable string is an ARRAY OF LINES**, each element ending `\n` except the last.
   A plain string where a line array is expected is rejected.
3. **Every repeated block must be sorted** — `data_sources.tables` by **identifier**, everything
   else by **`id`**. The API *hard-rejects* an unsorted array; it does not normalise it. This is the
   one that bites: append a table or an example and the deploy fails, insert it in sort position and
   it succeeds.

Round-trip UI edits back into the repo with
`databricks bundle generate genie-space --resource flowx_observability_genie_space --force`,
otherwise the next `bundle deploy` silently reverts them.

## E7 — The documentation generator

**Previous:** explaining a dataflow group to a new engineer or a customer meant assembling the
answer by hand from the spec, the control tables and the run history.

**Current:** `src/flowx/lakeflow_framework/observability/dataflow_documenter.py` renders one
Markdown design document per dataflow group — **8 sections**: purpose and scale, framework
capabilities exercised, flows (ingestion → transformation → reconciliation, each kind prefaced with
what that kind *is*), data quality, reconciliation, operational behaviour, observed lineage, tables
published — into `/Volumes/<catalog>/config/framework_docs/dataflow_groups/` plus a `README.md`
index. Four job parameters: `catalog`, `dataflow_group_id` (blank = all), `output_volume` (blank =
derive), `lookback_days` (default 30).

**Two decisions worth recording.**

- **It reads the control tables, not the spec files.** The document therefore describes the system
  **as onboarded and as running**, not as a spec file on someone's laptop claims it should be. When
  the two disagree the document is right and the spec is stale — which is the direction of trust
  you want from generated documentation, and the opposite of what a spec-driven generator gives you.
- **A pure-function boundary.** Rendering takes lists of dicts and returns a string; no Spark, no
  I/O. The notebook is the only thing that reads views and writes files. This is a *testability*
  decision: there is no local Spark in this repo (databricks-connect plus no Java), so anything
  touching a session is untestable offline. The split is what makes 28 test functions possible
  without a cluster.

It is the **batch counterpart to Genie**: Genie answers conversationally, this leaves a committable
artefact. Both read the same views, so they cannot disagree about the facts.

**Degrade-not-fail:** only a missing/empty `v_dataflow_group_catalog` is fatal (nothing to
document). `v_group_health_summary`, `v_dq_results`, `v_reconciliation_health` and
`v_dataflow_lineage` go through an `optional_rows()` helper that warns and returns `[]` — so with no
system-table grant the job still produces the **declarative** half of every document and omits the
operational sections, rather than producing nothing.

## Defects found and fixed during this work

Every one of these **produced no error and returned a plausible wrong answer.** That is the theme
of the release: a SQL semantic layer over metadata fails quietly, and only running it against real
data and reading the output critically catches it. Five of the six were caught by live data, not by
review.

| # | Defect | Root cause | Fix |
|---|---|---|---|
| 1 | `has_cdc` was **always FALSE**, on a tile whose only job was to say which groups do CDC | The control tables store load strategies **UPPERCASE** (`SCD1`, `SCD2`, `TRUNCATE_AND_LOAD`); the regex was lowercase-only | `LOWER(cdc_load_strategies) RLIKE '(scd|cdc|merge|truncate)'`. These enum values are **not case-normalised** — fold explicitly |
| 2 | A leading `", "` on every aggregated list | **`SPLIT('', ', ')` returns `['']`** — an array with ONE EMPTY element, not an empty array — which sorts first and `CONCAT_WS` renders as a leading separator. **`ARRAY_COMPACT` does not fix it**: it removes `NULL`s, not `''` | `FILTER(..., x -> x IS NOT NULL AND x <> '')` |
| 3 | `has_dq` was **TRUE for every group** in the workspace | `dq_config_json` is literally the two characters `'{}'` on many flows — an *empty* DQ config, faithfully serialized. `IS NOT NULL AND <> ''` is true of it | `TRIM(dq_config_json) NOT IN ('', '{{}}')`. For JSON-in-a-string, "present" and "non-empty" are different questions |
| 4 | `flow_status = RUNNING` with **understated** row counts on updates that had finished | Deduplicating `flow_progress` events by `event_time DESC` alone: a streaming flow can sit in `RUNNING` and emit its last progress event **mid-batch**, so the newest event carries a partial cumulative count | Order terminal statuses (`COMPLETED`/`FAILED`/`EXCLUDED`/`SKIPPED`) first, **then** `event_time DESC`. The last event received is not the event that concluded the thing |
| 5 | `FIELD_NOT_FOUND` on `settings.catalog` | `system.lakeflow.pipelines.settings` exposes only `photon`, `development`, `continuous`, `serverless`, `edition`, `channel` — there is **no** `catalog` and no `target`, so the event log location is not derivable from the pipeline row | Discover the table via `system.information_schema.tables` on the id-derived name. The one defect here that failed *loudly*, hence the cheapest |
| 6 | The repo's **brace trap**, again | `'{}'` inside an f-string DDL body must be written `'{{}}'`. An unescaped brace does not break one statement — Python fails to evaluate the f-string, so **every** DDL in the module breaks at import | Escaped in all four occurrences. `python -c "import ..."` on the module is the cheapest possible check and catches it instantly |

## Known gaps

- **Only ~30 hours of billing history exist on this workspace, so every forecast is wide.** The
  four AI_FORECAST rules make the forecast *credible*, not *precise*. Rule 4 (report the band and
  the hours of history) exists precisely so a reader cannot mistake one for the other. The
  confidence band narrows on its own as history accumulates; no code change is pending.
- **Job-side cost attribution has a start date, not a backfill.** `v_dataflow_cost` attributes job
  spend **only** by the `dataflow_group_id` tag, and `system.lakeflow.jobs` records the job
  definition as it was. So the tag takes effect **only for runs that happen after the tagged jobs
  are redeployed**; every historical run of a previously-untagged job stays on the `name_match`
  path in `v_job_runs` forever and contributes **no** attributed cost. This is visible in the
  `attribution` column rather than hidden, but it is a real gap in the first weeks after deploy.
- **`resources/observability/*.yml` remains commented out of `databricks.yml`'s `include:`.** That
  group is the *telemetry export* estate of doc 08 (the OTLP streaming pipeline and the triggered
  export job), and it is uncommented only when that suite is actually being run — the everyday
  deploy is scoped. It is listed in `MAY_BE_UNINCLUDED_GROUPS` in `test_resource_layout.py`, so the
  state is asserted rather than accidental. Nothing in this release changes it, and nothing in this
  release depends on it.
- **Two validation-copy assets should be deleted after review.** While reverse-engineering the
  Genie serialized format and the Lakeview widget contract, a scratch dashboard
  (`01f1aac02a6e1c9ea540b5606fef079c`) and a scratch Genie space
  (`01f1aac1f32a17b28dd0634c47e9a2d2`) were created under `/Users/<me>/flowx_obs_validation`.
  **The bundle deploys its own copies** of both from `resources/flowx_bi/` and
  `resources/flowx_genie/`, so these two are pure duplicates and are not referenced by any resource
  file. Delete them once the deployed versions have been reviewed — leaving them risks someone
  editing the scratch copy and wondering why `bundle generate` does not pick the change up.
- **No schedule is declared on `dataflow_documentation_job`.** It is run on demand (or after an
  onboarding change), because a document regenerated on a fixed cadence against an unchanged
  control plane produces a no-op commit. Whether it belongs on a weekly trigger is a decision for
  whoever consumes the output.
- **The Genie space's data-source identifiers spell the catalog literally** (`flowx.observability.
  v_...`). Unlike the dashboard there is no `dataset_catalog` equivalent to inject it, so deploying
  the space to a differently-named catalog requires editing those 15 identifiers — and keeping them
  sorted by identifier, or the API rejects the export outright.
