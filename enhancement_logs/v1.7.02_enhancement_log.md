# v1.7.02 Enhancement Log

**Release date:** 2026-09-02
**Progress Tracker:** `Completed — implemented and verified locally. Unit suite matches the
pre-change failure baseline exactly (9 failed / 113 errors, all pre-existing Spark-fixture
failures) with +68 new tests. databricks-app suite 163 passed / 19 skipped. bundle validate OK on
dev_metaflow. mkdocs build clean (231 pre-existing archive-link warnings, unchanged with and
without this change). NOT deployed — this release changes validation and agent-facing assets only;
no runtime pipeline code is touched.`

**Theme:** the agent skills could not generate a correct spec, because nothing ever told them they
were wrong.

The reported symptom was that LLM-generated onboarding specs "are totally not in sync with the
template — the structure is different, the attributes are different." Investigation found the
prose was not the problem: `agent_skills/SKILL.md` is accurate, and its copy of the attribute
reference is byte-identical to the canonical one. Three structural causes were found instead, and
the first is the one that made the other two invisible.

**C1 — nothing rejected an invented attribute.** A spec carrying six fabricated keys returned
`valid: true`, `error_count: 0`, `warnings: 0` from the framework's own `validate_json` tool:

```json
{"source_config": {"file_format": "csv", "infer_schema": true, "totally_made_up_key": 123},
 "target_config": {"another_fake": true},
 "cdc_config": {"keys": ["id"]},
 "data_quality": {"rules": []}}
```

Each of those onboards, writes its control-table row and runs the pipeline while doing nothing:
`data_quality` (the real key is `dq_config`) means **no DQ rule ever runs**; `cdc_config` is a v1
shape whose keys are **ignored**. This is exactly the failure mode `REMOVED_*_KEYS` and
`reject_removed_keys()` exist to prevent — it simply never covered keys that were *never* real,
which is overwhelmingly what a generated spec produces. The JSON schema was no backstop: only
**8 of its 103** object definitions set `additionalProperties: false`, and every container an
author writes into (`ingestionSourceConfig` 25 props, `targetConfig` 17, `ingestionFlow` 14,
`transformationFlow` 11, `dqConfig`, `sinkConfig`) was open.

**C2 — the skill offered no complete example to copy.** §3 rendered the spec as elided
placeholders (`"ingestion_flows": [ /* §3a */ ]`) and directed the agent to read
`spec_validator.py`. An agent that cannot open those files reconstructs field names from memory —
which is precisely how `file_format` appears in place of `format`.

**C3 — the skill was not discoverable.** `agent_skills/SKILL.md` has no YAML frontmatter and does
not sit on a skill search path (only the `governance/` sub-skill has frontmatter), so unlike the
30+ `.claude/skills/*/SKILL.md` skills it was never auto-loaded. It worked only if a human pasted
it in.

A fourth, found while building the fix: **C4 — transformation flows could not be validated
offline at all.** `_validate_sql_syntax` called `spark.sql(...)` unguarded, so `validate_spec(None,
spec)` — the documented offline path — raised `AttributeError` for any transformation or
reconciliation flow, surfacing as `unexpected error during validation`. The self-correction loop
the fix depends on was therefore impossible for two of the three flow types.

### Deliberately NOT locked down

`observability[]` and its `destination_config` keep open containers. They are validated by their
own dedicated functions against `ALLOWED_OBSERVABILITY_*` constants, and `destination_config` is
polymorphic on `destination_type` (`DATABRICKS_VOLUME` vs `OTLP_CONSUMER` take different fields).
Locking them would need a per-type allowlist and buys little: these blocks are template-copied far
more often than hand-written. This is also why `reject_unknown_keys` consults the caller's
allowlist **before** `UNKNOWN_KEY_ALIASES` — `file_format` is wrong under `source_config` but
genuinely correct under `observability[].destination_config`, and the shipped template uses it.

## 5. Defects Found

- **D10 — `validate_spec(None, spec)` raised for transformation and reconciliation flows.**
  `_validate_sql_syntax` called `spark.sql()` with no session guard, so the documented offline path
  (`agent_tools.validate_json`, which passes `spark=None`) failed with `AttributeError: 'NoneType'
  object has no attribute 'sql'`, reported as `unexpected error during validation`. Fixed under
  E74. Found only because the golden-spec generator validates every example — the transformation
  example failed, and the example was correct.

- **D11 — `alias` lookup was location-blind.** The first cut consulted `UNKNOWN_KEY_ALIASES` before
  the caller's allowlist, so `file_format` would have been reported as wrong even inside
  `observability[].destination_config`, where it is a real key used by the shipped template.
  Reordered so the allowlist decides first; pinned by
  `test_an_alias_name_is_accepted_where_it_is_genuinely_a_real_key`.

- **D12 — two inert keys shipped in a real spec.** `environment` and `catalog_name` at the root of
  `053_geneva_…`. A group's `catalog_name` is derived from the onboarding job's `--catalog`
  parameter (`control_plane/ddl_definitions.py`), never from the spec, so both were read nowhere.
  Exactly the silent-no-op class this release exists to catch; removed under E79.

- **D13 — a test asserted the behaviour being removed.**
  `test_depends_on_dataflow_group_ids_is_silently_ignored` codified "a v1 field must not error —
  it's just unread." Under hard rejection that is a contract change, not a break: the key could
  previously appear to declare an ordering the framework never enforced. Renamed and inverted.

- **D14 — hand-written allowlists would have been wrong.** An early draft treated
  `partition_columns` as invented; it is a real `targetConfig` key. Allowlists are generated from
  the schema and asserted against it, never typed by hand.

## 6. Known Gaps

- **`observability[]` containers remain open** (see §2). A spec may still carry an unread key
  inside an observability destination. Closing this needs a per-`destination_type` allowlist.

- **`transformationFlow` accepts one key the JSON schema does not declare.**
  `source_description` is a real control-table column (`metadata_upsert.py` reads it for both flow
  types) but appears only under `ingestionFlow` in the schema. The validator allows it for both;
  the anti-drift test asserts `⊆` rather than `==` for this one def. The schema should gain the
  property — deferred to keep this release enforcement-only.

- **The skill's `references/` are copies, not links.** Byte-equality is enforced by a test and
  re-synced by `scripts/sync_agent_skill.py`, but the copies must be regenerated whenever
  `agent_skills/` changes. A symlink would break on Windows checkouts, hence copies.

- **Nothing yet forces an agent to run the loop.** The skill instructs it and `validate_json` makes
  it cheap, but no hook rejects an unvalidated spec at the point a user is shown one.

- **Not deployed.** Validation and agent assets only; no runtime pipeline code changed. The next
  deploy should still be timed against the never-deploy-during-an-update rule.
