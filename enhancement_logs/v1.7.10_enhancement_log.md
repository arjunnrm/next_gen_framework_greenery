## 2. E1 — `columns_to_exclude` prose corrected (0.0.5)

### The contradiction

| Source | Claimed |
|---|---|
| `cdc/comparison_columns.py` docstring | "comparison-only … never drops it from the target table" |
| `spec_validator.py` ~1196 | "COMPARISON-ONLY now (never dropped from the target table)" |
| `docs/00_master_reference_index.md`, `agent_skills/SKILL.md` | same claim |
| **`cdc/scd.py::_build_except_column_list`** | **passes it to `apply_changes(except_column_list=…)`, which DOES drop the column** |

### Which side was right — settled empirically, not by reading

Live inspection of the deployed tables: `bt_digital_poc.bronze.physical_device` / `customer` /
`subscriber` **genuinely lacked** `sys_creation_date` and `sys_update_date` — exactly the two
columns those specs named. **The code was right; four prose locations were wrong.**

### Why the code was NOT "fixed" instead

My initial diagnosis was that `scd.py` was buggy. That was **backwards**, and a 95-agent
adversarial verification workflow caught it before deployment. `columns_to_exclude` →
`except_column_list` is the framework's **only** mechanism for "don't store this column at all"
on a CDC target:

- `data_standardization_sql` is strictly add/replace — a mandatory `AS <name>` alias means it can
  never un-create a column;
- `column_normalization` / `schema_config` only rename, cast or comment;
- `columns_to_check` scopes comparison;
- no `columns_to_drop` / `select_columns` exists in `ALLOWED_TARGET_CONFIG_KEYS`.

Narrowing it would have been a **capability regression with no replacement**, and would have
silently re-added columns to every already-materialized SCD target. It also emerged that the
"v2 decoupling" the docstrings described **never shipped**: no attribute delta, no release note,
no migration exists for it. It was intent written down, not a contract.

### Changes

| File | Change |
|---|---|
| `cdc/comparison_columns.py` | Module docstring rewritten: the attribute has **two** jobs; the overloading is deliberate and load-bearing; how the two compose; what the earlier claim got wrong and why the prose was corrected instead of the code. Also the `columns_to_exclude` parameter docstring, which said "Never affects what's stored on the target table". |
| `onboarding/spec_validator.py` | Comment rewritten to match. |
| `docs/00_master_reference_index.md` | Attribute row: "**Two jobs**… also drops them from the target table's schema… the only \"don't store this column at all\" mechanism". |
| `agent_skills/SKILL.md` | Split the claim: `columns_to_check` is comparison-only; `columns_to_exclude` does both. Synced via `scripts/sync_agent_skill.py`. |
| `databricks-app/config/attribute_knowledge{,.curated}.json` | Removed the stale hedge telling users *not* to rely on it for schema shaping. |

**Deliberately NOT changed:** `cdc/scd.py` (correct as shipped), and
`databricks-app/config/registry/shared.cdc.json` — its description
("Excludes columns from the target schema (except_column_list) and from comparison") was the most
accurate sentence in the repo all along. The app's `validation/rules.json` was already correct too.

## 3. E2 — SCD2 `<target>_current` removed (0.0.6)

### Previous vs current

| | Previous (≤0.0.5) | Current (0.0.6) |
|---|---|---|
| Datasets per SCD2 flow | **2** — the target, plus `<target>_current` | **1** — the target only |
| What `_current` was | `register_scd2_reporting_view()`, called unconditionally at the end of every `register_scd2` | removed, function and call both gone |
| Its actual materialization | `MATERIALIZED_VIEW` — despite a docstring documenting two bugs fought to make it a real `@dlt.table` | n/a |
| Its content | **every row, history included** — `bronze.customer_current` held all 40 rows, of which only 30 were current | n/a |
| Storage cost | a full second copy per SCD2 target (113 columns vs the base 110) | none |

### Why it was removed rather than renamed or filtered

It was actively harmful, not merely redundant: the name `_current` promised current rows and
delivered history too, silently. Anyone writing `SELECT * FROM customer_current` for a report got
wrong answers with no signal.

### Why no replacement was added — the tracking columns cannot be renamed in place

This was verified, not assumed:

- `dlt.apply_changes` has **18 parameters** and **none** names `__START_AT`/`__END_AT` (signature
  inspected directly);
- an SCD2 target is `create_streaming_table()` + `apply_changes()` — there is **no query body**
  for the framework to project or alias through; Lakeflow writes those columns itself;
- Databricks' own SCD2 guidance (`databricks-pipelines` skill,
  `references/scd-2-querying.md`) only ever aliases them **in a SELECT**
  (`__START_AT AS valid_from`), never in storage.

A rejected alternative worth recording: deriving `valid_from`/`valid_to` in the **staged view**
feeding `apply_changes`. That would be *worse* than the `__`-prefixed names — those values are
computed **before** `apply_changes` assigns versions, so they would not track the real version
boundaries. Authoritative-looking and wrong.

Consumers wanting the conventional names alias them in their own query, or in a plain UC view
created outside the pipeline (zero storage, and it can genuinely filter to current rows).
**Current rows are `WHERE __END_AT IS NULL`.**

### Changes

| File | Change |
|---|---|
| `cdc/scd.py` | Deleted `register_scd2_reporting_view()` (43 lines, removed **by line index** after asserting the fences — never a broad regex, per AGENTS.md) and its call in `register_scd2`. Module docstring and `register_scd2` docstring rewritten to record the removal, why the columns can't be renamed, and the staged-view trap. |
| `engine/flow_registration.py` | Stale comment: "only final sinks (targets, quarantine, SCD2 `_current`)" → targets and quarantine only. |
| `docs/13_known_limitations_and_gotchas.md` | "**Related**" block rewritten: removal, why, and how to get the friendly names instead. |
| `docs/faq.md` | Intermediate Object Rule answer no longer lists SCD2 `_current` as a published sink. |
| `agent_skills/SKILL.md` | SCD2 strategy row: publishes exactly one dataset. Synced. |
| `pyproject.toml` + `databricks.yml` | `0.0.5` → `0.0.6`, bumped together. |

1. **`--force` was used on both deploys.** A colleague had edited the
   `flowx_observability_dashboard` in the workspace UI; the deploy overwrote it. Their version was
   exported first to
   `BT_Usecase/_shared/backups/flowx_observability_dashboard.remote_backup_2026-09-11.lvdash.json`
   (200 KB) and is restorable. Operator-approved.
2. **Continuous billing is live.** The UC3 pipeline is `continuous: true`; serverless compute stays
   up until stopped (`databricks pipelines stop 94cee215-bffb-40b1-8b45-85e08202de09`).
3. **No migration for existing SCD2 `_current` tables elsewhere.** UC3's was dropped by hand. Any
   *other* workspace carrying a `<target>_current` from ≤0.0.5 keeps it as an orphan — the pipeline
   no longer maintains it, so it will silently go stale. There is no automated sweep; drop them
   manually. UC3 is the only SCD2 flow in this repo, so in-repo blast radius is nil.
4. **`tests/integration/test_pipeline_scd1_wide_table_column_exclusion.py` is orphaned.** It
   asserts the `columns_to_exclude` storage behaviour (so it agrees with E1), but its
   `sample_pipelines_job` and `poc` catalog no longer exist in the bundle, so it cannot run. Left
   in place as documentation of intent; it should be either re-homed or deleted.
5. **Anyone already querying `valid_from`/`valid_to`/`is_current` breaks.** Nothing in this repo
   does. External consumers must switch to `__START_AT`/`__END_AT` or add their own view.
