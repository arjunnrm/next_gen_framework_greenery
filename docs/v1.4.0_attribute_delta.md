# 🔀 v1.4.0 Attribute Delta

> **Audience**: anyone updating a spec-authoring surface — the Databricks App Spec Builder, a
> code generator, an LLM agent, or a hand-maintained onboarding JSON.

The machine-readable companion to this page is
[**`v1.4.0_json_attribute_delta.json`**](v1.4.0_json_attribute_delta.json) — a single self-contained
document listing every added, modified and removed spec attribute with its type, default, rejection
message, migration, and the concrete UI action each one implies. Feed that file to an automated
agent; read this page if you are doing it by hand.

## The one thing to know

**Every removed attribute is REJECTED at onboarding, never ignored.**

An ignored key is the worst of the three possible behaviours: the spec still onboards, the control
table still gets its row, the pipeline still runs — and it quietly does something other than what
the document says. For `normalize_column_names` and `generate_surrogate_key` specifically, ignoring
would flip a data-shaping behaviour from **on** to **off** with no signal at all: columns silently
stop being renamed, rows silently stop carrying the key their target table is diffed on.

So each removed attribute maps to its own migration sentence, named per spec path, and **presence
is the trigger, not truthiness** — `"generate_surrogate_key": false` is rejected too, because it
still describes a feature that does not exist.

## Two traps worth reading before you migrate

**1. A `column_normalization` object with only `case` used to be ON.** It deferred enablement to the
legacy boolean. With that boolean gone there is nothing to defer to, so `{"case": "preserve"}` on
its own now reads as written: **off**. If a spec relied on that deferral, add `"enabled": true` or
the flow silently stops renaming.

**2. A migrated snapshot flow needs a key that is genuinely unique.** Moving
`FULL_SNAPSHOT_CDC_NO_PK` → `FULL_SNAPSHOT_CDC` means choosing a `primary_keys`. Check it first:

```sql
SELECT k, count(*) FROM src GROUP BY k HAVING count(*) > 1
```

A non-unique key produces a target that looks fine and silently collapses rows. If nothing is
unique, the honest answer is `TRUNCATE_AND_LOAD`.

## Corrections applied 2026-08-30

The v1.4.0 app pass was re-verified by driving the app's own output through
`onboarding/spec_validator.py` rather than by re-reading this page. Ten disagreements between
what the Spec Builder offers or ships and what onboarding accepts were found and fixed; they are
recorded per-item under `app_surface_corrections` in the JSON delta.

**One of them was this document's fault**, and is corrected in place: the `app_action` for
`cdc_operation_column` said *"simplify the predicate to `isCdc(strategy)`"*, but `isCdc` is
`{SCD1, SCD2, SCD3, FULL_SNAPSHOT_CDC}` and this attribute's real set is
`{SCD1, SCD2, FULL_SNAPSHOT_CDC}` — which the same entry's `after` field already stated
correctly. The app implemented the instruction, so the builder offered the delete-marker fields
on SCD3 and onboarding rejected every spec that used them. The instruction now names the exact
set, and the old text is kept beside it under `app_action_superseded` so the contradiction stays
visible rather than being quietly rewritten.

The other nine span the app's registry, its validation rules, a shipped template, the framework's
own template pair and the agent skill. The load-bearing lesson is the one this release was built
on: **a surface is only correct if it is checked against the thing that enforces the rule.**
`databricks-app/tests/test_framework_spec_agreement.py` now does exactly that on every run —
every shipped template and every (strategy × attribute) pair goes through the real
`validate_spec`.
