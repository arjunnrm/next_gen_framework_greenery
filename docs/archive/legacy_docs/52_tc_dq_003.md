# Test Pipeline: DQ Action `fail` Pipeline Execution Abort (TC-DQ-003)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 4, TC-DQ-003), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove that a `dq_config` rule with `action: "fail"` genuinely **aborts the Lakeflow pipeline
update** the moment a violating row is encountered -- the strictest of the four DQ actions.
`"fail"` maps onto a native Lakeflow `expect_or_fail` expectation, unlike `"warn"` (TC-DQ-001,
non-blocking), `"drop"` (TC-DQ-002, silently filters the row), or `"quarantine"` (TC-DQ-004,
this framework's own extension that reroutes the row to a companion table). This is the one DQ
action where the pipeline update itself is expected to end in a `FAILED` state -- that is this
test case's correct, intended outcome, not a defect to fix.

**This test case is deliberately designed to fail its own pipeline run.** Anyone re-running
`flowx_test_dq_003_fail_job` and seeing the `run_pipeline` task end in `FAILED` (with a
Lakeflow expectation-violation / `ExpectationViolationException`-style error referencing
`dq_accounts_account_id_not_null_fail`) is seeing this scenario work exactly as designed.

## Responsibilities

* Land 5 banking account rows as a single plain CSV in
  `/Volumes/{{catalog}}/banking/landing_dq_fail/` -- 1 of the 5 (`Ama Boateng`) deliberately
  carries a **null `account_id`**, violating the rule under test.
* One `ingestion_flow` (`df_dq_003_accounts_strict_ingest`) with `source_type: "autoloader"` and
  exactly one `dq_config.rules[]` entry: `{"rule_id": "dq_accounts_account_id_not_null_fail",
  "expression": "account_id IS NOT NULL", "action": "fail"}`.
* `cdc_load_strategy: "APPEND"` -- this scenario is about DQ action semantics, not CDC
  behavior, so the simplest load strategy (plain streaming append, no `primary_keys`) keeps the
  flow focused on the one thing under test (same convention as TC-DQ-001/TC-ING-001).

## Inputs

* `flowx_testing/031_dq_003_fail.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/flowx_testing/banking_usecase/accounts_dq_fail.csv` (5 rows, columns
  `account_id, account_holder_name, balance, opened_at`) -- new fixture, added alongside this
  test case's build (see Build notes).
* `notebooks/00_seed_sample_data/03_seed_dq_003_fail_data.py` -- a **new, dedicated** seed
  notebook (kept separate from every other scenario's own seed notebook) that provisions the
  `banking`/`bronze_banking` schemas and `landing_dq_fail`/`_schemas` Volumes, then copies the
  fixture CSV directly into the landing Volume (no ZIP handling needed for this scenario).

## Outputs

* **The pipeline update itself: `FAILED`.** `dlt.expect_or_fail` raises the moment the null-
  `account_id` row is evaluated against `dq_accounts_account_id_not_null_fail`, aborting the
  update before it commits any data for this flow.
* `{{catalog}}.bronze_banking.accounts_strict_raw` is **never successfully materialized with
  data** by a run of this fixture -- a failed `expect_or_fail` update does not commit the
  streaming table's contents for that run. (The table object may still exist from a prior
  successful onboarding/graph-definition pass, but this scenario's own fixture never lets an
  update complete.)
* No `{{catalog}}.bronze_banking.accounts_strict_raw_quarantine` table -- `dq_config` here
  carries no `action: "quarantine"` rule, so `register_main_and_quarantine_tables` never
  registers one.
* The Lakeflow Jobs UI shows the job run's `run_pipeline` task as **FAILED**, with the pipeline
  update's own event log naming `dq_accounts_account_id_not_null_fail` as the failing
  expectation.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run flowx_test_dq_003_fail_job --target dev
```

Task chain: `setup_control_tables → seed_dq_003_fail_data → onboard_dq_003 → run_pipeline`.

**Expect the overall job run to end in a `FAILED` state**, with `run_pipeline` as the failing
task -- `setup_control_tables`, `seed_dq_003_fail_data`, and `onboard_dq_003` all still complete
`SUCCESS` (onboarding a `dq_config.rules[].action: "fail"` rule is itself a perfectly valid,
successfully-validated spec; only the subsequent pipeline *update*, once it actually evaluates
the landed data against that rule, fails).

## Expected results — simulation notes

**This is the one DQ test case where "the pipeline failed" is the passing assertion**, not a
defect. Verification is about *how* it failed, not working around the failure:

* **Pipeline update state**: `FAILED` (check via the Lakeflow Pipelines UI, or
  `databricks pipelines get-update --pipeline-id <id> --update-id <id>` /
  `databricks pipelines list-updates`).
* **Job task state**: `run_pipeline` task shows `FAILED` in the Jobs UI / job run output; the
  earlier three tasks (`setup_control_tables`, `seed_dq_003_fail_data`, `onboard_dq_003`) show
  `SUCCESS`.
* **Error content**: the pipeline's own event log / update failure message names
  `dq_accounts_account_id_not_null_fail` and the underlying null-`account_id` row as the cause
  (a native Lakeflow expectation-violation failure, since `action: "fail"` maps directly onto

## Build notes / judgment calls

* **New fixture, not a reuse.** No existing seeded fixture is a banking-domain accounts feed
  with an `account_id` primary-key-shaped column, so one new 5-row CSV (`accounts_dq_fail.csv`)
  and one new dedicated seed notebook were added, under a new `banking_usecase/` fixture
  directory (following the same one-fixture-directory-per-domain convention as
  `crm_usecase/`/`ops_usecase`/etc.).
* **Scaled down from the plan's implied larger batch to a minimal 5/1.** Per this build pass's
  explicit convention (a working, onboardable test case matters more than exhaustive row
  volume), 5 rows with exactly 1 null-`account_id` violation exercises the same `"fail"`-aborts
  assertion a larger batch would, with a trivially-identifiable single failing row.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but consistent with
  TC-DQ-001's own build (`docs/50_tc_dq_001.md`) and this pass's established convention, this
  build follows the real `setup_control_tables → seed → onboard → run_pipeline` chain only.
* **This test case is structurally a pipeline-failure test, not a bug to route around.** Per
  this build's own scope instructions, a TC whose "Expected Output & Verification Logic"
  describes the pipeline failing is built to genuinely fail (via a real `action: "fail"` DQ
  rule against a fixture with a real violating row), not given a fake success path. The
  `flowx_test_dq_003_fail_job` resource is fully valid and deployable; it is the *pipeline
  update it triggers* that is expected to fail, every time it runs against this fixture, by
  design.
* **`quarantine_table`/`record_id_column` omitted.** Both are DQ-quarantine-only fields (see
  `docs/17_onboarding_template_reference.md` §4.7); since this spec has no `action: "quarantine"`
  rule, including them would be misleading (they'd simply have no effect), so `dq_config` here
  carries only `rules[]`.
