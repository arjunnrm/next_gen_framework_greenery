# Test Pipeline: Streaming Append-Only Fact Loading (TC-CDC-001)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 2, TC-CDC-001), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § APPEND](02_cdc_load_strategies.md#append).

## Purpose

Prove that `target_config.cdc_load_strategy: "APPEND"` genuinely appends **every** row from
every landed micro-batch verbatim into the Bronze streaming table -- with no deduplication, no
`primary_keys`/`apply_changes` dispatch, no `__framework_hash_key`/`__framework_hash_value`
columns, and no history tracking of any kind. The one thing this scenario is specifically
designed to catch: two (or more) rows that share an identical `(user_id, event_timestamp)`
pair must **both** land in the target table, not be silently collapsed to one -- which is
exactly what would happen if `APPEND` were ever mistakenly routed through CDC dispatch (e.g. an
accidental `primary_keys` inference) instead of `engine/flow_registration.py`'s plain streaming
no-op path.

## Responsibilities

* Land 2 clickstream CSV batches in the same incoming Volume so Auto Loader's one triggered
  (`availableNow`) pipeline update processes both as separate micro-batches in a single run:
  * `page_clicks_batch1.csv` -- 8 rows, including one intentional duplicate `(user_id,
    event_timestamp)` pair (`CLK00005`/`CLK00006`, both `U1002` @ `2026-08-28T10:16:40Z`).
  * `page_clicks_batch2.csv` -- 6 rows, including a second intentional duplicate pair within
    the batch (`CLK00009`/`CLK00010`, both `U1005` @ `2026-08-28T10:20:00Z`) **and** a third
    row (`CLK00012`) that repeats batch 1's `(U1002, 2026-08-28T10:16:40Z)` key again -- proving
    `APPEND` never deduplicates across files/micro-batches either, not just within one.
* One `ingestion_flow` (`df_cdc_001_page_clicks_ingest`) with `source_type: "autoloader"`,
  plain CSV format, no `source_zip_handling` (out of scope for this scenario -- TC-ING-001/002
  already cover ZIP selection/retention).
* `cdc_load_strategy: "APPEND"`, no `primary_keys`, no `columns_to_check`/`columns_to_exclude`
  -- the simplest possible load strategy, keeping the flow focused on the one thing under test.

## Inputs

* `metaflow_testing/019_cdc_001_append.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/metaflow_testing/web_usecase/page_clicks_batch1.csv` (8 rows) /
  `page_clicks_batch2.csv` (6 rows) -- 14 rows total, hand-authored (no generator script needed
  for a fixture this small).
* `notebooks/00_seed_sample_data/03_seed_cdc_001_append_data.py` -- a **new, dedicated** seed
  notebook (kept separate from `02_seed_metaflow_testing_data.py`, which belongs to scenarios
  001/002/003) that provisions the `web`/`bronze_web` schemas and `landing_clicks`/`_schemas`
  Volumes, then copies both CSV fixtures straight into
  `/Volumes/{{catalog}}/web/landing_clicks/incoming/` -- no ZIP handling needed here, since
  plain Auto Loader CSV ingestion is this scenario's own focus.

## Outputs

* `{{catalog}}.bronze_web.page_clicks_stream` -- exactly 14 rows, one per input CSV row across
  both batches, with every `click_id` present and no row collapsed or merged.
* The 3 rows sharing key `(U1002, 2026-08-28T10:16:40Z)` (`CLK00005`, `CLK00006`, `CLK00012`)
  all present simultaneously; same for the 2 rows sharing `(U1005, 2026-08-28T10:20:00Z)`
  (`CLK00009`, `CLK00010`).
* No `__framework_hash_key`/`__framework_hash_value` columns on the target (APPEND is not
  CDC-dispatched, so `dq/quarantine.py::_apply_hash_and_surrogate_key_columns` never adds them
  regardless of `generate_hash_columns`'s default).

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Total row count: 14 (8 + 6), verbatim, no dedup
```

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture carries clickstream-shaped data
  with a deliberately duplicated `(user_id, timestamp)` key, so 2 small new CSV fixtures (14
  rows total) and 1 new dedicated seed notebook were added, kept separate from
  `02_seed_metaflow_testing_data.py` so this test case's build/run never touches scenarios
  001/002/003's own shared fixtures.
* **Two landed files instead of one**, deliberately, so Auto Loader's single triggered
  (`availableNow`) update genuinely processes more than one micro-batch in one job run,
  matching `TESTING_PLAN.md`'s "sum of rows across all micro-batches" framing -- and so the
  duplicate-key assertion also proves the no-dedup property holds *across* micro-batches/files,
  not only within a single one.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but per
  `TESTING_STATUS.md`'s framing, `TESTING_PLAN.md` is a planned/aspirational matrix, not a
  literal build spec -- no other real scenario's job wires observability in by default (it's
  opt-in, added via a spec's own `observability[]` array plus a separate job). This build
  follows the real `setup_control_tables -> seed -> onboard -> run_pipeline` convention
  instead; observability can be layered on later the same way scenario 100's was, if desired.
* **No DQ rules, no governance tags.** This scenario is scoped to `APPEND`'s own
  no-dedup/no-history behavior; DQ (`TC-DQ-*`) and governance (`TC-GOV-*`) are separate,
  already-tracked test modules with their own dedicated rows in `TESTING_PLAN.md`.
