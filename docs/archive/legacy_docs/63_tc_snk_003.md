> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md)
> (Module 8, TC-SNK-003), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md),
> [23_lakeflow_sinks.md](23_lakeflow_sinks.md) (the full `sink`/`external_sink` mechanics this
> scenario exercises), [16_encryption_and_secrets.md](16_encryption_and_secrets.md) (the PGP/secrets
> design), [35_tc_ing_005.md](35_tc_ing_005.md) (the mirror-image scenario — PGP **decryption** on
> ingest, whose secret-provisioning pattern this doc reuses for PGP **encryption** on egress).

## Purpose

Prove `target_config.sink_config.format: "pgp_zip"` with `post_export_archive.pgp_encryption.enabled:
true` end to end, against a **real** disposable PGP keypair: a small monthly financial settlements
batch is Auto Loader-ingested, materialized as a genuine, queryable Delta table
(`target_type: "external_sink"`), and — inside the *same* Lakeflow Declarative Pipeline update —
additionally exported as a PGP-encrypted ZIP archive via `dlt.create_sink` + `@dlt.append_flow`
(`engine/sink_registration.py::register_external_sink_export` → `archive/pgp_zip_sink.py`). The
recipient's public key is resolved from a genuine Unity Catalog secret at graph-definition time —
not a literal key embedded in the spec. This scenario's realistic production framing: a bank must
drop a monthly settlements extract into a partner's secure egress Volume, encrypted so that only the
partner (holder of the matching private key) can ever read it.

## Responsibilities

* One ingestion flow (`df_finance_settlements_ingest`), `source_type: "autoloader"`,
  `cdc_load_strategy: "APPEND"` — deliberately the simplest possible CDC strategy, since this
  scenario's whole point is the sink's PGP+ZIP export behavior, not CDC behavior (APPEND +
  autoloader still publishes a genuine Lakeflow Streaming Table, which is what
  `register_external_sink_export` requires of the main target before it will attach the export
  `@dlt.append_flow` — see [23_lakeflow_sinks.md](23_lakeflow_sinks.md)).
* `target_type: "external_sink"` — `metaflow.silver_finance.monthly_settlements` is materialized as
  a real, governed, DQ-quarantined table exactly like any other target type, **plus** a second
  `@dlt.append_flow` reads that same table (`dlt.read_stream`) into a `dlt.create_sink(format=
  "pgp_zip", ...)`.
* `sink_config.post_export_archive.pgp_encryption.enabled: true` with only
  `recipient_public_key_secret` set (no `sign_with_private_key_secret` — this scenario doesn't
  exercise sign-then-encrypt, only plain recipient-only encryption) — resolved eagerly, driver-side,
  at graph-definition time by `_resolve_secret_into_options`, then passed through to
  `archive/pgp_zip_sink.py`'s `_PgpZipStreamWriter.commit()` as an already-resolved plaintext value
  (`pgp_recipient_secret_value`), never re-resolved inside `write()`/`commit()` themselves — see that
  module's docstring for exactly why (`commit()`/`abort()` run in a separate streaming-sink runtime
  process with no working `dbutils` gateway).
* No `sink_config.post_export_archive.secret` (AES ZIP password) — this scenario exercises PGP
  encryption only, not the additional/independent AES-ZIP-password layer `pgp_zip` also supports.

## Inputs

* `metaflow_testing/041_snk_003_pgp_zip_sink.json` — the onboarding spec (one ingestion flow, no
  transformation/reconciliation flows).
* `sample_data/metaflow_testing/finance_egress_usecase/monthly_settlements.csv` — 5-row plaintext
  fixture (`settlement_id`, `account_id`, `settlement_amount`, `currency`, `settlement_date`,
  `counterparty`), landed as-is (no ZIP/PGP handling on the input side — that's deliberate, see
  Responsibilities above).
* `sample_data/metaflow_testing/finance_egress_usecase/pgp_egress_keypair_public.asc` /
  `pgp_egress_keypair_private.asc` — a dedicated, disposable, passphrase-less RSA-2048 PGP keypair
  generated specifically for this test scenario (via `PGPy`, the same library `crypto/pgp.py`
  wraps; generated locally with a one-off script and round-trip-verified against the framework's
  own `pgp_encrypt`/`pgp_decrypt` before committing) and committed to the repo. **Zero real
  security value** — it protects nothing but this scenario's own synthetic fixture, and represents
  the *external partner's* keypair: the framework only ever needs (and only ever gets, via UC
  secret) the **public** half, to encrypt outgoing exports; the **private** half is never uploaded
  as a secret anywhere in this bundle — it exists purely so this doc's own verification step can
  decrypt the exported archive back, standing in for the real partner's own private key.
* `notebooks/00_seed_sample_data/03_seed_snk_003_pgp_zip_sink_data.py` — lands
  `monthly_settlements.csv` into the input landing Volume and provisions the `finance_egress`/
  `secure_drops` schema+Volume the sink writes into (a sink's destination Volume is never
  auto-created by the pipeline itself, unlike the pipeline's own default `catalog`/`schema`).

## Outputs

* `{catalog}.silver_finance.monthly_settlements` — 5 rows, in plaintext, exactly matching
  `monthly_settlements.csv`'s content, plus the usual `__framework_*` technical metadata columns —
  a genuine, queryable Unity Catalog table (this is the "dual materialization" half of
  `external_sink`).
* `/Volumes/{catalog}/finance_egress/secure_drops/output/monthly_settlements_<batch_id>.zip.pgp` —
  one PGP-encrypted, ASCII-armored archive per micro-batch. Decrypting it with the matching private
  key (`pgp_egress_keypair_private.asc`) yields a plain `.zip` whose entries are the micro-batch's
  rows as JSON-Lines (`archive/pgp_zip_sink.py`'s staging format — not a re-serialized CSV; see
  `_STAGED_FILE_SUFFIX`/`write()`), covering all 5 settlement rows across however many micro-batches
  Auto Loader's single input file produces (typically one, since the whole fixture lands in one
  file).
* No plaintext `.zip` intermediate ever persisted under `secure_drops/output/` — `commit()` always
  removes the unencrypted intermediate immediately after PGP-wrapping it (see
  `archive/pgp_zip_sink.py::commit`).
* `information_schema.tables` shows `monthly_settlements` as a real table (unlike TC-SNK-002's pure
  `"sink"` target type, which registers no table at all).

### Required prerequisite: provision the recipient public key as a UC secret

**Manual, admin-audited step — not automated by this framework**, following the exact same
`security`-scope pattern [05_deployment_guide.md](05_deployment_guide.md)'s own prerequisites
section establishes for this project's other encryption keys, and the same pattern
[35_tc_ing_005.md](35_tc_ing_005.md) uses for its **private** key secret — here it's the **public**
key that must be a secret, since encryption (not decryption) is what runs inside the pipeline. This
step must run **before** `metaflow_test_snk_003_pgp_zip_sink_job`'s `run_pipeline_task` — the
pipeline's sink registration will fail fast with `SecretResolutionError` until it does:

```bash
# Test-only, disposable PGP public key -- protects nothing real (see sample_data/
# metaflow_testing/finance_egress_usecase/ header note). No passphrase, matching this project's
# other throwaway test keypairs.
databricks secrets put-secret security pgp_public_key_finance_egress_test \
  --string-value "$(cat sample_data/metaflow_testing/finance_egress_usecase/pgp_egress_keypair_public.asc)"
```

The matching private key (`pgp_egress_keypair_private.asc`) needs no secret at all — the pipeline
never decrypts anything on this path; it is only ever used locally (or by a real partner, in
production) to decrypt the exported `.zip.pgp` archive, per the verification command below.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks secrets put-secret security pgp_public_key_finance_egress_test \
  --string-value "$(cat sample_data/metaflow_testing/finance_egress_usecase/pgp_egress_keypair_public.asc)"
databricks bundle run metaflow_test_snk_003_pgp_zip_sink_job --target dev
```

Task chain: `setup_control_tables → seed_snk_003_pgp_zip_sink_data → onboard_snk_003 →
run_pipeline_task`.

## Expected results — verification logic

```sql
-- Exactly 5 plaintext rows, matching monthly_settlements.csv's known content
SELECT settlement_id, account_id, settlement_amount, currency, settlement_date, counterparty
FROM {catalog}.silver_finance.monthly_settlements
ORDER BY settlement_id;
-- expect: STL-9001..STL-9005, e.g. STL-9003 -> ACC-4003, 2100.00, EUR, 2026-07-31, Fabrikam Logistics
```

```bash
# Exported archive landed where post_export_archive.output_zip_path points, with a .zip.pgp
# extension (never a plaintext .zip left behind)
databricks fs ls dbfs:/Volumes/{catalog}/finance_egress/secure_drops/output/
# expect: monthly_settlements_<batch_id>.zip.pgp (no bare .zip files)
```

Decrypt-and-verify (documented here, not necessarily executed as part of this pass — see
`docs/35_tc_ing_005.md`'s identical "documented, not necessarily executed" convention for its own
decrypt-side verification):

```python
# Run locally (or in a notebook) with PGPy installed and the exported archive + private key
# fixture both available.
import pgpy, zipfile, io

with open("pgp_egress_keypair_private.asc") as f:
    private_key, _ = pgpy.PGPKey.from_blob(f.read())

with open("monthly_settlements_<batch_id>.zip.pgp", "rb") as f:
    message = pgpy.PGPMessage.from_blob(f.read())

decrypted = private_key.decrypt(message).message  # bytes/bytearray -- the plain ZIP's bytes
with zipfile.ZipFile(io.BytesIO(bytes(decrypted))) as zf:
    print(zf.namelist())  # one JSON-Lines file per partition that had rows
    for name in zf.namelist():
        print(zf.read(name).decode("utf-8"))  # each line: one settlement row as JSON
```

Expect the decrypted ZIP's JSON-Lines entries to cover all 5 settlement rows (across however many
partition files that micro-batch produced), each carrying `settlement_id`/`account_id`/
`settlement_amount`/`currency`/`settlement_date`/`counterparty` plus the framework's technical
metadata columns — a faithful round trip of what
`{catalog}.silver_finance.monthly_settlements` holds.

If the recipient public key secret hasn't been provisioned yet, or is malformed, the pipeline
update fails fast at graph-definition time with a `SecretResolutionError`/`FrameworkConfigError`
naming the secret coordinates — this is the expected, correct failure mode, not a bug to route
around; it proves the framework never silently falls through to an unencrypted export.

## Known gaps / judgment calls

* **Secret coordinates vs. `TESTING_PLAN.md`'s aspirational naming**: `TESTING_PLAN.md`'s own
  TC-SNK-003 row names `metaflow_partner_scope`/`partner_pgp_pubkey` (classic workspace secret-scope
  terminology). This build instead uses this project's real Unity Catalog three-level
  `{secret_catalog, secret_schema, secret_key}` shape — `{{catalog}}`, `security`,
  `pgp_public_key_finance_egress_test` — resolved via `dbutils.secrets.get(catalog=, schema=,
  key=)`, exactly the same pre-existing terminology gap [35_tc_ing_005.md](35_tc_ing_005.md)'s own
  "Known gaps" section already documents for TC-ING-005 (which the current instructions explicitly
  said to follow). Not something newly introduced or resolved by this test case.
* **No separate `run_observability_task`**: `TESTING_PLAN.md`'s row lists a second job task,
  `run_observability_task`, for every `TC-SNK-*` scenario. No other already-built scenario in this
  repo (including TC-ING-005, TC-SNK-001's own real build, or scenario 004) adds a dedicated
  observability job task — structured JSON logging (`observability/structured_logger.py`'s
  `logged_operation` context manager, wrapping `sink_registration.py`'s own `"sink_registration"`
  event) fires automatically as a side effect of `run_pipeline_task` itself, with no separate task
  needed to "activate" it. This build follows that same established, real pattern rather than the
  plan's aspirational extra task.
* **Reused the TC-ING-005 secret-provisioning *pattern*, not its literal keypair**: the task
  instructions said to reuse a real PGP keypair "the same way TC-ING-005 does" — read as reusing
  the *approach* (a disposable, passphrase-less, `PGPy`-generated RSA-2048 test keypair, committed
  to the repo, provisioned as a `security`-scope UC secret via a documented `databricks secrets
  put-secret` command), not literally reusing TC-ING-005's own `pgp_test_keypair_*.asc` bytes —
  those represent a different persona (the *finance partner sending data to us*, decrypted with a
  private-key secret) from this scenario's persona (*us sending data to an egress partner*,
  encrypted with a public-key secret). A new, dedicated keypair
  (`pgp_egress_keypair_{public,private}.asc`) was generated instead, matching TC-ING-005's own
  generation method exactly, and round-trip-verified locally (`pgp_encrypt`/`pgp_decrypt` against a
  ZIP payload) before being committed.
* **`export_file_name_format`**: set to `"monthly_settlements_{batch_id}"` for a clearer exported
  filename than the default `"batch_{batch_id}"` — purely cosmetic, doesn't change any verification
  logic above.
