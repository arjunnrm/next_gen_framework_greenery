# Test Pipeline: Column-Level AES-GCM Encryption with Random IV (TC-SEC-001)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 5, TC-SEC-001), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [16_encryption_and_secrets.md](16_encryption_and_secrets.md), [01_control_metadata_schema.md §4.3](01_control_metadata_schema.md#4-target_config-ingestion-and-transformation-flows).

## Purpose

Prove that `target_config.encrypted_columns` genuinely encrypts sensitive PII columns with
AES-GCM before a target table is ever materialized -- not just that the framework *claims* to
encrypt them, but that:

1. The physical bytes stored on disk for `ssn`/`credit_card` are real AES-GCM ciphertext
   (`BINARY`), never the plaintext values that were landed.
2. That ciphertext genuinely decrypts back to the exact original plaintext when the correct key
   is supplied -- a real round trip, not merely a "doesn't look like plaintext" check (see
   [16_encryption_and_secrets.md](16_encryption_and_secrets.md)'s own history: the project's
   original encryption test only ever checked "not plaintext" and missed a real ciphertext
   corruption bug for months as a result).
3. This all works using the project's **existing** `{{catalog}}.security.pii_encryption_key`
   Unity Catalog secret -- the same one `spec_08`/`spec_20`/`spec_22`/`spec_24` and the
   onboarding template already rely on -- with no new secret scope or key provisioned.

## Responsibilities

* One `ingestion_flow` (`df_sec_001_customer_pii_ingest`), `source_type: "autoloader"`, plain CSV,
  landing a 3-row raw customer PII fixture with `target_config.cdc_load_strategy: "APPEND"` --
  the simplest possible strategy, so this scenario stays scoped purely to `encrypted_columns`'s
  own behavior and never entangles with CDC/hash-column concerns (`APPEND` never gets
  `__framework_hash_key`/`__framework_hash_value` at all, so there is no risk of accidentally
  violating [16_encryption_and_secrets.md](16_encryption_and_secrets.md)'s explicit warning to
  never put an encrypted column in `columns_to_check`/an SCD comparison set).
* `target_config.encrypted_columns` encrypts both `ssn` and `credit_card`, each with
  `mode: "GCM"` (AES-GCM's random-IV mode -- the default and recommended mode), keyed off
  `{secret_catalog: "{{catalog}}", secret_schema: "security", secret_key: "pii_encryption_key"}`.

## Inputs

* `metaflow_testing/033_sec_001_aes_encrypt.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/metaflow_testing/sec_usecase/customer_pii_day1.csv` (3 rows) -- hand-authored;
  `customer_id`, `customer_name`, `ssn`, `credit_card` (well-known dummy card numbers -- the
  standard Visa/Mastercard/Amex test-number patterns, not real card data).
* `notebooks/00_seed_sample_data/03_seed_sec_001_aes_encrypt_data.py` -- a **new, dedicated** seed
  notebook (kept separate from every other scenario's own seed notebook) that provisions the
  `customers` schema and `landing_pii`/`_schemas` Volumes, then lands the fixture in
  `/Volumes/{{catalog}}/customers/landing_pii/incoming/`.
* **Requires the `{{catalog}}.security.pii_encryption_key` Unity Catalog secret to already exist**
  (see [05_deployment_guide.md](05_deployment_guide.md) §0 prerequisites) -- this scenario
  deliberately reuses it rather than provisioning anything new; the seed notebook does not
  provision it, exactly like every other encryption scenario in this project.

## Outputs

* `{{catalog}}.bronze_customers.customer_pii_encrypted` -- 3 rows. `ssn`/`credit_card` are
  `BINARY` AES-GCM ciphertext; `customer_id`/`customer_name`/`__framework_ingestion_timestamp_utc`
  (and the other `capture_technical_metadata` columns) remain plain, untouched values -- only the
  two configured columns are ever encrypted. No `__framework_hash_key`/`__framework_hash_value`
  (not CDC-dispatched -- `APPEND` never gets them).

## Expected results — simulation notes

**SQL assertion 1 -- stored values are non-plaintext ciphertext** (replace `{catalog}` with your
actual target catalog):

```sql
SELECT
  customer_id,
  typeof(ssn)          AS ssn_type,
  base64(ssn)          AS ssn_ciphertext_base64,
  typeof(credit_card)  AS credit_card_type,
  base64(credit_card)  AS credit_card_ciphertext_base64
FROM {catalog}.bronze_customers.customer_pii_encrypted
ORDER BY customer_id;
-- expect: ssn_type = 'binary', credit_card_type = 'binary' for every row; the base64 ciphertext
-- values bear no resemblance to the landed plaintext ("123-45-6789", "4111111111111111", ...)
-- and differ in length/content from each other despite the source values being short/similar.
```

**Round-trip decrypt verification -- a PySpark snippet, not a raw SQL query, and deliberately
so.** A plain SQL `aes_decrypt(ssn, secret('security', 'pii_encryption_key'), 'GCM')` query would
be wrong on two independent counts documented in
[16_encryption_and_secrets.md §2](16_encryption_and_secrets.md#2-resolving-a-secret-dbutilssecretsget-never-the-sql-secret-function):
the SQL `secret()` function only resolves a **classic workspace-level scope** and cannot address
this project's genuine three-level Unity Catalog secret at all, and — independently — a
live-confirmed Databricks redaction bug corrupts any ciphertext produced by a query whose *text*
contains a literal `secret(...)` call. `crypto/column_crypto.py` itself sidesteps both by
resolving the key via `dbutils.secrets.get(catalog=, schema=, key=)` and passing it to
`aes_decrypt`/`aes_encrypt` as a literal `Column`, never as SQL text -- the verification below
mirrors that exact, already-proven-correct pattern instead of reintroducing a broken one:

```python
from pyspark.sql import functions as F

pii_key = dbutils.secrets.get(catalog="metaflow", schema="security", key="pii_encryption_key")

verify_df = (
    spark.table("metaflow.bronze_customers.customer_pii_encrypted")
    .withColumn("ssn_plaintext", F.aes_decrypt(F.col("ssn"), F.lit(pii_key), F.lit("GCM")).cast("string"))
    .withColumn("credit_card_plaintext", F.aes_decrypt(F.col("credit_card"), F.lit(pii_key), F.lit("GCM")).cast("string"))
    .select("customer_id", "ssn_plaintext", "credit_card_plaintext")
    .orderBy("customer_id")
)
verify_df.show(truncate=False)
# expect:
# CUST001 | 123-45-6789 | 4111111111111111
# CUST002 | 234-56-7890 | 5500000000000004
# CUST003 | 345-67-8901 | 340000000000009
```

## Build notes / judgment calls

* **Secret name follows the task's own instruction and this repo's real, already-provisioned
  secret, not `TESTING_PLAN.md`'s placeholder names.** `TESTING_PLAN.md`'s own TC-SEC-001 row
  names a `metaflow_sec_scope`/`aes_gcm_256_key` secret scope/key that doesn't exist anywhere
  else in this project -- every real encryption spec already built (`spec_08`, `spec_20`,
  `spec_22`, `spec_24`, the onboarding template) uses the one shared
  `{secret_catalog, secret_schema, secret_key} = {"{{catalog}}", "security", "pii_encryption_key"}`
  reference, provisioned once per [05_deployment_guide.md](05_deployment_guide.md) §0. This
  build reuses that existing secret, per the task's own explicit instruction, rather than
  inventing a second, redundant one.
* **New fixture, not a reuse.** `sample_data/sample_customer_pii_encryption.csv` already exists,
  but it's shaped for the `crypto_abac_exhaustive` suite's own GCM/CBC/ECB-mode comparison
  (`account_id`/`region_code`/`ssn_for_gcm`/`ssn_for_cbc`/`ssn_for_ecb`/`ssn_for_override`) --
  not the `customer_id`/`ssn`/`credit_card` shape this test case asks for. A small, new 3-row
  CSV fixture and one dedicated seed notebook were added instead, following this project's
  established one-scenario-one-seed-notebook convention (e.g. `docs/42_tc_cdc_003.md`).
* **`cdc_load_strategy: "APPEND"`, not an SCD strategy.** `TESTING_PLAN.md`'s own row only asks
  to prove encryption-at-rest, not a CDC strategy; `APPEND` keeps this scenario scoped purely to
  `encrypted_columns`'s own behavior and sidesteps
  [16_encryption_and_secrets.md](16_encryption_and_secrets.md)'s explicit warning never to put an
  encrypted column in an SCD comparison set.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s "Proposed Pipeline & Job Architecture"
  column names a second `run_observability_task` step, but -- per this project's own real,
  established convention across every `TC-*` build so far (e.g. `docs/42_tc_cdc_003.md`) --
  observability is opt-in via a spec's own `observability[]` array plus a separate job, never
  wired into every scenario's job by default. This build follows the real
  `setup_control_tables -> seed -> onboard -> run_pipeline` convention instead.
* **Round-trip verification is a PySpark snippet, not a plain SQL query.** See "Expected
  results" above for the full reasoning -- a raw SQL `aes_decrypt(..., secret(...), ...)` query
  would be wrong twice over (wrong resolution function for a UC secret, and a live redaction
  bug), so this doc documents the same `dbutils.secrets.get()` + `F.aes_decrypt` pattern
  `crypto/column_crypto.py` itself uses, rather than a query shape known not to work correctly
  in this project.
* **`original_data_type` tag cross-check not exercised.** This scenario has no
  `transformation_flows`/`decrypted_columns`, so
  [16_encryption_and_secrets.md §4](16_encryption_and_secrets.md#4-original_data_type-type-validation--current-implementation-status)'s
  not-yet-wired `original_data_type` cross-check never comes into play here -- noted for
  completeness, not a gap specific to this build.
