# Test Pipeline: SCD Type 1 Overwrite with Delete Mapping (TC-CDC-003)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 2, TC-CDC-003), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § SCD1](02_cdc_load_strategies.md#scd1).

## Purpose

Prove two things about `target_config.cdc_load_strategy: "SCD1"` in one scenario:

1. **Overwrite-in-place, no history.** When the same primary key (`customer_id`) reappears in
   a later batch with a newer `sequence_by_column` value, `dlt.apply_changes(...,
   stored_as_scd_type="1")` overwrites that key's existing row wholesale -- the target never
   accumulates a second row for the same key, and the old attribute value is gone entirely
   (unlike SCD2, which would open a new history version instead).
2. **Delete mapping physically removes a row.** `cdc_operation_column`/
   `cdc_operation_mapping.delete_values` marks matching source rows as deletes;
   `apply_changes(..., apply_as_deletes=...)` removes the key from the target instead of
   upserting it -- whether or not that key ever previously existed in the target at all.

## Responsibilities

* Land a customer tier feed in 2 separate batches (Day-1, then Day-2) in the same incoming
  Volume, so the pipeline's two triggered updates each see exactly one batch:
  * Day-1: `C001` @ `tier=SILVER`, `cdc_op=UPSERT`.
  * Day-2: `C001` @ `tier=PLATINUM`, `cdc_op=UPSERT` (a genuine attribute change on an
    already-existing key) -- **and** `C002` @ `cdc_op=DELETED` (a delete marker for a key that
    was never landed on Day-1 at all, proving a delete op need not reference a pre-existing row
    to correctly result in "absent from the target").
* One `ingestion_flow` (`df_cdc_003_customer_scd1_ingest`) with `source_type: "autoloader"`,
  plain CSV format, `cdc_load_strategy: "SCD1"`, `primary_keys: ["customer_id"]`,
  `sequence_by_column: "updated_at"`, `cdc_operation_column: "cdc_op"`,
  `cdc_operation_mapping.delete_values: ["DELETED"]`.

## Inputs

* `metaflow_testing/021_cdc_003_scd1.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/metaflow_testing/crm_usecase/customer_scd1_day1.csv` (1 row) /
  `customer_scd1_day2.csv` (2 rows) -- hand-authored (no generator script needed for a fixture
  this small).
* `notebooks/00_seed_sample_data/03_seed_cdc_003_scd1_data.py` -- a **new, dedicated** seed
  notebook (kept separate from every other scenario's own seed notebook) that provisions the
  `crm` schema and `landing_customer`/`_schemas` Volumes, then lands **only** the Day-1 fixture
  in `/Volumes/{{catalog}}/crm/landing_customer/incoming/`. The Day-2 fixture is deliberately
  **not** landed by this notebook -- see "Main execution flow" below for the manual second step
  this scenario requires.

## Outputs

* `{{catalog}}.silver_crm.dim_customer_scd1` -- after the Day-1 run: exactly 1 row, `C001` @
  `tier=SILVER`. After the Day-2 run: still exactly 1 row for `C001`, now `tier=PLATINUM` (the
  Day-1 value is gone, overwritten in place, no second row) -- and **0 rows** for `C002` (its
  delete marker means it is never upserted at all).
* `__framework_hash_key`/`__framework_hash_value` columns present (SCD1 is CDC-dispatched;
  `generate_hash_columns` defaults `true`).

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run metaflow_test_cdc_003_scd1_job --target dev
```

Task chain: `setup_control_tables -> seed_cdc_003_scd1_data -> onboard_cdc_003 ->
run_pipeline`. This first job run lands and processes **only** the Day-1 fixture -- confirm
`dim_customer_scd1` holds exactly 1 row (`C001` @ `tier=SILVER`) before moving on.

**Day-2 step (manual, by design -- this is the behavior the scenario exists to prove):**

1. Copy the Day-2 fixture into the same incoming Volume, e.g. from a notebook attached to the
   same catalog:
   ```python
   dbutils.fs.cp(
       "file:/path/to/sample_data/metaflow_testing/crm_usecase/customer_scd1_day2.csv",
       "/Volumes/metaflow/crm/landing_customer/incoming/customer_scd1_day2.csv",
   )
   ```
   (or `databricks fs cp` from the CLI against the same destination path).
2. Re-run just the pipeline (no need to re-run the whole job -- `setup_control_tables`/
   `seed_cdc_003_scd1_data`/`onboard_cdc_003` are all a one-time/idempotent prerequisite, not
   part of the behavior under test here):
   ```bash
   databricks bundle run metaflow_test_cdc_003_scd1_pipeline --target dev
   ```
3. Auto Loader picks up `customer_scd1_day2.csv` as a new file in its next triggered
   (`availableNow`) update, and `apply_changes` processes both of its rows: `C001`'s existing
   row is overwritten with `tier=PLATINUM` (sequenced by `updated_at`, which is newer than
   Day-1's); `C002`'s row is recognized as a delete (`cdc_op=DELETED` matches
   `cdc_operation_mapping.delete_values`) and is never inserted.

## Expected results — simulation notes

**SQL assertions** (after the Day-2 run, replace `{catalog}` with your actual target catalog):

```sql
-- C001 overwritten in place -- exactly 1 row, latest tier value
SELECT tier FROM {catalog}.silver_crm.dim_customer_scd1 WHERE customer_id = 'C001';
-- expect: PLATINUM (1 row)

-- C002's delete marker means it is never present in the target
SELECT count(*) FROM {catalog}.silver_crm.dim_customer_scd1 WHERE customer_id = 'C002';
-- expect: 0

-- No history kept -- SCD1 never accumulates a second row per key
SELECT count(*) FROM {catalog}.silver_crm.dim_customer_scd1 WHERE customer_id = 'C001';
-- expect: 1 (not 2 -- contrast with TC-CDC-004's SCD2, which would show 2)
```

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture carries a `customer_id`/`tier`
  shape with a dedicated delete-operation column, so 2 small new CSV fixtures (3 rows total)
  and 1 new dedicated seed notebook were added, kept separate from every other scenario's own
  seed notebook and fixtures.
* **Two-step execution is intentional, not a workaround.** SCD1's overwrite/delete behavior is
  only observable *across* two separate pipeline updates against the same target -- a single
  job run landing both fixtures at once would still produce the correct final state, but would
  never demonstrate the "Day-1 row visibly changes in place on Day-2" property the test case
  asks for. The job's own automated run therefore covers only Day-1 (a clean, idempotent,
  fully self-contained job execution); the Day-2 re-land-and-rerun step is documented here as a
  manual follow-up, the same convention already established by
  [18_test_pipeline_scd1_wide_table_column_exclusion.md](18_test_pipeline_scd1_wide_table_column_exclusion.md)'s
  own Day-1/Day-2 narrative.
* **`C002` has no Day-1 row.** `TESTING_PLAN.md`'s own scenario description sends `C002` only
  on Day-2, already carrying the delete marker -- this is deliberate (per the row's own
  wording: "verify ... physically drops records matching delete operation codes"), and
  correctly exercises `apply_changes`'s handling of a delete for a key with no prior state:
  the row is simply never inserted, rather than inserted-then-immediately-deleted.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but per
  `TESTING_STATUS.md`'s framing, `TESTING_PLAN.md` is a planned/aspirational matrix, not a
  literal build spec -- no other real scenario's job wires observability in by default (it's
  opt-in, added via a spec's own `observability[]` array plus a separate job). This build
  follows the real `setup_control_tables -> seed -> onboard -> run_pipeline` convention
  instead; observability can be layered on later the same way scenario 100's was, if desired.
* **No DQ rules, no governance tags.** This scenario is scoped to SCD1's own
  overwrite-in-place/delete-mapping behavior; DQ (`TC-DQ-*`) and governance (`TC-GOV-*`) are
  separate, already-tracked test modules with their own dedicated rows in `TESTING_PLAN.md`.
