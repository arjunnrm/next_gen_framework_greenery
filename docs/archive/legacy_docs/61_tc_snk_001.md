# Test Pipeline: External Sink Dual Materialization & Plain ZIP Export (TC-SNK-001)

> See also: [Documentation index](README.md), [23_lakeflow_sinks.md](23_lakeflow_sinks.md) (the
> `sink`/`external_sink` mechanics this scenario exercises), [47_tc_trf_001.md](47_tc_trf_001.md)
> (the 4-way join shape this scenario reuses), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md).

## Purpose

Prove `target_type: "external_sink"`'s dual-output contract end to end: a single
`transformation_flows` entry both (1) materializes a real, governed, queryable Delta table via
the unchanged `register_main_and_quarantine_tables` + CDC-dispatch path, and (2) additionally
exports that same table's rows as a genuine Lakeflow sink artifact -- a plain, unencrypted ZIP
archive -- via a second, independent `dlt.create_sink(format="pgp_zip")` + `@dlt.append_flow`
reading `dlt.read_stream(qualified_main_table)` (`engine/sink_registration.py::register_external_sink_export`).
Both outputs come from **one** pipeline update, not a separate post-deployment export job.

## Responsibilities

* Reuses TC-TRF-001's own 4-way streaming/batch inner-join shape verbatim: 1 streaming Auto
  Loader fact table (`assignments_raw`, `is_streaming: true`) inner-joined against 3
  batch-read dimension tables (`employees_raw`/`departments_raw`/`projects_raw`,
  `is_streaming: false`) -- see [47_tc_trf_001.md](47_tc_trf_001.md) for the join-exclusion
  behavior (`employee_id = 'E005'` has no assignment row) this same fixture data also proves
  here, incidentally.
* 4 `ingestion_flows`, all `source_type: "autoloader"`, all `target_type: "streaming_table"`,
  landing plain (unzipped) CSVs into this test case's own dedicated bronze tables
  (`df_snk001_assignments_ingest` -> `bronze_ea.snk001_assignments_raw`, and similarly for
  `employees`/`departments`/`projects`).
* One `transformation_flows` entry (`ts_snk001_ea_joined_assignments_sink`),
  `target_type: "external_sink"`, `cdc_load_strategy: "APPEND"` (the flow's own `is_streaming`
  resolves `true` because its `snk001_assignments_raw` source input is marked
  `is_streaming: true` -- `notebooks/03_engine/03_lakeflow_declarative_pipeline.py`'s
  `is_streaming = flow_row.target_type == "streaming_table" or any(input.is_streaming ...)`
  -- which is exactly what satisfies `register_external_sink_export`'s "main table must be a
  genuine Streaming Table" check for a non-`streaming_table` `target_type`):

  ```sql
  SELECT a.employee_id, a.project_id, a.hours_allocated, e.employee_name, e.role, e.dept_id,
         d.dept_name, d.region, p.project_name, p.budget
  FROM snk001_assignments_raw a
  JOIN snk001_employees_raw e ON a.employee_id = e.employee_id
  JOIN snk001_departments_raw d ON e.dept_id = d.dept_id
  JOIN snk001_projects_raw p ON a.project_id = p.project_id
  ```

* `target_config.sink_config`: `format: "pgp_zip"`, staging `path` under
  `egress_ea.export_zips/_staging/snk001/`, `post_export_archive.enabled: true` writing to
  `egress_ea.export_zips/output/snk001/` -- **no** `secret` and **no** `pgp_encryption` block,
  which is what makes this a **plain**, unencrypted ZIP export (contrast with
  `spec_24_new_27_08_test_flagship.json`'s `ts_flagship_customer_scd1_egress`, the
  PGP-encrypted worked example in [23_lakeflow_sinks.md](23_lakeflow_sinks.md)).

## Build notes / judgment calls

* **Genuine naming collision with scenario 001 -- resolved by renaming this test case's own
  targets, not scenario 001's.** TC-SNK-001's own task detail names the literal target
  `metaflow.silver_ea.ea_joined_assignments` -- but scenario 001
  (`metaflow_test_001_zip_join_export_pipeline`, already deployed) **already owns a real,
  already-materialized `external_sink` flow against that exact three-part name**, including
  the identical join SQL, the identical `pgp_zip` sink format, and the identical
  `egress_ea.export_zips/_staging/` \/ `egress_ea.export_zips/output/` Volume paths (see
  `metaflow_testing/001_zip_file_onboarding.json`). Two different Lakeflow Declarative
  Pipelines cannot both declare a table/sink against the identical Unity Catalog object or
  write concurrently into the identical output directory with the same batch-numbered file
  name -- attempting either would risk a deployment-time table-ownership conflict or a
  runtime file-name collision between two unrelated pipelines' `batch_0.zip` outputs, not two
  independent, separately-verifiable test results. Per this build's scope discipline (never
  edit another test case's files), the fix is on this test case's own side, following the
  exact precedent [47_tc_trf_001.md](47_tc_trf_001.md) already set for the same reason: every
  bronze/silver target is named `snk001_<name>` (`bronze_ea.snk001_*_raw` /
  `silver_ea.snk001_ea_joined_assignments`), and the sink's staging/output paths are scoped to
  a `snk001/` subfolder and a `snk001_`-prefixed `export_file_name_format` -- still inside the
  exact same `bronze_ea`/`silver_ea`/`egress_ea.export_zips` schemas/Volume the task names,
  just disambiguated from scenario 001's own already-deployed objects and files. The join
  semantics, the CDC/DQ configuration, and the expected row-count/ZIP-presence assertions are
  otherwise exactly what the task describes.
* **Reused fixtures and seed notebooks, no new sample data.** Both ingestion input (the 4 EA
  CSVs) and the required schema/Volume provisioning (`ea`/`bronze_ea`/`silver_ea`/`egress_ea`)
  are fully covered by two already-existing, idempotent seed notebooks
  (`02_seed_metaflow_testing_data.py`, `03_seed_trf_001_4way_join_data.py`), reused as-is in
  this test case's own job. No new CSV fixture and no new seed notebook were written.
* **`pgp_zip` chosen deliberately for the "plain ZIP export" requirement.** The framework's
  `sink_config.format` enum is `{"delta", "kafka", "pgp_zip"}` -- `pgp_zip` is the only format
  that produces a real `.zip` file at all (`delta`/`kafka` write Delta/Kafka records, not an
  archive). Per [23_lakeflow_sinks.md](23_lakeflow_sinks.md), `post_export_archive.secret` and
  `.pgp_encryption` are both independently optional; omitting both (as this spec does) is what
  yields a genuinely plain, unencrypted `.zip` rather than an AES-password-protected or
  PGP-encrypted one -- this is the literal, real "plain ZIP export" this test case name calls
  for, not a naming coincidence with the format's own `pgp_zip` identifier.
