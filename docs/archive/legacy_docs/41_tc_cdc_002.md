# Test Pipeline: Full Materialized View Snapshot (TC-CDC-002)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 2, TC-CDC-002), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § TRUNCATE_AND_LOAD](02_cdc_load_strategies.md#truncate_and_load).

## Purpose

Prove that `target_config.cdc_load_strategy: "TRUNCATE_AND_LOAD"` on a `target_type:
"materialized_view"` transformation flow genuinely **fully recomputes** its target from its
source on every pipeline update -- rather than incrementally appending -- so a small reference
dimension (daily FX currency rates) always reflects exactly the current source content, with no
stale/superseded rows ever accumulating no matter how many times the pipeline is triggered. This
is the direct structural contrast with `APPEND` (TC-CDC-001): a materialized view is a full
recompute, so re-running the same pipeline update against unchanged source data must leave the
target's row count completely unchanged, never growing.

## Responsibilities

* Land one 50-row FX rate CSV extract (one row per distinct ISO currency code, all dated the
  same `rate_date`) in a landing Volume so Auto Loader's one triggered (`availableNow`) pipeline
  update ingests all 50 rows into Bronze in a single micro-batch.
* One `ingestion_flow` (`df_cdc_002_fx_rates_ingest`) with `source_type: "autoloader"`, plain CSV
  format, `cdc_load_strategy: "APPEND"` -- a plain Bronze landing table, no ZIP handling, no CDC
  dispatch (out of scope for this scenario; the strategy under test lives entirely in the
  downstream transformation flow).
* One `transformation_flow` (`ts_cdc_002_fx_rates_truncate_load`) reading that Bronze table as a
  batch `source_inputs` view and writing `target_type: "materialized_view"` with
  `cdc_load_strategy: "TRUNCATE_AND_LOAD"` -- the flow under test.

## Inputs

* `metaflow_testing/020_cdc_002_truncate.json` -- one ingestion flow + one transformation flow,
  no `reconciliation_flows`.
* `sample_data/metaflow_testing/ref_usecase/fx_rates_batch1.csv` -- 50 rows, hand-authored (no
  generator script needed for a fixture this small): 50 distinct real ISO 4217 currency codes
  (`AED` … `ZAR`), each with a plausible `exchange_rate` against USD, all sharing `rate_date =
  2026-08-28`.
* `notebooks/00_seed_sample_data/03_seed_cdc_002_truncate_data.py` -- a **new, dedicated** seed
  notebook (kept separate from every other scenario's own seed notebook) that provisions the
  `ref`/`bronze_ref`/`silver_ref` schemas and `landing_fx`/`_schemas` Volumes, then copies the CSV
  fixture straight into `/Volumes/{{catalog}}/ref/landing_fx/incoming/`.

## Outputs

* `{{catalog}}.bronze_ref.fx_rates_raw` -- exactly 50 rows after the CSV is ingested (a plain
  `APPEND` streaming table; no `__framework_hash_key`/`__framework_hash_value` columns, since
  `APPEND` is never CDC-dispatched).
* `{{catalog}}.silver_ref.dim_fx_rates_current` -- exactly 50 rows, **every time the pipeline is
  triggered**, regardless of how many times it runs against the same unchanged Bronze content --
  the property this scenario exists to prove. A materialized view under `TRUNCATE_AND_LOAD` is
  recomputed wholesale from `transformation_sql` on each update, so there is no incremental state
  to accumulate.

## Configuration

`metaflow_testing/020_cdc_002_truncate.json`'s ingestion flow:

```json
"source_config": {
  "path": "/Volumes/{{catalog}}/ref/landing_fx/incoming/",
  "format": "csv",
  "schema_location": "/Volumes/{{catalog}}/ref/_schemas/fx_rates_raw/",
  "reader_options": {"header": "true", "cloudFiles.inferColumnTypes": "true"},
  "capture_technical_metadata": true
},
"target_config": {"cdc_load_strategy": "APPEND", "storage_format": "delta"}
```

Target: `{{catalog}}.bronze_ref.fx_rates_raw`, `target_type: "streaming_table"`.

Its transformation flow -- the flow under test:

```json
"source_inputs": [
  {"input_name": "fx_rates_raw_src", "table": "{{catalog}}.bronze_ref.fx_rates_raw", "is_streaming": false}
],
"transformation_sql": "SELECT currency_code, rate_date, exchange_rate FROM fx_rates_raw_src",
"target_config": {"cdc_load_strategy": "TRUNCATE_AND_LOAD", "storage_format": "delta"}
```

Target: `{{catalog}}.silver_ref.dim_fx_rates_current`, `target_type: "materialized_view"`.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run metaflow_test_cdc_002_truncate_job --target dev
```

Task chain: `setup_control_tables -> seed_cdc_002_truncate_data -> onboard_cdc_002 ->
run_pipeline`.

**To exercise the "no accumulation across runs" property directly**: after the first successful
job run, simply run `databricks bundle run metaflow_test_cdc_002_truncate_job --target dev`
again (or trigger just the pipeline update on its own) without re-landing any new file -- Auto
Loader's checkpoint means Bronze stays at 50 rows regardless, and the materialized view's own
full recompute means Silver stays at 50 rows too, on every subsequent update.

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Bronze: exactly 50 rows, one per landed CSV row
SELECT count(*) FROM {catalog}.bronze_ref.fx_rates_raw;
-- expect: 50

-- Silver materialized view: exactly 50 rows -- the core assertion
SELECT count(*) FROM {catalog}.silver_ref.dim_fx_rates_current;
-- expect: 50

-- Re-run the pipeline update again (no new source file landed) and re-query:
SELECT count(*) FROM {catalog}.silver_ref.dim_fx_rates_current;
-- expect: still 50 -- no accumulation, no duplication, across repeated triggered updates

-- Every distinct currency code from the fixture is present exactly once
SELECT currency_code, count(*) FROM {catalog}.silver_ref.dim_fx_rates_current
GROUP BY currency_code HAVING count(*) <> 1;
-- expect: 0 rows returned
```

## Build notes / judgment calls

* **New fixture, not a reuse.** `sample_data/sample_fx_rates.csv` already exists in this repo,
  but it belongs to the original `test_specs/*.json` sample suite (seeded directly as
  `raw_fx_rates` by `notebooks/00_seed_sample_data/00_seed_sample_data.py`, not landed via a
  Volume/Auto Loader), has only 10 rows, and deliberately includes one invalid negative rate
  (`BRL,-0.10`) for a different, DQ-focused purpose. Neither its shape (already a table, not a
  landable CSV) nor its row count (10, not the 50 this TC specifically calls for) fit this
  scenario, so a new 50-row `sample_data/metaflow_testing/ref_usecase/fx_rates_batch1.csv` fixture
  and its own dedicated seed notebook were added instead, following the same
  `sample_data/metaflow_testing/<domain>_usecase/` convention every other `metaflow_testing/*`
  scenario's fixtures already use.
* **One CSV extract, not two.** `TESTING_PLAN.md` frames the scenario as "daily FX rates arrive
  as a full replacement extract," but proving "no accumulation across *runs*" only requires
  landing the fixture once and triggering the pipeline more than once against the same unchanged
  Bronze content -- a materialized view's full-recompute semantics make that the correct,
  minimal way to exercise the property under test (see "Main execution flow" above). A second,
  differently-valued daily extract was considered but is not needed to prove this TC's own
  assertion and would only add fixture volume without adding coverage.
* **Bronze ingestion is plain `APPEND`, not `TRUNCATE_AND_LOAD`.** The TC names
  `TRUNCATE_AND_LOAD`/`materialized_view` for the flow under test only; the raw landing step is
  ordinary Bronze ingestion (matching every other scenario's Bronze layer), keeping the strategy
  under test isolated to the one transformation flow it's meant to exercise.
* **No `run_observability_task`.** Same judgment call as `docs/40_tc_cdc_001.md`: no other real
  scenario's job wires observability in by default (it's opt-in, via a spec's own
  `observability[]` array plus a separate job); this build follows the real
  `setup_control_tables -> seed -> onboard -> run_pipeline` convention instead.
* **No DQ rules, no governance tags, no reconciliation.** This scenario is scoped to
  `TRUNCATE_AND_LOAD`'s own full-recompute behavior; DQ (`TC-DQ-*`), governance (`TC-GOV-*`), and
  reconciliation are separate, already-tracked test modules with their own dedicated rows in
  `TESTING_PLAN.md`.
