# Test Pipeline: TC-ING-006 -- Nested JSON Struct Flattening (`explode_columns`)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 1, TC-ING-006), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove `source_config.explode_columns` (Auto Loader / `source_type: "autoloader"`, `format:
"json"`) correctly flattens a nested JSON array-of-structs column into discrete top-level
columns, one row per array element -- see
[01_control_metadata_schema.md §3](01_control_metadata_schema.md#3-source_config-ingestion-flows-only)
and [ingestion/json_flattening.py](../src/flowx/lakeflow_framework/ingestion/json_flattening.py).

This session added a new `auto_flatten_all` flag that changes `explode_columns`'s *default*
behavior: an empty/absent `explode_columns` is now a schema-preserving pass-through (no
implicit flattening) unless `auto_flatten_all: true` is also set. This scenario deliberately
sets `explode_columns` **explicitly** to `["metrics"]` rather than relying on any default, to
prove the named-column-scoped explode path specifically -- not the `auto_flatten_all`
"flatten everything" path (which is out of scope for this test case).

## Responsibilities

* Land 2 nested JSON device-telemetry records into a dedicated `iot` landing Volume -- each
  record carries a `metrics` array of 2 `{sensor, val}` elements, e.g.:
  ```json
  {"device_id": "D1", "device_type": "env_sensor", "event_ts": "2026-08-28T09:00:00Z", "metrics": [{"sensor": "temp", "val": 22.5}, {"sensor": "pressure", "val": 101.3}]}
  ```
* Onboard one ingestion flow with `source_config.explode_columns: ["metrics"]` and
  `target_config.cdc_load_strategy: "APPEND"` (immutable telemetry facts -- no dedup/history
  needed), targeting `{catalog}.bronze_iot.sensor_telemetry_flat`.
* `apply_explode_columns` (`ingestion/json_flattening.py`) explodes the `metrics`
  `array<struct<sensor, val>>` column (`explode_outer`, one row per element) and immediately
  flattens the resulting struct element in the same pass, producing `metrics_sensor` and
  `metrics_val` as discrete top-level columns -- exactly the behavior
  `tests/unit/test_json_flattening.py::test_populated_explode_columns_on_array_of_struct_fully_denests_in_one_entry`
  already unit-tests.
* Needs no dedicated seed fixture reuse -- no existing seeded table/volume carries a nested
  JSON struct/array shape, so this scenario seeds its own small dedicated fixture rather than
  repurposing scenario 001/002/003/100's flat CSV/Zerobus fixtures.

## Expected results -- simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Exactly 4 rows: 2 devices x 2 metrics elements each
SELECT count(*) FROM {catalog}.bronze_iot.sensor_telemetry_flat;
-- expect: 4

-- Exactly 2 rows per device
SELECT device_id, count(*) FROM {catalog}.bronze_iot.sensor_telemetry_flat
GROUP BY device_id ORDER BY device_id;
-- expect: D1 -> 2, D2 -> 2

-- metrics_sensor / metrics_val present and populated, "metrics" itself gone
DESCRIBE {catalog}.bronze_iot.sensor_telemetry_flat;
-- expect: metrics_sensor (string), metrics_val (double) present; no "metrics" struct/array column

SELECT device_id, metrics_sensor, metrics_val
FROM {catalog}.bronze_iot.sensor_telemetry_flat
ORDER BY device_id, metrics_sensor;
-- expect: (D1, pressure, 101.3), (D1, temp, 22.5), (D2, pressure, 99.8), (D2, temp, 24.1)
```
