# Test Pipeline: TC-ING-007 -- Inline Data Standardization SQL

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 1, TC-ING-007), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove `source_config.data_standardization_sql` (Auto Loader / `source_type: "autoloader"`,
`format: "csv"`) applies simple per-column normalization -- trimming whitespace and fixing
casing -- to specific columns at ingest time, before the row ever reaches the Bronze table --
see [01_control_metadata_schema.md §3](01_control_metadata_schema.md#3-source_config-ingestion-flows-only)
and [22_ingestion_pgp_zip_json_standardization.md §5](22_ingestion_pgp_zip_json_standardization.md#5-data_standardization_sql--a-column-expression-allowlist-deliberately-more-restricted-than-transformation_sql)
for the full grammar and its rationale.

This scenario deliberately uses only the restricted column-expression grammar the framework
enforces (`ingestion/standardization_sql.py` / `onboarding/spec_validator.py::_validate_data_standardization_sql`):
each entry is exactly one column expression ending in an explicit `AS <column_name>` clause,
applied via `withColumn(alias, F.expr(expression))` -- **not** a full `SELECT` statement. A
value containing a bare `SELECT`/`FROM`/`JOIN`/`UNION`/`WHERE`/any DDL/DML keyword, or a `;`,
is rejected outright at onboarding time.

## Responsibilities

* Land 3 dirty company records into a dedicated `master` landing Volume -- each carries a
  `region` and `email` value with extra leading/trailing whitespace and/or inconsistent
  casing, e.g.:
  ```csv
  company_id,company_name,region,email,updated_at
  CO001,Acme Corp LLC,"  us-east  "," invalid-email@test.com  ",2026-08-28T09:00:00
  ```
* Onboard one ingestion flow with two `data_standardization_sql` entries --
  `"TRIM(UPPER(region)) AS region"` and `"LOWER(TRIM(email)) AS email"` -- and
  `target_config.cdc_load_strategy: "APPEND"` (plain append, no dedup/history needed for this
  reference feed), targeting `{catalog}.bronze_master.companies_standardized`.
* `apply_data_standardization_sql` (`ingestion/standardization_sql.py`) applies each
  expression in order, one `withColumn` at a time, overwriting the existing `region`/`email`
  columns in place -- exactly the behavior
  `tests/unit/test_standardization_sql.py::test_multiple_expressions_applied_in_order`
  already unit-tests.
* Needs no dedicated seed fixture reuse -- no existing seeded table/volume carries this
  dirty-string-normalization shape, so this scenario seeds its own small dedicated fixture
  rather than repurposing another scenario's CSV fixtures.

## Outputs

* `{catalog}.bronze_master.companies_standardized` -- 3 rows, with `company_id`,
  `company_name` (untouched -- not one of the two standardized columns), standardized
  `region`/`email`, `updated_at`, plus the usual `__framework_*` technical-metadata columns

## Expected results -- simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Exactly 3 rows landed
SELECT count(*) FROM {catalog}.bronze_master.companies_standardized;
-- expect: 3

-- The test-case brief's literal example row: whitespace trimmed, region upper-cased,
-- email lower-cased
SELECT region, email FROM {catalog}.bronze_master.companies_standardized WHERE company_id = 'CO001';
-- expect: region = 'US-EAST', email = 'invalid-email@test.com'

-- Every row's region/email is standardized the same way, regardless of input casing/padding
SELECT company_id, region, email FROM {catalog}.bronze_master.companies_standardized ORDER BY company_id;
-- expect:
--   CO001 | US-EAST  | invalid-email@test.com
--   CO002 | EU-WEST  | contact@globex.com
--   CO003 | AP-SOUTH | support@northwind.example

-- The count from the test-case brief's own assertion form: every row satisfies the
-- standardized CO001 pattern's *shape* (no residual leading/trailing whitespace, region
-- fully upper-case, email fully lower-case) -- confirmed per-row above rather than via a
-- single aggregate, since only CO001 shares the brief's exact literal values.
SELECT count(*) FROM {catalog}.bronze_master.companies_standardized
WHERE region = trim(upper(region)) AND email = lower(trim(email));
-- expect: 3 (equals total row count -- no row was left un-standardized)

-- company_name (not a standardized column) still carries its original padding untouched
SELECT company_id, company_name FROM {catalog}.bronze_master.companies_standardized WHERE company_id = 'CO003';
-- expect: company_name = '  Northwind Traders  ' (unchanged)
```
