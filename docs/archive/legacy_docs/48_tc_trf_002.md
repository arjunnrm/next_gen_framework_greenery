# Test Pipeline: Multi-Regional Ingestion UNION ALL Consolidation (TC-TRF-002)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 3, TC-TRF-002), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md).

## Purpose

Prove that `transformation_sql` genuinely combines two independently-ingested regional
Bronze tables via `UNION ALL` into one consolidated enterprise Silver dataset -- no rows
lost, none duplicated, none deduplicated away -- and that both regions' rows survive intact
(their `region` value included) rather than one region's data silently overwriting or
shadowing the other.

## Responsibilities

* Two `ingestion_flows`, each a plain streaming Auto Loader CSV ingest with
  `cdc_load_strategy: "APPEND"` (no primary keys, no CDC comparison -- this scenario is about
  `UNION ALL` consolidation, not CDC behavior, so the simplest load strategy keeps the flow
  focused on the one thing under test):
  * `df_trf_002_orders_na_ingest` -> `{{catalog}}.bronze_sales.orders_na_raw` (5 rows).
  * `df_trf_002_orders_eu_ingest` -> `{{catalog}}.bronze_sales.orders_eu_raw` (4 rows).
* One `transformation_flow` (`ts_trf_002_union_all_global_orders`) with two `source_inputs`
  (both `is_streaming: true`, referencing the two Bronze tables above) and
  `transformation_sql: "SELECT * FROM orders_na_raw UNION ALL SELECT * FROM orders_eu_raw"` ->
  `{{catalog}}.silver_sales.all_global_orders`.
* Row counts (5 NA / 4 EU) are deliberately scaled down from `TESTING_PLAN.md`'s own 500/400
  -- the **ratio** (unequal sizes, both non-trivial) is what this scenario proves, not the
  absolute count, and small fixtures keep onboarding/pipeline runs fast. Deliberately unequal
  sizes so a passing row-count assertion can't be explained by one side accidentally being
  read twice.

## Inputs

* `metaflow_testing/027_trf_002_union_all.json` -- 2 ingestion flows + 1 transformation flow
  (no `reconciliation_flows`).
* `sample_data/metaflow_testing/sales_usecase/orders_na_raw.csv` (5 rows, `region = 'NA'`) /
  `orders_eu_raw.csv` (4 rows, `region = 'EU'`).
* `notebooks/00_seed_sample_data/03_seed_trf_002_union_all_data.py` -- a new, dedicated seed
  notebook (kept separate from every other test case's own seed step) that provisions the
  `sales`/`bronze_sales`/`silver_sales` schemas and two independent per-region landing
  Volumes (`landing_orders_na`, `landing_orders_eu` -- deliberately separate, not one shared
  incoming folder, so each Auto Loader flow only ever discovers its own region's file), then
  lands one CSV batch per region.

## Outputs

* `{{catalog}}.bronze_sales.orders_na_raw` -- exactly 5 rows.
* `{{catalog}}.bronze_sales.orders_eu_raw` -- exactly 4 rows.
* `{{catalog}}.silver_sales.all_global_orders` -- exactly 9 rows (5 + 4), with both `NA` and
  `EU` values present in its `region` column.

## Configuration

`metaflow_testing/027_trf_002_union_all.json`'s `transformation_flows[0]`:

```json
"source_inputs": [
  {"input_name": "orders_na_raw", "table": "{{catalog}}.bronze_sales.orders_na_raw", "is_streaming": true},
  {"input_name": "orders_eu_raw", "table": "{{catalog}}.bronze_sales.orders_eu_raw", "is_streaming": true}
],
"transformation_sql": "SELECT * FROM orders_na_raw UNION ALL SELECT * FROM orders_eu_raw",
"target_config": {"cdc_load_strategy": "APPEND", "storage_format": "delta"}
```

No watermark is needed on either `source_inputs[]` entry -- watermarks are only required when
two streaming inputs are **joined**; a plain `UNION ALL` across streams has no such
requirement (see [17_onboarding_template_reference.md §3.2/§3.4](17_onboarding_template_reference.md)).
The engine rewrites the bare `FROM orders_na_raw`/`FROM orders_eu_raw` references to
`FROM STREAM ...` automatically at runtime since both inputs are marked `is_streaming: true`
-- the spec itself never writes `STREAM`.

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
SELECT count(*) FROM {catalog}.bronze_sales.orders_na_raw;   -- expect: 5
SELECT count(*) FROM {catalog}.bronze_sales.orders_eu_raw;   -- expect: 4
SELECT count(*) FROM {catalog}.silver_sales.all_global_orders;  -- expect: 9

-- both regional codes represented, in the right proportion
SELECT region, count(*) FROM {catalog}.silver_sales.all_global_orders
GROUP BY region ORDER BY region;
-- expect: EU -> 4, NA -> 5
```

## Build notes / judgment calls

* **New, dedicated fixtures, not a reuse of `sample_data/sample_orders_region_a.csv` /
  `sample_orders_region_b.csv`.** Those two existing CSVs already back an unrelated,
  pre-existing legacy scenario (`tests/integration/test_transformation_union_all.py`, a
  `poc`-catalog `bronze_union_test`/`silver_union_test` suite outside this `metaflow_testing/`
  TC series) whose assertions depend on their exact row counts (5 and 6) and order IDs --
  reusing or trimming them here would either not match this TC's required 5/4 split or risk
  destabilizing that other suite's fixtures. New fixtures
  (`sample_data/metaflow_testing/sales_usecase/orders_na_raw.csv` /
  `orders_eu_raw.csv`, 5 and 4 rows) were generated instead, following the exact same CSV
  shape (`order_id, order_ts, customer_id, product_id, quantity, unit_price, region`) so the
  two scenarios stay structurally analogous without sharing state.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step for every test case in
  the matrix, but per the established convention already followed by every other
  individually-built TC in this repo (e.g. `docs/31_tc_ing_001.md`'s own build notes),
  `TESTING_PLAN.md` is a planned/aspirational matrix, not a literal build spec -- observability
  is opt-in, wired via a spec's own `observability[]` array plus a separate job, not a default
  task on every pipeline job. This build follows the real
  `setup_control_tables → seed → onboard → run_pipeline` convention instead.
* **Region values `'NA'`/`'EU'`** (matching the ingestion flow/table naming) rather than the
  `region_a`/`region_b` values used by the unrelated legacy fixture noted above -- chosen to
  read naturally against this TC's own `orders_na_raw`/`orders_eu_raw` table names and the
  "both regional codes represented" verification wording in `TESTING_PLAN.md`.
