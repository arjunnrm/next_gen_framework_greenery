# Test Pipeline: SHA-256 Hash Key & Value Determinism (TC-SEC-002)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 5, TC-SEC-002), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § The hash-key/hash-value framework](02_cdc_load_strategies.md#the-hash-keyhash-value-framework), [01_control_metadata_schema.md §4a](01_control_metadata_schema.md#4a-hash-keyvalue----a-framework-design-principle).

## Purpose

Prove that `__framework_hash_key`/`__framework_hash_value` generation is genuinely
deterministic and reproducible for a **composite** primary key, end to end against a real,
persisted target table:

1. **`__framework_hash_key` is exactly `sha2(concat_ws('||', region, account_id), 256)`** for
   every row -- not an approximation, not order-dependent, not something that only holds for a
   single-column key.
2. **A composite key actually matters.** The same `account_id` (`ACC001`) recurs under 3
   different `region` values in the fixture; a hash keyed on `account_id` alone would incorrectly
   collide these into "the same logical row," while the real composite-key hash gives each
   `(region, account_id)` pair its own distinct `__framework_hash_key`.
3. **`__framework_hash_value` is populated** (non-`NULL`) whenever the resolved comparison-column
   set is non-empty, and is stable for rows whose comparison columns don't change.

## Where this is actually implemented (read before building or debugging this scenario)

`__framework_hash_key`/`__framework_hash_value` are **not** a reconciliation-only feature.
Confirmed by reading both modules in full this pass:

* `cdc/hashing.py::compute_hash_columns` is the sole place either column is computed --
  `__framework_hash_key = sha2(concat_ws('||', <coalesced-to-string, ordered primary_keys>), 256)`,
  `__framework_hash_value` = the same construction over the resolved comparison-column set (or a
  constant `NULL` when that set is empty).
* `dq/quarantine.py::_apply_hash_and_surrogate_key_columns` is the **only call site** for an
  ingestion/transformation flow, invoked unconditionally for **any** CDC-dispatched strategy
  (`SCD1`/`SCD2`/`SCD3`/`FULL_SNAPSHOT_CDC`/`FULL_SNAPSHOT_CDC_NO_PK`) whenever
  `target_config.generate_hash_columns` resolves truthy (default `true`) -- gated only by
  `needs_cdc_dispatch`, not by anything reconciliation-specific. This runs on the *clean*
  (quarantine-filtered) upstream, before `dlt.apply_changes`/`apply_changes_from_snapshot` ever
  sees the data, so every row that lands in the real target table already carries both columns.
* `reconciliation/matcher.py` **consumes** these columns (via `hash_precomputed: true`) or
  recomputes them inline for its own join -- it is a second, independent caller of the exact same
  `cdc/hashing.py::compute_hash_columns` function, not the place hash generation "lives." A
  reconciliation flow's own `prepare_dataset_for_matching` only ever materializes hash columns
  into an `append_target_table` for rows it actually appends (missing/drifted records) -- never
  for every row of a real target table the way a CDC-dispatched ingestion flow does.

**Build decision: this scenario is a plain `ingestion_flow` (`SCD1`), not a
`reconciliation_flow`.** A genuine CDC-dispatched ingestion flow is the more direct, minimal, and
verifiable exercise of the real hash-generation code path (`dq/quarantine.py` ->
`cdc/hashing.py`) -- every row of the persisted `{{catalog}}.silver_accounts.accounts_hashed`
table gets `__framework_hash_key`/`__framework_hash_value`, which is exactly what "verify
`__framework_hash_key` equals `sha2(...)` for every row via direct SQL comparison" needs. A
reconciliation-flow-only version would not materialize hash columns on every row of a real table
(only on the subset it appends), making a "for every row" SQL assertion structurally impossible
to satisfy that way.

## Responsibilities

* Land a small accounts feed (single batch) with a genuine composite business key: `region` +
  `account_id`. `ACC001` recurs under `US`/`EU`/`APAC`; `ACC002` recurs under `US`/`EU`.
* One `ingestion_flow` (`df_sec_002_accounts_hashed_ingest`) with `source_type: "autoloader"`,
  plain CSV format, `cdc_load_strategy: "SCD1"`, `primary_keys: ["region", "account_id"]`,
  `generate_hash_columns: true` (explicit, though it's already the default for any
  CDC-dispatched strategy -- set here for clarity in a scenario dedicated to this exact feature).

  `transformation_flows`/`reconciliation_flows`).

* `delta.enableChangeDataFeed = true` on the target (every CDC-dispatched target gets this --

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Row count: 6 distinct (region, account_id) composite keys, all upserted
SELECT count(*) FROM {catalog}.silver_accounts.accounts_hashed;
-- expect: 6

-- Determinism: __framework_hash_key equals sha2(concat_ws('||', region, account_id), 256)
-- for EVERY row, via direct SQL recomputation -- this is the scenario's core assertion.
SELECT count(*) AS mismatched_rows
FROM {catalog}.silver_accounts.accounts_hashed
WHERE __framework_hash_key <> sha2(concat_ws('||', region, account_id), 256);
-- expect: 0

-- Composite key genuinely matters: the same account_id under different regions gets a
-- distinct hash_key each time (not collapsed to one row/one hash).
SELECT region, account_id, __framework_hash_key
FROM {catalog}.silver_accounts.accounts_hashed
WHERE account_id = 'ACC001'
ORDER BY region;
-- expect: 3 rows (APAC/EU/US), 3 distinct __framework_hash_key values

-- __framework_hash_value is populated (comparison-column set is non-empty here)
SELECT count(*) AS null_hash_value_rows
FROM {catalog}.silver_accounts.accounts_hashed
WHERE __framework_hash_value IS NULL;
-- expect: 0
```

## Build notes / judgment calls

* **Built as an `ingestion_flow`, not a `reconciliation_flow`** -- see "Where this is actually
  implemented" above for the precise code-reading that led to this choice: hash-column
  generation is a CDC-dispatch-time feature (`dq/quarantine.py`/`cdc/hashing.py`), independent of
  and prior to reconciliation; reconciliation only ever *consumes* or *re-derives* the same
  columns, and only for a subset of rows (its own append set), which cannot satisfy a
  "for every row" assertion against a real, fully-materialized target table.
* **New fixture, not a reuse.** No existing seeded fixture carries a `(region, account_id)`
  composite-key shape with a deliberately recurring `account_id` across regions, so 1 small new
  CSV fixture (6 rows) and 1 new dedicated seed notebook were added, kept separate from every
  other scenario's own seed notebook and fixtures (including TC-SEC-001's own `sec_usecase`
  fixture, `customer_pii_day1.csv`, which this scenario's fixture sits alongside without
  overlapping).
* **`SCD1` chosen over `SCD2`/`FULL_SNAPSHOT_CDC`.** Any of the five CDC-dispatched strategies
  would exercise the identical hash-generation code path (`_apply_hash_and_surrogate_key_columns`
  doesn't branch on which strategy triggered it); `SCD1` is the simplest to reason about for a
  single-batch, no-history determinism check, and needs no delete-marker/history-column noise.
* **No DQ rules, no governance tags, no encryption.** This scenario is scoped to hash-key/value
  determinism; DQ (`TC-DQ-*`), governance (`TC-GOV-*`), and encryption (`TC-SEC-001`/`TC-SEC-003`)
  are separate, already-tracked test modules with their own dedicated rows in `TESTING_PLAN.md`.
