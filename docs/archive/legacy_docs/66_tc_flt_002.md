# Test Pipeline: Continuous Day-1 to Day-2 Incremental Ingestion Cycle (TC-FLT-002)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 10, TC-FLT-002), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § SCD1](02_cdc_load_strategies.md#scd1).

## Purpose

Prove that a triggered (non-continuous) Lakeflow Declarative Pipeline genuinely resumes an
incremental Auto Loader ingestion cycle across two **separate** pipeline updates -- not just
that `dlt.apply_changes` sorts a single mixed batch correctly within one run. Day-1 lands an
initial seed load and the pipeline is run once; only afterward does Day-2 land a batch of
attribute updates to *existing* rows plus a couple of brand-new rows, and the pipeline is run a
second time. Under `cdc_load_strategy: "SCD1"`, the Day-2 updates must overwrite the matching
rows in place (no duplicates, no history kept) while the Day-2 inserts must land as genuinely
new rows -- so the final row count is `day1_count + new_count`, **not** `day1_count +
day2_count`, since every Day-2 row that shares a `customer_id` with Day-1 is an upsert, not an
additional row.

## Responsibilities

* One `ingestion_flow` (`df_flt_002_customer_lifecycle_ingest`), `source_type: "autoloader"`,
  `target_config.cdc_load_strategy: "SCD1"` -- SCD1 is valid directly on an ingestion flow, so
  this scenario needs no separate transformation step.
* `primary_keys: ["customer_id"]`, `sequence_by_column: "updated_at"` -- the latest value per
  customer (by `updated_at`) wins on every upsert.
* Two CSV "day" extracts landed into the **same** Auto Loader incoming path, but on two
  genuinely separate job runs of the seed step, with a real pipeline update run in between:
  * `lifecycle_day1.csv` -- 10 customers (`CUST501`-`CUST510`), the initial seed load.
  * `lifecycle_day2.csv` -- 3 of those same `customer_id`s (`CUST501`, `CUST505`, `CUST509`)
    re-sent with changed `city`/`tier` and an advanced `updated_at` (an update, under SCD1),
    plus 2 brand-new `customer_id`s (`CUST511`, `CUST512`) appearing for the first time (a
    plain insert).
* Scaled down from the TESTING_PLAN.md-suggested 1,000/150/50 to 10/3/2 -- the ratio (existing
  rows updated vs. brand-new rows inserted, both a small minority of the total) is what this
  scenario proves, not the absolute row count.

## Inputs

* `metaflow_testing/044_flt_002_lifecycle.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/metaflow_testing/crm_usecase/lifecycle_day1.csv` (10 rows) /
  `lifecycle_day2.csv` (5 rows: 3 updates + 2 inserts) -- new fixtures, hand-authored (see
  Build notes).
* `notebooks/00_seed_sample_data/03_seed_flt_002_lifecycle_data.py` -- a new, dedicated seed
  notebook that provisions the `crm`/`silver_crm` schemas and `landing_lifecycle`/`_schemas`
  Volumes, then lands **one** stage's CSV file per invocation (`stage` widget, `day1` or
  `day2`) into `/Volumes/{{catalog}}/crm/landing_lifecycle/incoming/` -- deliberately not both
  at once, since the whole point of this scenario is two separate triggered updates, not one
  batch containing both days' data.

## Outputs

* `{{catalog}}.silver_crm.dim_customer_lifecycle` -- the real SCD1 target, a genuine Lakeflow
  Streaming Table regardless of its declared `target_type` (`dlt.apply_changes` requires one).
  After the Day-1 run: exactly 10 rows. After the Day-2 run: exactly 12 rows (`10 + 2` new,
  **not** `10 + 5`) -- `CUST501`/`CUST505`/`CUST509` overwritten in place with their Day-2
  `city`/`tier` values, `CUST502`-`CUST504`/`CUST506`-`CUST508`/`CUST510` unchanged from
  Day-1, `CUST511`/`CUST512` newly present.
* `__framework_hash_key`/`__framework_hash_value` and `delta.enableChangeDataFeed = "true"` on
  the target (every SCD1-dispatched target gets both, per
  [02_cdc_load_strategies.md § the hash-key/hash-value framework](02_cdc_load_strategies.md#the-hash-keyhash-value-framework)).

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run metaflow_test_flt_002_lifecycle_job --target dev
```

Task chain: `setup_control_tables → seed_day1_customers → onboard_flt_002 →
run_pipeline_day1 → seed_day2_customers → run_pipeline_day2`.

**The drop-day2-in-and-rerun sequence, explained.** `seed_day1_customers` (the seed notebook
with `stage=day1`) lands only `lifecycle_day1.csv`; `run_pipeline_day1` then triggers the
pipeline's first update, which Auto Loader discovers and ingests as its very first batch --
10 inserts, since the target starts empty. Only once that update has fully committed does
`seed_day2_customers` (`stage=day2`) land `lifecycle_day2.csv` into the **same** incoming path.
`run_pipeline_day2` then triggers a second, independent pipeline update: Auto Loader's own
checkpoint means it discovers only the newly-arrived `lifecycle_day2.csv` file (it already
processed `lifecycle_day1.csv` on the prior update and will not re-read it), and
`dlt.apply_changes` upserts those 5 rows against the already-materialized 10-row target --
3 keys match and overwrite in place, 2 keys are new and insert. This two-separate-runs
structure is what actually exercises "yesterday's load, today's incremental delta," as opposed
to a single run that happens to see a pre-mixed batch of both days' data at once (which would
prove `apply_changes`'s sequencing but not a real triggered-pipeline day-over-day cycle).

## Expected results — simulation notes

**SQL assertions** (after both runs, replace `{catalog}` with your actual target catalog):

```sql
-- Final row count: day1_count (10) + new_count (2) = 12, not day1+day2 (15)
SELECT count(*) FROM {catalog}.silver_crm.dim_customer_lifecycle;
-- expect: 12

-- Updated rows reflect Day-2 values
SELECT customer_id, city, tier
FROM {catalog}.silver_crm.dim_customer_lifecycle
WHERE customer_id IN ('CUST501', 'CUST505', 'CUST509')
ORDER BY customer_id;
-- expect: CUST501 -> San Francisco, GOLD
--         CUST505 -> Miami, GOLD
--         CUST509 -> Seattle, SILVER

-- Untouched Day-1 rows are unchanged
SELECT customer_id, city, tier
FROM {catalog}.silver_crm.dim_customer_lifecycle
WHERE customer_id = 'CUST502';
-- expect: Austin, SILVER (Day-1 value, never resent on Day-2)

-- Brand-new Day-2 customers are present exactly once
SELECT customer_id FROM {catalog}.silver_crm.dim_customer_lifecycle
WHERE customer_id IN ('CUST511', 'CUST512')
ORDER BY customer_id;
-- expect: 2 rows

-- No history/duplicates: SCD1 keeps exactly one row per key
SELECT customer_id, count(*) FROM {catalog}.silver_crm.dim_customer_lifecycle
GROUP BY customer_id HAVING count(*) > 1;
-- expect: 0 rows
```

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture matches this scenario's exact
  requirement (a specific small set of existing keys updated plus a couple of brand-new keys,
  landed across two genuinely separate pipeline runs), so 2 new CSV fixtures and 1 new
  dedicated seed notebook were added, following the same pattern established by
  `metaflow_test_cdc_004_scd2_job` (`03_seed_cdc_004_scd2_data.py`) rather than extending
  `02_seed_metaflow_testing_data.py`. Note that `sample_data/metaflow_testing/crm_usecase/`
  already holds an unrelated `customer_scd1_day1.csv`/`customer_scd1_day2.csv` pair (a
  different, single-row delete-focused fixture for another test case in this same batch) --
  this scenario deliberately uses its own `lifecycle_day1.csv`/`lifecycle_day2.csv` names to
  avoid touching that other test case's files.
* **Scaled down, ratio preserved.** TESTING_PLAN.md's own text names 1,000 seed / 150 updates /
  50 new; this build uses 10 / 3 / 2 instead, keeping "a small minority of rows updated, a
  smaller minority newly inserted, most rows untouched" as the actual property under test
  rather than the absolute scale.
* **Two real pipeline-update tasks against one pipeline, not one.** Unlike most other
  scenarios in this batch (which land all their fixture data before a single triggered
  update), this job's task chain runs `run_pipeline_day1` and `run_pipeline_day2` as two
  separate `pipeline_task` job tasks, both pointed at the same
  `metaflow_test_flt_002_lifecycle_pipeline`, with `seed_day2_customers` landing the Day-2 file
  strictly in between them. This is a deliberate, necessary departure from the
  land-everything-then-run-once convention -- TC-FLT-002's entire premise (a real day-over-day
  incremental cycle across separate triggered runs) would not be exercised by a single run that
  happens to see both days' files at once.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column for TC-FLT-002 names a second `run_observability_task` step, but
  consistent with every other real scenario built in this batch, observability is opt-in
  (wired via a spec's own `observability[]` array plus a separate job) and not part of this
  scenario's minimal build.
