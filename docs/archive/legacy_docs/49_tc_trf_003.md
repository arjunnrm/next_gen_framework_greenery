## Purpose

Prove that a column encrypted at rest in Bronze can be decrypted **in-memory, inside the same
Lakeflow Declarative Pipeline DAG**, immediately ahead of a real business computation over its
plaintext value — never as a separate post-processing job, and never landing a decrypted copy
back to storage. `target_config.encrypted_columns` (ingestion) and
`source_inputs[].decrypted_columns` (transformation) are both individually exercised elsewhere in
this project's docs/templates, but this scenario is the first to chain them end to end against a
genuinely computed aggregate (`sum(billing_amount)`) and assert the *exact* resulting number,
proving the round trip is lossless, not merely "no longer plaintext" (see
[16_encryption_and_secrets.md §2](16_encryption_and_secrets.md#2-resolving-a-secret-dbutilssecretsget-never-the-sql-secret-function)'s
own account of a real, live-confirmed corruption bug this exact kind of round-trip assertion was
needed to catch).

## Responsibilities

* One ingestion flow (`df_health_patient_visits_ingest`), `source_type: "autoloader"`,
  `cdc_load_strategy: "APPEND"` — deliberately the simplest possible CDC strategy, since an
  AES-GCM-encrypted column must never be compared for change detection (random IV per call — see
  [16_encryption_and_secrets.md §3](16_encryption_and_secrets.md#3-column-level-aes-encryption-and-decryption)),
  and `APPEND` has no comparison concept at all to worry about.
* `target_config.encrypted_columns` AES-GCM-encrypts `billing_amount` in place (`output_column`
  same as `column_name`) before it lands in
  `{{catalog}}.bronze_health.patient_visits_raw` — keyed off
  `{{catalog}}.security.pii_encryption_key`, the **existing** UC secret this project already
  documents provisioning for in [05_deployment_guide.md](05_deployment_guide.md)'s prerequisites
  section (reused verbatim, not a new key).
* One transformation flow (`ts_trf_003_patient_billing_summary`), reading
  `patient_visits_raw` as a **batch** input (`is_streaming: false` — a full-recompute aggregate
  has no meaningful incremental/streaming form), whose `source_inputs[].decrypted_columns`
  decrypts `billing_amount` back to plaintext (`cast_to_type: "double"`, matching the column's
  pre-encryption inferred CSV type) before `transformation_sql` ever runs.
* `transformation_sql: "SELECT sum(billing_amount) AS billing_amount FROM patient_visits_input"`
  computes the aggregate over the now-plaintext column, published as a `materialized_view`
  (`cdc_load_strategy: "TRUNCATE_AND_LOAD"` — a full recompute on every pipeline update, the same
  pairing [17_onboarding_template_reference.md §4.1](17_onboarding_template_reference.md#41-target_type-five-values)
  documents for `ts_template_truncate_and_load_example`) into
  `{{catalog}}.silver_health.patient_billing_summary`.

## Inputs

* `flowx_testing/028_trf_003_decrypt_transform.json` — the onboarding spec (one ingestion
  flow, one transformation flow, no reconciliation flows).
* `sample_data/flowx_testing/health_usecase/patient_visits_batch1.csv` — 5-row plaintext
  fixture (`visit_id`, `patient_id`, `patient_name`, `visit_date`, `department`,

* `notebooks/00_seed_sample_data/03_seed_trf_003_decrypt_transform_data.py` — a new, dedicated
  seed notebook (per this test case's own instructions: a genuinely new fixture, not a reuse of

  `landing_visits`/`_schemas` Volumes, then lands the CSV fixture directly — the same
  "plain Auto Loader CSV, no ZIP handling needed" pattern `03_seed_cdc_002_truncate_data.py`
  already established for a materialized-view target scenario.

## Outputs

* `{catalog}.bronze_health.patient_visits_raw` — 5 rows; `billing_amount` stores AES-GCM
  ciphertext (base64-encoded binary), not plaintext, plus the usual `__framework_*` technical
  metadata columns.
* `{catalog}.silver_health.patient_billing_summary` — exactly **1 row**, one column
  (`billing_amount`), holding the decrypted-then-summed value.

## Configuration

`flowx_testing/028_trf_003_decrypt_transform.json`'s ingestion-side encryption:

```json
"target_config": {
  "cdc_load_strategy": "APPEND",
  "storage_format": "delta",
  "encrypted_columns": [
    {
      "column_name": "billing_amount",
      "output_column": "billing_amount",
      "mode": "GCM",
      "secret": {"secret_catalog": "{{catalog}}", "secret_schema": "security", "secret_key": "pii_encryption_key"}
    }
  ]
}
```

...and the transformation-side decryption immediately ahead of the aggregate:

```json
"source_inputs": [
  {
    "input_name": "patient_visits_input",
    "table": "{{catalog}}.bronze_health.patient_visits_raw",
    "is_streaming": false,
    "decrypted_columns": [
      {
        "column_name": "billing_amount",
        "output_column": "billing_amount",
        "mode": "GCM",
        "cast_to_type": "double",
        "secret": {"secret_catalog": "{{catalog}}", "secret_schema": "security", "secret_key": "pii_encryption_key"}
      }
    ]
  }
],
"transformation_sql": "SELECT sum(billing_amount) AS billing_amount FROM patient_visits_input"
```

`mode: "GCM"` matches on both sides deliberately — `aes_decrypt` is not mode-agnostic, it must
match whatever mode the column was originally encrypted with (see
[16_encryption_and_secrets.md §3](16_encryption_and_secrets.md#3-column-level-aes-encryption-and-decryption)).

### Required prerequisite: the `pii_encryption_key` UC secret must already exist

**Manual, admin-audited step — not automated by this framework, and not (re-)provisioned by this
test case.** This scenario deliberately reuses the *exact* key
[05_deployment_guide.md](05_deployment_guide.md)'s own prerequisites section already documents
provisioning for this project's other encryption scenarios — no new key is created:

```bash
databricks secrets create-scope security   # no-op if it already exists from an earlier scenario
databricks secrets put-secret security pii_encryption_key --string-value "$(openssl rand -hex 16)"
```

This must run **before** `flowx_test_trf_003_decrypt_transform_job`'s `run_pipeline_task` —
both the ingestion flow's encryption step and the transformation flow's decryption step fail
with `CryptoError`/`SecretResolutionError` until it does. If this secret was already provisioned
for an earlier scenario in this same workspace (e.g. `TC-SEC-001`, or the crypto exhaustive
suite), this scenario reuses it as-is and needs no separate provisioning step at all.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks secrets put-secret security pii_encryption_key --string-value "$(openssl rand -hex 16)"   # skip if already provisioned
databricks bundle run flowx_test_trf_003_decrypt_transform_job --target dev
```

Task chain: `setup_control_tables → seed_trf_003_decrypt_transform_data → onboard_trf_003 →
run_pipeline_task`.

## Expected results — verification logic

```sql
-- Bronze: billing_amount is ciphertext, never plaintext
SELECT billing_amount FROM {catalog}.bronze_health.patient_visits_raw LIMIT 1;
-- expect: base64-looking binary, never a value resembling "250.00"/"175.50"/etc.

-- Silver: the decrypted-then-summed value matches the fixture's known plaintext sum exactly
SELECT sum(billing_amount) FROM {catalog}.silver_health.patient_billing_summary;
-- expect: 1256.00  (== 250.00 + 175.50 + 320.25 + 99.75 + 410.50, the fixture's own known total)
```

If `encrypted_columns`/`decrypted_columns`' secret hasn't been provisioned yet, or is wrong, the
pipeline update fails fast with a `CryptoError`/`SecretResolutionError` naming the secret
coordinates — this is the expected, correct failure mode, not a bug to route around. If
`decrypted_columns[].mode`/`cast_to_type` were ever set inconsistently with how the column was
actually encrypted, `aes_decrypt` would either raise or return garbage bytes rather than the
correct plaintext — this scenario's exact-sum assertion is specifically designed to catch that
class of silent corruption, not just "is it no longer plaintext."

## Known gaps / judgment calls

* **`target_type` choice for the Silver aggregate**: this test case's own instructions describe
  the transformation as computing "running revenue totals" but leave the exact `target_type`
  unspecified. A plain `SELECT sum(...)` with no `GROUP BY`/window has no natural streaming or
  incremental form (Lakeflow streaming tables need an append-friendly, row-preserving query, not
  a single collapsing aggregate), so this scenario reads Bronze as a **batch** input
  (`is_streaming: false`) and publishes a **`materialized_view`** with
  `cdc_load_strategy: "TRUNCATE_AND_LOAD"` — a full recompute of the one-row summary on every
  pipeline update, the same pairing already established by `ts_template_truncate_and_load_example`
  (see [17_onboarding_template_reference.md §4.1](17_onboarding_template_reference.md#41-target_type-five-values)).
  A per-row "running total" (e.g. a window function) was considered and rejected as unnecessary
  complexity beyond what the SQL assertion in this test case's own spec
  (`SELECT sum(billing_amount) FROM ...`) actually requires — a single summary row.
* **Scope-vs-catalog terminology, `pii_encryption_key`**: identical to the pre-existing gap
  [`35_tc_ing_005.md`](35_tc_ing_005.md) already flags for `pgp_private_key_finance_test` — the
  `databricks secrets put-secret security pii_encryption_key ...` command above follows
  [05_deployment_guide.md](05_deployment_guide.md)'s own prerequisites-section CLI pattern
  exactly (as this test case's own instructions required, "reusing the EXISTING key"), which that
  guide's prose labels a classic workspace-level secret scope command, while the onboarding spec
  addresses this same key via the Unity Catalog three-level `{secret_catalog, secret_schema,
  secret_key}` shape, resolved via `dbutils.secrets.get(catalog=, schema=, key=)` — a different,
  newer secret system per [16_encryption_and_secrets.md §1](16_encryption_and_secrets.md#1-the-secret-reference-shape-secret_catalog-secret_schema-secret_key).
  Not introduced or resolved by this test case; follow whichever secrets CLI syntax your
  workspace/CLI version actually requires to create a Unity Catalog secret at
  `{{catalog}}.security.pii_encryption_key` — the important, framework-relevant part is the
  resulting secret coordinates, not the exact provisioning command's flag syntax.
* **No dedicated DQ/quarantine rules** were added to either flow — out of scope for what this
  test case's own detail asks for (decrypt-then-compute correctness), and adding one would have
  meant inventing an unrelated business rule with no bearing on the encryption/decryption path
  under test.
