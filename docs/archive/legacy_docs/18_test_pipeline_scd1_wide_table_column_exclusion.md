# Test Pipeline: SCD1 Wide-Table Column Exclusion (Customer Master)

> See also: [README.md](README.md) — the full Metaflow documentation set.

## Purpose

Prove that `target_config.columns_to_exclude` lets a wide source (50 columns) onboard to
SCD1 by naming only the handful of columns to *drop*, instead of hand-listing every
column to *keep* -- and that technical/audit columns (load timestamps, run ids, checksum
hashes) can change on every single run without polluting the target table's schema.
Entirely onboarding configuration -- zero changes to Metaflow's `lakeflow_framework`
engine code beyond the one shared `columns_to_exclude` feature added to `cdc/scd.py` (see
[02_cdc_load_strategies.md](02_cdc_load_strategies.md)) and exercised here.

## Responsibilities

* Land a 50-column customer master CSV extract from a
  [Unity Catalog Volume](https://docs.databricks.com/aws/en/connect/unity-catalog/volumes)
  (Bronze, `APPEND`).
* Derive one SCD1 dimension (`dim_wide_customer_scd1`) from all 50 Bronze columns via a
  plain `SELECT *` -- no manual column enumeration on either side -- while
  `target_config.columns_to_exclude` drops 5 named technical/audit columns from the
  target's schema entirely.

## Inputs

* `sample_data/sample_wide_customer_master_day1.csv` / `_day2.csv` -- 5 customers on day
  1; day 2 changes `WC001`'s `account_status`/`risk_segment` (a genuine business change),
  re-sends `WC002` with **only** its technical columns different (`batch_load_ts`,
  `etl_run_id`, `checksum_hash`, `source_extract_filename` all change; every business
  column is byte-identical to day 1), and adds a new customer `WC006` -- covering an
  update, a technical-only no-op, and an insert in one fixture pair. Generated by
  `sample_data/generate_wide_customer_scd1_fixtures.py` (`python
  sample_data/generate_wide_customer_scd1_fixtures.py` to regenerate).
* `test_specs/spec_14_wide_table_scd1_column_exclusion.json`.

## Outputs

* `{catalog}.bronze_wide_customer_ops.raw_wide_customer_master` -- the 50 source CSV
  columns, plus the framework's own ingestion-time additions (`__framework_pipeline_run_id`/
  `__framework_record_id` from `record_id_column`, `_rescued_data` from `schema_evolution_mode:
  "rescue"`, and 4 `capture_technical_metadata` columns) -- 57 columns as deployed here.
  Plus a `_quarantine` sibling for rows failing `dq_account_status_known_value`.
* `{catalog}.silver_wide_customer_ops.dim_wide_customer_scd1` -- **exactly 5 fewer
  columns than Bronze**: `batch_load_ts`, `source_extract_filename`, `etl_run_id`,
  `checksum_hash`, and `ingestion_notes` are absent from the schema, even though the
  upstream `SELECT *` included them. Every other Bronze column -- the 45 non-excluded
  source columns *and* the framework's own added columns -- passes through untouched;
  `columns_to_exclude` only ever removes what it names.

## Configuration

See `test_specs/spec_14_wide_table_scd1_column_exclusion.json` in full. The only
mechanism new to this pipeline is `target_config.columns_to_exclude` on the SCD1
transformation flow:

```json
{
  "cdc_load_strategy": "SCD1",
  "target_config": {
    "primary_keys": ["customer_id"],
    "sequence_by_column": "updated_at",
    "columns_to_exclude": ["batch_load_ts", "source_extract_filename", "etl_run_id", "checksum_hash", "ingestion_notes"]
  }
}
```

Everything else -- `source_type: gcs_autoloader`, `cdc_load_strategy: APPEND`/`SCD1`,
`primary_keys`/`sequence_by_column` -- is already documented in
[01_control_metadata_schema.md](01_control_metadata_schema.md) and
[02_cdc_load_strategies.md](02_cdc_load_strategies.md).

## Main execution flow

1. `resources/sample_pipelines_job.yml`: `setup_control_tables` -> `seed_sample_data` ->
   `onboard_spec_14` -> `run_wide_customer_scd1_exclusion_pipeline` ->
   `apply_governance_wide_customer_scd1_exclusion`.
2. The pipeline itself (`resources/sample_pipelines.yml`'s
   `wide_customer_scd1_exclusion_pipeline`) attaches the exact same
   `notebooks/03_engine/03_lakeflow_declarative_pipeline.py` used by every other group --
   only its `dataflow.group.id` configuration value differs.
3. First run (day 1 data only): `dim_wide_customer_scd1` has 5 rows, one per customer,
   with none of the 5 excluded columns in its schema (confirmed live -- 57 Bronze columns,
   52 Silver columns).
4. Drop `sample_wide_customer_master_day2.csv` into
   `/Volumes/{catalog}/landing/wide_customer_master_zone/incoming/` and re-run the
   pipeline: `WC001`'s row is overwritten in place with `account_status = 'SUSPENDED'`;
   `WC002`'s row is overwritten too (its `updated_at` did advance) but every visible
   business column is unchanged from day 1; `WC006` is inserted. The target's column set
   never changes -- the day 2 technical-column values for `WC001`/`WC002`/`WC006` never
   reach the table at all.

## Design decisions

* **`except_column_list`, not a SQL projection trick.** `transformation_sql` is a bare
  `SELECT * FROM dim_wide_customer_scd1_src` -- the exclusion happens at the
  `dlt.apply_changes(..., except_column_list=...)` layer (`cdc/scd.py::_build_except_column_list`),
  not by hand-writing a 45-column `SELECT` list. This is the actual point of the feature:
  a spec author names the 5 columns they *don't* want, not the 45 they do.
* **SCD1 has no per-column diff to "skip."**
  [`apply_changes(stored_as_scd_type="1")`](https://docs.databricks.com/aws/en/dlt/cdc)
  always overwrites a key's row with the latest values by `sequence_by_column` --
  there's no native concept of "only update if something changed." `columns_to_exclude`
  therefore doesn't change *whether* an upsert happens for `WC002`'s technical-only
  reload; it changes *what columns exist in the target at all*. See
  [02_cdc_load_strategies.md](02_cdc_load_strategies.md) for the same point made against
  SCD2/SCD3, where `columns_to_exclude` and `columns_to_check` are two independent,
  composable levers.
* **`updated_at` (business) is deliberately a different column than `batch_load_ts`
  (technical).** Conflating "when did the source record last change" with "when did this
  ETL run execute" is a common real-world mistake -- it would make every re-extract look
  like a business change. Keeping them separate, and excluding only the technical one
  from the target, is the realistic shape of this problem.

## Error handling

Same framework-wide typed-exception conventions as every other flow --
`FrameworkConfigError` for malformed JSON/config, `CdcStrategyError` for a misconfigured
SCD strategy. `onboarding/spec_validator.py` additionally rejects a `columns_to_exclude`
entry that overlaps `primary_keys`/`sequence_by_column`/`columns_to_check` at onboarding
time (`apply_changes` needs those columns present), rather than failing at
pipeline-deployment time.

## Extension points

Add more technical columns to exclude, or apply the same `columns_to_exclude` pattern to
an SCD2/SCD3 target, by editing `target_config` alone -- no code change required.

## Example usage

```bash
databricks bundle run sample_pipelines_job --profile dev
# then, after copying sample_wide_customer_master_day2.csv into the landing volume:
databricks bundle run wide_customer_scd1_exclusion_pipeline --profile dev
databricks bundle run sample_pipelines_job --profile dev  # re-applies governance idempotently
```

## Relevant tests

`tests/integration/test_pipeline_scd1_wide_table_column_exclusion.py` -- target table
exists with exactly 5 fewer columns than Bronze (and the 5 excluded columns absent by
name specifically, not just by count), one row per customer (no SCD1 history), day 2's
business-attribute overwrite for `WC001`, day 2's technical-only reload leaving `WC002`'s
visible data unchanged, and day 2's insert of `WC006`.
