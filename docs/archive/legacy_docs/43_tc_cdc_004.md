# Test Pipeline: SCD Type 2 Full History & Active Companion View (TC-CDC-004)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 2, TC-CDC-004), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § SCD2](02_cdc_load_strategies.md#scd2).

## Purpose

Prove that `target_config.cdc_load_strategy: "SCD2"` genuinely opens a **new history row**
(native `__START_AT`/`__END_AT` tracking columns) the moment a *tracked* column changes for an
existing key -- rather than overwriting the row in place the way `SCD1` would -- and that the
framework's auto-generated `<target_table>_current` companion **table**
(`cdc/scd.py::register_scd2_reporting_view`) reports only the single currently-active version
per key. A second, narrower thing this scenario also proves: `target_config.columns_to_check`
genuinely *scopes* what counts as a change -- advancing `sequence_by_column` alone, with the
tracked column unchanged, must **not** open a spurious new version.

## Responsibilities

* One `ingestion_flow` (`df_cdc_004_employee_scd2_ingest`), `source_type: "autoloader"`,
  `target_config.cdc_load_strategy: "SCD2"` -- SCD2 is valid directly on an ingestion flow (only
  `SCD3` is transformation-only, see [02_cdc_load_strategies.md](02_cdc_load_strategies.md)), so
  this scenario needs no separate transformation step to exercise it.
* `primary_keys: ["employee_id"]`, `sequence_by_column: "updated_at"`, `columns_to_check:
  ["dept_id"]` -- history tracking is scoped to department transfers only.
* Two CSV "day" extracts landed in the same incoming Volume before the pipeline's one triggered
  run: `E101` moves from dept `D1` to `D2` (must open a new version); `E102`/`E103` are re-sent
  with an advanced `updated_at` but an **unchanged** `dept_id` (must *not* open a new version);
  `E104` is a new hire appearing only in the day-2 extract (plain insert). `dlt.apply_changes`
  orders strictly by `sequence_by_column`, not file arrival order, so landing both extracts
  before a single run is equivalent to two separate daily runs for this scenario's purposes.

## Outputs

* `{{catalog}}.silver_hr.dim_employee_scd2` -- the real SCD2 target, a genuine Lakeflow
  Streaming Table regardless of its declared `target_type` (`dlt.apply_changes` requires one --
  see [02_cdc_load_strategies.md](02_cdc_load_strategies.md#target_type-is-orthogonal-to-cdc_load_strategy)).
  Exactly 2 rows for `employee_id = 'E101'`: one closed (`__END_AT` populated, `dept_id = 'D1'`),
  one open (`__END_AT IS NULL`, `dept_id = 'D2'`). Exactly 1 row each for `E102`/`E103`/`E104`
  (no spurious version for the two untracked-column bumps).
* `{{catalog}}.silver_hr.dim_employee_scd2_current` -- the auto-generated companion **table**
  (a real `@dlt.table`, not a `@dlt.view` -- see the two live-deployment bugs this design
  specifically fixes, documented in
  [02_cdc_load_strategies.md § SCD2](02_cdc_load_strategies.md#scd2)). Exactly 1 row for
  `E101`, with `dept_id = 'D2'`.
* `__framework_hash_key`/`__framework_hash_value` and `delta.enableChangeDataFeed = "true"` on
  the main target (every SCD2-dispatched target gets both, per
  [02_cdc_load_strategies.md § the hash-key/hash-value framework](02_cdc_load_strategies.md#the-hash-keyhash-value-framework)).

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Full history: 2 rows for E101 (one closed, one open)
SELECT dept_id, __START_AT, __END_AT
FROM {catalog}.silver_hr.dim_employee_scd2
WHERE employee_id = 'E101'
ORDER BY __START_AT;
-- expect: (D1, <day1 ts>, <day2 ts>), (D2, <day2 ts>, NULL)

SELECT count(*) FROM {catalog}.silver_hr.dim_employee_scd2 WHERE employee_id = 'E101';
-- expect: 2

-- Untracked-column bump does not open a spurious version
SELECT employee_id, count(*) FROM {catalog}.silver_hr.dim_employee_scd2
WHERE employee_id IN ('E102', 'E103') GROUP BY employee_id;
-- expect: 1 row each

-- Companion "current" table reports only the active D2 row
SELECT dept_id FROM {catalog}.silver_hr.dim_employee_scd2_current WHERE employee_id = 'E101';
-- expect: D2
```

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture matches this scenario's exact
  requirement (a specific employee/department transfer plus an untracked-column-only bump on
  two other keys, all verification-critical), so 2 new CSV fixtures and 1 new dedicated seed
  notebook were added, following the exact pattern `flowx_test_cdc_001_append_job` already
  established (`03_seed_cdc_001_append_data.py`) rather than extending
  `02_seed_flowx_testing_data.py` or the pre-existing `ea_usecase` employee fixtures (those
  use a different, static single-snapshot shape with no day-1/day-2 department transfer and no
  `E101`/`D1`/`D2` naming the test case specifically calls for).
* **`columns_to_check` scoping folded into the same fixture.** Rather than building a second,
  separate scenario for `columns_to_check`, `E102`/`E103` re-sending an advanced `updated_at`
  with an unchanged `dept_id` in the day-2 extract cheaply proves that lever within this same
  test case, at no extra fixture cost.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column for TC-CDC-004 names a second `run_observability_task` step, but per
  `TESTING_STATUS.md`'s framing and every other real scenario built so far (including sibling
  `flowx_test_cdc_001_append_job`), `TESTING_PLAN.md` is a planned/aspirational matrix, not a
  literal build spec -- observability is opt-in, wired via a spec's own `observability[]` array
  plus a separate job, as scenario 100's `dlt_observability_job.yml` does. This build follows
  the real `setup_control_tables → seed → onboard → run_pipeline` convention instead.
* **Companion object is a table, not a view.** The TC detail line says "companion view"; per
  [02_cdc_load_strategies.md](02_cdc_load_strategies.md#scd2) the framework deliberately
  registers `dim_employee_scd2_current` as a genuine `@dlt.table` (not a `@dlt.view`) -- this
  doc and its SQL assertions use the real, live object name/kind rather than the TC's
  colloquial "view" wording.
