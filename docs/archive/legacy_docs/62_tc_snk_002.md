# Test Pipeline: TC-SNK-002 -- Pure Sink Export Without Table Materialization

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 8, TC-SNK-002), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md), [23_lakeflow_sinks.md](23_lakeflow_sinks.md) (full `sink`/`external_sink` mechanics).

## Purpose

Prove `target_type: "sink"` (`engine/sink_registration.py::register_sink_target`) writes a
flow's streaming output directly to an egress Volume via a genuine `dlt.create_sink` +
`@dlt.append_flow` -- and, critically, that **no Delta table is ever registered in Unity
Catalog for the sink itself**. This is the structural distinction from `target_type:
"external_sink"` (TC-SNK-001): `external_sink` materializes a real, governed table *and*
exports it; `sink` never materializes anything on the clean/main side -- the flow's own
staged (quarantine-filtered) `@dlt.view` feeds the sink directly. See
[23_lakeflow_sinks.md](23_lakeflow_sinks.md) for the full mechanics and the
`"sink"` vs `"external_sink"` comparison table.

## Responsibilities

* Land a small, 5-row IoT sensor readings CSV fixture and ingest it via Auto Loader into a
  genuine bronze streaming table, `{catalog}.bronze_iot_snk002.sensor_readings_raw`
  (`cdc_load_strategy: "APPEND"` -- immutable sensor readings, no dedup/history needed). This
  table **is** queryable -- it is the downstream sink flow that is not.
* A same-spec `transformation_flow` (`ts_snk_002_pure_sink_export`) reads that bronze table as
  a streaming `source_inputs` entry and sets `target_type: "sink"` with `sink_config: {"format":
  "delta", "path": "/Volumes/{{catalog}}/egress_iot/partner_drops/"}` -- writing every row
  straight to the partner egress Volume as Delta files, with **no** `@dlt.table` registered for
  this flow at all.
* Needs no dependency on any other already-onboarded scenario -- its own job runs
  `setup_control_tables -> seed -> onboard -> run_pipeline` end to end from a clean environment.

## Inputs

* `flowx_testing/040_snk_002_pure_sink.json` -- one ingestion flow
  (`df_snk_002_iot_sensor_ingest`) + one transformation flow (`ts_snk_002_pure_sink_export`, the
  pure sink), no `reconciliation_flows`.
* `sample_data/flowx_testing/iot_usecase/sensor_readings_snk002.csv` -- 5 IoT sensor
  readings (`device_id`, `sensor_type`, `reading_value`, `event_ts`, `region`) across 5 devices
  and 3 regions.
* `notebooks/00_seed_sample_data/03_seed_snk_002_pure_sink_data.py` -- provisions
  `{catalog}.iot_snk002` (landing schema + `landing_sensor`/`_schemas` Volumes),
  `{catalog}.bronze_iot_snk002` (the bronze target schema), and `{catalog}.egress_iot` +
  its `partner_drops` Volume (the sink's actual write destination -- unlike a normal table
  target, this Volume is never auto-provisioned by the pipeline itself, so it must be created
  ahead of time, same as scenario 001/002/003's own `egress_ea`/`export_zips` precedent), then
  lands the fixture file into the incoming landing Volume.

## Outputs

* `{catalog}.bronze_iot_snk002.sensor_readings_raw` -- 5 rows, the genuine bronze table (plus
  the usual `__framework_*` technical-metadata columns).
* `/Volumes/{catalog}/egress_iot/partner_drops/` -- one or more Delta data files written
  directly by `@dlt.append_flow` -> `dlt.create_sink(format="delta", ...)`, containing the same
  5 rows' `device_id`/`sensor_type`/`reading_value`/`event_ts`/`region` columns.
* **No table** named `partner_drops_sink` (or any other name) is ever registered under
  `{catalog}.egress_iot` in `information_schema.tables` -- the entire point of `target_type:
  "sink"` (`register_sink_target` never calls `dlt.create_streaming_table`/`@dlt.table` for the
  sink's own clean/main side; see [23_lakeflow_sinks.md](23_lakeflow_sinks.md)).

## Configuration

`flowx_testing/040_snk_002_pure_sink.json`'s pure-sink transformation flow
(`ts_snk_002_pure_sink_export`):

```json
{
  "flow_step_id": "ts_snk_002_pure_sink_export",
  "dataflow_id": "df_snk_002_iot_sensor_ingest",
  "target_catalog": "{{catalog}}",
  "target_schema": "egress_iot",
  "target_table": "partner_drops_sink",
  "target_type": "sink",
  "source_inputs": [
    {
      "input_name": "sensor_readings_for_sink",
      "table": "{{catalog}}.bronze_iot_snk002.sensor_readings_raw",
      "is_streaming": true
    }
  ],
  "transformation_sql": "SELECT device_id, sensor_type, reading_value, event_ts, region FROM sensor_readings_for_sink",
  "target_config": {
    "cdc_load_strategy": "APPEND",
    "sink_config": {
      "format": "delta",
      "path": "/Volumes/{{catalog}}/egress_iot/partner_drops/"
    }
  }
}
```

`target_catalog`/`target_schema`/`target_table` are still required fields on the schema (used
to build the internal sink node name `_partner_drops_sink_sink` and the append-flow name
`partner_drops_sink_sink_flow`), but -- unlike every other `target_type` -- they never resolve
to a real Unity Catalog object here; no `CREATE SCHEMA`/`CREATE TABLE` happens for
`egress_iot`/`partner_drops_sink` at all. `cdc_load_strategy` is present (schema-required) but
functionally inert for a `"sink"` flow -- it is never consulted for CDC dispatch, only carried
as a label on the `sink_registration` structured log event.

## Expected results -- simulation notes

**SQL/file-system assertions** (after a run, replace `{catalog}` with your actual target
catalog):

```sql
-- Bronze ingestion table: exactly 5 rows
SELECT count(*) FROM {catalog}.bronze_iot_snk002.sensor_readings_raw;
-- expect: 5

-- The sink target NEVER appears as a table anywhere in the catalog -- this is the assertion
-- this scenario exists to prove
SELECT table_catalog, table_schema, table_name
FROM {catalog}.information_schema.tables
WHERE table_schema = 'egress_iot';
-- expect: 0 rows (schema exists as a container for the Volume, but hosts no table)

SELECT table_catalog, table_schema, table_name
FROM {catalog}.information_schema.tables
WHERE table_name LIKE '%partner_drops%';
-- expect: 0 rows anywhere in the catalog
```

```bash
# Egress Volume actually received exported Delta files
databricks fs ls dbfs:/Volumes/{catalog}/egress_iot/partner_drops/ --profile <PROFILE>
# expect: a _delta_log/ directory plus one or more .parquet data files -- Delta files written
# directly by the append_flow, readable back with a plain
# spark.read.format("delta").load("/Volumes/{catalog}/egress_iot/partner_drops/") if you want to
# spot-check the 5 rows' content (this ad-hoc read is outside the framework -- there is no
# managed/governed table object backing this path).
```
