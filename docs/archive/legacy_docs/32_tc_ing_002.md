# Test Pipeline: ZIP Source Purge Retention Policy (TC-ING-002)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove `source_zip_handling.delete_source_after_extract: true` (§3 of
[01_control_metadata_schema.md](01_control_metadata_schema.md)) actually purges a landed ZIP
archive from its incoming Volume once its contents have been successfully extracted --
distinct from the `false` default demonstrated elsewhere in this repo (scenario 001's `ea_*.zip`
archives, and scenario 100's `customer_plain_raw` flow, both set it `false` explicitly so their
source archives persist for repeated local test runs). This is a single-flow, ingestion-only
scenario -- no CDC dispatch, no transformation, no reconciliation.

## Responsibilities

* Land a single ZIP archive, `orders_batch_01.zip`, in
  `/Volumes/{catalog}/sales/landing_zip/incoming/`.
* Extract it via Auto Loader's `source_zip_handling` into
  `/Volumes/{catalog}/sales/landing_zip/extracted/orders/`.
* Ingest the extracted CSV into `{catalog}.bronze_sales.orders_raw` (`cdc_load_strategy:
  "APPEND"` -- an immutable batch of order records, no upsert/history concept needed).
* Verify the source ZIP is gone from `incoming/` post-extraction, the extracted CSV is present
  in `extracted/orders/`, and `orders_raw` holds the expected row count.

## Inputs

* `flowx_testing/011_ing_002_zip_retention.json` -- ingestion-only onboarding spec (no
  `transformation_flows`/`reconciliation_flows`), one flow:
  `df_ing_002_zip_retention_orders_ingest`.
* `sample_data/sample_raw_orders.csv` -- reused as-is (10 rows: `order_id`, `order_ts`,
  `account_id`), no new sample data needed for this scenario. Re-zipped on-cluster into
  `orders_batch_01.zip` by `notebooks/00_seed_sample_data/03_seed_ing_002_zip_retention_data.py`
  (same in-memory-buffer-then-single-sequential-write pattern
  `02_seed_flowx_testing_data.py` already uses for the `ea_*.zip` archives -- see
  [12_zip_ingestion_pipeline.md](12_zip_ingestion_pipeline.md)'s platform-gotchas section for why
  a pre-built `.zip` can't just be synced through the bundle instead).

## Outputs

* `{catalog}.bronze_sales.orders_raw` (Delta, streaming table) -- 10 rows, one per source order.
* `/Volumes/{catalog}/sales/landing_zip/incoming/orders_batch_01.zip` -- **absent** after a
  successful pipeline update (this is the behavior under test).
* `/Volumes/{catalog}/sales/landing_zip/extracted/orders/orders_batch_01.csv` -- present, the
  extracted member file Auto Loader read from.

## Configuration

`flowx_testing/011_ing_002_zip_retention.json`'s one ingestion flow:

```json
"source_config": {
  "path": "/Volumes/{{catalog}}/sales/landing_zip/extracted/orders/",
  "format": "csv",
  "schema_location": "/Volumes/{{catalog}}/sales/_schemas/orders/",
  "reader_options": {"header": "true", "cloudFiles.inferColumnTypes": "true"},
  "capture_technical_metadata": true,
  "source_zip_handling": {
    "enabled": true,
    "source_zip_path": "/Volumes/{{catalog}}/sales/landing_zip/incoming/",
    "zip_file_pattern": "orders_batch_01.zip",
    "target_volume_path": "/Volumes/{{catalog}}/sales/landing_zip/extracted/orders/",
    "delete_source_after_extract": true
  }
},
"target_config": {"cdc_load_strategy": "APPEND", "storage_format": "delta"}
```

## Expected results -- verification logic

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- orders_raw: expected row count (10, one per source CSV row)
SELECT COUNT(*) FROM {catalog}.bronze_sales.orders_raw;
```

**Volume assertions** (via `dbutils.fs.ls` or the Catalog Explorer UI):

```python
# orders_batch_01.zip removed from incoming/ after a successful extract
assert not any(
    f.name == "orders_batch_01.zip"
    for f in dbutils.fs.ls(f"/Volumes/{catalog}/sales/landing_zip/incoming/")
)

# extracted CSV exists in the extract Volume
assert any(
    f.name.endswith(".csv")
    for f in dbutils.fs.ls(f"/Volumes/{catalog}/sales/landing_zip/extracted/orders/")
)
```
