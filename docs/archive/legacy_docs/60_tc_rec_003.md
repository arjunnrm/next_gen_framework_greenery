# Test Pipeline: Pre-Computed Hash Matcher (`hash_precomputed`) Plan Assertion (TC-REC-003)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 7, TC-REC-003), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md), [07_reconciliation.md § Hash-first matching, and why](07_reconciliation.md#hash-first-matching-and-why), [02_cdc_load_strategies.md § The hash-key/hash-value framework](02_cdc_load_strategies.md#the-hash-keyhash-value-framework).

## Purpose

Prove that `reconciliation_flows[].source_config`/`target_configs[].hash_precomputed: true`
genuinely reuses an already-materialized `__framework_hash_key`/`__framework_hash_value` pair
instead of recomputing it inline, by:

1. Building two independent CDC-dispatched targets (`{{catalog}}.silver_sales.orders_src` /
   `orders_tgt`), each carrying real, physically-stored `__framework_hash_key`/
   `__framework_hash_value` columns (`SCD1` + `generate_hash_columns: true` — see
   [02_cdc_load_strategies.md §4a](01_control_metadata_schema.md#4a-hash-keyvalue--a-framework-design-principle)).
2. Reconciling them against each other with `hash_precomputed: true` on **both** sides.
3. Showing, via a real `EXPLAIN` physical plan against the two persisted tables, exactly what
   `matcher.py`'s single-column `__framework_hash_key` equi-join looks like once the hash columns
   are trusted as-is — and, by contrast, what the extra `sha2(concat_ws(...))` expression node
   looks like when a hash has to be recomputed inline instead.

**A deliberate scale-down from `TESTING_PLAN.md`'s own description.** `TESTING_PLAN.md` frames
TC-REC-003 around "large datasets (1M rows)" and an "Execution completes within SLA" assertion.
This build uses **24 rows per side** instead — enough to prove the *mechanism* (the join
genuinely runs on `__framework_hash_key`, the hash columns are genuinely reused rather than
recomputed, and the matcher genuinely classifies `MATCHED`/`VALUE_DRIFT`/`MISSING_IN_TARGET`/
`MISSING_IN_SOURCE` correctly), not the performance claim. **No SLA/timing assertion is made
anywhere in this doc — it would not mean anything at 24 rows.** See "Build notes / judgment
calls" below for why this substitution is the right one.

## Where this is actually implemented (read before building or debugging this scenario)

Confirmed by reading `reconciliation/matcher.py` in full this pass:

* `prepare_dataset_for_matching(df, match_keys, compare_columns, hash_precomputed, ...)` is the
  **only** place `hash_precomputed` is consulted. When `True`, it just asserts
  `__framework_hash_key`/`__framework_hash_value` are already present on `df` (raising
  `FrameworkConfigError` if not — defense in depth, since a hand-edited control-table row could
  claim `hash_precomputed: true` for a table that was never actually CDC-dispatched) and returns
  `df` unchanged. When `False`, it calls `cdc/hashing.py::compute_hash_columns(df, match_keys,
  resolved_compare_columns)` to add both columns via a fresh `sha2(concat_ws('||', ...), 256)`
  expression.
* `match_reconciliation_target(source_df, target_df, ...)` — the function that actually
  joins — runs **identically regardless of `hash_precomputed`**:
  `source_narrow.join(target_narrow, on=HASH_KEY_COLUMN, how="full_outer")`. The join is always
  a single-column equality on `__framework_hash_key`. **`hash_precomputed` does not change which
  column the join runs on — it changes whether that column arrives as a stored physical column
  (read straight off the table scan) or a freshly-computed expression evaluated immediately
  upstream of the join.** This is the one nuance worth being precise about: the "cost avoidance"
  `02_cdc_load_strategies.md` describes is a `Project`-node (the `sha2(concat_ws(...))`
  expression) that `hash_precomputed: true` lets the matcher skip entirely — not a different join
  strategy or join key. See "Expected results" below for what this looks like in a real
  `EXPLAIN` plan.

## Responsibilities

* Two `ingestion_flows`, each `source_type: "autoloader"` (plain CSV), `cdc_load_strategy:
  "SCD1"`, `primary_keys: ["order_id"]`, `generate_hash_columns: true` (explicit, though already
  the default for any CDC-dispatched strategy) — landing independently into
  `{{catalog}}.silver_sales.orders_src` and `orders_tgt`.
* One `reconciliation_flow` (`recon_rec_003_orders_precomputed_hash`) comparing `orders_src`
  (source) against `orders_tgt` (target), both sides `hash_precomputed: true`,
  `comparison_direction: "both"` — both self-heals (`source_to_target`: append
  missing/drifted source rows into `orders_tgt`) **and** audits (`target_to_source`: report,
  never write, target-only rows).

## Configuration

`flowx_testing/038_rec_003_precomputed_hash.json`'s reconciliation flow:

```json
{
  "reconciliation_id": "recon_rec_003_orders_precomputed_hash",
  "source_config": {
    "type": "table",
    "table": "{{catalog}}.silver_sales.orders_src",
    "read_mode": "batch",
    "hash_precomputed": true
  },
  "target_configs": [
    {
      "target_id": "orders_tgt",
      "type": "table",
      "table": "{{catalog}}.silver_sales.orders_tgt",
      "read_mode": "batch",
      "hash_precomputed": true,
      "comparison_direction": "both",
      "append_target_table": "{{catalog}}.silver_sales.orders_tgt"
    }
  ],
  "match_keys": ["order_id"],
  "compare_columns": ["status", "amount"],
  "generate_surrogate_key": false,
  "error_handling": {"on_failure": "warn"}
}
```

Both `ingestion_flows[].target_config` entries are identical (`SCD1`, `primary_keys:
["order_id"]`, `sequence_by_column: "order_date"`, `generate_hash_columns: true`,
`storage_format: "delta"`) — the two targets are independently CDC-dispatched, so each one's own
`__framework_hash_key`/`__framework_hash_value` is computed by `dq/quarantine.py`
(`_apply_hash_and_surrogate_key_columns`), **not** by the reconciliation flow itself; the
reconciliation flow's `hash_precomputed: true` only ever consumes what already exists.

`compare_columns: ["status", "amount"]` at the reconciliation-flow level is independent of each
target's own upstream comparison-column resolution (which, with no `columns_to_check` set,
covers every applicable column) — it only scopes what
`mismatch_detail_df`/`reconciliation_mismatch_log.differing_columns_json` reports per drifted
record, and whether `hash_equal` is checked at all (non-empty → real hash-value equality;
empty → forced `true`, key-presence-only matching). `error_handling.on_failure: "warn"` mirrors
scenario 003's own choice, so a transient failure logs rather than hard-fails the job.

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Row counts
SELECT count(*) FROM {catalog}.silver_sales.orders_src;   -- expect: 24
SELECT count(*) FROM {catalog}.silver_sales.orders_tgt;   -- expect: 24 (23 landed + 1 self-healed)

-- reconciliation_run_log: the classification this scenario exists to prove
SELECT matched_count, missing_in_target_count, value_drift_count, missing_in_source_count, appended_count, status
FROM {catalog}.config.reconciliation_run_log
WHERE reconciliation_id = 'recon_rec_003_orders_precomputed_hash' AND target_id = 'orders_tgt'
ORDER BY run_at DESC LIMIT 1;
-- expect: matched_count=22, missing_in_target_count=2, value_drift_count=1,
--         missing_in_source_count=1, appended_count=2, status='SUCCESS'

-- reconciliation_mismatch_log: per-record detail
SELECT match_key_values_json, mismatch_type, differing_columns_json
FROM {catalog}.config.reconciliation_mismatch_log
WHERE reconciliation_id = 'recon_rec_003_orders_precomputed_hash'
ORDER BY detected_at DESC LIMIT 3;
-- expect: O2023/VALUE_DRIFT (status differs), O2024/MISSING_IN_TARGET, O2099/MISSING_IN_SOURCE
```

**Plan assertion — what a hash-precomputed join genuinely looks like.** This is the real check
`TESTING_PLAN.md` asks for; run it directly against the two persisted tables (no notebook
instrumentation needed, since both already carry real `__framework_hash_key` columns):

```sql
EXPLAIN
SELECT s.order_id AS src_order_id, t.order_id AS tgt_order_id, s.__framework_hash_key
FROM   {catalog}.silver_sales.orders_src s
FULL OUTER JOIN {catalog}.silver_sales.orders_tgt t
       ON s.__framework_hash_key = t.__framework_hash_key;
```

Expected physical plan shape (exact join strategy/exchange nodes will vary with Spark version
and table size — at 24 rows Spark will likely pick a broadcast or sort-merge join either way —
but the **join condition** and the **absence of any hash-computing expression** are the two
load-bearing details):

```
== Physical Plan ==
*(3) SortMergeJoin FullOuter, (__framework_hash_key#123 = __framework_hash_key#456)
:- *(1) Sort [__framework_hash_key#123 ASC NULLS FIRST], false, 0
:  +- *(1) ColumnarToRow
:     +- FileScan delta silver_sales.orders_src[order_id#...,__framework_hash_key#123,...] ...
+- *(2) Sort [__framework_hash_key#456 ASC NULLS FIRST], false, 0
   +- *(2) ColumnarToRow
      +- FileScan delta silver_sales.orders_tgt[order_id#...,__framework_hash_key#456,...] ...
```

The join condition is a single `(__framework_hash_key = __framework_hash_key)` equality — never
`order_id` or any multi-column `match_keys` condition — and `__framework_hash_key` comes straight
off each `FileScan delta` node with **no `Project`/`sha2`/`concat_ws` expression anywhere in the
tree**, because `hash_precomputed: true` trusts it as an already-materialized physical column.

**Contrast — what the plan looks like when the hash has to be recomputed inline**, i.e. what
`cdc/hashing.py::compute_hash_columns` inserts upstream of the identical join when
`hash_precomputed: false` (illustrated here directly against `orders_src`, recomputing
`__framework_hash_key` from its own `match_keys` the same way `prepare_dataset_for_matching`
would if it couldn't trust the stored column):

```sql
EXPLAIN
SELECT order_id, sha2(concat_ws('||', CAST(order_id AS STRING)), 256) AS recomputed_hash_key
FROM   {catalog}.silver_sales.orders_src;
```

Expected: a `Project` node — `Project [order_id#..., sha2(concat_ws(||,
cast(order_id#... as string)), 256) AS recomputed_hash_key#...]` — sitting directly above the
`FileScan delta` node. **This is the exact expression node `hash_precomputed: true` lets the
matcher skip on both sides of every reconciliation join**, at any table size — the join itself
(`SortMergeJoin`/`BroadcastHashJoin` on `__framework_hash_key`) is identical either way, which is
also why hash-first matching "doesn't require precomputation to work" (`07_reconciliation.md`) —
precomputation is purely this `Project` node's avoidance, not a different join mechanism.

## Build notes / judgment calls

* **Scaled down from 1M rows to 24 rows per side — and the SLA claim is dropped, not
  approximated.** `TESTING_PLAN.md`'s original framing ("Execution completes within SLA") is a
  performance claim that only means something at real scale against real concurrent workload;
  asserting *any* timing number against a 24-row fixture would be theater, not verification. What
  a small fixture *can* genuinely prove — and what this doc asserts instead — is the mechanism:
  the join really runs on `__framework_hash_key`, the hash columns really come from a stored
  column rather than a recomputed expression, and the matcher's four-way classification really
  works. The `EXPLAIN` plan comparison above is the mechanism-level equivalent of the original
  SLA assertion.
* **Two independent ingestion flows, not one table read twice.** `hash_precomputed: true` is
  only interesting to prove when both sides are genuinely separate CDC-dispatched targets, each
  with its own independently-computed `__framework_hash_key` — reconciling a table against
  itself would trivially match every row and never exercise `VALUE_DRIFT`/`MISSING_*`
  classification at all.
* **New fixture, not a reuse.** No existing seeded fixture carries two independently-landed
  order populations with a deliberate drift/missing/extra mix under `silver_sales.orders_src`/
  `orders_tgt` (the exact object names `TESTING_PLAN.md` itself specifies for this test case), so
  2 small new CSV fixtures (24 rows each) and 1 new dedicated seed notebook were added — kept
  separate from TC-TRF-002's own `sales_usecase`/`bronze_sales`/`silver_sales.all_global_orders`
  fixtures and pipeline, which this scenario's tables sit alongside in the same `silver_sales`
  schema without overlapping (schema creation is idempotent `CREATE SCHEMA IF NOT EXISTS`).
* **`SCD1` chosen for both ingestion flows** (not `SCD2`/`FULL_SNAPSHOT_CDC`) — any
  CDC-dispatched strategy exercises the identical hash-generation code path
  (`_apply_hash_and_surrogate_key_columns` doesn't branch on which strategy triggered it); `SCD1`
  is the simplest to reason about for a single-batch load with no history/delete-marker noise,
  consistent with TC-SEC-002's own choice for the same reason.
* **No DQ rules, no governance tags, no encryption** — this scenario is scoped to the
  `hash_precomputed` matcher path specifically; DQ (`TC-DQ-*`), governance (`TC-GOV-*`), and
  encryption (`TC-SEC-001`/`TC-SEC-003`) are separate, already-tracked test modules.
