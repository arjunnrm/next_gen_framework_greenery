# Test Pipeline: DQ Action `drop` Silent Row Filtering (TC-DQ-002)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 4, TC-DQ-002), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove that a `dq_config` rule with `action: "drop"` **silently filters** a violating row out
of the stream -- the row never lands in the target table, no companion `_quarantine` table is
ever created, and the pipeline update itself does not fail. `"drop"` maps onto a native
Lakeflow expectation (`expect_or_drop`, not `expect`/`expect_or_fail`), so unlike `"warn"`
(TC-DQ-001, `docs/50_tc_dq_001.md`, row still lands) or `"fail"` (TC-DQ-003, aborts the
update) or `"quarantine"` (TC-DQ-004, this framework's own extension that reroutes the row to
a companion table), a `"drop"` violation leaves no trace in the target table or in any
additional control-table-registered object at all. This scenario also proves the negative
case: no `<table>_quarantine` table is ever created, since quarantine table registration is
conditional on at least one `rules[]` entry having `action == "quarantine"` (see
`docs/01_control_metadata_schema.md` §5 / `docs/17_onboarding_template_reference.md` §4.7) --
this spec has none.

## Responsibilities

* Land 10 transaction rows (scaled down from `TESTING_PLAN.md`'s 100/10 template to a minimal
  10/2, per this pass's "minimal, real, onboardable" convention) as a single plain CSV in
  `/Volumes/{{catalog}}/txns/landing_dq_drop/` -- 2 of the 10 (`TXN-2003` amount `-25.00`,
  `TXN-2005` amount `0.00`) violate the rule under test.
* One `ingestion_flow` (`df_dq_002_txns_drop_ingest`) with `source_type: "autoloader"` and
  exactly one `dq_config.rules[]` entry: `{"rule_id": "dq_txn_amount_positive_drop",
  "expression": "amount > 0", "action": "drop"}`.
* `cdc_load_strategy: "APPEND"` -- this scenario is about DQ action semantics, not CDC
  behavior, so the simplest load strategy (plain streaming append, no `primary_keys`) keeps
  the flow focused on the one thing under test (same convention as TC-DQ-001/TC-ING-001).

## Inputs

* `flowx_testing/030_dq_002_drop.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/flowx_testing/txns_usecase/txns_dq_drop.csv` (10 rows, columns
  `txn_id, account_id, amount, currency, txn_date, merchant`) -- new fixture, added alongside
  this test case's build (see Build notes).
* `notebooks/00_seed_sample_data/03_seed_dq_002_drop_data.py` -- a **new, dedicated** seed
  notebook (kept separate from `02_seed_flowx_testing_data.py` and every other test case's
  own seed notebook, e.g. `03_seed_dq_001_warn_data.py`) that provisions the `txns`/
  `bronze_txns` schemas and `landing_dq_drop`/`_schemas` Volumes, then copies the fixture CSV
  directly into the landing Volume (no ZIP handling needed for this scenario).

## Outputs

* `{{catalog}}.bronze_txns.txns_clean_raw` -- exactly 8 rows (10 landed minus the 2 that fail
  `amount > 0`) -- `"drop"` silently excludes `TXN-2003` and `TXN-2005` before they ever reach
  the target table.
* No `{{catalog}}.bronze_txns.txns_clean_raw_quarantine` table -- `dq_config` here carries no
  `action: "quarantine"` rule, so `register_main_and_quarantine_tables` never registers one;
  confirmed independently via `information_schema.tables` (see verification SQL below), not
  merely by the absence of a `quarantine_table` field in the spec.
* The pipeline's own expectation metrics (Lakeflow's native per-expectation pass/fail/dropped
  counts, visible in the pipeline's event log / DLT UI) show 2 dropped records against
  `dq_txn_amount_positive_drop` out of 10 evaluated.

## Expected results — simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- only the 8 valid rows land; the 2 amount <= 0 rows are silently dropped
SELECT count(*) FROM {catalog}.bronze_txns.txns_clean_raw;
-- expect: 8

SELECT txn_id, amount FROM {catalog}.bronze_txns.txns_clean_raw WHERE amount <= 0;
-- expect: 0 rows -- TXN-2003 (-25.00) and TXN-2005 (0.00) never landed

-- no quarantine table should exist -- check the catalog's own information_schema, not just
-- SHOW TABLES, so the assertion is unambiguous about schema-qualified existence
SELECT table_name
FROM {catalog}.information_schema.tables
WHERE table_schema = 'bronze_txns' AND table_name = 'txns_clean_raw_quarantine';
-- expect: 0 rows
```

## Build notes / judgment calls

* **New fixture, not a reuse.** `sample_data/flowx_testing/finance_usecase/txns_raw.csv`
  is the only existing fixture with an `amount` column, but it belongs to TC-ING-005 (PGP ZIP
  decrypt) -- only 5 rows, none with `amount <= 0`, and its schema/domain target is unrelated
  to this scenario's `bronze_txns.txns_clean_raw`. So one new 10-row CSV
  (`txns_dq_drop.csv`) and one new dedicated seed notebook were added under a new
  `txns_usecase/` fixture directory (following the existing one-directory-per-source-domain
  convention, e.g. `crm_usecase/`, `finance_usecase/`), rather than repurposing
  `finance_usecase/`'s existing fixture.
* **Scaled down from the plan's 100/10 to 10/2.** Per this build pass's explicit convention
  (a working, onboardable test case matters more than exhaustive row volume), 10 rows with 2
  `amount <= 0` violations (one negative, one exactly zero -- both fail `amount > 0`) exercise
  the same `"drop"`-silently-filters assertion as 100/10 would, just with a
  trivially-checkable row count.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but consistent with
  `TESTING_STATUS.md`'s framing (that plan is aspirational, not a literal build spec) and
  TC-DQ-001's own build (`docs/50_tc_dq_001.md`), this build follows the real
  `setup_control_tables → seed → onboard → run_pipeline` convention only -- observability can
  be layered on later as an additive, opt-in job the same way scenario 100's
  `dlt_observability_job.yml` is.
* **`quarantine_table`/`record_id_column` omitted.** Both are DQ-quarantine-only fields (see
  `docs/17_onboarding_template_reference.md` §4.7); since this spec has no `action:
  "quarantine"` rule, including them would be misleading (they'd simply have no effect), so
  `dq_config` here carries only `rules[]`.
