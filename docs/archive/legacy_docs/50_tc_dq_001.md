# Test Pipeline: DQ Action `warn` Non-Blocking Validation (TC-DQ-001)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 4, TC-DQ-001), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove that a `dq_config` rule with `action: "warn"` is genuinely **non-blocking** -- a row that
fails a `"warn"` rule still lands in the target table exactly like a passing row. `"warn"`
maps onto a native Lakeflow expectation (`expect`, not `expect_or_drop`/`expect_or_fail`), so
the only observable effect of a violation is that it is counted/surfaced in the pipeline's own
expectation metrics/event log -- unlike `"drop"` (TC-DQ-002, filters the row), `"fail"`
(TC-DQ-003, aborts the update), or `"quarantine"` (TC-DQ-004, this framework's own extension
that reroutes the row to a companion table). This scenario also proves the negative case: no
`<table>_quarantine` table is ever created, since quarantine table registration is conditional
on at least one `rules[]` entry having `action == "quarantine"` (see
`docs/01_control_metadata_schema.md` §5 / `docs/17_onboarding_template_reference.md` §4.7) --
this spec has none.

## Responsibilities

* Land 10 customer rows (scaled down from `TESTING_PLAN.md`'s 100/15 template to a minimal
  10/2, per this pass's "minimal, real, onboardable" convention) as a single plain CSV in
  `/Volumes/{{catalog}}/crm/landing_dq_warn/` -- 2 of the 10 (`C003` age 16, `C006` age 15)
  violate the rule under test.
* One `ingestion_flow` (`df_dq_001_customer_warn_ingest`) with `source_type: "autoloader"` and
  exactly one `dq_config.rules[]` entry: `{"rule_id": "dq_customer_age_adult_warn",
  "expression": "age >= 18", "action": "warn"}`.
* `cdc_load_strategy: "APPEND"` -- this scenario is about DQ action semantics, not CDC
  behavior, so the simplest load strategy (plain streaming append, no `primary_keys`) keeps
  the flow focused on the one thing under test (same convention as TC-ING-001).

## Inputs

* `flowx_testing/029_dq_001_warn.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/flowx_testing/crm_usecase/customer_dq_warn.csv` (10 rows, columns
  `customer_id, customer_name, age, email`) -- new fixture, added alongside this test case's
  build (see Build notes).
* `notebooks/00_seed_sample_data/03_seed_dq_001_warn_data.py` -- a **new, dedicated** seed
  notebook (kept separate from `02_seed_flowx_testing_data.py` and
  `03_seed_ing_001_zip_filter_data.py`) that provisions the `crm`/`bronze_crm` schemas and
  `landing_dq_warn`/`_schemas` Volumes, then copies the fixture CSV directly into the landing
  Volume (no ZIP handling needed for this scenario).

## Outputs

* `{{catalog}}.bronze_crm.customer_warn_raw` -- exactly 10 rows, including both
  age-violating rows (`C003`, `C006`) -- `"warn"` never blocks or drops.
* No `{{catalog}}.bronze_crm.customer_warn_raw_quarantine` table -- `dq_config` here carries
  no `action: "quarantine"` rule, so `register_main_and_quarantine_tables` never registers one.
* The pipeline's own expectation metrics (Lakeflow's native per-expectation pass/fail counts,
  visible in the pipeline's event log / DLT UI) show 2 failing records against
  `dq_customer_age_adult_warn` out of 10 evaluated.

## Build notes / judgment calls

* **New fixture, not a reuse.** No existing seeded fixture carries an `age` column (checked
  `sample_data/flowx_testing/crm_usecase/customer_data.csv`, the various
  `sample_customer_*.csv` files, and the wide-customer SCD1 fixtures), so one new 10-row CSV
  (`customer_dq_warn.csv`) and one new dedicated seed notebook were added, reusing the existing
  `crm_usecase/` fixture directory rather than creating a new one.
* **Scaled down from the plan's 100/15 to 10/2.** Per this build pass's explicit convention
  (a working, onboardable test case matters more than exhaustive row volume), 10 rows with 2
  age violations exercise the same `"warn"`-never-blocks assertion as 100/15 would, just with a
  trivially-checkable row count.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but consistent with
  `TESTING_STATUS.md`'s framing (that plan is aspirational, not a literal build spec) and
  TC-ING-001's own build (`docs/31_tc_ing_001.md`), this build follows the real
  `setup_control_tables → seed → onboard → run_pipeline` convention only -- observability can be
  layered on later as an additive, opt-in job the same way scenario 100's `dlt_observability_job.yml`
  is.
* **`quarantine_table`/`record_id_column` omitted.** Both are DQ-quarantine-only fields (see
  `docs/17_onboarding_template_reference.md` §4.7); since this spec has no `action: "quarantine"`
  rule, including them would be misleading (they'd simply have no effect), so `dq_config` here
  carries only `rules[]`.
