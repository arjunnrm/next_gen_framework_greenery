# Test Pipeline: TC-ING-005 — Landing PGP Decryption via UC Secrets

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md)
> (Module 1, TC-ING-005), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md),
> [16_encryption_and_secrets.md](16_encryption_and_secrets.md) (the full PGP/secrets design),
> [22_ingestion_pgp_zip_json_standardization.md](22_ingestion_pgp_zip_json_standardization.md)
> (the `source_zip_handling`/`pre_extraction_decryption` mechanics this scenario exercises).

## Purpose

Prove `source_config.source_zip_handling.pre_extraction_decryption.type: "pgp"` end to end,
against a **real** PGP-encrypted-then-ZIPped archive, decrypted with a private key resolved
from a genuine Unity Catalog secret at pipeline execution time — not merely a structural spec
example (`onboarding_templates/pipeline_onboarding_template.json`'s own `pre_extraction_decryption`
example was never itself deployed; the closest prior live coverage,
`test_specs/spec_25_ingestion_pgp_zip_decrypt.json`, ran against the `poc` catalog, not
`metaflow`). This scenario's realistic production framing: a finance partner drops a
PGP-encrypted transactions extract into a landing volume; the framework must decrypt it with
nothing more than a securely-stored private key, unzip the plaintext CSV, and land it in
Bronze, with no decrypted intermediate ever persisted to permanent storage.

## Responsibilities

* One ingestion flow (`df_finance_pgp_txns_ingest`), `source_type: "autoloader"`,
  `cdc_load_strategy: "APPEND"` — deliberately the simplest possible CDC strategy, since this
  scenario's whole point is the decrypt-then-unzip-then-ingest path, not CDC behavior.
* `source_zip_handling.pre_extraction_decryption` dispatches the `"pgp"` handler
  (`ingestion/readers.py::_apply_source_zip_handling` → `crypto/pgp.py::pgp_decrypt`), keyed
  by `private_key_secret` — no `passphrase_secret` is configured, since this scenario's
  test-only keypair (like this project's other throwaway test keypairs) was deliberately
  generated without one.
* `delete_source_after_extract: false` — deliberately, so the source
  `financial_txns_202608.zip.pgp` fixture survives a run and can be re-verified without
  re-seeding (the same choice `spec_25`'s own PGP scenario made, for the same reason). This is
  orthogonal to the "no intermediate plaintext persisted" guarantee below: the **decrypted**
  `.decrypted` temp file is always removed in a `finally` block regardless of this flag —only
  the original *encrypted* source file's retention is configurable.

## Inputs

* `metaflow_testing/014_ing_005_pgp_decrypt.json` — the onboarding spec (one ingestion flow,
  no transformation/reconciliation flows).
* `sample_data/metaflow_testing/finance_usecase/txns_raw.csv` — 5-row plaintext fixture
  (`txn_id`, `account_id`, `amount`, `currency`, `txn_date`, `merchant`), zipped and
  PGP-encrypted on-cluster by the seed step below.
* `sample_data/metaflow_testing/finance_usecase/pgp_test_keypair_public.asc` /
  `pgp_test_keypair_private.asc` — a dedicated, disposable, passphrase-less RSA-2048 PGP
  keypair generated specifically for this test scenario (via `PGPy`, the same library
  `crypto/pgp.py` wraps) and committed to the repo. **Zero real security value** — it protects
  nothing but this scenario's own synthetic fixture, and is never reused by any other test case
  in this repo.
* `notebooks/00_seed_sample_data/03_seed_pgp_decrypt_test_data.py` — builds
  `financial_txns_202608.zip.pgp` in-memory (ZIP the CSV, then PGP-encrypt the ZIP's bytes via
  the framework's own `crypto/pgp.py::pgp_encrypt`) and lands it directly on-cluster, the same
  "build the archive in-process rather than sync a pre-built binary through the bundle"
  approach `02_seed_metaflow_testing_data.py` already established (workspace-bundle sync can
  mangle a pre-built `.zip`/binary upload).

## Outputs

* `{catalog}.bronze_finance.txns_raw` — 5 rows, in plaintext, exactly matching
  `txns_raw.csv`'s content, plus the usual `__framework_*` technical metadata columns.
* `/Volumes/{catalog}/finance/landing_pgp/extracted/txns/` — the decrypted, unzipped
  `txns_raw.csv`, landed there by `extract_encrypted_zip` before Auto Loader reads it.
* `/Volumes/{catalog}/finance/landing_pgp/incoming/financial_txns_202608.zip.pgp` — still
  present after a run (`delete_source_after_extract: false`, see above).
* **No `.decrypted` intermediate file anywhere on the Volume** — `_apply_source_zip_handling`
  always removes it in a `finally` block, success or failure, regardless of
  `delete_source_after_extract` (see [22_ingestion_pgp_zip_json_standardization.md §1.1](22_ingestion_pgp_zip_json_standardization.md#11-pre_extraction_decryption--a-type-registry-not-a-schema-field-per-algorithm)).

## Configuration

`metaflow_testing/014_ing_005_pgp_decrypt.json`'s one ingestion flow:

```json
"source_zip_handling": {
  "enabled": true,
  "source_zip_path": "/Volumes/{{catalog}}/finance/landing_pgp/incoming/",
  "zip_file_pattern": "financial_txns_202608.zip.pgp",
  "target_volume_path": "/Volumes/{{catalog}}/finance/landing_pgp/extracted/txns/",
  "pre_extraction_decryption": {
    "type": "pgp",
    "private_key_secret": {
      "secret_catalog": "{{catalog}}",
      "secret_schema": "security",
      "secret_key": "pgp_private_key_finance_test"
    }
  },
  "delete_source_after_extract": false
}
```

### Required prerequisite: provision the private key as a UC secret

**Manual, admin-audited step — not automated by this framework**, following the exact same
`security`-scope pattern [05_deployment_guide.md](05_deployment_guide.md)'s own prerequisites
section already establishes for this project's other encryption keys (`pii_encryption_key`,
`cdr_zip_passphrase`, `egress_zip_password`). This step must run **before**
`metaflow_test_ing_005_pgp_decrypt_job`'s `run_pipeline_task` — the pipeline's
`pre_extraction_decryption` step will fail with `SecretResolutionError` until it does:

```bash
# Test-only, disposable PGP private key -- protects nothing real (see sample_data/
# metaflow_testing/finance_usecase/ header note). No passphrase, matching this project's
# other throwaway test keypairs.
databricks secrets put-secret security pgp_private_key_finance_test \
  --string-value "$(cat sample_data/metaflow_testing/finance_usecase/pgp_test_keypair_private.asc)"
```

The matching public key (`pgp_test_keypair_public.asc`) needs no secret at all — it's used
directly, in the clear, by the seed notebook to encrypt the fixture; only the private key
half needs to live behind a UC secret.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks secrets put-secret security pgp_private_key_finance_test \
  --string-value "$(cat sample_data/metaflow_testing/finance_usecase/pgp_test_keypair_private.asc)"
databricks bundle run metaflow_test_ing_005_pgp_decrypt_job --target dev
```

Task chain: `setup_control_tables → seed_pgp_decrypt_test_data → onboard_ing_005 →
run_pipeline_task`.

## Expected results — verification logic

```sql
-- Exactly 5 plaintext rows, matching txns_raw.csv's known content
SELECT txn_id, account_id, amount, currency, txn_date, merchant
FROM {catalog}.bronze_finance.txns_raw
ORDER BY txn_id;
-- expect: FTX-1001..FTX-1005, e.g. FTX-1003 -> ACC-4003, 300.00, EUR, 2026-08-22, Fabrikam Logistics
```

```bash
# Extracted plaintext CSV landed where source_zip_handling.target_volume_path points
databricks fs ls dbfs:/Volumes/{catalog}/finance/landing_pgp/extracted/txns/

# Source PGP+ZIP archive still present (delete_source_after_extract: false)
databricks fs ls dbfs:/Volumes/{catalog}/finance/landing_pgp/incoming/
# expect: financial_txns_202608.zip.pgp

# No lingering *.decrypted intermediate anywhere under landing_pgp/
databricks fs ls -r dbfs:/Volumes/{catalog}/finance/landing_pgp/ | grep decrypted
# expect: no output
```

If `pre_extraction_decryption`'s secret hasn't been provisioned yet, or is wrong, the pipeline
update fails fast with a `CryptoError`/`SecretResolutionError` naming the secret coordinates —
this is the expected, correct failure mode, not a bug to route around; it proves the framework
never silently falls through to treating an undecryptable file as a plain ZIP.

## Known gaps / judgment calls

* **Scope-vs-catalog terminology**: this doc's `databricks secrets put-secret security
  pgp_private_key_finance_test` command follows [05_deployment_guide.md](05_deployment_guide.md)'s
  own prerequisites-section CLI pattern exactly (as this test case's own instructions
  required), which that guide itself labels a **classic workspace-level** secret scope
  command. The onboarding spec instead addresses this secret via the **Unity Catalog**
  three-level `{secret_catalog, secret_schema, secret_key}` shape (`{{catalog}}`, `security`,
  `pgp_private_key_finance_test`), resolved via `dbutils.secrets.get(catalog=, schema=,
  key=)` — a different, newer secret system per
  [16_encryption_and_secrets.md §1](16_encryption_and_secrets.md#1-the-secret-reference-shape-secret_catalog-secret_schema-secret_key).
  This is a pre-existing terminology gap in this project's own docs (the identical pattern
  already exists for `pii_encryption_key`/`cdr_zip_passphrase`/`egress_zip_password` in
  `05_deployment_guide.md`, and `docs/20_crypto_abac_exhaustive_test_suite.md` explicitly maps
  `put-secret security pii_encryption_key` to `{secret_catalog, secret_schema, secret_key} =
  {catalog, security, pii_encryption_key}`) — not something introduced or newly resolved by
  this test case. Follow whichever secrets CLI syntax your workspace/CLI version actually
  requires to create a Unity Catalog secret at `{{catalog}}.security.pgp_private_key_finance_test`;
  the important, framework-relevant part is the resulting secret coordinates, not the exact
  provisioning command's flag syntax.
* **Fixture generation approach**: per this test case's own instructions, the PGP-encrypted
  ZIP fixture is generated by a **new seed notebook step**
  (`notebooks/00_seed_sample_data/03_seed_pgp_decrypt_test_data.py`), not a one-off local
  script whose binary output gets committed — consistent with this repo's established
  aversion to syncing pre-built binary/ZIP artifacts through the bundle (see
  [05_deployment_guide.md](05_deployment_guide.md)'s ASN.1 section). A one-off local script
  (using `crypto/pgp.py` directly, matching this test case's own suggested approach) *was*
  used, once, to generate the disposable test keypair itself and to verify the full
  PGP-decrypt-then-unzip round trip locally before writing any of these artifacts. The
  keypair's own PGP User ID identifies it as disposable test-only material ("Metaflow
  TC-ING-005 Test Key (finance, disposable, no passphrase)", visible via `gpg --list-packets`
  or any PGP key inspector) -- not a plaintext comment in the `.asc` file itself, which is
  otherwise a standard OpenPGP armored block with no room for free-text annotation.
