# Test Pipeline: Multi-Source Streaming-to-Batch 4-Way Inner Join (TC-TRF-001)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 3, TC-TRF-001), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove that a `transformation_flows` entry can join one **streaming** Auto Loader source
(`is_streaming: true`) against three **batch**-read dimension tables (`is_streaming: false`)
in a single `transformation_sql` inner join, and that the join genuinely excludes an entity
present on one side but absent on the other -- not just that a 4-way join parses and runs in
general (scenario 001 already proves that, but every row on every side of its join always
matches, so it never exercises the exclusion behavior itself).

## Responsibilities

* 4 `ingestion_flows`, all `source_type: "autoloader"`, all `target_type: "streaming_table"`,
  landing plain (unzipped) CSVs into this test case's own dedicated bronze tables:
  * `df_trf001_assignments_ingest` -> `bronze_ea.trf001_assignments_raw` -- the fact table,
    read `is_streaming: true` at the join.
  * `df_trf001_employees_ingest` -> `bronze_ea.trf001_employees_raw` -- dimension, read
    `is_streaming: false`.
  * `df_trf001_departments_ingest` -> `bronze_ea.trf001_departments_raw` -- dimension, read
    `is_streaming: false`.
  * `df_trf001_projects_ingest` -> `bronze_ea.trf001_projects_raw` -- dimension, read
    `is_streaming: false`.
* One `transformation_flows` entry (`ts_trf001_ea_joined_assignments`) with 4
  `source_inputs`, doing a plain `JOIN` (SQL `JOIN` = inner join) across all 4, reusing
  scenario 001's own join-SQL pattern verbatim (see
  `resources/flowx_test_001_zip_join_export_pipeline.yml`'s header comment and
  `flowx_testing/001_zip_file_onboarding.json`'s `transformation_sql`) -- only the
  `source_inputs[].table` values differ (this test case's own `trf001_*` bronze tables, not
  scenario 001's ZIP-ingested ones):

  ```sql
  SELECT a.employee_id, a.project_id, a.hours_allocated, e.employee_name, e.role, e.dept_id,
         d.dept_name, d.region, p.project_name, p.budget
  FROM assignments_raw a
  JOIN employees_raw e ON a.employee_id = e.employee_id
  JOIN departments_raw d ON e.dept_id = d.dept_id
  JOIN projects_raw p ON a.project_id = p.project_id
  ```

* `employee_id = 'E005'` (`Olivia Brown`, `dept_id = 'D004'`) exists in
  `trf001_employees_raw` but has **no row** in `trf001_assignments_raw` -- the inner join
  must silently drop it, not error and not appear in the output with `NULL` join columns
  (that would be a `LEFT JOIN`, not what this SQL does).
* `cdc_load_strategy: "APPEND"` on every flow -- this scenario is about join semantics, not
  CDC behavior, so the simplest load strategy keeps the flow focused on the one thing under
  test (same choice scenario 001 and TC-ING-001 both already made for the same reason).

## Outputs

* `{{catalog}}.silver_ea.trf001_ea_joined_assignments` -- exactly **5 rows** (one per
  `assignments.csv` row: `E001`/`P001`, `E002`/`P001`, `E002`/`P002`, `E003`/`P003`,
  `E004`/`P004`), every join column populated (no `NULL`s from the reference sides, since
  every `dept_id`/`project_id` referenced by `assignments.csv`/`employees.csv` resolves in
  both `departments.csv`/`projects.csv`).
* **Zero** rows with `employee_id = 'E005'` anywhere in that table.
* `{{catalog}}.bronze_ea.trf001_employees_raw` still has all 5 employees (`E001`-`E005`) --
  `E005`'s absence is a property of the *join output* only, not of the ingested employee
  dimension itself.

## Build notes / judgment calls

* **Reused fixture, not new sample data.**
  `sample_data/flowx_testing/ea_usecase/{employees,departments,projects,assignments}.csv`
  (already seeded by scenario 001's own `02_seed_flowx_testing_data.py`, as plain ZIP
  payloads) already have exactly this test case's required shape with zero changes needed:
  `employees.csv` has 5 rows (`E001`-`E005`), `assignments.csv` has exactly 5 rows covering
  only `E001`-`E004`, and every `dept_id`/`project_id` referenced anywhere resolves cleanly
  in `departments.csv`/`projects.csv`. Per this project's build convention (reuse over
  inventing new sample data), this test case's own seed notebook reads the same 4 CSV files
  directly rather than generating new ones -- only the *landing mechanism* differs (plain
  copy here vs. on-cluster ZIP-then-land in scenario 001's seed step).
* **Genuine naming collision with scenario 001 -- resolved by renaming this test case's own
  targets, not scenario 001's.** `TESTING_PLAN.md`'s own Databricks-object-names column for
  TC-TRF-001 names bronze targets `employees_raw`/`departments_raw`/`projects_raw`/
  `assignments_raw` and a silver target `ea_joined_assignments` -- but scenario 001
  (`flowx_test_001_zip_join_export_pipeline`, already deployed) **already owns real,
  already-materialized Lakeflow objects with those exact same
  `{catalog}.bronze_ea.*`/`{catalog}.silver_ea.ea_joined_assignments` three-part names**. Two
  different Lakeflow Declarative Pipelines cannot both declare a streaming
  table/materialized-view/sink against the identical Unity Catalog table -- Lakeflow ties a
  managed table to the one pipeline that created it, so this test case's own pipeline
  attempting to `CREATE STREAMING TABLE` over scenario 001's already-owned tables would fail
  at deployment/runtime with a table-ownership conflict, not produce two independent test
  results. Per this build's scope discipline (never edit another test case's files), the fix
  had to be on this test case's side: every one of this spec's own bronze targets is named
  `trf001_<name>_raw` and its silver target is named `trf001_ea_joined_assignments`, all
  still under the same `bronze_ea`/`silver_ea` schemas `TESTING_PLAN.md` names, just with a
  disambiguating table-name prefix. The join-SQL pattern, the DQ/CDC semantics, and the
  expected row-count assertions are otherwise byte-for-byte what `TESTING_PLAN.md` and the
  task both describe -- only the literal target table names changed, and only to avoid
  breaking an already-deployed, real object this build is barred from touching.
* **No `run_observability_task`.** Same judgment call TC-ING-001's doc already made:
  `TESTING_PLAN.md`'s "Proposed Pipeline & Job Architecture" column names a second
  `run_observability_task` step, but per `TESTING_STATUS.md`'s own framing, that column is
  planned/aspirational, not a literal build spec -- no other real scenario's job wires
  observability in by default (it's opt-in, layered on separately, as scenario 100's
  `dlt_observability_job.yml` does). This build follows the real `setup_control_tables → seed
  → onboard → run_pipeline` convention instead.
