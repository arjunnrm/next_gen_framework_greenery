# Test Pipeline: Schema Evolution & Malformed Column Rescue (TC-ING-009)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 1, TC-ING-009), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md).

## Purpose

Prove that `source_config.schema_evolution_mode: "rescue"` (Auto Loader's
`cloudFiles.schemaEvolutionMode`, see
[ingestion/readers.py](../src/NextGen_Metadata_Framework/lakeflow_framework/ingestion/readers.py)`::read_autoloader_source`)
genuinely protects a streaming ingestion flow against two distinct drift shapes arriving in
the same day-2 batch, without failing the stream and without silently dropping data:

1. **An unannounced new column** (`unannounced_flag`) that was never part of the schema Auto
   Loader inferred from the day-1 batch.
2. **A malformed value in an already-typed column** -- one day-2 row's `id` is the
   non-numeric string `"ABC"`, where every day-1 row's `id` inferred as an integer.

In `"rescue"` mode, Auto Loader never widens the schema or fails the micro-batch for either
case: instead, both the extra column's value and the unparseable typed value are captured as
JSON into the framework's `_rescued_data` column for the affected row(s), leaving every
other column's value on that row intact. This is a different tradeoff from
`"addNewColumns"` (would evolve the schema and restart the stream) or `"failOnNewColumns"`
(would hard-fail the micro-batch) -- see
[01_control_metadata_schema.md §3](01_control_metadata_schema.md#3-source_config-ingestion-flows-only)
and [17_onboarding_template_reference.md §2.2](17_onboarding_template_reference.md#22-source_config--fields-common-to-every-source_type)
for the full `schema_evolution_mode` enum.

## Responsibilities

* One `ingestion_flow` (`df_ing_009_rescue_schema_ingest`), `source_type: "autoloader"`,
  reading CSV from `/Volumes/{{catalog}}/ops/landing_drift/` with
  `schema_evolution_mode: "rescue"` and `reader_options: {"header": "true",
  "cloudFiles.inferColumnTypes": "true"}` (so `id` infers as `INT` from the day-1 batch,
  making day-2's `"ABC"` a genuine type mismatch rather than a same-type string value).
* `cdc_load_strategy: "APPEND"` -- this scenario is about schema/type drift capture, not CDC
  behavior, so the simplest load strategy keeps the flow focused on the one thing under test.
* Land day-1 (`feed_day1.csv`, columns `id, name`, 3 clean rows) first and run the pipeline
  once, establishing the inferred schema at `schema_location`. Then land day-2
  (`feed_day2.csv`, columns `id, name, unannounced_flag`, 3 rows -- one with a non-numeric
  `id`) and re-run the pipeline: every day-2 row should land with `_rescued_data IS NOT
  NULL` (from the unannounced column alone), and the one malformed-`id` row should
  additionally show `id IS NULL` for that row (its value went to `_rescued_data` instead,
  since `"ABC"` cannot cast to `INT`).

## Inputs

* `metaflow_testing/018_ing_009_rescue_schema.json` -- single-ingestion-flow onboarding spec
  (no `transformation_flows`/`reconciliation_flows`).
* `sample_data/metaflow_testing/ops_usecase/feed_day1.csv` -- day-1 batch, `id, name`, 3 rows
  (`1,Alice` / `2,Bob` / `3,Carol`).
* `sample_data/metaflow_testing/ops_usecase/feed_day2.csv` -- day-2 batch, `id, name,
  unannounced_flag`, 3 rows (`4,Dave,Y` / `5,Eve,N` / `ABC,Frank,Y`) -- the third row's `id`
  is the non-numeric string `"ABC"`.
* `notebooks/00_seed_sample_data/03_seed_ing_009_rescue_schema_data.py` -- a new, dedicated
  seed notebook (kept separate from every other scenario's seed step) that provisions the
  `ops`/`bronze_ops` schemas and `landing_drift`/`_schemas` Volumes, then lands **only**
  `feed_day1.csv`. It deliberately does not land `feed_day2.csv` -- see "Triggering day-2
  schema drift" below.

## Outputs

* `{{catalog}}.bronze_ops.feed_rescued_raw` -- after the day-1-only run: 3 rows (`id`
  1/2/3), `_rescued_data` `NULL` for all of them (clean batch, nothing to rescue).
* After day-2 lands and the pipeline re-runs: 3 more rows land (6 total). All 3 new rows have
  `_rescued_data IS NOT NULL` (each carries the `unannounced_flag` value Auto Loader
  couldn't place on the inferred schema). The `Frank` row additionally has `id IS NULL`
  (its literal `"ABC"` is inside `_rescued_data` instead, not silently coerced or dropped).
* No pipeline failure, no quarantine table (no `dq_config.rules` configured) -- `"rescue"`
  mode's entire point is to keep the stream running through both drift shapes.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run metaflow_test_ing_009_rescue_schema_job --target dev
```

Task chain: `setup_control_tables -> seed_ing_009_rescue_schema_data -> onboard_ing_009 ->
run_ing_009_pipeline`. This job run lands and ingests **day-1 only** (`feed_day1.csv`), which
establishes Auto Loader's inferred schema (`id: INT`, `name: STRING`) at `schema_location`.

### Triggering day-2 schema drift

Day-2 is deliberately **not** part of the automated task chain -- it must be dropped in
manually, after day-1 has already been onboarded and run once, so Auto Loader's schema is
already committed to `schema_location` before the drifted batch arrives (the same
day-1-then-day-2 convention [08_test_pipeline_1_volume_scd.md](08_test_pipeline_1_volume_scd.md)
uses for its own SCD drift test):

```bash
# 1. Copy the day-2 fixture into the same landing Volume day-1 already landed in:
databricks fs cp sample_data/metaflow_testing/ops_usecase/feed_day2.csv \
  dbfs:/Volumes/metaflow/ops/landing_drift/feed_day2.csv --profile dev

# 2. Re-run just the pipeline (Auto Loader picks up the new file on the next update;
#    no need to re-run setup/seed/onboard):
databricks bundle run metaflow_test_ing_009_rescue_schema_pipeline --target dev
```

(Equivalently, from a notebook attached to the same workspace: `dbutils.fs.cp("file:...",
"/Volumes/metaflow/ops/landing_drift/feed_day2.csv")`.)

## Expected results -- simulation notes

**SQL assertions** (after the day-1-only run, replace `{catalog}` with your actual target
catalog):

```sql
SELECT count(*) AS row_count, count(_rescued_data) AS rescued_count
FROM {catalog}.bronze_ops.feed_rescued_raw;
-- expect: row_count=3, rescued_count=0
```

**After day-2 lands and the pipeline re-runs**:

```sql
SELECT count(*) FROM {catalog}.bronze_ops.feed_rescued_raw;
-- expect: 6 (3 day-1 + 3 day-2)

-- Every day-2 row should have been rescued (unannounced_flag alone triggers this)
SELECT id, name, _rescued_data
FROM {catalog}.bronze_ops.feed_rescued_raw
WHERE name IN ('Dave', 'Eve', 'Frank')
ORDER BY name;
-- expect: _rescued_data IS NOT NULL for all 3 rows (contains "unannounced_flag" in the JSON)

-- The malformed-id row specifically: id itself must be NULL, not "ABC" or a cast error
SELECT id, name, _rescued_data
FROM {catalog}.bronze_ops.feed_rescued_raw
WHERE name = 'Frank';
-- expect: id IS NULL; _rescued_data contains both "id":"ABC" and "unannounced_flag":"Y"

-- Day-1 rows remain completely unaffected by the later drift
SELECT id, name, _rescued_data
FROM {catalog}.bronze_ops.feed_rescued_raw
WHERE name IN ('Alice', 'Bob', 'Carol');
-- expect: _rescued_data IS NULL for all 3, id populated (1, 2, 3)
```

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture combines an unannounced new
  column with a malformed value in an already-typed column in the same drift batch, so 2 new
  small CSV fixtures and 1 new dedicated seed notebook were added, following the same
  "separate seed notebook per new test case" convention `03_seed_ing_006_json_explode_data.py`
  and `03_seed_ing_001_zip_filter_data.py` already established.
* **Day-2 landing is a manual, documented step, not a job task.** This mirrors the existing
  `08_test_pipeline_1_volume_scd.md` convention (its own day-2 CSV is "dropped in" manually
  between two `bundle run` invocations, not automated inside the job) rather than inventing a
  new pattern -- the point of this test case is the schema-evolution *behavior* on a second,
  independent Auto Loader trigger, which a single job run landing both files at once would not
  exercise cleanly (Auto Loader could plausibly infer the union schema from one combined
  initial batch instead of genuinely evolving mid-stream).
* **One row deliberately breaks the inferred type, not the column set.** The task's own
  wording ("a non-numeric value in a typed column") is satisfied by `id` specifically, since
  `cloudFiles.inferColumnTypes: "true"` + a clean all-integer day-1 batch is what makes `id`
  a genuinely typed (`INT`) column in the first place -- a non-numeric value in an
  already-`STRING` column (e.g. `name`) would never be "malformed," just a normal string.
