# Test Pipeline: Post-Deployment UC Table & Column Tag Application (TC-GOV-001)

> See also: [Documentation index](README.md), [01_control_metadata_schema.md §6](01_control_metadata_schema.md#6-governance_tags-ingestion-and-transformation-flows), [06_governance_integration.md](06_governance_integration.md), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md).

## Purpose

Prove that `governance_tags` (table tags + column tags) declared on an onboarding spec are
genuinely applied, post-deployment, as real Unity Catalog `ALTER TABLE ... SET TAGS`/
`ALTER TABLE ... ALTER COLUMN ... SET TAGS` DDL against an **already-materialized** table --
independent of whether a new Lakeflow pipeline update just wrote that table. This is the
"tags-only governance model" documented in
[06_governance_integration.md](06_governance_integration.md): the framework applies key-value
tags; it does not create or bind the Unity Catalog masking/row-filter policy that gives a tag
its enforcement behavior.

This scenario deliberately builds **no new ingestion pipeline**. It re-onboards a new
`ingestion_flow` (its own new `dataflow_group_id`) that targets scenario 100's already-deployed
`{{catalog}}.bronze_test.customer_raw` table, carrying only `governance_tags` -- then runs
`notebooks/04_governance/04_apply_governance_and_egress.py` directly, exactly like scenario
100's own job would as its own post-`run_pipeline` task, just without a pipeline update in front
of it this time (the table is already there).

## Responsibilities

* Reuse `{{catalog}}.bronze_test.customer_raw` (created by
  `metaflow_test_100_zipcsv_pipeline` / `metaflow_test_100_job`, per
  [TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md)'s own "Executed -- Pass" entry for
  scenario 100, most recently re-verified 2026-08-29) as the tag target -- no new table, no new
  fixture data, no new pipeline.
* One `ingestion_flow` (`df_gov_001_tagging_customer_raw`, under a brand-new
  `dataflow_group_id: "dfg_metaflow_gov_001_tagging"`) whose `target_catalog`/`target_schema`/
  `target_table` point at that same `bronze_test.customer_raw` coordinates, carrying:
  * `governance_tags.table_tags`: `{"domain": "finance", "compliance": "sox"}`.
  * `governance_tags.column_tags`: `[{"column": "CustomerID", "tags": {"classification":
    "restricted", "mask": "PII"}}]`.
* A job that onboards this spec (a pure control-table upsert -- `dataflow_group_spec`/
  `ingestion_flow_spec` rows only, no DLT graph involved) and then calls
  `04_apply_governance_and_egress.py` directly against `dataflow_group_id:
  "dfg_metaflow_gov_001_tagging"`, which loops that group's one active `ingestion_flow_spec`
  row and issues the tag DDL against `bronze_test.customer_raw`.

## Inputs

* `metaflow_testing/036_gov_001_tagging.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`), reusing scenario 100's own `source_config`/
  `target_config` shape (`autoloader`, `SCD1`, `primary_keys: ["CustomerID"]`) purely so the
  spec onboards cleanly -- this flow's `source_config`/`target_config` are never actually
  executed by any pipeline (see Build notes).
* Depends on `{{catalog}}.bronze_test.customer_raw` already existing in the target workspace --
  i.e. `metaflow_test_100_job` having run at least once already. No seed step of its own.

## Outputs

* `system.information_schema.table_tags` -- one row each for `domain = 'finance'` and
  `compliance = 'sox'` against `{{catalog}}.bronze_test.customer_raw`.
* `system.information_schema.column_tags` -- one row each for `classification = 'restricted'`
  and `mask = 'PII'` against the `CustomerID` column of the same table.
* `{{catalog}}.config.dataflow_group_spec` / `ingestion_flow_spec` -- one new row each, under
  `dataflow_group_id = 'dfg_metaflow_gov_001_tagging'`, with `governance_tags_json` populated.
  No DLT pipeline is deployed or run against this group -- these rows exist purely so
  `apply_all_governance_tags` has a `governance_tags_json`/target-table triple to read.
* `{{catalog}}.bronze_test.customer_raw` itself is **untouched data-wise** -- same row count,
  same content as scenario 100 last left it. Only its UC tag metadata changes.

## Configuration

`metaflow_testing/036_gov_001_tagging.json`'s one `ingestion_flows[]` entry:

```json
"target_catalog": "{{catalog}}",
"target_schema": "bronze_test",
"target_table": "customer_raw",
"target_config": {
  "cdc_load_strategy": "SCD1",
  "primary_keys": ["CustomerID"],
  "generate_hash_columns": true,
  "storage_format": "delta"
},
"dq_config": { "rules": [] },
"governance_tags": {
  "table_tags": { "domain": "finance", "compliance": "sox" },
  "column_tags": [
    { "column": "CustomerID", "tags": { "classification": "restricted", "mask": "PII" } }
  ]
}
```

`resources/metaflow_test_gov_001_tagging_job.yml`'s `apply_governance_gov_001` task parameters:

```yaml
notebook_path: ../notebooks/04_governance/04_apply_governance_and_egress.py
base_parameters:
  catalog: metaflow
  dataflow_group_id: dfg_metaflow_gov_001_tagging
  apply_abac: "true"
  capture_cdc_change_counts: "false"
```

`capture_cdc_change_counts: "false"` deliberately disables this notebook's unrelated Phase 10
SCD/CDC change-count capture for this job -- this scenario is about tag application only, and
this flow's `dataflow_id` was never actually run through a pipeline update, so there is no
meaningful "since the last run" change-count story to capture for it.

## Build notes / judgment calls

* **No new pipeline, by design.** TC-GOV-001 is explicitly a tags-application test, not an
  ingestion test -- per this build's own scope, no `resources/metaflow_test_gov_001_*_pipeline.yml`
  is created. `governance_tags` has no dedicated control table and is applied purely as
  post-deployment DDL (`docs/01_control_metadata_schema.md` §1/§6), so a pipeline run was never
  a prerequisite for this scenario to exercise the real code path -- only the target table
  needs to already exist, which scenario 100's own table already does.
* **Reused scenario 100's `customer_raw`, not a new `metaflow_test_dq_004` table.** Per this
  TC's own instructions, `metaflow_test_dq_004`'s table was checked first
  (`metaflow_testing/TESTING_STATUS.md` line for `TC-DQ-004`: "Partially Covered -- Scenario 100
  exercises quarantine routing generally", i.e. no dedicated DQ-004 scenario/spec file exists
  yet in this repo as of this build), so scenario 100's own already-deployed
  `{{catalog}}.bronze_test.customer_raw` (`TESTING_STATUS.md`: "Executed -- Pass", re-verified
  2026-08-29) is the simpler and only currently-real choice.
  * Genuine gap: this makes `metaflow_test_gov_001_tagging_job` **dependent on**
    `metaflow_test_100_job` having run at least once first in the shared dev workspace -- there
    is no job-level `depends_on` between the two bundle jobs (they're separate `resources.jobs`
    entries), so this ordering is a real, undeclared cross-job dependency, not enforced by the
    bundle itself. Flagged here rather than silently assumed.
* **New `dataflow_group_id`, not scenario 100's own `dfg_zip_csv_dataload`.** Re-onboarding this
  flow under scenario 100's own group id would add a second `ingestion_flow_spec` row targeting
  the exact same physical table into the group scenario 100's own pipeline (`dataflow.group.id:
  dfg_zip_csv_dataload`) actually builds its DAG from -- risking a second, competing DLT node
  definition for `customer_raw` the next time that pipeline runs. A dedicated
  `dfg_metaflow_gov_001_tagging` group id keeps this row completely outside that pipeline's own
  graph; it exists purely as a `governance_tags_json` carrier for
  `apply_all_governance_tags` to read.
* **`source_config`/`target_config` mirror scenario 100's own shape but are never executed.**
  Since this flow is never run through a Lakeflow pipeline (no pipeline resource references
  `dfg_metaflow_gov_001_tagging`), its `source_config.path`/`target_config.cdc_load_strategy`
  etc. only need to satisfy onboarding-time validation, not describe a real data flow -- they
  were set to mirror scenario 100's real, working `df_zip_csv_file_ingest` flow
  (`metaflow_testing/100_zipcsv_onbaording.json`) for realism and to guarantee they pass
  `spec_validator.py` cleanly, not because they do anything at runtime.
* **`capture_cdc_change_counts: "false"`.** Left enabled (the notebook's own default), Phase 10
  would still run harmlessly (`capture_all_scd_change_counts` never raises -- a per-flow
  failure is logged and skipped, per `control_plane/post_deployment.py`'s own docstring) and
  would, incidentally, capture this table's full change history against this flow's own
  `last_processed_cdc_version` watermark. Disabled here to keep this job's scope crisply about
  governance tagging only, per this TC's own title.
