# Test Pipeline: Full Snapshot Diffing With Natural PK (TC-CDC-006)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 2, TC-CDC-006), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md), [02_cdc_load_strategies.md § FULL_SNAPSHOT_CDC](02_cdc_load_strategies.md#full_snapshot_cdc).

## Purpose

Prove that `target_config.cdc_load_strategy: "FULL_SNAPSHOT_CDC"` correctly diffs successive
full extracts from a source that **does** carry a natural business key -- a daily inventory
dump. With `primary_keys: ["item_id"]` configured, `cdc/snapshot.py::register_full_snapshot_cdc`
hands each newly-landed full extract to `dlt.apply_changes_from_snapshot(keys=["item_id"],
stored_as_scd_type="1")`, which diffs it against the previous extract by that key: a key absent
from the latest dump is removed from the target, a key present in both but with changed
attribute values is updated in place (unlike `FULL_SNAPSHOT_CDC_NO_PK`'s
"delete-old-hash-row/insert-new-hash-row" behavior -- see [TC-CDC-007](46_tc_cdc_007.md) -- a
real key lets Lakeflow perform a genuine upsert), and a key never seen before is inserted.

## Responsibilities

* Land a warehouse inventory extract in 2 successive full snapshots (Day-1, then Day-2) in the
  same landing Volume, so the pipeline's two triggered updates each diff one extract against the
  previous state:
  * Day-1 (`inventory_snapshot_day1.csv`, 3 rows): baseline snapshot, keys `[1, 2, 3]`.
  * Day-2 (`inventory_snapshot_day2.csv`, 3 rows): key `1` (`Steel Bolts`) is absent entirely (a
    delete); key `2` (`Copper Wire`) is unchanged; key `3` (`Rubber Gaskets`) keeps its identity
    but its `quantity` and `warehouse` attributes change (an update, `300 -> 850`,
    `WH-EAST -> WH-CENTRAL`); key `4` (`Aluminum Sheets`) is a brand-new row (an insert).
* One `ingestion_flow` (`df_cdc_006_inventory_snapshot_ingest`) with `source_type:
  "autoloader"`, plain CSV format, `cdc_load_strategy: "FULL_SNAPSHOT_CDC"`,
  `primary_keys: ["item_id"]`, no `cdc_operation_column`/`cdc_operation_mapping` -- this
  scenario relies purely on "absent from the latest dump" to express a delete, not an explicit
  delete-marker column.

## Inputs

* `flowx_testing/024_cdc_006_snapshot_pk.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/flowx_testing/inventory_usecase/inventory_snapshot_day1.csv` (3 rows) /
  `inventory_snapshot_day2.csv` (3 rows) -- **new, hand-authored fixtures**: no existing seeded
  fixture pairs a natural business key with a 2-day insert/update/delete full-snapshot shape --
  the closest existing pair, `sample_data/sample_mainframe_customer_master_day1/2.csv`, is
  deliberately key-less (it is reused by [TC-CDC-007](46_tc_cdc_007.md)'s
  `FULL_SNAPSHOT_CDC_NO_PK` scenario instead) -- so 2 small new CSVs (6 rows total) were added
  under their own `inventory_usecase/` subdirectory, following this project's per-scenario
  fixture convention.
* `notebooks/00_seed_sample_data/03_seed_cdc_006_snapshot_pk_data.py` -- a **new, dedicated**
  seed notebook (kept separate from every other scenario's own seed notebook) that provisions
  the `inventory` schema and `landing_dumps`/`_schemas` Volumes, then lands **only** the Day-1
  extract in `/Volumes/{{catalog}}/inventory/landing_dumps/`. The Day-2 extract is deliberately
  **not** landed by this notebook -- see "Main execution flow" below for the manual second step
  this scenario requires.

## Outputs

* `{{catalog}}.silver_inventory.inventory_snapshot_cdc` -- after the Day-1 run: exactly 3 rows,
  keys `{1, 2, 3}`. After the Day-2 run: exactly 3 rows, keys `{2, 3, 4}` -- key `1` is gone,
  key `3` carries its new `quantity`/`warehouse` values (same row, updated in place, not a
  second row), key `4` is present as a new row.
* `__framework_hash_key`/`__framework_hash_value` present on every row (`generate_hash_columns`
  defaults to `true` for every CDC-dispatched strategy) -- hashed from `item_id` and from every
  non-key business column respectively.

```json
  "storage_format": "delta"

```

Target: `{{catalog}}.silver_inventory.inventory_snapshot_cdc`, `target_type: "streaming_table"`

were empty for this strategy.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run flowx_test_cdc_006_snapshot_pk_job --target dev
```

Task chain: `setup_control_tables -> seed_cdc_006_snapshot_pk_data -> onboard_cdc_006 ->
run_pipeline`. This first job run lands and processes **only** the Day-1 extract -- confirm
`inventory_snapshot_cdc` holds exactly 3 rows, keys `{1, 2, 3}`, before moving on.

**Day-2 step (manual, by design -- this is the behavior the scenario exists to prove):**

1. Copy the Day-2 fixture into the same landing Volume, e.g. from a notebook attached to the
   same catalog:
   ```python
   dbutils.fs.cp(
       "file:/path/to/sample_data/flowx_testing/inventory_usecase/inventory_snapshot_day2.csv",
       "/Volumes/flowx/inventory/landing_dumps/inventory_snapshot_day2.csv",
   )
   ```
   (or `databricks fs cp` from the CLI against the same destination path).
2. Re-run just the pipeline (no need to re-run the whole job --
   `setup_control_tables`/`seed_cdc_006_snapshot_pk_data`/`onboard_cdc_006` are all a
   one-time/idempotent prerequisite, not part of the behavior under test here):
   ```bash
   databricks bundle run flowx_test_cdc_006_snapshot_pk_pipeline --target dev
   ```
3. Auto Loader picks up `inventory_snapshot_day2.csv` as a new file in its next triggered
   (`availableNow`) update; `cdc/snapshot.py`'s `_latest_snapshot` callback hands the full Day-2
   extract to `apply_changes_from_snapshot` as the new latest-snapshot version, which diffs it
   against the Day-1 version by `item_id`: key `1` is removed (absent from Day-2), key `3` is
   updated in place (same key, new attribute values), and key `4` is inserted (a key never seen
   before). Key `2` is untouched either way.

## Expected results — simulation notes

**SQL assertions** (after the Day-2 run, replace `{catalog}` with your actual target catalog):

```sql
-- Final key set is exactly {2, 3, 4} -- key 1 is gone
SELECT item_id FROM {catalog}.silver_inventory.inventory_snapshot_cdc ORDER BY item_id;
-- expect: 2, 3, 4 (3 rows -- no row for item_id = 1)

-- Row count reflects the net Day-2 delta (3 in, 3 out: -1 delete, +1 insert, 1 in-place update)
SELECT count(*) FROM {catalog}.silver_inventory.inventory_snapshot_cdc;
-- expect: 3

-- item_id 1 was removed (present on Day-1, absent from Day-2)
SELECT count(*) FROM {catalog}.silver_inventory.inventory_snapshot_cdc WHERE item_id = 1;
-- expect: 0

-- item_id 3 was updated in place -- same key, new attribute values, still exactly 1 row
SELECT quantity, warehouse FROM {catalog}.silver_inventory.inventory_snapshot_cdc
WHERE item_id = 3;
-- expect: 850, WH-CENTRAL (1 row, not 2)

-- item_id 4 was inserted (new on Day-2)
SELECT item_name, quantity, warehouse FROM {catalog}.silver_inventory.inventory_snapshot_cdc
WHERE item_id = 4;
-- expect: Aluminum Sheets, 150, WH-WEST (1 row)

-- item_id 2 was untouched across both runs
SELECT item_name, quantity, warehouse FROM {catalog}.silver_inventory.inventory_snapshot_cdc
WHERE item_id = 2;
-- expect: Copper Wire, 1200, WH-WEST (1 row)
```

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture carries a natural-business-key
  full-snapshot pair shaped for `FULL_SNAPSHOT_CDC` (the framework's other snapshot fixture pair,
  `sample_mainframe_customer_master_day1/2.csv`, is deliberately key-less, purpose-built for
  [TC-CDC-007](46_tc_cdc_007.md)'s `FULL_SNAPSHOT_CDC_NO_PK` scenario instead) -- so 2 small new
  CSV fixtures (6 rows total) and 1 new dedicated seed notebook were added, kept separate from
  every other scenario's own fixtures/seed notebook.
* **Two-step execution is intentional, not a workaround** -- the same convention already
  established by [`docs/42_tc_cdc_003.md`](42_tc_cdc_003.md)'s SCD1 Day-1/Day-2 scenario and
  [`docs/46_tc_cdc_007.md`](46_tc_cdc_007.md)'s `FULL_SNAPSHOT_CDC_NO_PK` scenario. Full-snapshot
  insert/update/delete diffing is only observable *across* two separate pipeline updates against
  the same target: a single job run landing both extracts at once would let Auto Loader's one
  triggered update see both files' rows together, which would not demonstrate a genuine "next
  full snapshot supersedes the previous one" diff. The job's own automated run therefore covers
  only Day-1 (a clean, idempotent, fully self-contained job execution); the Day-2 re-land-and-
  rerun step is documented above as a manual follow-up.
* **No explicit delete marker.** `cdc_operation_column`/`cdc_operation_mapping` are omitted
  entirely -- this scenario proves the simpler, unmarked case: a key's mere absence from the
  latest full extract is itself sufficient for `apply_changes_from_snapshot` to treat it as a
  delete, no source-side delete flag required. (An explicit delete-marker column is exercised
  elsewhere -- see `SCD1`'s `cdc_operation_column` example in
  [02_cdc_load_strategies.md](02_cdc_load_strategies.md).)
* **`target_type: "streaming_table"`**, matching every other ingestion flow in this repo. This
  field only controls whether the framework's internal quarantine-filtered "clean" view is read
  as a stream or a batch upstream of CDC dispatch (`engine/flow_registration.py`: `is_streaming
  = flow_row.target_type == "streaming_table"` for ingestion flows) -- the strategy's real
  published target table is always a genuine Streaming Table regardless
  (`cdc/snapshot.py::register_full_snapshot_cdc` always calls `dlt.create_streaming_table`), so
  this setting does not change the scenario's observable behavior; it is kept purely for
  consistency with every other ingestion flow already onboarded in this project.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but per
  `TESTING_STATUS.md`'s framing, `TESTING_PLAN.md` is a planned/aspirational matrix, not a
  literal build spec -- no other real scenario's job wires observability in by default (it's
  opt-in, added via a spec's own `observability[]` array plus a separate job). This build
  follows the real `setup_control_tables -> seed -> onboard -> run_pipeline` convention instead.
* **No DQ rules, no governance tags.** This scenario is scoped to `FULL_SNAPSHOT_CDC`'s own
  natural-key diffing behavior; DQ (`TC-DQ-*`) and governance (`TC-GOV-*`) are separate,
  already-tracked test modules with their own dedicated rows in `TESTING_PLAN.md`.
