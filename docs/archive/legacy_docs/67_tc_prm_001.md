# Test Pipeline: TC-PRM-001 -- Parameterized Dynamic Volume & File Paths

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [17_onboarding_template_reference.md §3.4](17_onboarding_template_reference.md#34-transformation_sql-parameters-union-and-the-stream-keyword).

## Purpose

Prove `transformation/parameters.py::substitute_path_parameters` -- the new capability added
this session that extends `${param}` runtime substitution into **path/URI-shaped** fields
(`source_config.path`/`schema_location`), not just SQL text. Until this pass, `${param}`
substitution only existed for `transformation_sql`/reconciliation's `transform_sql`/
`filter_condition` via the SQL-literal-quoting `substitute_dynamic_parameters` -- a string
parameter used there comes back single-quoted, which would corrupt a filesystem path
(`/Volumes/x/'2026-08-28'/y` is not a valid path). `substitute_path_parameters` is the sibling
function this scenario exercises: it renders every value via plain `str()`, never quoted, and
runs directly against the **raw JSON text** of `source_config_json`/`target_config_json`, before
`json.loads(...)` -- see `notebooks/03_engine/03_lakeflow_declarative_pipeline.py`'s
`generate_ingestion_flow`, which calls it on both fields before the config dict is ever built.

This is a **runtime** substitution (re-read fresh from `PIPELINE_PARAMETERS` on every pipeline
update), unlike the one-time `{{catalog}}`/`{{env}}` substitution `onboarding/spec_loader.py`
applies once, forever, at onboarding time -- the two mechanisms are independent and both appear
in this scenario's spec: `{{catalog}}` resolves to `metaflow` when the spec is onboarded;
`${data_domain}`/`${batch_date}` resolve to `finance_ops`/`2026-08-28` fresh every time the
pipeline updates.

## Responsibilities

* One `ingestion_flow` (`df_prm_001_daily_txns_ingest`), `source_type: "autoloader"`, plain CSV,
  `cdc_load_strategy: "APPEND"` -- landing raw daily transaction rows into
  `{{catalog}}.bronze_finance.daily_txns_raw`, no dedup, no CDC dispatch.
* Top-level `pipeline_parameters: {"data_domain": "finance_ops", "batch_date": "2026-08-28"}`,
  referenced twice: `source_config.path` uses both `${data_domain}` and `${batch_date}`;
  `source_config.schema_location` uses `${data_domain}` alone -- proving the same parameter
  substitutes correctly across two different fields, not just once incidentally.
* Land the fixture CSV directly under the **literal, fully-resolved** path
  (`/Volumes/metaflow/finance_ops/landing/2026-08-28/`) the substitution is expected to produce,
  so Auto Loader only finds the file if the substitution genuinely ran correctly end to end --
  a wrong resolution (e.g. a literal `${data_domain}` left unsubstituted, or the wrong value)
  means Auto Loader finds nothing, a visible failure rather than a silent false pass.
* Verify `__framework_source_file_name` on the landed rows names a file under that exact
  resolved path -- the concrete, queryable proof the engine actually read from the
  parameter-resolved location and not some other path.

## Inputs

* `metaflow_testing/045_prm_001_path_param.json` -- ingestion-only onboarding spec (no
  `transformation_flows`/`reconciliation_flows`), one flow: `df_prm_001_daily_txns_ingest`.
* `sample_data/metaflow_testing/finance_usecase/daily_txns_batch1.csv` -- 4 daily transaction

## Outputs

* `{{catalog}}.bronze_finance.daily_txns_raw` -- 4 rows, with `txn_id`, `account_id`, `amount`,
  `currency`, `txn_date`, plus the usual `__framework_*` technical-metadata columns
  (`capture_technical_metadata` defaults `true`, and is set explicitly here). No quarantine table
  (`dq_config.rules` is an empty list).
* `__framework_source_file_name` on every row resolves to a path containing
  `finance_ops/landing/2026-08-28/daily_txns_batch1.csv` -- the assertion this scenario exists to

  is created under the `${data_domain}`-resolved path too, proving the same placeholder resolves
  consistently across both `source_config` fields in one pipeline update.

## Configuration

`metaflow_testing/045_prm_001_path_param.json`'s one ingestion flow -- the part of this spec that
is actually new/interesting:

```json
"pipeline_parameters": {
  "data_domain": "finance_ops",
  "batch_date": "2026-08-28"
},
"ingestion_flows": [{
  "source_type": "autoloader",
  "target_catalog": "{{catalog}}",
  "target_schema": "bronze_finance",
  "target_table": "daily_txns_raw",
  "target_type": "streaming_table",
  "source_config": {
    "path": "/Volumes/{{catalog}}/${data_domain}/landing/${batch_date}/",
    "format": "csv",
    "schema_location": "/Volumes/{{catalog}}/${data_domain}/_schemas/daily_txns_raw/",
    "reader_options": {"header": "true", "cloudFiles.inferColumnTypes": "true"},
    "capture_technical_metadata": true
  },
  "target_config": {"cdc_load_strategy": "APPEND", "storage_format": "delta"}
}]
```

Note the two-layer substitution order: `{{catalog}}` is replaced with `metaflow` by
`onboarding/spec_loader.py::substitute_environment_placeholders` **once, at onboarding time**,
before the JSON is ever parsed into the control tables -- so the control table's
`source_config_json` column already reads `/Volumes/metaflow/${data_domain}/landing/${batch_date}/`
the moment onboarding completes. `${data_domain}`/`${batch_date}` are left untouched at that point
and only resolve **every time the pipeline updates**, via
`generate_ingestion_flow`'s call to `substitute_path_parameters` against
`PIPELINE_PARAMETERS` (itself re-read fresh from `GROUP_ROW.pipeline_parameters_json` on every
pipeline update, not cached from onboarding time) -- so changing `pipeline_parameters` in the
control table (e.g. re-onboarding with a new `batch_date` for the next day's batch) changes where
the *next* pipeline update reads from, with no code change and no need to touch `source_config`
again.

## Expected results -- simulation notes

**SQL assertions** (after a run, replace `{catalog}` with your actual target catalog):

```sql
-- Exactly 4 rows landed
SELECT count(*) FROM {catalog}.bronze_finance.daily_txns_raw;
-- expect: 4

-- The actual proof this scenario exists for: __framework_source_file_name resolves to the
-- ${data_domain}/${batch_date}-substituted path, not a literal "${data_domain}"/"${batch_date}"
-- string and not some other path
SELECT DISTINCT __framework_source_file_name FROM {catalog}.bronze_finance.daily_txns_raw;
-- expect every value to contain: .../finance_ops/landing/2026-08-28/daily_txns_batch1.csv

-- Equivalent, more mechanical assertion for scripted verification
SELECT count(*) FROM {catalog}.bronze_finance.daily_txns_raw
WHERE __framework_source_file_name LIKE '%/finance_ops/landing/2026-08-28/%';
-- expect: 4 (equals total row count -- every row's source file is under the resolved path)

-- Row content, unaffected by the path parameterization itself
SELECT txn_id, account_id, amount, currency, txn_date
FROM {catalog}.bronze_finance.daily_txns_raw ORDER BY txn_id;
-- expect:
--   TXN1001 | ACC5001 | 250.75   | USD | 2026-08-28
--   TXN1002 | ACC5002 | 89.10    | USD | 2026-08-28
--   TXN1003 | ACC5001 | 15000.00 | USD | 2026-08-28
--   TXN1004 | ACC5003 | 42.50    | USD | 2026-08-28
```

**Negative check, if you want to actively rule out a "silently reads the wrong path" false pass**:
land a decoy file under the *unsubstituted* literal path
(`/Volumes/metaflow/$%7Bdata_domain%7D/landing/$%7Bbatch_date%7D/` is not even a valid Volume path
component, so this isn't practically constructible -- the stronger real-world check is simply
that Auto Loader finds **zero** files, and the pipeline update either idles or errors, if the
fixture is landed under any path other than the exact resolved
`/Volumes/metaflow/finance_ops/landing/2026-08-28/` -- which is exactly why this scenario's seed
notebook computes that path from the same `data_domain`/`batch_date` values the spec declares,
rather than hardcoding a path string independently that could silently drift out of sync).

## Build notes / judgment calls

* **New fixture, new dedicated seed notebook.** No existing seeded fixture lands data under a
  `${param}`-resolved, date-partitioned Volume path, so one small new 4-row CSV fixture
  (`sample_data/metaflow_testing/finance_usecase/daily_txns_batch1.csv`) and one new seed notebook
  (`03_seed_prm_001_path_param_data.py`) were added, following this repo's established
  one-seed-notebook-per-scenario convention (e.g. `03_seed_ing_007_standardize_data.py`) rather
  than editing the shared `02_seed_metaflow_testing_data.py`.
* **`APPEND`, not a CDC strategy.** This scenario is scoped to proving path parameterization, not
  CDC/dedup behavior -- `APPEND` needs no `primary_keys` and keeps the spec minimal, matching
  several other single-flow ingestion scenarios' own choice (e.g. TC-ING-007).
* **No DQ rules, no governance tags, no encryption, no transformation/reconciliation flows.**
  Scoped narrowly to the one new capability under test.
* **`schema_location` only carries `${data_domain}`, not `${batch_date}`.** Auto Loader's schema
  tracking location is conventionally stable per source (not per landing batch), so only the
  domain-level parameter applies there -- this also incidentally proves the substitution engine
  handles a partial parameter set per field correctly (not every declared `pipeline_parameter`
  needs to appear in every path field).
