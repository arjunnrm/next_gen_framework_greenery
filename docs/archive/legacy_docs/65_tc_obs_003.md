# Test Pipeline: TC-OBS-003 — Telemetry Export to Unity Catalog Volume (`.jsonl.gz`)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 9), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [docs/25_dlt_observability_module.md](25_dlt_observability_module.md), [docs/27_dlt_observability_onboarding_reference.md](27_dlt_observability_onboarding_reference.md).

## Purpose

Prove that the pre-existing **batch** DLT observability engine
(`notebooks/08_observability/08_dlt_observability_engine.py`,
`observability/destination_dispatcher.py::dispatch_to_volume`) genuinely writes a real,
readable `.jsonl.gz` OTel export to a Unity Catalog Volume path — `destination_type:
"DATABRICKS_VOLUME"` (confirmed the correct real value; **not** `"UNITY_CATALOG_VOLUME"`, which
some docs incorrectly say). This is deliberately the same *batch* engine scenario 100's own
`dlt_observability_job.yml` already exercises — **not** this project's separate *continuous*
streaming OTel design (`observability_otel_streaming_pipeline`, see
[docs/29_test_pipeline_otel_streaming.md](29_test_pipeline_otel_streaming.md)), which is a
materially different, additive capability out of scope here.

## Responsibilities

* Reuse an already-onboarded pipeline as "the pipeline being observed" — no new Lakeflow
  pipeline resource is defined for this test case. This job reuses
  `metaflow_test_100_zipcsv_pipeline` (`dataflow.group.id = dfg_zip_csv_dataload`), the same
  pipeline `resources/dlt_observability_job.yml` already wraps.
* Add a **second, TC-OBS-003-owned** `observability_config` row —
  `destination_id: "dest-obs-003-vol-export"` — scoped to that same `dataflow_group_id`,
  additive alongside (not a replacement for) scenario 100's own pre-existing
  `"dest-dbx-volume"` row. `destination_config.volume_path` is
  `/Volumes/{{catalog}}/observability/app_logs/`, `compression: "GZIP"`, `file_format: "JSONL"`.
* Run the observed pipeline, then `08_dlt_observability_engine.py`, and confirm a real
  `.jsonl.gz` file lands under that volume path and decompresses to valid OTel-shaped
  `ResourceLogs` JSON lines.

## Inputs

* `metaflow_testing/043_obs_003_vol_export.json` — this test case's own dedicated onboarding
  spec. Its `observability[]` array carries the new destination described above. Its
  `dataflow_group_id` (`dfg_zip_csv_dataload`) **must** match the observed pipeline's own
  `dataflow.group.id` configuration entry — `observability/event_log_extractor.py::
  resolve_dataflow_group_id` resolves that group id straight from the Pipelines API at runtime
  (`pipeline.spec.configuration["dataflow.group.id"]`), independent of any control-table state,
  so this is the one value that has to line up for the new destination to actually be picked up
  by `load_destination_configs` when this pipeline's telemetry is dispatched.
* Reuses scenario 100's already-seeded landing fixtures (`/Volumes/{{catalog}}/landing/input/
  customer*/`, seeded via the existing `customer*.zip` fixtures scenario 100 already lands) — no
  new sample data was created for this test case.

## Outputs

* `{catalog}.config.observability_config` — one additional row,
  `config_id = "obscfg_dfg_zip_csv_dataload_dest-obs-003-vol-export"`, `enabled = true`,
  `destination_type = "DATABRICKS_VOLUME"`.
* A new file at
  `/Volumes/{catalog}/observability/app_logs/dfg_zip_csv_dataload/<run-date>/dfg_zip_csv_dataload_<run_pipeline_update task_run_id>.jsonl.gz`
  (naming per `destination_dispatcher.py::_volume_file_path` — deterministic
  `<dataflow_group_id>_<task_run_id>`, one file per `DATABRICKS_VOLUME` destination per
  observability task run). Because scenario 100's own `"dest-dbx-volume"` destination is also
  enabled for this same `dataflow_group_id`, **two** files land side by side for the same run —
  one per destination row — both under the identical `volume_path` prefix; this is expected, not
  a collision (the dispatcher runs once per destination, and each destination's dispatch is
  independent — see `destination_dispatcher.py::dispatch_all`).
* Each `.jsonl.gz` line, once gunzipped, is one `{"resourceLogs": [...]}` JSON object — one line
  per `ResourceLogs` entry (one per flow/update in the observed window).

## Configuration

`metaflow_testing/043_obs_003_vol_export.json`'s `observability[]` entry:

```json
{
  "id": "dest-obs-003-vol-export",
  "enabled": true,
  "type": "DATABRICKS_VOLUME",
  "destination_config": {
    "volume_path": "/Volumes/{{catalog}}/observability/app_logs/",
    "compression": "GZIP",
    "file_format": "JSONL"
  }
}
```

**Judgment call / real gap**: `onboarding/spec_validator.py::validate_spec` requires at least one
of `ingestion_flows`/`transformation_flows`/`reconciliation_flows` to be non-empty — an
observability-only spec (empty flow arrays, only an `observability[]` array) is rejected outright
(`"At least one of 'ingestion_flows', 'transformation_flows', or 'reconciliation_flows' must be
non-empty"`), even though `_validate_observability_destinations` itself carries no such
requirement. Rather than inventing new sample data or a new pipeline node just to satisfy this
rule, this spec's `ingestion_flows[]` re-declares scenario 100's own `"df_zip_csv_file_ingest"`
flow **verbatim** — identical `dataflow_id`, identical `source_config`/`target_config`/
`dq_config`. Confirmed safe: every `onboarding/metadata_upsert.py::upsert_*` function is a plain
`MERGE` keyed on that flow's own natural id (`dataflow_id` here), so onboarding this spec is a
no-op update against the exact row scenario 100's own spec already created — it neither
duplicates nor drifts that row, and `dataflow_group_spec.has_ingestion_flows`/
`has_transformation_flows` (the only fields this could otherwise disturb) are pure metadata,
read by nothing in `notebooks/03_engine/03_lakeflow_declarative_pipeline.py`. Confirmed against
the real schema (`onboarding_templates/onboarding_spec.schema.json`) and the real
`validate_spec()` function directly (not just the JSON Schema) — zero errors.

## Main execution flow

```bash
databricks bundle deploy --target dev
databricks bundle run metaflow_test_obs_003_vol_export_job --target dev
```

Task chain: `setup_control_tables → onboard_100 → onboard_obs_003 → run_pipeline_update →
observability_export`. Self-contained and idempotent — `onboard_100` re-onboards scenario 100's

`metaflow_test_100_job`/`dlt_observability_job` having already been run; re-running this job
never accumulates duplicate control-table rows or extra Volume files beyond one new file per
distinct `run_pipeline_update` task run.

## Expected results — verification logic

```python
# Databricks notebook / Python cell, after a run
import gzip, json

base = "/Volumes/metaflow/observability/app_logs/dfg_zip_csv_dataload"
run_date_dirs = dbutils.fs.ls(base)          # one subdir per UTC run date
for d in run_date_dirs:
    for f in dbutils.fs.ls(d.path):
        if f.name.endswith(".jsonl.gz"):
            local = f.path.replace("dbfs:", "")
            with gzip.open(local, "rt", encoding="utf-8") as fh:
                for line in fh:
                    payload = json.loads(line)                       # must not raise
                    rl = payload["resourceLogs"][0]                  # strict OTel shape
                    attrs = {a["key"]: a["value"] for a in rl["resource"]["attributes"]}
                    assert "databricks.dataflow_group_id" in attrs
                    for scope_log in rl["scopeLogs"]:
                        for record in scope_log["logRecords"]:
                            assert record["timeUnixNano"]
                            assert isinstance(record["severityNumber"], int)
                            assert "body" in record
            print(f.path, "OK")
```

```sql
-- Confirm the new destination row was onboarded
SELECT config_id, destination_id, enabled, destination_type, destination_config_json
FROM metaflow.config.observability_config
WHERE dataflow_group_id = 'dfg_zip_csv_dataload'
ORDER BY destination_id;
-- expect 2 rows: 'dest-dbx-volume' (scenario 100's own) and 'dest-obs-003-vol-export' (this test)

-- Ad hoc Spark SQL read of the exported JSONL straight off the Volume (auto-detects .gz)
SELECT
  filter(resourceLogs[0].resource.attributes, a -> a.key = 'databricks.dataflow_group_id')[0].value.stringValue AS group_id,
  filter(resourceLogs[0].resource.attributes, a -> a.key = 'databricks.dataflow_id')[0].value.stringValue AS dataflow_id
FROM json.`/Volumes/metaflow/observability/app_logs/dfg_zip_csv_dataload/*/*.jsonl.gz`;
```
