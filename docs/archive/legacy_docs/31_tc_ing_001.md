# Test Pipeline: Selective Glob Pattern ZIP Extraction (TC-ING-001)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 1, TC-ING-001), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md).

## Purpose

Prove that `source_config.source_zip_handling.zip_file_pattern` genuinely **filters** which
archives get extracted and ingested when the incoming Volume holds more than one ZIP file --
not just that ZIP extraction works in general (scenario 001 already proves that, but only
ever lands one uniquely-named archive per flow, so it never exercises the filtering behavior
itself). A non-matching archive must be left completely alone: not extracted, not ingested,
and not deleted or otherwise modified in the incoming Volume.

## Responsibilities

* Land 2 ZIP archives in the same incoming Volume:
  * `customer_data_20260828.zip` -- 100 rows, filename matches `zip_file_pattern:
    "customer_*.zip"`.
  * `vendor_feed_20260828.zip` -- 50 rows, filename does **not** match that pattern.
* One `ingestion_flow` (`df_ing_001_customer_zip_filter_ingest`) with `source_type:
  "autoloader"` and `source_zip_handling.enabled: true`, `zip_file_pattern: "customer_*.zip"`,
  `delete_source_after_extract: false` (so both the matching and non-matching archive's
  post-run state in the incoming Volume can be inspected).
* `cdc_load_strategy: "APPEND"` -- this scenario is about ZIP/file selection, not CDC
  behavior, so the simplest load strategy (plain streaming append, no `primary_keys`)
  keeps the flow focused on the one thing under test.

## Inputs

* `flowx_testing/010_ing_001_zip_filter.json` -- single-ingestion-flow onboarding spec (no
  `transformation_flows`/`reconciliation_flows`).
* `sample_data/flowx_testing/crm_usecase/customer_data.csv` (100 rows) /
  `vendor_feed.csv` (50 rows) -- generated by
  `sample_data/flowx_testing/crm_usecase/generate_crm_zip_filter_fixtures.py`.
* `notebooks/00_seed_sample_data/03_seed_ing_001_zip_filter_data.py` -- a **new, dedicated**
  seed notebook (kept separate from `02_seed_flowx_testing_data.py`, which belongs to
  scenarios 001/002/003) that provisions the `crm`/`bronze_crm` schemas and
  `landing_zip`/`_schemas` Volumes, then zips each CSV fixture directly on-cluster into
  `/Volumes/{{catalog}}/crm/landing_zip/incoming/` -- the same "build the archive bytes
  in-process" convention `02_seed_flowx_testing_data.py` already uses for scenario 001's
  own ZIPs, since workspace-bundle sync can mangle a pre-built `.zip` upload.

## Outputs

* `{{catalog}}.bronze_crm.customer_raw` -- exactly 100 rows, all sourced from
  `customer_data_20260828.zip`.
* `vendor_feed_20260828.zip` remains untouched in
  `/Volumes/{{catalog}}/crm/landing_zip/incoming/` (not extracted, not deleted).
* No `vendor_feed` records anywhere in `{{catalog}}.bronze_crm.customer_raw` or in
  `/Volumes/{{catalog}}/crm/landing_zip/extracted/customer/` -- that extract Volume should
  contain only the CSV unpacked from `customer_data_20260828.zip`.

## Configuration

`flowx_testing/010_ing_001_zip_filter.json`'s one `ingestion_flows[]` entry:

```json
"source_config": {
  "path": "/Volumes/{{catalog}}/crm/landing_zip/extracted/customer/",
  "format": "csv",
  "schema_location": "/Volumes/{{catalog}}/crm/_schemas/customer/",
  "source_zip_handling": {
    "enabled": true,
    "source_zip_path": "/Volumes/{{catalog}}/crm/landing_zip/incoming/",
    "zip_file_pattern": "customer_*.zip",
    "target_volume_path": "/Volumes/{{catalog}}/crm/landing_zip/extracted/customer/",
    "delete_source_after_extract": false
  }
}
```

`target_config: {"cdc_load_strategy": "APPEND", "storage_format": "delta"}` -- plain
streaming table, no primary keys.

## Build notes / judgment calls

* **New fixtures, not a reuse.** No existing seeded fixture matches this scenario's exact
  requirement (2 specific archives with specific, verification-critical row counts of 100 and
  50 landing in the same incoming Volume), so 2 new CSV fixtures and 1 new dedicated seed
  notebook were added rather than extending `02_seed_flowx_testing_data.py` -- kept separate
  so this test case's build/run never touches scenarios 001/002/003's own shared seed step.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column for TC-ING-001 names a second `run_observability_task` step, but per
  `TESTING_STATUS.md`'s framing, `TESTING_PLAN.md` is a planned/aspirational matrix, not a
  literal build spec -- no other real scenario's job wires observability in by default (it's
  opt-in, added via a spec's own `observability[]` array plus a separate job, as scenario 100's
  `dlt_observability_job.yml` does). This build follows the real
  `setup_control_tables → seed → onboard → run_pipeline` convention instead; observability can
  be layered on later the same way scenario 100's was, if desired.
