# Test Pipeline: TC-ING-008 -- Technical Metadata Enrichment & Column Ordering

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 1, TC-ING-008), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md).

## Purpose

Prove that the framework's technical-metadata enrichment (`source_config.capture_technical_metadata`,
defaulting `true` -- [ingestion/technical_metadata.py](../src/NextGen_Metadata_Framework/lakeflow_framework/ingestion/technical_metadata.py))
lands the correct, *current* set of `__framework_*` columns on a plain CSV Auto Loader
ingestion, and that business columns always occupy the leading positions of the target
table's schema -- never pushed behind the framework's own generated columns.

**Doc-drift note (read this before trusting any other document's column list):** this
session confirmed `metaflow_testing/TESTING_PLAN.md`'s own narrative for this test case names
7 columns (`_rescued_data` plus 6 `__framework_*` names) and its header claims "8". Neither
number matches the real code. The two source-of-truth functions actually wired into the
ingestion path (`notebooks/03_engine/03_lakeflow_declarative_pipeline.py::_build_ingestion_dataframe`
and `engine/flow_registration.py::register_staged_view`) are:

* [`ingestion/technical_metadata.py`](../src/NextGen_Metadata_Framework/lakeflow_framework/ingestion/technical_metadata.py)
  -- `attach_technical_metadata` (4 columns) + `attach_framework_ingestion_timestamp` (1 column).
* [`dq/quarantine.py`](../src/NextGen_Metadata_Framework/lakeflow_framework/dq/quarantine.py)
  -- `add_quarantine_columns`, which runs **unconditionally** on every flow (not only when
  `dq_config.rules` is non-empty) and always attaches 5 more columns.

That's **10** real `__framework_*` columns, plus the native (not `__framework_`-prefixed)
Auto Loader `_rescued_data` column -- see Configuration below for the exact list and order.

## Responsibilities

* Land a plain (non-ZIP) CSV file into a dedicated `ea`/`bronze_ea` landing Volume.
* One `ingestion_flow` (`df_ing_008_dept_tech_metadata_ingest`) with `source_type:
  "autoloader"`, `format: "csv"`, and `capture_technical_metadata: true` -- explicitly set,
  even though it only reasserts the function's own default, so the spec self-documents the
  behavior under test.
* `cdc_load_strategy: "APPEND"`, no `primary_keys`/`liquid_clustering_columns` -- this
  scenario is about column presence/ordering, not CDC or Delta-stats behavior, so
  [`storage/column_ordering.py::reorder_columns_for_delta_stats`](../src/NextGen_Metadata_Framework/lakeflow_framework/storage/column_ordering.py)
  is a deliberate no-op here: with no `primary_keys`/`liquid_clustering_columns` and no
  surrogate/hash columns generated, its front-priority list matches nothing on this
  DataFrame, so it returns the DataFrame **unchanged** -- the append-order column sequence
  from the read is exactly what lands in the target table.

## Expected results -- simulation notes

**Row count** (after a run, replace `{catalog}` with your actual target catalog):

```sql
SELECT count(*) FROM {catalog}.bronze_ea.departments_tech_metadata_raw;
-- expect: 4
```

**Schema-order assertion** -- the core claim of this test case. `ordinal_position` in
`information_schema.columns` reflects the table's actual physical column order:

```sql
SELECT column_name, ordinal_position
FROM {catalog}.information_schema.columns
WHERE table_catalog = '{catalog}'
  AND table_schema = 'bronze_ea'
  AND table_name = 'departments_tech_metadata_raw'
ORDER BY ordinal_position;
-- expect, in this exact order:
--  0 dept_id
--  1 dept_name
--  2 region
--  3 _rescued_data
--  4 __framework_source_file_name
--  5 __framework_source_file_size
--  6 __framework_source_file_modification_time
--  7 __framework_source_file_metadata_headers
--  8 __framework_ingestion_timestamp_utc
--  9 __framework_dq_failed_rule_ids
-- 10 __framework_dq_failure_reasons
-- 11 __framework_dq_quarantine_flag
-- 12 __framework_pipeline_run_id
-- 13 __framework_record_id

-- Equivalent single-boolean assertion: every business column's ordinal_position must be
-- strictly less than every _rescued_data/__framework_* column's ordinal_position.
SELECT
  max(CASE WHEN column_name IN ('dept_id', 'dept_name', 'region') THEN ordinal_position END)
    < min(CASE WHEN column_name = '_rescued_data' OR column_name LIKE '\_\_framework\_%' THEN ordinal_position END)
  AS business_columns_precede_technical_columns
FROM {catalog}.information_schema.columns
WHERE table_catalog = '{catalog}' AND table_schema = 'bronze_ea'
  AND table_name = 'departments_tech_metadata_raw';
-- expect: true
```

**Column-population assertion** -- technical metadata columns must actually be populated
(non-null), not merely present:

```sql
SELECT
  count(*) AS total_rows,
  count(__framework_source_file_name) AS non_null_file_name,
  count(__framework_source_file_size) AS non_null_file_size,
  count(__framework_source_file_modification_time) AS non_null_file_mod_time,
  count(__framework_ingestion_timestamp_utc) AS non_null_ingestion_ts,
  count(_rescued_data) AS non_null_rescued_data
FROM {catalog}.bronze_ea.departments_tech_metadata_raw;
-- expect: total_rows = 4, all four __framework_* counts = 4;
-- non_null_rescued_data = 0 (all 4 rows have a clean 3-column match, nothing to rescue)
```

## Build notes / judgment calls

* **Target table renamed to avoid a real collision.** Both this test case's own brief and
  `TESTING_PLAN.md` name the target table `{{catalog}}.bronze_ea.departments_raw` -- but that
  exact three-part name is already the real, live target of scenario 001's
  `df_ea_departments_ingest` flow (`metaflow_testing/001_zip_file_onboarding.json`,
  `resources/metaflow_test_001_zip_join_export_pipeline.yml`). Two independent Lakeflow
  Declarative Pipelines cannot both own/materialize a streaming table under the identical
  catalog.schema.table name -- whichever job ran second would fail against the other
  pipeline's already-existing table ownership. Rather than silently letting that collision
  surface later (in the centralized deploy/run phase, across 45 test cases at once), this
  build uses `departments_tech_metadata_raw` instead, keeping the same `bronze_ea` schema and
  the same underlying EA department reference data semantics. This is a genuine, deliberate
  deviation from the literal brief -- flagged here rather than silently building something
  that would break scenario 001 (or itself) when actually run.
* **Reused fixture, not a new one.** `sample_data/metaflow_testing/ea_usecase/departments.csv`
  already carries `dept_id`/`dept_name` (plus one extra `region` business column) across 4
  rows -- it was reused as-is per this project's "reuse before inventing new sample data"
  convention, landed as a plain CSV rather than scenario 001's ZIP-wrapped copy of the same
  file. The extra `region` column doesn't weaken the schema-order assertion (if anything, it
  strengthens it: 3 business columns must precede the technical ones, not just 2).
  `source_zip_handling` is intentionally absent from this flow's `source_config` -- unlike
  scenario 001, this file lands unzipped.
* **No `run_observability_task`.** `TESTING_PLAN.md`'s own "Proposed Pipeline & Job
  Architecture" column names a second `run_observability_task` step, but per
  `TESTING_STATUS.md`'s framing and the precedent already set by
  [docs/31_tc_ing_001.md](31_tc_ing_001.md)'s own build notes, `TESTING_PLAN.md` is a
  planned/aspirational matrix, not a literal build spec -- observability is opt-in (a spec's
  own `observability[]` array plus a separate job, as scenario 100's does), not part of the
  default `setup_control_tables -> seed -> onboard -> run_pipeline` chain every other real
  scenario in this repo follows.
