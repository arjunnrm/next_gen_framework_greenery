# Test Pipeline: Governance Tag Application Idempotency (TC-GOV-002)

> See also: [Documentation index](README.md), [flowx_testing/TESTING_PLAN.md](../flowx_testing/TESTING_PLAN.md) (Module 6, TC-GOV-002), [flowx_testing/TESTING_STATUS.md](../flowx_testing/TESTING_STATUS.md), [06_governance_integration.md](06_governance_integration.md) (ground truth for the tags-only model this scenario exercises).

## Purpose

Prove that re-running `notebooks/04_governance/04_apply_governance_and_egress.py` against a
target table that **already carries** its governance tags is safe: no DDL conflict, no metadata
lock contention, no corrupted or duplicated tag state. `ALTER TABLE ... SET TAGS` / `ALTER TABLE
... ALTER COLUMN ... SET TAGS` is a plain key-value upsert, not a ledgered operation -- see
[06_governance_integration.md §4](06_governance_integration.md#4-idempotency-why-no-ledger-is-needed),
which is why this framework carries no `governance_applied_log` control table or
`governance/idempotency.py` module. This scenario is the dedicated, repeated-invocation proof of
that design claim: run the exact same tagging pass three times in a row and confirm all three
succeed, with the tag values unchanged after the third run.

## Responsibilities

* Re-invoke `apply_all_governance_tags` (via the same notebook, same widget parameters) three
  times in strict sequence against the same already-onboarded dataflow group and the same
  already-materialized target table -- no new spec, no new pipeline, no new fixture data.
* Each invocation is a full, independent `ALTER TABLE ... SET TAGS` re-execution (not a
  ledger-skip) -- the point is that the *DDL itself* is naturally idempotent, not that the
  framework detects "already applied" and no-ops.

## Inputs

* **No new onboarding spec.** This scenario reuses TC-GOV-001's exact same onboarded flow and
  tags:
  * Catalog: `flowx` (the `{{catalog}}` placeholder resolves to this for every resource in this
    repo)
  * Schema: `bronze_crm`
  * Target table: `customer_raw`
  * `dataflow_group_id`: `dfg_gov_001_tagging`
  * `table_tags`: `{"domain": "finance", "compliance": "sox"}`
  * `column_tags`: `CustomerID` -> `{"classification": "restricted", "mask": "PII"}`

  See `flowx_test_gov_001_tagging_job.yml` / `flowx_test_gov_001_tagging_pipeline.yml` (TC-GOV-001)
  for the spec that onboards this group and the pipeline that materializes `customer_raw` in the
  first place.
* `notebooks/04_governance/04_apply_governance_and_egress.py` -- unmodified; called with
  `apply_abac`/`capture_cdc_change_counts` left at their coded widget defaults (`true`/`true`),
  same as every other governance invocation.

## Outputs

* Three independent job task runs (`apply_governance_run_1/2/3`), each expected to end
  `SUCCESS` (exit code 0).
* `system.information_schema.table_tags` for `flowx.bronze_crm.customer_raw` -- still exactly
  `domain: finance`, `compliance: sox` after the third run (unchanged from after the first).
* `system.information_schema.column_tags` for the same table's `CustomerID` column -- still
  exactly `classification: restricted`, `mask: PII` after the third run.
* No new control-table rows anywhere -- governance has no dedicated control table
  (`01_control_metadata_schema.md` §1), so "ran 3 times" leaves no ledger artifact to inspect;
  the only observable effect is the tag state itself, which must be identical before/after.

## Configuration

`resources/flowx_test_gov_002_idempotent_tag_job.yml` -- three `notebook_task` entries, chained
`depends_on`, each calling the identical notebook with the identical `base_parameters`:

```yaml
base_parameters:
  catalog: flowx
  dataflow_group_id: dfg_gov_001_tagging
```

`apply_abac` and `capture_cdc_change_counts` are intentionally omitted from `base_parameters` --
the notebook's own widget defaults (`"true"`/`"true"`) apply, matching how TC-GOV-001's own job
invokes it, so this scenario tests genuine repeat invocation under normal parameters rather than a
specially reduced configuration.

## Main execution flow

```bash
databricks bundle deploy --target dev
# TC-GOV-001's own job must have been run at least once first, so customer_raw exists and
# already carries its tags before this job's first task starts:
databricks bundle run flowx_test_gov_001_tagging_job --target dev
databricks bundle run flowx_test_gov_002_idempotent_tag_job --target dev
```

Task chain: `apply_governance_run_1 -> apply_governance_run_2 -> apply_governance_run_3`. No
`setup_control_tables`/seed/onboard/pipeline tasks in this job on purpose -- this scenario is
scoped narrowly to the tagging task's own repeat-invocation safety, not a re-test of onboarding or
pipeline-build behavior (both already covered by TC-GOV-001 and, more generally, TC-ING-001/etc.).

## Expected results — simulation notes

**Execution assertion** (per `flowx_testing/TESTING_PLAN.md`'s own row for this test case):
all 3 runs return exit code 0; tags remain active and uncorrupted in Unity Catalog.

```sql
-- Run before AND after this job, compare results -- expect byte-for-byte identical rows both times.
SELECT tag_name, tag_value
FROM system.information_schema.table_tags
WHERE catalog_name = 'flowx' AND schema_name = 'bronze_crm' AND table_name = 'customer_raw'
ORDER BY tag_name;
-- expect: compliance -> sox, domain -> finance (both times)

SELECT column_name, tag_name, tag_value
FROM system.information_schema.column_tags
WHERE catalog_name = 'flowx' AND schema_name = 'bronze_crm' AND table_name = 'customer_raw'
ORDER BY column_name, tag_name;
-- expect: CustomerID -> classification -> restricted, CustomerID -> mask -> PII (both times)
```

Job-run assertion: all three tasks (`apply_governance_run_1`, `_run_2`, `_run_3`) show `SUCCESS`
in the Jobs UI / `databricks jobs get-run` output, with no `AbacApplicationError` in any task's
logs.

## Build notes / judgment calls

* **Real gap: TC-GOV-001 did not exist in this repo at the time this scenario was built.**
  `flowx_testing/TESTING_STATUS.md` lists it as "Not Started," and no
  `flowx_test_gov_001_tagging_*` spec/resource files were present. Per this build pass's scope
  discipline, building TC-GOV-001 itself is out of bounds for this task (a separate, parallel
  build owns it). This job resource therefore references TC-GOV-001's expected coordinates --
  catalog `flowx`, schema `bronze_crm`, table `customer_raw`, and `dataflow_group_id
  dfg_gov_001_tagging` -- inferred from `flowx_testing/TESTING_PLAN.md`'s own TC-GOV-001 row
  plus this repo's strict, universally-observed naming convention (every existing spec's
  `dataflow_group_id` is `dfg_<the job name's own middle segment>`, e.g. `dfg_dq_001_warn` for
  `flowx_test_dq_001_warn_job`, `dfg_ing_001_zip_filter` for
  `flowx_test_ing_001_zip_filter_job`). If TC-GOV-001 is ultimately built with a different
  `dataflow_group_id`, this job's `base_parameters` need a one-line update to match.
* **No new pipeline resource, no new onboarding spec, no new fixture data** -- exactly per this
  task's own instructions: this scenario is entirely about the idempotency of one already-proven
  notebook call, not about DAG shape or ingestion behavior, so it adds only the one job resource.
* **Omitted `setup_control_tables`/seed/onboard/pipeline tasks.** Every other job in this repo
  chains those first; this one deliberately does not, because doing so would make it a redundant
  re-test of TC-GOV-001's own onboarding/pipeline-build path rather than a focused test of repeat
  tagging invocation. This job's first task assumes `customer_raw` already exists and already
  carries TC-GOV-001's tags -- i.e. TC-GOV-001's own job must run at least once before this one.
* **`apply_abac`/`capture_cdc_change_counts` left at notebook defaults** rather than pinned
  explicitly in `base_parameters`, so this scenario exercises the same code path TC-GOV-001's own
  job invokes, not a specially reduced one.
