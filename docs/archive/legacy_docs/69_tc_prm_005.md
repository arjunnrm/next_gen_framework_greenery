## Purpose

Prove `transformation/parameters.py::substitute_path_parameters` — this session's new
`${param}`-in-path-fields feature — on a **sink** target's `target_config.sink_config`, not just
an ingestion source's `source_config` (that's TC-PRM-001; see
`flowx_testing/045_prm_001_path_param.json` and [67_tc_prm_001.md](67_tc_prm_001.md)). A small
ACME Corp export-staging batch is
Auto Loader-ingested and, inside the *same* Lakeflow Declarative Pipeline update, additionally
exported as a ZIP archive via a genuine `dlt.create_sink(format="pgp_zip")` + `@dlt.append_flow`.
`pipeline_parameters: {"client_code": "ACME_CORP", "export_tier": "GOLD"}` are substituted into
`sink_config.path` and `post_export_archive.output_zip_path` fresh on every pipeline update —
never at onboarding time — so the egress Volume path is resolved dynamically per client, a
realistic multi-tenant egress shape (each client gets its own Unity Catalog Volume,
`{catalog}.egress.{client_code}`).

This scenario **also** deliberately demonstrates a second, wholly unrelated templating mechanism
living right next to the first one — `archive/pgp_zip_sink.py`'s `export_file_name_format`, a
plain Python `str.format()` template with its own placeholders (`{batch_id}`/`{timestamp}`),
resolved at commit time by the sink's driver-side writer directly from the microbatch id and the
UTC clock. See "Known gaps / judgment calls" below for exactly why these two mechanisms are kept
separate in this build, contrary to `TESTING_PLAN.md`'s own drafted row for this test case.

## Responsibilities

* One ingestion flow (`df_prm_005_acme_export_ingest`), `source_type: "autoloader"`,
  `cdc_load_strategy: "APPEND"` — deliberately the simplest CDC strategy, since this scenario's
  whole point is path/filename parameterization, not CDC behavior (APPEND + autoloader still
  publishes a genuine Lakeflow Streaming Table, which `target_type: "external_sink"` requires of
  the main target before it will attach the export `@dlt.append_flow` — every CDC strategy except
  `SCD3` satisfies this).
* `target_type: "external_sink"` — `flowx.silver_exports.acme_export_staging` is materialized as
  a real, governed, queryable Delta table exactly like any other target type, **plus** a second
  `@dlt.append_flow` reads that same table into a `dlt.create_sink(format="pgp_zip", ...)`.
* `sink_config.path` (staging) and `sink_config.post_export_archive.output_zip_path` (final egress
  destination) both carry `${client_code}`/`${export_tier}` placeholders — resolved against this
  spec's own `pipeline_parameters` by `substitute_path_parameters`, applied to the raw
  `target_config_json` text before `json.loads(...)`, so both fields resolve in a single pass:
  * `sink_config.path`: `"/Volumes/{{catalog}}/egress/${client_code}/_staging/${export_tier}/"` →
    `/Volumes/flowx/egress/ACME_CORP/_staging/GOLD/`
  * `post_export_archive.output_zip_path`:
    `"/Volumes/{{catalog}}/egress/${client_code}/output/"` →
    `/Volumes/flowx/egress/ACME_CORP/output/`
* No `post_export_archive.pgp_encryption` block — unlike TC-SNK-003, this scenario exports a plain
  (unencrypted) `.zip`, keeping the test focused on path/filename parameterization rather than
  encryption.
* `export_file_name_format: "acme_export_{batch_id}_{timestamp}"` — the pre-existing
  `str.format()` mechanism, using **only** its own supported placeholders (`{batch_id}`,
  `{timestamp}`), never `${client_code}`/`${export_tier}`.

## Inputs

* `flowx_testing/047_prm_005_sink_param.json` — the onboarding spec (one ingestion flow, no
  transformation/reconciliation flows).
* `sample_data/flowx_testing/acme_export_usecase/acme_export_staging.csv` — 5-row plaintext
  fixture (`export_id`, `client_code`, `export_tier`, `account_ref`, `amount`, `export_date`),
  landed as-is. Its own `client_code`/`export_tier` *column values* happen to match the spec's
  `pipeline_parameters` (both `ACME_CORP`/`GOLD`) for a coherent scenario narrative, but this is
  purely cosmetic — path resolution is driven entirely by `pipeline_parameters`, never by row data.
* `notebooks/00_seed_sample_data/03_seed_prm_005_sink_param_data.py` — lands
  `acme_export_staging.csv` into the input landing Volume (`exports_ingest.landing`) and
  provisions the per-client sink output Volume (`egress.ACME_CORP`) — a sink's destination Volume
  is never auto-created by the pipeline itself, unlike the pipeline's own default `catalog`/
  `schema` (here `flowx.silver_exports`).

## Outputs

* `{catalog}.silver_exports.acme_export_staging` — 5 rows, in plaintext, exactly matching
  `acme_export_staging.csv`'s content, plus the usual `__framework_*` technical metadata columns —
  a genuine, queryable Unity Catalog table (the "dual materialization" half of `external_sink`).
* `/Volumes/{catalog}/egress/ACME_CORP/output/acme_export_<batch_id>_<timestamp>.zip` — one plain
  (unencrypted) archive per micro-batch, landed in the **client-code-parameterized** Volume path.
  Its entries are the micro-batch's rows as JSON-Lines (`archive/pgp_zip_sink.py`'s staging
  format), covering all 5 export rows across however many micro-batches Auto Loader's single input
  file produces (typically one).
* `information_schema.tables` shows `acme_export_staging` as a real table (unlike a pure `"sink"`
  target type, which registers no table at all — see TC-SNK-002).

## Configuration

`flowx_testing/047_prm_005_sink_param.json`'s one ingestion flow's `target_config`:

```json
"target_config": {
  "cdc_load_strategy": "APPEND",
  "storage_format": "delta",
  "sink_config": {
    "path": "/Volumes/{{catalog}}/egress/${client_code}/_staging/${export_tier}/",
    "format": "pgp_zip",
    "post_export_archive": {
      "enabled": true,
      "output_zip_path": "/Volumes/{{catalog}}/egress/${client_code}/output/",
      "export_file_name_format": "acme_export_{batch_id}_{timestamp}"
    }
  }
}
```

`{{catalog}}` is resolved once, at onboarding time, by `onboarding/spec_loader.py`. `${client_code}`
and `${export_tier}` are resolved fresh on **every pipeline update**, by
`substitute_path_parameters`, from `pipeline_parameters: {"client_code": "ACME_CORP",
"export_tier": "GOLD"}` at the top of the same spec — the two substitutions are independent
mechanisms that happen to compose in the same string. `{batch_id}`/`{timestamp}` in
`export_file_name_format` are resolved later still, at commit time, by
`archive/pgp_zip_sink.py::_PgpZipStreamWriter._render_export_file_name` — a third, completely
separate resolution step, never touched by either of the above.

## Known gaps / judgment calls

* **`export_file_name_format` deliberately does NOT use `${client_code}`/`${export_tier}`, contrary
  to `TESTING_PLAN.md`'s own drafted row.** `TESTING_PLAN.md`'s TC-PRM-005 description combines both
  mechanisms into one string — `"export_file_name_format": "${client_code}_${export_tier}_export_
  {batch_id}"` — implying the exported filename itself would read `ACME_CORP_GOLD_export_<batch_id>
  .zip`. This build's own task instructions explicitly called this out as two **different**
  mechanisms that must not be conflated in the spec or this doc: `substitute_path_parameters` (this
  session's new feature) only ever needs to run against `sink_config.path`/
  `post_export_archive.output_zip_path` to prove the new capability; `export_file_name_format` is a
  pre-existing, independent `str.format()` template whose only documented, supported placeholders
  are `{batch_id}`/`{timestamp}` (`archive/pgp_zip_sink.py::_render_export_file_name` raises
  `ArchiveError` on any other placeholder it doesn't recognize inside the format string *after*
  `${...}` substitution has already run). Note this is **not** a hard technical limitation of
  `substitute_path_parameters` itself — that function runs against the *entire* raw
  `target_config_json` text (per `transformation/parameters.py`'s own docstring: "applies uniformly
  to every string value the JSON contains"), so `${client_code}` embedded inside
  `export_file_name_format` too would, mechanically, also get substituted before `pgp_zip_sink.py`
  ever sees it. The two mechanisms were kept separate here as a deliberate test-design choice (per
  this build's explicit instructions), not because mixing them would fail — so the exported archive
  name in this build is `acme_export_<batch_id>_<timestamp>.zip`, not
  `ACME_CORP_GOLD_export_<batch_id>.zip` as `TESTING_PLAN.md`'s row would suggest. A future pass
  wanting to prove the filename can *also* carry `${param}` text (exercising the interaction between
  the two mechanisms deliberately, rather than avoiding it) would need a new/updated test case, not
  a change to this one.
* **New fixture, not a reused one.** No existing seeded table/CSV in this repo carries an
  ACME-Corp-shaped, per-client export-staging record (`client_code`/`export_tier` columns) or a
  client-code-named egress Volume — `sample_data/flowx_testing/acme_export_usecase/
  acme_export_staging.csv` (5 rows) and its own seed notebook were created new, kept minimal per
  this build's scope-discipline instructions.
* **No `post_export_archive.pgp_encryption` block.** Included only in TC-SNK-003 (which
  specifically proves PGP-encrypted egress); this scenario proves path/filename parameterization
  only, so the exported archive is a plain, unencrypted `.zip` — matching the task's own
  verification wording ("a `.zip` lands there", not `.zip.pgp`).
