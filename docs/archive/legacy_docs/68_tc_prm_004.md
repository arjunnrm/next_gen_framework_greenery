# Test Pipeline: Parameterized DQ Rule Expressions (TC-PRM-004)

> See also: [Documentation index](README.md), [metaflow_testing/TESTING_PLAN.md](../metaflow_testing/TESTING_PLAN.md) (Module 11, TC-PRM-004), [metaflow_testing/TESTING_STATUS.md](../metaflow_testing/TESTING_STATUS.md), [17_onboarding_template_reference.md](17_onboarding_template_reference.md) §3.4 / §4.7.

## Purpose

`TESTING_PLAN.md`'s TC-PRM-004 describes a `dq_config` rule whose expression itself contains
`${param}` placeholders (`"txn_amount <= ${max_allowed_txn_limit} AND txn_date >=
'${cutoff_date}'"`), substituted from `pipeline_parameters` the same way `transformation_sql`
and reconciliation's `filter_condition`/`transform_sql` already are.

**This build pass confirmed that mechanism does not exist in the framework today.** Before
writing this spec, every call site of `substitute_dynamic_parameters`/`substitute_path_parameters`
was located by grepping `onboarding/spec_validator.py`, `transformation/parameters.py`,
`transformation/inputs.py`, `reconciliation/appender.py`, `reconciliation/dataset_reader.py`,
`control_plane/repository.py`, and `control_plane/ddl_definitions.py` -- and, separately, `dq/`
was grepped directly (`dq/quarantine.py`, `dq/expectations.py`) for any `${`/`pipeline_parameters`
reference at all: **zero matches**. `dq_config.rules[].expression` is passed straight through,
verbatim, into the native Lakeflow expectation / quarantine-flag expression -- no substitution
pass ever touches it. `17_onboarding_template_reference.md` §3.4 independently confirms this in
prose: `${param}` substitution is wired into `transformation_sql`, reconciliation's
`filter_condition`/`transform_sql`, and `source_config`/`target_config` **path** fields only, and
explicitly calls out that it is "Not wired into `dq_config` or
`observability_config.destination_config.volume_path`."

So this test case cannot be built as literally described in `TESTING_PLAN.md` -- there is no
configuration that makes `${max_allowed_txn_limit}`/`${cutoff_date}` resolve inside a DQ rule
expression today. What *can* be built, and is built here, is the same rule with the same two
literal values (`50000` / `2026-01-01`) hand-copied into the expression instead of the
placeholders, proving the `quarantine`-action mechanics genuinely work for a two-condition
`AND` boundary expression, while documenting the missing substitution path as a real,
independently-confirmed framework gap rather than a build mistake.

## Responsibilities

* One `ingestion_flow` (`df_prm_004_txns_validated_ingest`), `source_type: "autoloader"`,
  `cdc_load_strategy: "APPEND"` -- the simplest load strategy, so the flow stays focused on DQ
  rule/parameter behavior only (same convention as TC-DQ-001/002/004).
* `pipeline_parameters: {"max_allowed_txn_limit": 50000, "cutoff_date": "2026-01-01"}` is
  declared on the spec for structural fidelity to `TESTING_PLAN.md`'s own TC-PRM-004 shape, even
  though nothing in this ingestion-only spec (no `transformation_flows`/`reconciliation_flows`)
  ever consumes it -- `dq_config` can't, and there's no other flow type here that could.
* `dq_config.rules[]` carries exactly one rule, `valid_txn_bounds`: `"txn_amount <= 50000 AND
  txn_date >= '2026-01-01'"`, `action: "quarantine"` -- the literal-value stand-in for the
  placeholder expression `TESTING_PLAN.md` describes.
* 8 fixture rows (see Inputs) deliberately split across all four combinations of the rule's two
  conditions -- pass-both, fail-amount-only, fail-date-only, fail-both -- so the test proves
  quarantine routing works for *either* half of the combined `AND` expression independently, not
  only the amount bound `TESTING_PLAN.md`'s own simplified SQL assertion checks.

## Build notes / judgment calls

* **The core finding of this test case is a framework gap, not a build workaround.**
  `${param}` substitution inside `dq_config.rules[].expression` is not implemented anywhere in
  the currently-deployed code -- confirmed by grepping every `substitute_dynamic_parameters`/
  `substitute_path_parameters` call site (none touch `dq/quarantine.py` or `dq/expectations.py`)
  and independently corroborated by `17_onboarding_template_reference.md` §3.4's own prose. As
  literally specified, `TESTING_PLAN.md`'s TC-PRM-004 (`${max_allowed_txn_limit}`/`${cutoff_date}`
  inside the DQ expression) is not buildable today. This spec instead uses the same two values
  as literals in the expression, which faithfully exercises the *quarantine* mechanics the test
  case cares about, while `pipeline_parameters` is retained on the spec (unused) purely to keep
  the spec's shape recognizable against the plan.
* **New fixture, not a reuse.** No existing CSV fixture has both a `txn_amount` and `txn_date`
  column combination exercising this rule's exact boundary values, so one new 8-row CSV
  (`txns_dq_param.csv`) and one new dedicated seed notebook were added, reusing the existing
  `txns_usecase/` fixture-domain directory (established by TC-DQ-002) rather than creating a new
  domain directory, since both scenarios share the same transaction-feed use case.
* **8 rows, 4/4 pass/quarantine split, covering all four condition combinations.** Chosen over a
  larger volume so the split is trivially checkable by row count while still proving the
  `AND` expression's two halves are each independently capable of triggering quarantine (not
  just the amount bound, which is all `TESTING_PLAN.md`'s own SQL assertion for this test case
  checks).
* **`cdc_load_strategy: "APPEND"`.** Same convention as every other DQ-focused test case
  (TC-DQ-001/002/004) -- the simplest load strategy, so nothing about CDC dispatch is in play
  while the DQ rule/parameter behavior is what's actually under test.
