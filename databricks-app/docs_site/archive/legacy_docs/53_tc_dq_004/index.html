    Test Pipeline: DQ Action quarantine Routing & Diagnostics (TC-DQ-004)¶

    See also: Documentation index, metaflow_testing/TESTING_PLAN.md (Module 4, TC-DQ-004), metaflow_testing/TESTING_STATUS.md.

    Purpose¶

    Prove that a dq_config rule with action: "quarantine" -- this framework's own extension, with no native Lakeflow equivalent -- genuinely reroutes a failing row to a companion <table>_quarantine table enriched with diagnostic columns, while a passing row proceeds downstream into the main target table untouched. This scenario deliberately exercises two independent quarantine-action rules on the same flow (Country IS NOT NULL, an Email format check), unlike TC-DQ-001/002/003's single-rule builds, to prove __framework_dq_failed_rule_ids correctly enumerates which rule(s) a given row failed, not merely that it failed some rule. Companion to docs/50_tc_dq_001.md ("warn") -- "drop" (TC-DQ-002) and "fail" (TC-DQ-003) remain Not Started as of this build (see TESTING_STATUS.md).

    Responsibilities¶

    • Land 10 customer rows (scaled down from TESTING_PLAN.md's 85/10/5 template to a minimal 8/1/1, per this pass's "minimal, real, onboardable" convention) as a single plain CSV in /Volumes/{{catalog}}/test/landing_dq_quarantine/ -- 1 of the 10 (CUST006) has a null Country, 1 (CUST007) has a malformed Email, the other 8 are fully valid.
    • One ingestion_flow (df_dq_004_customer_quarantine_ingest) with source_type: "autoloader" and exactly two dq_config.rules[] entries, both action: "quarantine": dq_customer_country_not_null (Country IS NOT NULL) and dq_customer_email_format_valid (Email IS NOT NULL AND Email RLIKE '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$').
    • record_id_column: "CustomerID" -- surfaced as __framework_record_id on quarantined rows, so a failing row's original business key survives into the quarantine table for diagnostics.
    • cdc_load_strategy: "APPEND" -- this scenario is about DQ quarantine-routing semantics, not CDC behavior, so the simplest load strategy (plain streaming append, no primary_keys) keeps the flow focused on the one thing under test (same convention as TC-DQ-001).
    • Reuses scenario 100's exact dq_config shape (rules[] + quarantine_table + record_id_column, following its Country_not_null rule pattern almost verbatim) rather than inventing a new one -- per this build's own instruction to treat scenario 100 as the reference quarantine implementation.

    Inputs¶

    • metaflow_testing/032_dq_004_quarantine.json -- single-ingestion-flow onboarding spec (no transformation_flows/reconciliation_flows).
    • sample_data/metaflow_testing/crm_usecase/customer_dq_quarantine.csv (10 rows, columns CustomerID, CustomerName, Country, Email) -- new fixture, added alongside this test case's build (see Build notes).
    • notebooks/00_seed_sample_data/03_seed_dq_004_quarantine_data.py -- a new, dedicated seed notebook (kept separate from every other 03_seed_* notebook) that provisions the test/bronze_test schemas and landing_dq_quarantine/_schemas Volumes, then copies the fixture CSV directly into the landing Volume (no ZIP handling needed for this scenario).

    Outputs¶

    • {{catalog}}.bronze_test.customer_raw -- exactly 8 rows (the 8 fully-valid customers).
    • {{catalog}}.bronze_test.customer_raw_quarantine -- exactly 2 rows (CUST006, CUST007), auto-generated because at least one rules[] entry has action == "quarantine" (see docs/01_control_metadata_schema.md §5). Each row carries a populated __framework_dq_failed_rule_ids (naming exactly the one rule it failed -- these two fixture rows each fail only one of the two rules, not both) and a populated __framework_record_id (the row's own CustomerID).

    Configuration¶

    metaflow_testing/032_dq_004_quarantine.json's one ingestion_flows[] entry:

    "source_config": {
  "path": "/Volumes/{{catalog}}/test/landing_dq_quarantine/",
  "format": "csv",
  "schema_location": "/Volumes/{{catalog}}/test/_schemas/customer_quarantine/",
  "reader_options": {"header": "true", "cloudFiles.inferColumnTypes": "true"},
  "capture_technical_metadata": true
},
"target_config": {"cdc_load_strategy": "APPEND", "storage_format": "delta"},
"dq_config": {
  "rules": [
    {"rule_id": "dq_customer_country_not_null", "expression": "Country IS NOT NULL", "action": "quarantine"},
    {"rule_id": "dq_customer_email_format_valid", "expression": "Email IS NOT NULL AND Email RLIKE '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$'", "action": "quarantine"}
  ],
  "quarantine_table": "customer_raw_quarantine",
  "record_id_column": "CustomerID"
}

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run metaflow_test_dq_004_quarantine_job --target dev

    Task chain: setup_control_tables → seed_dq_004_quarantine_data → onboard_dq_004 → run_pipeline.

    Expected results — simulation notes¶

    SQL assertions (after a run, replace {catalog} with your actual target catalog):

    -- main table: only the 8 fully-valid rows
SELECT count(*) FROM {catalog}.bronze_test.customer_raw;
-- expect: 8

-- quarantine table: exactly the 2 failing rows, with diagnostics populated
SELECT __framework_record_id, __framework_dq_failed_rule_ids
FROM {catalog}.bronze_test.customer_raw_quarantine
ORDER BY __framework_record_id;
-- expect: CUST006 -> ["dq_customer_country_not_null"]
--         CUST007 -> ["dq_customer_email_format_valid"]

SELECT count(*) FROM {catalog}.bronze_test.customer_raw_quarantine;
-- expect: 2

    This pass's actual verification status: see metaflow_testing/TESTING_STATUS.md for whether this job was actually run against the live workspace and what the real result was -- this document describes what should happen structurally; the status tracker records what did happen, if anything, each time this scenario is executed. (Per this project's build convention, that tracker is updated centrally in a later phase, not by this build itself.)

    Build notes / judgment calls¶

    • New fixture, not a reuse. No existing seeded fixture carries both Country and Email columns together (checked sample_data/metaflow_testing/crm_usecase/customer_data.csv, customer_dq_warn.csv, the various sample_customer_*.csv files, and the wide-customer SCD1 fixtures), so one new 10-row CSV (customer_dq_quarantine.csv) and one new dedicated seed notebook were added, reusing the existing crm_usecase/ fixture directory rather than creating a new one.
    • Scaled down from the plan's 85/10/5 to 8/1/1. Per this build pass's explicit convention (a working, onboardable test case matters more than exhaustive row volume), 10 rows with 1 null-Country violation and 1 malformed-Email violation exercise the same two-rule quarantine-routing assertion as 85/10/5 would, just with a trivially-checkable row count.
    • A real, unresolved naming collision, flagged rather than silently avoided. TESTING_PLAN.md's own "Databricks Object Names" column for TC-DQ-004 names the target as {{catalog}}.bronze_test.customer_raw (+ customer_raw_quarantine) -- the exact same catalog.schema.table coordinates the pre-existing, already-deployed metaflow_test_100_zipcsv_pipeline scenario already uses for its own customer_raw (a different dataflow_group_id, different pipeline, and a different source schema: CustomerID/Country/SignupDate there vs. CustomerID/CustomerName/Country/Email here). Lakeflow Declarative Pipelines tie a streaming table's ownership to the specific pipeline that created it -- two independent pipelines targeting the same three-part table name in the same catalog will conflict the moment both have actually run once (whichever runs second will fail claiming the table). This build follows the TC's own literal spec (and reuses scenario 100's exact quarantine-config pattern, per this task's own instruction) rather than unilaterally renaming the target table to something collision-free, since resolving cross-scenario physical conflicts across the full 45-test-case matrix is explicitly this project's later, centralized deployment phase's job, not an individual test-case build's. In practice: only one of metaflow_test_100_zipcsv_pipeline / metaflow_test_dq_004_quarantine_pipeline can be run against a given catalog's bronze_test.customer_raw at a time until that centralized phase either renames one target or resolves the conflict some other way.
    • quarantine_table/record_id_column both set explicitly. Unlike TC-DQ-001 (no quarantine-action rule, so both fields were correctly omitted there), this spec has two quarantine-action rules, so both fields are populated here per docs/17_onboarding_template_reference.md §4.7.
