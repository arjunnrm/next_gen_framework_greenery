    Test Pipeline: TC-ING-003 -- Zerobus Streaming Delta Feed Ingestion (Append-Count Assertion)¶

    See also: Documentation index, flowx_testing/TESTING_PLAN.md (Module 1, TC-ING-003), flowx_testing/TESTING_STATUS.md, docs/30_test_pipeline_recon_features.md (the doc-writing template this follows).

    Purpose¶

    Prove that source_type: "zerobus" ingestion (streaming read of an existing Delta table -- see 01_control_metadata_schema.md §3) correctly picks up a genuinely large batch of newly-appended source rows across two separate pipeline updates -- not just the handful of illustrative records scenario 002's own onboarding already exercises. This test deliberately reuses the already-deployed flowx_test_002_zerobus_pipeline (dataflow_group_id: dfg_flowx_002_zerobus_bronze) rather than standing up a dedicated pipeline of its own -- TC-ING-003 needs no new DAG shape, only a bigger, two-phase data volume against the existing one.

    Responsibilities¶

    • Seed {catalog}.Excalibur_usecase.zerobus_source_bus with 1,000 baseline synthetic customer rows (TC003-000001..TC003-001000), generated on-cluster -- additive to, and non-colliding with, scenario 002/003's own small C001-C007 fixture rows already in that table.
    • Re-onboard dfg_flowx_002_zerobus_bronze from this test's own spec (012_ing_003_zerobus_append.json) so this job is self-contained (works from a clean environment, the same pattern flowx_test_004_recon_features_job already uses to re-onboard scenario 002/003) -- the spec's ingestion flow is a faithful copy of 002_zerobus_data_load.json's own, so onboarding it is an idempotent no-op against an already-onboarded control-table row.
    • Run flowx_test_002_zerobus_pipeline once against the 1,000-row baseline.
    • Append 200 more synthetic rows (TC003-001001..TC003-001200) to the same source table.
    • Run the same pipeline a second time and confirm zerobus_bronze's row count grew by exactly 200 between the two updates.

    Inputs¶

    • flowx_testing/012_ing_003_zerobus_append.json -- re-onboards dfg_flowx_002_zerobus_bronze / df_excalibur_zerobus_ingest (the same dataflow group and flow id scenario 002 already onboards); no new fields beyond that spec's own shape.
    • notebooks/00_seed_sample_data/03_seed_ing_003_zerobus_baseline.py -- new seed notebook, parameterized by id_prefix/start_index/row_count, called twice by this job (baseline 1,000, then append 200).
    • Depends on scenario 002's own seed step (02_seed_flowx_testing_data.py) having provisioned the Excalibur_usecase schema and zerobus_source_bus's baseline shape -- this job runs that step itself first, so it works standalone rather than assuming flowx_test_002_003_job has already run.

    Outputs¶

    • {catalog}.Excalibur_usecase.zerobus_source_bus -- gains 1,000, then 200 more TC003-* rows, on top of whatever scenario 002/003 fixtures already put there.
    • {catalog}.bronze_excalibur.zerobus_bronze -- the shared Bronze streaming table scenario 002 also writes to; after this job's two pipeline updates, its row count has grown by exactly baseline_count + 200 attributable to this run (see Expected results for the exact delta-based assertion).

    Configuration¶

    012_ing_003_zerobus_append.json's single ingestion_flows[] entry: source_type: "zerobus" reading {{catalog}}.Excalibur_usecase.zerobus_source_bus, target_config.cdc_load_strategy: "APPEND", targeting {{catalog}}.bronze_excalibur.zerobus_bronze -- the same shape as scenario 002's own spec, since this test is only about data volume, not a new configuration surface.

    03_seed_ing_003_zerobus_baseline.py widgets:

    Widget Purpose Baseline call Append call
    catalog Target catalog flowx flowx
    id_prefix Synthetic customer_id prefix TC003 TC003
    start_index First synthetic row's 1-based index 1 1001
    row_count How many rows to generate this call 1000 200

    Rows are generated directly from spark.range(start_index, start_index + row_count) (no CSV fixture -- 1,000+ literal rows in a checked-in file would be unwieldy for no real fixture value) with customer_id = '<prefix>-%06d', customer_name = 'TC-ING-003 Synthetic Customer <n>', status = 'ACTIVE', then MERGEd into zerobus_source_bus scoped to just those 3 columns (the same dynamic-column MERGE idiom 02_seed_flowx_testing_data.py::seed_zerobus_style_table_from_csv already uses, so it never collides with any extra column the table has picked up from scenario 003's own self-healing appends, e.g. updated_at). Each call is idempotent: it first counts existing rows already inside its own [start_index, start_index + row_count) id range and skips generation entirely if that range is already fully populated.

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run flowx_test_ing_003_zerobus_append_job --target dev

    Task chain: setup_control_tables -> seed_flowx_testing_data -> seed_ing_003_zerobus_baseline -> onboard_ing_003 -> run_pipeline_baseline -> seed_ing_003_zerobus_append -> run_pipeline_append.

    Expected results¶

    SQL assertions (replace {catalog} with your actual target catalog; capture n1 right after run_pipeline_baseline completes, then n2 after run_pipeline_append):

    -- capture the bronze row count right after the first pipeline update (n1)
SELECT count(*) AS n1 FROM {catalog}.bronze_excalibur.zerobus_bronze;

-- after appending 200 rows and re-running the pipeline, confirm the delta is exactly 200
SELECT count(*) AS n2 FROM {catalog}.bronze_excalibur.zerobus_bronze;
-- expect: n2 - n1 = 200

-- confirm the source bus itself carries all 1,200 synthetic rows this test added
SELECT count(*) FROM {catalog}.Excalibur_usecase.zerobus_source_bus WHERE customer_id LIKE 'TC003-%';
-- expect: 1200

-- Change Data Feed cross-check: exactly 200 append events on the second update
SELECT count(*) FROM table_changes('{catalog}.bronze_excalibur.zerobus_bronze', <version_before_run_pipeline_append>, <version_after_run_pipeline_append>)
WHERE _change_type = 'insert';
-- expect: 200

    TESTING_PLAN.md's original TC-ING-003 template describes an absolute assertion (count(*) = 1,200 exactly, against a dedicated pipeline/schema of its own). This build deliberately reuses scenario 002's shared pipeline and shared zerobus_source_bus/ zerobus_bronze tables instead (per this build's own task instructions), so the row-count assertion above is delta-based (n2 - n1 = 200) rather than an absolute literal, since zerobus_bronze may already carry rows from scenario 002/003/004's own prior runs before this job ever executes. The WHERE customer_id LIKE 'TC003-%' filter isolates this test's own synthetic rows from that pre-existing data everywhere it matters.

    Not yet executed against a live workspace -- see flowx_testing/TESTING_STATUS.md for actual run status; a later phase runs and records it centrally, per this build pass's own scope.

    Real gap / judgment calls made building this¶

    • Reused the existing flowx_test_002_zerobus_pipeline / dfg_flowx_002_zerobus_bronze exactly as instructed, rather than TESTING_PLAN.md's own aspirational dedicated flowx_test_ing_003_zerobus_stream_pipeline/excalibur_usecase schema -- so this test shares its target tables with scenario 002/003/004. Synthetic rows are namespaced under a TC003- customer_id prefix specifically so they never collide with scenario 002/003/004's own C001-C007 fixture rows or their reconciliation-match assertions (which key off those exact ids) -- but this job does add ~1,200 extra rows to a table other scenarios also read from, and both this job and scenario 002/003's own job drive the same Zerobus streaming checkpoint, which is a real, shared-state fragility already flagged for this exact pipeline in TESTING_STATUS.md's scenario 002/003 row (running the two jobs concurrently against the same workspace is not safe; run them sequentially).
    • Generated the 1,000+200 baseline/append rows programmatically (spark.range(...)) in a new seed notebook rather than a static CSV fixture, since a 1,000-row literal CSV would add size with no real fixture value over generated data -- consistent with this build's own "keep this minimal" guidance.
    • The row-count verification is expressed as a delta (n2 - n1 = 200) rather than TESTING_PLAN.md's own absolute 1,200, since the shared table may already carry other scenarios' rows by the time this job runs -- see "Expected results" above for the reasoning.
