    ZIP Ingestion Pipeline¶

    See also: Documentation index.

    Purpose¶

    This FlowX pipeline ingests a batch of ZIP archives landed in a Unity Catalog Volume, joins their contents together, and re-packages the result as a ZIP placed back into an egress Volume -- with explicit, actionable errors for every way a batch of input archives can be wrong.

    Responsibilities¶

    • Validate 4 input ZIPs as a batch (existence, non-empty, structurally valid, no two byte-identical archives) before extracting any of them.
    • Extract each archive, load its member CSV(s) into named staging views.
    • Run a configured join/transform SQL across those staging views.
    • Write the result as a Delta table and as CSV, then re-compress the CSV output into a single output ZIP placed in the egress Volume.
    • Clean up every extracted temp file once the output ZIP exists.

    Inputs¶

    • sample_data/zip_ingestion/ (generated by sample_data/generate_zip_ingestion_fixtures.py): zip_sales_branch_east.zip / zip_sales_branch_west.zip (order extracts) + zip_ref_customers.zip / zip_ref_products.zip (reference data) -- the "4 ZIP files" batch -- plus zip_malformed.zip, zip_sales_branch_east_duplicate.zip, zip_empty.zip for negative-path tests only (never part of the real batch).
    • zip_ingestion_configs/sales_enrichment.json -- zip_paths, extract_dir, staging_view_configs (extracted filename -> view name), join_sql, output_table, output_csv_dir, output_zip_path.

    Outputs¶

    • {catalog}.silver_sales_ops.enriched_sales_orders (Delta) -- 5 orders (3 east + 2 west) each enriched with customer and product attributes plus a computed line_total.
    • /Volumes/{catalog}/egress/zip_ingestion_output/enriched_sales_orders.zip.

    Configuration¶

    Not control-table-driven, unlike ingestion/transformation/reconciliation flows -- see Design decisions below. zip_ingestion_configs/sales_enrichment.json is templated with the same {{catalog}}/{{env}} mechanism as onboarding specs (onboarding/spec_loader.py::substitute_environment_placeholders, reused rather than reimplemented).

    Main execution flow¶

    notebooks/06_zip_ingestion/06_zip_ingestion_pipeline.py -> archive/zip_ingestion_pipeline.py::ingest_zip_batch:

    1. validate_zip_batch -- every problem across the whole batch, collected and reported together (same exhaustive-validation convention as onboarding/spec_validator.py).
    2. extract_encrypted_zip (reused from archive/zip_utils.py) once per archive.
    3. Each extracted file with a configured staging view name is loaded and registered as a temp view; anything extracted but not in staging_view_configs is loaded and logged, not joined -- an unexpected extra file in an archive can't silently participate.
    4. join_sql runs against the registered views.
    5. Result written to output_table (Delta) and output_csv_dir (CSV).
    6. compress_and_encrypt_sink (reused from archive/zip_utils.py) re-archives the CSV output into output_zip_path.
    7. Every extracted temp file is removed in a finally block, regardless of success/failure.

    Platform gotchas: three distinct Volumes/ZIP constraints¶

    Three separate, non-obvious platform behaviors shaped this pipeline's implementation -- easy to conflate, so documented separately:

    1. Don't sync pre-built ZIPs through Databricks Workspace Files. Workspace Files import auto-detects .zip-suffixed uploads and extracts them (the same code path used for notebook-export archives), rather than storing the raw bytes. A sample_data/*.zip fixture built locally and synced by databricks bundle deploy never survives as a .zip by the time a job reads it back -- it silently becomes a directory of its extracted contents.
    2. Don't build a ZIP container directly against a Volume path either. Writing a zipfile.ZipFile/pyzipper.AESZipFile straight to a /Volumes/... destination fails with OSError: [Errno 5] Input/output error on close -- the ZIP format needs to seek back and patch the local file header / write the central directory once every member is added, and Volumes' FUSE mount only supports sequential writes, not seeking on an open-for-write file handle.
    3. Never prepend a file: scheme to a /Volumes/... path passed to a Spark reader. spark.read.csv(f"file:{path}") on an extracted member raised LocalFilesystemAccessDeniedException: Cannot access non /Workspace local filesystem path the first time this pipeline actually ran on serverless/Unity-Catalog-shared compute -- an explicit file: scheme routes the read through a restricted local filesystem implementation that only allow-lists /Workspace, bypassing the Unity Catalog Volume filesystem a bare, unscoped /Volumes/... path resolves through correctly. ingest_zip_batch now passes extracted_path straight through with no scheme prefix.

    The first two are why 00_seed_sample_data.py builds the 4 input ZIPs, and archive/zip_utils.py::compress_and_encrypt_sink builds the output ZIP, the same way: construct the archive in an in-memory io.BytesIO() buffer (always fully seekable), then write the finished bytes to the Volume path with one plain sequential write -- never a pre-built local file synced in, never the archive library targeting the Volume path directly. sample_data/generate_zip_ingestion_fixtures.py still exists for local, offline unit testing (tests/unit/test_zip_ingestion_validation.py reads those files directly off local disk, never through workspace sync or a Volume) -- just don't rely on that local copy reaching a deployed job's Volume path unchanged.

    Design decisions¶

    • Not control-table-driven. A one-shot batch transform's configuration doesn't need always-on control-table treatment the way a continuously-running ingestion/ transformation flow does. A plain JSON config (parallel to, but independent from, test_specs/*.json) is a better fit -- avoids a control table with no ongoing state to track.
    • Batch-level validation before any extraction. Extracting archive 1 and 2 successfully, then discovering archive 3 is corrupt, would leave partially-extracted state to clean up. Validating the whole batch first means a bad batch fails atomically, before any side effect.
    • Duplicate detection is content-based (SHA-256), not name-based. Two archives with different names but identical bytes are exactly as much of a data-quality problem as the same file landed twice under one name -- name-based dedup would miss this.
    • staging_view_configs is an allow-list, not a passthrough. Only extracted files explicitly named are registered as views; anything else extracted is logged and ignored rather than joined, so garbage-in from an archive with an unexpected extra file can't silently change the join's shape.

    Error handling¶

    ArchiveError, naming every problem found, for: missing file, zero-byte file, malformed/ corrupt ZIP, a member failing its CRC check, an archive with zero members, and a byte-identical duplicate archive. FrameworkConfigError if join_sql is malformed or the config JSON is missing a required key.

    Extension points¶

    A 5th+ archive just needs an additional zip_paths entry and (if it introduces a new join input) a staging_view_configs entry -- no code change.

    Example usage¶

    databricks bundle run sample_pipelines_job --profile dev   # task: run_zip_ingestion_sales_enrichment

    Relevant tests¶

    tests/unit/test_zip_ingestion_validation.py -- every negative-path case (missing, empty, malformed, no-members, duplicate), against both synthetic tmp_path fixtures and the real generated sample data. tests/integration/test_zip_ingestion.py -- output table completeness, join correctness, computed column correctness, output ZIP creation, and temp-file cleanup.
