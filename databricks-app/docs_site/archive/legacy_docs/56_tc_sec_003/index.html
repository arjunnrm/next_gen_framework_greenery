    Test Pipeline: Secret Masking & Redaction in Telemetry (TC-SEC-003)¶

    See also: Documentation index, flowx_testing/TESTING_PLAN.md (Module 5, TC-SEC-003), flowx_testing/TESTING_STATUS.md, 16_encryption_and_secrets.md (the full AES/PGP secret-resolution design, including §2's own account of the redaction mechanics this test exercises), 23_lakeflow_sinks.md (sink_config/pgp_zip mechanics), 54_tc_sec_001.md (the AES encrypted_columns config this scenario reuses verbatim), 63_tc_snk_003.md (the PGP sink_config config this scenario reuses verbatim, and the job-architecture convention this scenario follows).

    Purpose¶

    Verify that an encryption key resolved via dbutils.secrets.get() is genuinely never exposed in plaintext anywhere this framework's own telemetry surfaces reach — this project's own structured JSON logs, and the Spark driver/query-plan diagnostics a pipeline update produces. Read this whole document before treating a clean job run as a pass: per this session's own explicit instructions, this build is deliberately NOT written to paper over a real, already-investigated, NOT-yet-fixed gap in crypto/column_crypto.py — see "Expected results" below for exactly what is and isn't actually redacted today, and why.

    One ingestion flow does double duty, exercising both secret-handling code paths this project has in one pipeline update:

    1. target_config.encrypted_columns AES-GCM-encrypts secret_value before {{catalog}}.bronze_sec.secrets_audit_raw is ever materialized, keyed off the SAME {{catalog}}.security.pii_encryption_key UC secret TC-SEC-001/ TC-TRF-003 already reuse. Resolution happens in crypto/column_crypto.py::apply_aes_column_encryption, on the pipeline driver, at graph-definition time.
    2. target_config.sink_config (target_type: "external_sink", format pgp_zip) additionally PGP-exports that same, already-ciphertext row set as a .zip.pgp archive, keyed off the SAME {{catalog}}.security.pgp_public_key_finance_egress_test UC secret TC-SNK-003 already provisions. Resolution happens in engine/sink_registration.py::_resolve_secret_into_options, also on the driver, also at graph-definition time — see 16_encryption_and_secrets.md §6.

    Both are genuine, already-built, real configs from sibling test cases — this scenario does not invent a new encryption/PGP mechanism, only combines the two on one flow specifically to give the redaction assertion below two independent secret-handling code paths to inspect side by side.

    Responsibilities¶

    • One ingestion flow (df_sec_003_secrets_audit_ingest), source_type: "autoloader", cdc_load_strategy: "APPEND" — deliberately the simplest possible CDC strategy (same reasoning as TC-SEC-001/TC-SNK-003): APPEND never touches columns_to_check/hash comparison at all, so there is no risk of violating 16_encryption_and_secrets.md's explicit warning never to put an encrypted (random-IV) column in a change-comparison set, and APPEND + autoloader still publishes a genuine Lakeflow Streaming Table, which target_type: "external_sink" requires of its main table (see 23_lakeflow_sinks.md).
    • target_type: "external_sink" — {{catalog}}.bronze_sec.secrets_audit_raw is materialized as a real, governed, DQ-quarantined table exactly like any other target type, plus a second @dlt.append_flow reads that same table (dlt.read_stream) into dlt.create_sink(format="pgp_zip", ...) — the single target this test case's own instructions name (flowx.bronze_sec.secrets_audit_raw), with the PGP export as an additional side effect of the SAME flow rather than a second, separate transformation flow.
    • target_config.encrypted_columns encrypts secret_value (mode: "GCM"), the one column in this fixture standing in for genuine credential/API-key material.
    • target_config.sink_config.post_export_archive.pgp_encryption is recipient_public_key_secret only (no sign_with_private_key_secret, no AES post_export_archive.secret ZIP password) — the exact same shape TC-SNK-003 already exercises, reused as-is rather than extended, so this scenario's PGP leg is not itself a new thing under test.

    Inputs¶

    • flowx_testing/035_sec_003_redaction.json — the onboarding spec (one ingestion flow, no transformation/reconciliation flows).
    • sample_data/flowx_testing/sec_usecase/secrets_audit_batch1.csv — 5-row plaintext fixture (audit_id, secret_name, secret_value, accessed_by, accessed_at, access_reason) — a small, synthetic credential-vault access-audit log; every secret_name/secret_value is a clearly fake, example-shaped placeholder (AKIAIOSFODNN7EXAMPLE, sk_live_51Hc...EXAMPLE..., etc. — the same "well-known dummy value" convention TC-SEC-001 already established for ssn/credit_card), never real credential material.
    • notebooks/00_seed_sample_data/03_seed_sec_003_redaction_data.py — a new, dedicated seed notebook that provisions the sec landing schema/Volumes, the egress_sec schema + PGP-sink staging/output Volumes (a sink's destination Volume is never auto-created by the pipeline itself — see TC-SNK-003), and lands the fixture CSV.
    • Requires TWO Unity Catalog secrets to already exist, both reused verbatim, neither provisioned by this test case:
    • {{catalog}}.security.pii_encryption_key — see 05_deployment_guide.md §0 prerequisites.
    • {{catalog}}.security.pgp_public_key_finance_egress_test — provisioned by flowx_test_snk_003_pgp_zip_sink_job (see TC-SNK-003) from the disposable test keypair at sample_data/flowx_testing/finance_egress_usecase/ pgp_egress_keypair_public.asc. If TC-SNK-003 hasn't been run against a given workspace yet, provision it directly (same command TC-SNK-003's own doc gives): 
      databricks secrets put-secret security pgp_public_key_finance_egress_test \
  --string-value "$(cat sample_data/flowx_testing/finance_egress_usecase/pgp_egress_keypair_public.asc)"

    Outputs¶

    • {{catalog}}.bronze_sec.secrets_audit_raw — 5 rows; secret_value is BINARY AES-GCM ciphertext, never the plaintext values landed; audit_id/secret_name/accessed_by/ accessed_at/access_reason (and the usual __framework_* technical metadata columns) remain plain, untouched values.
    • /Volumes/{catalog}/egress_sec/audit_zips_export/secrets_audit_<batch_id>.zip.pgp — one PGP-encrypted archive per micro-batch, containing the already-ciphertext row set (the export @dlt.append_flow reads from the already-materialized main table, so secret_value is ciphertext in the exported archive too — a double-encrypted column, by construction, never a plaintext leak on the egress side).
    • Driver-side structured JSON log lines (observability/structured_logger.py::log_flow_event, emitted from logged_operation wrapping flow_registration/sink_registration) for this flow's flow_registration/sink_registration operations — metadata only (flow_id, status, record counts, duration_ms, sink_format, target_type, etc.); see "Expected results" for why this specific surface is not where this test case's real exposure lives.

    Main execution flow¶

    databricks bundle deploy --target dev
# only if not already provisioned by an earlier TC-SNK-003 run in this workspace:
databricks secrets put-secret security pgp_public_key_finance_egress_test \
  --string-value "$(cat sample_data/flowx_testing/finance_egress_usecase/pgp_egress_keypair_public.asc)"
databricks bundle run flowx_test_sec_003_redaction_job --target dev

    Task chain: setup_control_tables → seed_sec_003_redaction_data → onboard_sec_003 → run_pipeline. No separate observability job task — see "Known gaps / judgment calls".

    Expected results — this test is expected to FAIL its own core assertion, not pass cleanly¶

    Read this section before running anything. This is not a normal "run the job, check the counts" scenario. TESTING_PLAN.md's own row for TC-SEC-003 asserts: "Grep driver and task logs for secret key string → 0 matches. All secret references display as [REDACTED]." Two genuinely different things happen when that assertion is actually checked against this framework as it exists today, and conflating them is exactly the mistake this doc exists to prevent:

    1. This project's own structured JSON logs (log_flow_event/logged_operation) — expected to pass cleanly. By design (observability/structured_logger.py's own docstring), the payload this module ever emits is a fixed set of business-level fields — operation, flow_id, status, record counts, duration_ms, error, plus caller-supplied metadata like sink_format/ target_type/cdc_load_strategy. It never carries column data or a resolved secret value at all — there is no code path by which pii_encryption_key's or pgp_public_key_finance_egress_test's plaintext value could reach one of these JSON lines. A grep of this framework's own driver-log JSON output for either secret's literal value is expected to find zero matches, and resolve_secret_value's own error-path logging (crypto/secrets.py) only ever names the catalog.schema.key label, never the value, even on a resolution failure.

    2. Spark's own query-plan/execution-plan surface — expected to FAIL. TESTING_PLAN.md's own wording explicitly includes "execution plans" alongside driver logs, and this is exactly where this framework's current implementation falls short, per a real gap this session investigated and explicitly left open (see crypto/column_crypto.py's own module docstring, and 16_encryption_and_secrets.md §2's "Trade-off this accepts" paragraph — memory: architecture-review-remediation-2026-08, if available):

    "This does mean the resolved key value now exists as a Python string on the driver for the duration of one flow's graph-definition call ... an intentional trade against the alternative of encryption being silently non-functional."

    apply_aes_column_encryption resolves pii_encryption_key's plaintext value once via resolve_secret_ref, then passes it into F.aes_encrypt(F.col(...), F.lit(resolved_key), F.lit(mode)) — as a literal Column value, not interpolated SQL text. That change was made specifically (and correctly) to fix a different, earlier bug: Databricks' spark.redaction.regex credential-redaction machinery keys off the literal substring secret( appearing in a query's text, and previously corrupted the resulting ciphertext when that substring was present. Avoiding that substring genuinely fixes the corruption bug. It does not, however, make the resolved key value itself invisible. F.lit(resolved_key) embeds that plaintext value directly into the DataFrame's expression tree as a Catalyst Literal node — a basic, verifiable property of how F.lit() works, independent of any redaction mechanism. Nothing in this framework's code path additionally masks a Literal node's displayed value, and spark.redaction.regex's own substring-matching approach has nothing to key off here (there is no secret-named key or config string anywhere near this literal — contrast with sink_registration.py's own _resolve_secret_into_options, which deliberately keeps secret in the option key name precisely so that redaction mechanism still fires for the sink's own diagnostics — see 16_encryption_and_secrets.md §6). Concretely, expect the resolved pii_encryption_key value to appear in plaintext wherever this flow's staged-view DataFrame's plan is ever displayed or captured — a .explain(True)/.explain("formatted") call against the staged view, the Spark UI's SQL/DataFrame execution tab for this flow's update, or a full DEBUG-level Catalyst/driver log capture of the optimized plan.

    What this means for the two verification steps below: do not treat a completed job run, or a clean grep of this project's own JSON structured logs, as proof this test case passed. This scenario's honest, complete result is: (a) encryption and PGP export both work correctly (the ciphertext round-trips, the archive decrypts) — functionally this is a passing pipeline; but (b) the "secrets never appear anywhere in telemetry" assertion, taken as broadly as TESTING_PLAN.md states it (driver logs and execution plans), currently fails on the AES leg, specifically because of the gap quoted above. This is the accurate, complete status to record — not a silent pass.

    -- Bronze: secret_value is ciphertext, never plaintext (this part is expected to hold)
SELECT secret_name, typeof(secret_value), base64(secret_value)
FROM {catalog}.bronze_sec.secrets_audit_raw ORDER BY audit_id;
-- expect: typeof = 'binary' for every row; base64 output bears no resemblance to the landed

databricks fs ls dbfs:/Volumes/{catalog}/egress_sec/audit_zips_export/
# expect: secrets_audit_<batch_id>.zip.pgp (no bare .zip files)

    Known gaps / judgment calls¶

    • This test case is built to genuinely surface a known, open gap, not to fake a clean pass. Per this session's own explicit instructions: the spec/resources/fixtures above are built faithfully and are fully deployable, but the "Expected results" section above is written to describe the real, current outcome (encryption/PGP export succeed; the broader no-secret-in-telemetry assertion does not hold for the AES leg's query-plan surface) rather than writing verification steps that would misleadingly suggest full masking already works. Treat any future fix to crypto/column_crypto.py's key-resolution approach (e.g., a genuine per-executor key-derivation scheme that never places the raw key value in a Catalyst Literal) as the trigger to revisit and rewrite this section, not this test case's build itself.
    • Single combined flow, not two. target_config.encrypted_columns and target_config.sink_config coexisting on one target_type: "external_sink" ingestion flow is not explicitly demonstrated elsewhere in this project's existing docs/specs, but nothing in 01_control_metadata_schema.md §4/ 23_lakeflow_sinks.md restricts either field to a particular target_type or to mutual exclusion with the other, and this shape lets one flow satisfy this test case's own single named target (flowx.bronze_sec.secrets_audit_raw) while still genuinely exercising both secret-handling code paths side by side, matching TESTING_PLAN.md's own framing ("Pipeline executes AES encryption and PGP sink packaging") more directly than splitting them across an ingestion flow and a second transformation flow would have.
    • PGP secret reused verbatim from TC-SNK-003, not TESTING_PLAN.md's own placeholder naming. Same pre-existing terminology/naming gap TC-SNK-003 and TC-ING-005 already document — TESTING_PLAN.md's own row doesn't name a secret for TC-SEC-003 at all beyond the ambient "Databricks Secrets" mention, so this build reuses TC-SNK-003's real, already-provisioned {{catalog}}.security.pgp_public_key_finance_egress_test rather than inventing a third PGP keypair/secret for this project to track.
    • No separate run_observability_task. TESTING_PLAN.md's own "Proposed Pipeline & Job Architecture" column names a second task for every TC-* scenario including this one, but — per this project's now-consistent, real, established convention across every already-built scenario (TC-SEC-001, TC-DQ-001, TC-DQ-003, and especially TC-SNK-003, the methodologically closest sibling — see 63_tc_snk_003.md's own "Known gaps" section) — structured JSON logging fires automatically as a side effect of run_pipeline itself, with no separate task needed to "activate" it. This is, in fact, the exact log surface this doc's own "Expected results" section inspects (and finds clean) above.
    • New fixture, not a reuse. sample_data/flowx_testing/sec_usecase/ already holds customer_pii_day1.csv (TC-SEC-001) and accounts_hashed_batch1.csv (TC-SEC-002), but neither is shaped for a credential-vault audit log — a small, new 5-row CSV (secrets_audit_batch1.csv) and one dedicated seed notebook were added instead, under the same sec_usecase/ fixture directory (a genuine, minimal addition, not a new top-level use case directory).
    • egress_sec schema/Volumes are a genuinely new provisioning step, not a reuse of TC-SNK-003's own finance_egress/secure_drops Volumes — kept separate so this scenario's own PGP archives never mix with TC-SNK-003's, even though both flows resolve the exact same recipient public key secret.
