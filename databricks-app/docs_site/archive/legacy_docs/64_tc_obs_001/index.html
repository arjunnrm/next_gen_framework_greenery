    Test Pipeline: TC-OBS-001 -- In-Pipeline Structured JSON Logging Validation¶

    See also: Documentation index, flowx_testing/TESTING_PLAN.md (Module 9, TC-OBS-001), flowx_testing/TESTING_STATUS.md, 25_dlt_observability_module.md (the separate, OTel-oriented observability engine -- not what this test case is about; see the Build notes below).

    Purpose¶

    Prove that every framework-level operation this pipeline exercises -- reading the ingestion source, staging/quarantine-routing, registering the target flow, and (post-deployment) capturing SCD/CDC change counts -- emits exactly one structured JSON log line via observability/structured_logger.py::log_flow_event, and that every one of those lines parses as valid JSON carrying a non-null business identifier and timestamp. This is deliberately a single minimal ingestion flow combining a quarantine-action dq_config rule with an SCD1 cdc_load_strategy, so all of ingestion_read / dq_staging / flow_registration / cdc_change_capture fire from one pipeline run instead of needing several separate scenarios to reach each code path.

    Doc-drift note (read this before writing an assertion against this test case) -- the exact field-name discrepancy this build actually found reading structured_logger.py directly, per this build's own instruction not to invent field names. Both TESTING_PLAN.md's own Module 9 row and this test case's own brief describe the emitted payload as carrying timestamp_utc and pipeline_run_id. Neither name is what log_flow_event actually emits. Reading observability/structured_logger.py::log_flow_event (the sole place this payload is built) top to bottom, the real JSON object is:

    {
  "timestamp": "2026-08-29T12:34:56.789012+00:00",
  "operation": "ingestion_read",
  "flow_id": "df_obs_001_structured_log_ingest",
  "status": "SUCCESS",
  "records_read": null,
  "records_written": null,
  "records_rejected": null,
  "records_quarantined": null,
  "duration_ms": 12.345,
  "error": null
}
    • The timestamp field is named timestamp, not timestamp_utc -- its value is UTC (datetime.datetime.now(datetime.timezone.utc).isoformat()), but the key itself has no _utc suffix. Assert against timestamp.
    • There is no pipeline_run_id field on this payload at all, in any operation this scenario reaches. __framework_pipeline_run_id is a real, current, __framework_-prefixed identifier in this codebase -- but it is a Delta table column stamped onto every row by dq/quarantine.py::add_quarantine_columns (visible on test_structured_log_raw's quarantined rows via a SELECT, see Expected results below), never a field inside this JSON log line. Use flow_id (always present, always non-null in every call site this scenario reaches) as this payload's own business-identifier assertion instead of pipeline_run_id.
    • Per-operation **extra fields actually merged in for the operations this scenario reaches: flow_registration carries target_table/target_catalog/target_schema/target_type/ cdc_load_strategy; ingestion_read carries staged_view_name; dq_staging carries target_table/is_streaming (plus records_read/records_rejected/records_quarantined only on the non-streaming branch -- see Outputs below for why this flow's own dq_staging event omits counts); cdc_change_capture carries target_table/cdc_load_strategy/ captured_version/inserted_count/updated_count/deleted_count (plus starting_version on a real, non-zero capture).

    Responsibilities¶

    • Land 5 synthetic "event" rows (scaled down from any larger volume, per this project's "minimal, real, onboardable" convention) as a single plain CSV in /Volumes/{{catalog}}/ea/landing_obs_json_log/ -- 1 of the 5 (E003) has a NULL amount.
    • One ingestion_flow (df_obs_001_structured_log_ingest), source_type: "autoloader", targeting {{catalog}}.bronze_ea.test_structured_log_raw:
    • dq_config.rules: one action: "quarantine" rule (amount IS NOT NULL) -- this is what makes a quarantine table actually get created and populated (see 01_control_metadata_schema.md §5), which is what makes dq_staging's structured log event meaningful to check, not merely present.
    • target_config.cdc_load_strategy: "SCD1", primary_keys: ["event_id"] -- what makes this flow CDC-dispatched at all, which is the precondition for flow_registration's own cdc_load_strategy field being anything other than APPEND/TRUNCATE_AND_LOAD's no-op label, and for the downstream capture_cdc_change_counts_obs_001 job task's capture_all_scd_change_counts to find a real CDC-dispatched flow to report on.
    • A fourth job task, capture_cdc_change_counts_obs_001 (notebooks/04_governance/04_apply_governance_and_egress.py, capture_cdc_change_counts: "true", apply_abac: "false" since this spec's governance_tags is empty -- nothing to tag), chained after run_pipeline, exercises the fourth and last structured-log-emitting code path this test case cares about: control_plane/post_deployment.py:: capture_all_scd_change_counts runs DESCRIBE HISTORY/table_changes(...) against the now-materialized test_structured_log_raw and emits one operation: "cdc_change_capture" log line -- this must run as a separate, later job task, since a CDC target's post-update Delta commit version isn't knowable from inside the pipeline's own graph-definition code (see 02_cdc_load_strategies.md § Change-count capture via Change Data Feed).

    Inputs¶

    • flowx_testing/042_obs_001_json_log.json -- single-ingestion-flow onboarding spec (no transformation_flows/reconciliation_flows).
    • sample_data/flowx_testing/obs_usecase/structured_log_events.csv (5 rows: event_id, event_type, amount, event_ts) -- new fixture, see Build notes.
    • notebooks/00_seed_sample_data/03_seed_obs_001_json_log_data.py -- a new, dedicated seed notebook that provisions the already-established ea/bronze_ea schemas (idempotent, shared with several other test cases) plus a new landing_obs_json_log Volume, then copies the fixture CSV directly into it (no ZIP handling for this scenario).

    Outputs¶

    • {{catalog}}.bronze_ea.test_structured_log_raw -- 4 rows (E001, E002, E004, E005; E003 is quarantined).
    • {{catalog}}.bronze_ea.test_structured_log_raw_quarantine -- 1 row (E003), carrying a populated __framework_dq_failed_rule_ids (["dq_obs_001_amount_not_null"]), a populated __framework_record_id ("E003"), and a populated __framework_pipeline_run_id -- the real, current location of a per-row run identifier in this codebase, distinct from (and not to be confused with) the structured log line's own field set described above.
    • Structured JSON log lines (driver/cluster stdout for the pipeline update; the governance job task's own "Logs" tab for cdc_change_capture) -- see Expected results for exactly how to retrieve and assert against them. Because test_structured_log_raw is a genuinely streaming target, dq_staging's own log line for this flow lands via the streaming branch of dq/quarantine.py's _quarantine_table() closure -- is_streaming: true, no records_read/records_rejected/records_quarantined counts (a streaming DataFrame cannot be eagerly aggregated inside that closure; see that function's own docstring) -- so this scenario's real, countable quarantine assertion is the SELECT count(*) against test_structured_log_raw_quarantine above, not the dq_staging log line's own (absent) count fields.

    Resources:

    • resources/flowx_test_obs_001_json_log_pipeline.yml -- flowx_test_obs_001_json_log_pipeline (catalog: flowx, schema: bronze_ea, serverless, dataflow.group.id: dfg_obs_001_json_log).
    • resources/flowx_test_obs_001_json_log_job.yml -- flowx_test_obs_001_json_log_job.

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run flowx_test_obs_001_json_log_job --target dev

    Task chain: setup_control_tables -> seed_obs_001_json_log_data -> onboard_obs_001 -> run_pipeline -> capture_cdc_change_counts_obs_001.

    Expected results -- simulation notes¶

    Row counts (after a run, replace {catalog} with your actual target catalog):

    SELECT count(*) FROM {catalog}.bronze_ea.test_structured_log_raw;
-- expect: 4

SELECT count(*) FROM {catalog}.bronze_ea.test_structured_log_raw_quarantine;
-- expect: 1

SELECT __framework_record_id, __framework_dq_failed_rule_ids, __framework_pipeline_run_id
FROM {catalog}.bronze_ea.test_structured_log_raw_quarantine;
-- expect: E003, ["dq_obs_001_amount_not_null"], <a non-null run/update id>

    Log assertion -- how to actually retrieve these lines. structured_logger.py's own module docstring is explicit that Lakeflow Declarative Pipelines' event log has a fixed, closed set of event_type values with no documented API to inject a custom event -- so databricks pipelines get-update/an event-log query will never surface these lines; querying the event log is the wrong tool for this assertion. The real, inspectable surface is driver/cluster stdout:

    1. For the pipeline update itself (ingestion_read/dq_staging/flow_registration): open the pipeline's run in the Databricks UI (Jobs & Pipelines -> Pipelines -> flowx_test_obs_001_json_log_pipeline -> this update), open its cluster from the update's own compute link, and use the cluster detail page's Driver logs tab (stdout sub-tab) -- every logger.info/logger.warning/logger.error call this framework makes, including every log_flow_event line, lands there as one line of plain text containing the JSON payload.
    2. For the governance task's own cdc_change_capture line: since capture_cdc_change_counts_obs_001 is a plain job-task notebook run (not a Lakeflow Declarative Pipeline update), its stdout is available more directly: the Jobs UI's per-task Logs tab for that specific task run (Jobs & Pipelines -> Jobs -> flowx_test_obs_001_json_log_job -> this run -> capture_cdc_change_counts_obs_001 task -> Logs), or databricks jobs get-run-output --run-id <task_run_id>'s logs field via the CLI/SDK.
    3. Copy the driver/task log text into a local file and run it through a JSON-line parser, filtering to lines containing "operation": (every non-framework log line in that same stream will simply fail to parse as JSON and should be skipped, not treated as a failure of this test):
    import json

parsed, failed = [], []
for line in open("driver_stdout.txt", encoding="utf-8"):
    line = line.strip()
    if '"operation":' not in line:
        continue  # not one of this framework's structured log lines
    try:
        parsed.append(json.loads(line))
    except json.JSONDecodeError:
        failed.append(line)

assert not failed, f"{len(failed)} structured log line(s) failed to parse as JSON"
assert all(p.get("timestamp") and p.get("flow_id") for p in parsed), \
    "every structured log line must carry a non-null timestamp and flow_id"
operations_seen = {p["operation"] for p in parsed}
assert {"ingestion_read", "dq_staging", "flow_registration"} <= operations_seen  # pipeline-update lines
# "cdc_change_capture" is emitted by the separate governance task run -- check its own log
# stream (step 2 above) for that one operation name specifically.

    Expect, at minimum, one line each for operation: "ingestion_read", "dq_staging", and "flow_registration" from the pipeline update's own driver log, and one "cdc_change_capture" line from the governance task's log -- each with a non-null timestamp/flow_id and status: "SUCCESS" (the log-level-mapping table in structured_logger.py's own docstring: SUCCESS -> logger.info, so all of these should appear at INFO level on a clean run).

    This pass's actual verification status: see flowx_testing/TESTING_STATUS.md for whether this job was actually run against the live workspace and what the real result was -- this document describes what should happen structurally; the status tracker records what did happen, if anything, each time this scenario is executed. This build phase deliberately does not run databricks bundle deploy/run itself -- a separate, later phase handles deployment/execution centrally across all test cases together.

    Build notes / judgment calls¶

    • Field-name discrepancy, not a blocker. Both this TC's own brief and TESTING_PLAN.md's Module 9 row claim timestamp_utc/pipeline_run_id as the emitted fields. Reading observability/structured_logger.py::log_flow_event directly (per this build's own instruction to verify against that module, not invent names) shows the real field is timestamp (UTC-valued, not _utc-suffixed) and that pipeline_run_id is not a log-line field at all in the current codebase -- it's the unrelated __framework_pipeline_run_id Delta column dq/quarantine.py stamps onto quarantined rows. This doc's own verification section (above) asserts against the real field names; flagged here explicitly rather than silently building a test that would assert against fields the code never emits.
    • New fixture, not a reuse. No existing seeded CSV (checked every sample_data/ flowx_testing/*_usecase/ fixture) carries an event_id/amount/event_ts shape suited to a quarantine-plus-SCD1 combination without pulling in an unrelated business domain (CRM customers, EA departments, etc.), so one new 5-row CSV (sample_data/flowx_testing/obs_usecase/structured_log_events.csv) and one new dedicated seed notebook were added, following this project's existing per-TC fixture convention.
    • bronze_ea/ea schemas reused, landing Volume is new. {{catalog}}.ea/ {{catalog}}.bronze_ea already exist, idempotently provisioned by several other test cases (scenario 001, TC-ING-008, TC-TRF-001, TC-SNK-001) -- reused here rather than inventing a new schema pair, exactly as this task's own target-table instruction (flowx.bronze_ea.test_structured_log_raw) implies. The landing Volume (ea.landing_obs_json_log) is new and distinct from TC-ING-008's own ea.landing_csv, so this scenario's fixture never collides with that test case's own file. The target table name itself (test_structured_log_raw) does not collide with any other test case's own bronze_ea.* target (departments_raw/employees_raw/projects_raw/assignments_raw from scenario 001, departments_tech_metadata_raw from TC-ING-008, trf001_*_raw/snk001_*_raw from TC-TRF-001/TC-SNK-001).
    • A fourth job task added, beyond the usual setup -> seed -> onboard -> run_pipeline chain. This test case is specifically about proving every framework operation's structured log line parses as JSON, not just the ones a bare pipeline-update chain reaches on its own -- cdc_change_capture only ever fires from the separate, post-deployment governance task (see Responsibilities above), so capture_cdc_change_counts_obs_001 was added deliberately. This reuses the existing 04_apply_governance_and_egress.py notebook exactly as TC-GOV-001 does, just with apply_abac: "false" (this spec sets no governance_tags, so there is nothing to tag) and capture_cdc_change_counts: "true" (the one thing this task exists to exercise).
    • No run_observability_task. TESTING_PLAN.md's own "Proposed Pipeline & Job Architecture" column for TC-OBS-001 names a second run_observability_task step. Per TESTING_STATUS.md's own framing (TESTING_PLAN.md is a planned/aspirational matrix, not a literal build spec) and the precedent already set by docs/38_tc_ing_008.md's own build notes, that task is not built here: it would run the separate, observability[]-config-driven OTel/DLT-event-log engine (25_dlt_observability_module.md) that TC-OBS-002/OBS-003 are actually about, not the in-pipeline structured_logger.py stdout logging this test case targets -- TESTING_STATUS.md's own Module 9 row already notes "every scenario's pipeline run already emits structured JSON logs... as a side effect," confirming no dedicated observability job task is needed to exercise it.
