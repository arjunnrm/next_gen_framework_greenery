    Test Pipeline: TC-PRM-006 -- Negative Validation: Undefined Parameter Reference Error¶

    See also: Documentation index, flowx_testing/TESTING_PLAN.md (Module 11, TC-PRM-006), flowx_testing/TESTING_STATUS.md, 17_onboarding_template_reference.md §3.4.

    Purpose¶

    Prove the negative path of ${param} substitution: an onboarding spec whose transformation_sql references a ${param} placeholder that pipeline_parameters never defines must be rejected at onboarding time, before a single row ever reaches the transformation_flow_spec control table. This is the mirror image of TC-PRM-002 (which proves substitution succeeds) -- this scenario proves the guard rail that catches an author's typo/omission fires correctly and fails loud, not silent.

    The mechanism under test is real and already wired: onboarding/spec_validator.py's _validate_sql_syntax calls transformation/parameters.py::substitute_dynamic_parameters against every transformation flow's transformation_sql before it ever runs EXPLAIN against it. That function diffs every ${...} placeholder found in the SQL text against the keys of pipeline_parameters; any placeholder with no matching key raises FrameworkConfigError("Transformation SQL references undefined parameter(s): [...]"). _validate_sql_syntax catches that specific exception and appends it to validate_spec's collected errors list rather than raising immediately (so a spec with multiple problems still gets one full report) -- but 02_onboarding_engine.py then raises OnboardingValidationError the moment validation_errors is non-empty, before any of upsert_dataflow_group_spec/upsert_ingestion_flow_spec/upsert_transformation_flow_spec/ upsert_reconciliation_flow_spec are ever called. So the undefined-parameter check is a genuine preflight gate, not merely a runtime pipeline failure.

    Responsibilities¶

    • One transformation_flows[] entry (ts_prm_006_invalid_param_table), no ingestion_flows/ reconciliation_flows -- the spec only needs to exercise the one broken field.
    • pipeline_parameters: {"region_code": "APAC"} -- deliberately declares one legitimate parameter (also referenced correctly in the SQL, as ${region_code}) so the spec looks like a realistic authoring mistake (a second parameter, dept_code, was simply forgotten) rather than an empty/absent pipeline_parameters block that would trivially explain the failure.
    • transformation_sql: "SELECT employee_id, employee_name, department_id FROM employee_raw_input WHERE department_id = ${dept_code} AND region = ${region_code}" -- ${dept_code} has no corresponding key in pipeline_parameters, ${region_code} does. substitute_dynamic_parameters computes missing = {${...} placeholders} - {parameter keys}, so missing = {"dept_code"} exactly -- region_code being present and used correctly proves the check is precise (it doesn't just fail because some parameter is undefined anywhere in the spec) rather than a coincidental blanket failure.
    • source_inputs still points at a plausible upstream table ({{catalog}}.bronze_hr.employee_raw) purely for spec realism -- it is never actually read. The FrameworkConfigError raises inside substitute_dynamic_parameters itself, which runs strictly before the EXPLAIN <resolved_sql> call that would otherwise touch that table, so this scenario needs no seeded fixture data and no dedicated Lakeflow pipeline at all.

    Inputs¶

    • flowx_testing/048_prm_006_negative_param.json -- transformation-only onboarding spec (no ingestion_flows/reconciliation_flows), one deliberately-broken flow.
    • No sample data / seed notebook -- genuinely not needed. Validation fails before any table is ever read, so there is nothing for a seed step to usefully provision for this scenario.

    Outputs¶

    • Zero rows land in {catalog}.config.transformation_flow_spec (or any other control table) for dfg_prm_006_negative_param -- upsert_transformation_flow_spec (and every sibling upsert call) is never reached, because 02_onboarding_engine.py raises OnboardingValidationError immediately after validate_spec returns a non-empty validation_errors list, before the upsert section of the notebook runs at all.
    • The job's onboard_prm_006 task ends in a FAILED state, with the driver/task error message containing the substring: 
      Transformation SQL references undefined parameter(s): ['dept_code']
      (embedded inside the outer OnboardingValidationError's own message, itself of the form "Onboarding spec validation failed with 1 issue(s):\n - ts_prm_006_invalid_param_table.transformation_sql: Transformation SQL references undefined parameter(s): ['dept_code']".)
    • A FAILED audit-log row is still written to {catalog}.config.onboarding_audit_log for dfg_prm_006_negative_param (02_onboarding_engine.py's own except FrameworkError / OnboardingValidationError branch writes the failure audit entry before re-raising) -- proving the failure is captured, not merely an uncaught crash.

    Configuration¶

    flowx_testing/048_prm_006_negative_param.json's one transformation_flows[] entry (the whole spec, since this is a minimal negative-test fixture):

    "pipeline_parameters": {"region_code": "APAC"},
"transformation_flows": [{
  "flow_step_id": "ts_prm_006_invalid_param_table",
  "dataflow_id": "df_prm_006_employee_dept_filter",
  "target_catalog": "{{catalog}}",
  "target_schema": "silver_hr",
  "target_table": "invalid_param_table",
  "target_type": "streaming_table",
  "source_inputs": [
    {"input_name": "employee_raw_input", "table": "{{catalog}}.bronze_hr.employee_raw", "is_streaming": false}
  ],
  "transformation_sql": "SELECT employee_id, employee_name, department_id FROM employee_raw_input WHERE department_id = ${dept_code} AND region = ${region_code}",
  "target_config": {"cdc_load_strategy": "APPEND", "storage_format": "delta"},
  "dq_config": {"rules": []},
  "governance_tags": {}
}]

    Resources:

    • No pipeline resource -- this scenario never reaches a point where a Lakeflow Declarative Pipeline graph could even be built; onboarding itself is the thing under test.
    • resources/flowx_test_prm_006_negative_param_job.yml -- flowx_test_prm_006_negative_param_job, action_type: CREATE against 048_prm_006_negative_param.json (chosen over VALIDATE_ONLY specifically so the "zero rows committed to transformation_flow_spec" assertion is meaningful proof that the FrameworkConfigError guard actually blocked a real create attempt, not merely a structural given of the VALIDATE_ONLY action type, which always skips the upsert regardless of validation outcome).

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run flowx_test_prm_006_negative_param_job --target dev

    Task chain: setup_control_tables -> onboard_prm_006. This job run is expected to end in a FAILED state -- onboard_prm_006 is the (sole, intended) failing task.

    Expected results -- simulation notes¶

    Assertions (after a run, replace {catalog} with your actual target catalog):

    -- Zero rows ever committed for this dataflow group -- the onboarding upsert never ran
SELECT count(*) FROM {catalog}.config.transformation_flow_spec
WHERE dataflow_group_id = 'dfg_prm_006_negative_param';
-- expect: 0

SELECT count(*) FROM {catalog}.config.dataflow_group_spec
WHERE dataflow_group_id = 'dfg_prm_006_negative_param';
-- expect: 0

-- A FAILED audit entry was still written, capturing the exact error text
SELECT status, error_message FROM {catalog}.config.onboarding_audit_log
WHERE dataflow_group_id = 'dfg_prm_006_negative_param'
ORDER BY onboarded_at DESC LIMIT 1;
-- expect: status = 'FAILED', error_message LIKE '%references undefined parameter(s): %dept_code%'

    Job-level check: the onboard_prm_006 task's own run output/exception should contain the literal substring references undefined parameter(s): ['dept_code']. A run where this task instead succeeds means the guard rail regressed -- that would be a fail of this test case, not a pass, however counterintuitive a "successful" job run sounds.

    This pass's actual verification status: see flowx_testing/TESTING_STATUS.md for whether this job was actually run against the live workspace and what the real result was -- this document describes what should happen structurally; the status tracker records what did happen, if anything, each time this scenario is executed. This build phase deliberately does not run databricks bundle deploy/run itself -- a separate, later phase handles deployment/execution centrally across all test cases together.

    Build notes / judgment calls¶

    • No pipeline resource, by design. TESTING_PLAN.md's own TC-PRM-006 row names a pipeline (flowx_test_prm_006_negative_param_pipeline) in its "Proposed Pipeline & Job Architecture" column, but a Lakeflow Declarative Pipeline is never reached in this scenario -- onboarding fails before any pipeline could be created or run against real data. Building an unused pipeline resource just to match the plan's naming column would be pure ceremony, so this build deliberately omits it (per this pass's own build instructions, a reconciliation/governance/onboarding-only scenario needs no dedicated pipeline).
    • action_type: CREATE, not VALIDATE_ONLY. Both trigger the identical validate_spec call and identical FrameworkConfigError/OnboardingValidationError failure (the check runs unconditionally, before the ACTION_TYPE branch). CREATE was chosen because it makes the "zero rows land in transformation_flow_spec" assertion a genuine proof that the guard blocked a real write attempt; under VALIDATE_ONLY the upsert is always skipped regardless of outcome, so that same assertion would hold trivially even if the parameter guard were broken and validation wrongly passed.
    • No seed step, no new fixture CSV. Every other scenario built this pass reuses or adds sample data because its pipeline genuinely reads rows. This one's whole point is that no read ever happens -- substitute_dynamic_parameters raises inside spec validation, strictly before the post-substitution EXPLAIN call and long before any real pipeline execution. Per this pass's own scope discipline ("test case existing and being onboardable/deployable correctly matters far more than exhaustively real sample data volumes"), inventing a fixture and a seed notebook that would never be touched was judged unnecessary ceremony, not a gap.
    • One decoy parameter (region_code), not an empty pipeline_parameters. Declaring one correct, correctly-referenced parameter alongside the missing one makes this a more faithful negative test than an empty/absent pipeline_parameters block would be -- it proves substitute_dynamic_parameters's missing-key diff is precise (missing = {"dept_code"} exactly, not "parameters is empty so everything is missing"), matching TESTING_PLAN.md's own framing of a realistic single-field omission, not a wholesale missing config block.
