    Test Pipeline: SCD Type 3 Current & Previous State (TC-CDC-005)¶

    See also: Documentation index, flowx_testing/TESTING_PLAN.md (Module 2, TC-CDC-005), flowx_testing/TESTING_STATUS.md, 02_cdc_load_strategies.md § SCD3.

    Purpose¶

    Prove that target_config.cdc_load_strategy: "SCD3" tracks only the current and immediately-previous value of a monitored column — current_status/previous_status — as a subscription's status changes over time, with no full history kept (unlike SCD2) and no overwrite-with-no-trace-of-the-past (unlike SCD1). cdc/scd.py::register_scd3 has no native Lakeflow apply_changes equivalent for this: it materializes full history into a hidden _dim_subscription_scd3_scd2_history table (via stored_as_scd_type="2"), then pivots the two most recent versions of each key into current_<col>/previous_<col> columns on the public target — this scenario is the one place in this test suite that actually exercises that pivot end to end, across 3 genuinely separate pipeline updates (not 3 rows landed at once).

    SCD3 is transformation-flow only — spec_validator.py::_validate_target_config rejects it explicitly on an ingestion_flow ("SCD3 pivots current/previous state via an internal history table, which only makes sense downstream of a raw ingestion flow"). So this scenario's spec necessarily pairs a plain APPEND ingestion flow (landing raw status-change events into Bronze) with a downstream SCD3 transformation flow reading that Bronze table incrementally — it cannot be built as ingestion-only.

    Responsibilities¶

    • One ingestion_flow (df_cdc_005_subscription_events_ingest), source_type: "autoloader", plain CSV, cdc_load_strategy: "APPEND" — every landed status-change event is appended verbatim into {{catalog}}.bronze_sub.subscription_status_events_raw, no dedup, no CDC dispatch (APPEND never needs primary_keys).
    • One transformation_flow (ts_cdc_005_scd3_subscription), reading that Bronze table streaming, with cdc_load_strategy: "SCD3", primary_keys: ["sub_id"], columns_to_check: ["status"], sequence_by_column: "event_ts" — publishing {{catalog}}.silver_sub.dim_subscription_scd3.
    • Land subscription S100's status through 3 separate batches, each followed by its own pipeline update — not 3 rows landed together in one run — so the current/previous pivot is proven to advance correctly across separate incremental updates to the hidden SCD2 history table, the way a real subscription lifecycle actually arrives over time:
    • subscription_batch1.csv — status: TRIAL (event_ts: 2026-08-01T09:00:00Z).
    • subscription_batch2.csv — status: ACTIVE (event_ts: 2026-08-10T09:00:00Z).
    • subscription_batch3.csv — status: CHURNED (event_ts: 2026-08-20T09:00:00Z).

    Inputs¶

    • flowx_testing/023_cdc_005_scd3.json — one ingestion_flows entry (APPEND, Bronze) + one transformation_flows entry (SCD3, Silver); no reconciliation_flows.
    • sample_data/flowx_testing/sub_usecase/subscription_batch{1,2,3}.csv — 3 fixtures, one row each, same sub_id/customer_id/plan_name, differing only in status/event_ts.
    • notebooks/00_seed_sample_data/03_seed_cdc_005_scd3_data.py — a new, dedicated seed notebook, parameterized by a batch_number widget ("1"/"2"/"3") so it can be invoked 3 separate times across the job, landing exactly one new file into /Volumes/{{catalog}}/sub/landing_sub/incoming/ each time. Provisions the sub/bronze_sub/silver_sub schemas and landing_sub/_schemas Volumes (idempotent, re-run before every batch).

    Outputs¶

    • {{catalog}}.bronze_sub.subscription_status_events_raw — 3 rows after all 3 updates, one per landed event, verbatim (APPEND, no dedup).
    • {{catalog}}.silver_sub.dim_subscription_scd3 — exactly 1 row for sub_id = 'S100':
    • After pipeline update 1: current_status = 'TRIAL', previous_status = NULL (only one version exists yet — register_scd3's rank-2 max_by window finds nothing to pull).
    • After pipeline update 2: current_status = 'ACTIVE', previous_status = 'TRIAL'.
    • After pipeline update 3 (final, asserted state): current_status = 'CHURNED', previous_status = 'ACTIVE'.
    • A hidden {{catalog}}.silver_sub._dim_subscription_scd3_scd2_history streaming table (2 versions after update 2, 3 versions after update 3) — the real SCD2 history register_scd3 pivots over; not meant to be queried directly by consumers, but confirms the mechanism.
    • customer_id/plan_name (passthrough, non-tracked columns) present unprefixed on every row — only status is named in columns_to_check, so only it gets pivoted into current_<col>/previous_<col>.

    Configuration¶

    flowx_testing/023_cdc_005_scd3.json's transformation flow — the part of this spec that is actually new/interesting (the ingestion flow is a plain APPEND landing, identical in shape to TC-CDC-001's):

    "source_inputs": [
  {"input_name": "subscription_events_src", "table": "{{catalog}}.bronze_sub.subscription_status_events_raw", "is_streaming": true}
],
"transformation_sql": "SELECT sub_id, customer_id, plan_name, status, event_ts FROM subscription_events_src",
"target_config": {
  "cdc_load_strategy": "SCD3",
  "primary_keys": ["sub_id"],
  "sequence_by_column": "event_ts",
  "columns_to_check": ["status"]
}

    sequence_by_column: "event_ts" is set explicitly (rather than relying on the __framework_ingestion_timestamp_utc fallback) so version ordering inside the hidden SCD2 history table is driven by the subscription event's own business timestamp, not by whichever wall-clock moment each batch happened to be processed at — the more realistic choice for a lifecycle event feed, and independent of exactly when each batch's pipeline update actually runs.

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run flowx_test_cdc_005_scd3_job --target dev

    Task chain (one job, 3 interleaved land/run cycles):

    setup_control_tables
  -> seed_cdc_005_batch1 (lands TRIAL)
    -> onboard_cdc_005
      -> run_pipeline_batch1   (update 1: current=TRIAL, previous=NULL)
        -> seed_cdc_005_batch2 (lands ACTIVE)
          -> run_pipeline_batch2   (update 2: current=ACTIVE, previous=TRIAL)
            -> seed_cdc_005_batch3 (lands CHURNED)
              -> run_pipeline_batch3   (update 3: current=CHURNED, previous=ACTIVE)

    Onboarding (onboard_cdc_005) runs exactly once, immediately before the first pipeline update — the spec itself never changes across batches, only the landed data does, so re-onboarding between batches would be redundant (a harmless no-op upsert, but not needed). Each run_pipeline_batchN task targets the same flowx_test_cdc_005_scd3_pipeline — Auto Loader's own checkpoint ensures each triggered (availableNow) update only picks up the one newly-landed file, and the transformation flow's streaming source input reads that single new row incrementally into the hidden SCD2 history table, which is exactly what makes 3 separate updates necessary to observe 3 separate current/previous pivots (landing all 3 files before any pipeline update would instead collapse all 3 status changes into one Auto Loader micro-batch, and the SCD2 history table would likely see all 3 versions open in the same update — still technically producing current=CHURNED, previous=ACTIVE at the end, but proving nothing about whether the pivot behaves correctly across separate updates, which is this scenario's actual point).

    Expected results — simulation notes¶

    SQL assertions (after all 3 updates have run, replace {catalog} with your actual target catalog):

    -- The asserted final state (TESTING_PLAN.md's own TC-CDC-005 row)
SELECT current_status, previous_status
FROM {catalog}.silver_sub.dim_subscription_scd3
WHERE sub_id = 'S100';
-- expect: current_status = 'CHURNED', previous_status = 'ACTIVE'

-- Exactly one row for this key (SCD3 keeps no separate history rows on the public target)
SELECT count(*) FROM {catalog}.silver_sub.dim_subscription_scd3 WHERE sub_id = 'S100';
-- expect: 1

-- Passthrough columns are untouched (not pivoted, since only 'status' is in columns_to_check)
SELECT customer_id, plan_name FROM {catalog}.silver_sub.dim_subscription_scd3 WHERE sub_id = 'S100';
-- expect: CUST5001, PRO_MONTHLY

-- The raw Bronze landing has all 3 events, verbatim
SELECT count(*) FROM {catalog}.bronze_sub.subscription_status_events_raw;
-- expect: 3

-- The hidden SCD2 history table backing the pivot has all 3 versions
SELECT status FROM {catalog}.silver_sub._dim_subscription_scd3_scd2_history ORDER BY __START_AT;
-- expect: TRIAL, ACTIVE, CHURNED (3 rows)

    Mid-sequence assertions, if you want to verify the pivot advances correctly at each step rather than only checking the final state (run these between run_pipeline_batch1 and run_pipeline_batch2, and again between run_pipeline_batch2 and run_pipeline_batch3):

    -- After update 1 only
SELECT current_status, previous_status FROM {catalog}.silver_sub.dim_subscription_scd3 WHERE sub_id = 'S100';
-- expect: current_status = 'TRIAL', previous_status = NULL

-- After update 2 only
SELECT current_status, previous_status FROM {catalog}.silver_sub.dim_subscription_scd3 WHERE sub_id = 'S100';
-- expect: current_status = 'ACTIVE', previous_status = 'TRIAL'

    This pass's actual verification status: see flowx_testing/TESTING_STATUS.md for whether this job was actually run against the live workspace and what the real result was — this document describes what should happen structurally; the status tracker records what did happen, if anything, each time this scenario is executed. (Per this project's build convention, that tracker is updated centrally in a later phase, not by this build itself.)

    Build notes / judgment calls¶

    • Real, verified column names. current_<col>/previous_<col> are read directly out of cdc/scd.py::register_scd3's own implementation (current_columns/previous_columns list comprehensions over tracked_columns, i.e. columns_to_check) rather than assumed — for this spec's columns_to_check: ["status"], that resolves to exactly current_status/ previous_status, matching TESTING_PLAN.md's own TC-CDC-005 assertion verbatim.
    • New fixtures and a new, parameterized seed notebook. No existing seeded fixture carries a subscription-status-lifecycle shape, so 3 small new one-row CSV fixtures and 1 new seed notebook (03_seed_cdc_005_scd3_data.py, kept separate from every other scenario's own seed notebook) were added. The seed notebook is parameterized by batch_number rather than split into 3 separate notebooks, since all 3 batches share identical schema/Volume-provisioning logic and differ only in which single fixture file gets copied.
    • 3 separate pipeline_task job steps against the same pipeline, interleaved with 3 separate seed steps — a deliberate departure from every other scenario's single run_pipeline step, required by SCD3's nature: the current/previous pivot can only be meaningfully proven to advance if each status change is processed by its own pipeline update, not batched together. onboard_cdc_005 still runs only once, since the spec content itself is unchanged across batches.
    • ingestion_flow needed even though this TC is "about" SCD3. SCD3 is validator-rejected on ingestion flows, so a bronze landing step is structurally required regardless of how minimal this scenario intends to keep things — this mirrors the onboarding template's own ts_template_scd3_example, which likewise reads from an already-ingested bronze table rather than defining SCD3 as an ingestion-side flow.
    • No DQ rules, no governance tags, no encryption. This scenario is scoped to SCD3's own current/previous pivot behavior; DQ (TC-DQ-*) and governance (TC-GOV-*) are separate, already-tracked test modules with their own dedicated rows in TESTING_PLAN.md.
    • No run_observability_task. TESTING_PLAN.md's "Proposed Pipeline & Job Architecture" column names one, but per TESTING_STATUS.md's framing and every other real scenario's own job (e.g. TC-CDC-001's), observability is opt-in via a spec's own observability[] array plus a separate job — not wired in by default here.
