    Test Pipeline: Attribute Value Drift Detection (TC-REC-002)¶

    See also: Documentation index, flowx_testing/TESTING_PLAN.md (Module 7, TC-REC-002), flowx_testing/TESTING_STATUS.md, 07_reconciliation.md.

    Purpose¶

    Prove that the reconciliation engine's hash-based matcher correctly classifies a record present on both sides of a comparison, under the same match_keys, as VALUE_DRIFT the moment a compare_columns attribute differs -- as opposed to MISSING_IN_TARGET/MISSING_IN_SOURCE, which apply only when a key is absent from one side entirely. Customer C001 is landed on both sides with a different status value (SUSPENDED in the baseline, ACTIVE in the CDC feed) so the drift is unambiguous and attributable to exactly one column.

    Responsibilities¶

    • Two small ingestion flows, both source_type: "autoloader", plain CSV, cdc_load_strategy: "APPEND" (a raw landing table for reconciliation comparison, same convention already used by scenario 002/003's own zerobus_bronze/autoload_bronze -- see 02_cdc_load_strategies.md § APPEND):
    • df_rec_002_customer_baseline_ingest -> {{catalog}}.silver_crm.customer_baseline -- C001 @ status=SUSPENDED.
    • df_rec_002_customer_cdc_ingest -> {{catalog}}.silver_crm.customer_cdc -- C001 @ status=ACTIVE.
    • One reconciliation flow (recon_rec_002_customer_drift) comparing customer_baseline (source) against customer_cdc (target) on match_keys: ["customer_id"], compare_columns: ["status"], comparison_direction: "target_to_source" -- deliberately the audit-only direction, so this run never appends/mutates either table (see the flagged gap below for what this direction choice actually means for the VALUE_DRIFT assertion).

    Inputs¶

    • flowx_testing/037_rec_002_drift.json -- 2 ingestion flows + 1 reconciliation flow onboarding spec (no transformation_flows).
    • sample_data/flowx_testing/crm_usecase/customer_baseline_drift.csv (1 row) / customer_cdc_drift.csv (1 row) -- hand-authored, new fixtures (no existing seeded fixture carries this exact baseline-vs-CDC status drift shape on a shared key).
    • notebooks/00_seed_sample_data/03_seed_rec_002_drift_data.py -- a new, dedicated seed notebook (kept separate from every other scenario's own seed notebook) that provisions the crm schema and a dedicated landing_customer_drift Volume (baseline//cdc/ subfolders, so each ingestion flow gets its own Auto Loader incoming zone), then lands both fixtures.

    Outputs¶

    • {{catalog}}.silver_crm.customer_baseline -- exactly 1 row, C001 @ status=SUSPENDED.
    • {{catalog}}.silver_crm.customer_cdc -- exactly 1 row, C001 @ status=ACTIVE.
    • {{catalog}}.config.reconciliation_run_log -- one row for recon_rec_002_customer_drift, matched_count=0, value_drift_count=1 (see 07_reconciliation.md: value_drift_count is a genuine independent aggregate, populated regardless of comparison_direction, since all four classifications are computed in the same join pass).
    • {{catalog}}.config.reconciliation_mismatch_log -- see the flagged gap immediately below for what this configuration actually writes here.

    Configuration¶

    flowx_testing/037_rec_002_drift.json's reconciliation flow:

    {
  "reconciliation_id": "recon_rec_002_customer_drift",
  "source_config": {"type": "table", "table": "{{catalog}}.silver_crm.customer_baseline", "read_mode": "batch", "hash_precomputed": false},
  "target_configs": [
    {
      "target_id": "customer_cdc_target",
      "type": "table",
      "table": "{{catalog}}.silver_crm.customer_cdc",
      "read_mode": "batch",
      "hash_precomputed": false,
      "comparison_direction": "target_to_source"
    }
  ],
  "match_keys": ["customer_id"],
  "compare_columns": ["status"],
  "generate_surrogate_key": false,
  "error_handling": {"on_failure": "warn"}
}

    append_target_table is correctly omitted -- it is only required when comparison_direction includes source_to_target (see 07_reconciliation.md § target_configs[]-only fields), and this flow never appends anywhere.

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run flowx_test_rec_002_drift_job --target dev

    Task chain: setup_control_tables -> seed_rec_002_drift_data -> onboard_rec_002 -> run_pipeline -> run_rec_002_reconciliation.

    Expected results — simulation notes¶

    SQL assertions (after a run, replace {catalog} with your actual target catalog):

    -- Both raw landing tables carry exactly one C001 row, drifted on status
SELECT status FROM {catalog}.silver_crm.customer_baseline WHERE customer_id = 'C001'; -- SUSPENDED
SELECT status FROM {catalog}.silver_crm.customer_cdc      WHERE customer_id = 'C001'; -- ACTIVE

-- reconciliation_run_log: value_drift_count reflects the drift regardless of direction
SELECT matched_count, value_drift_count, missing_in_target_count, missing_in_source_count
FROM {catalog}.config.reconciliation_run_log
WHERE reconciliation_id = 'recon_rec_002_customer_drift'
ORDER BY run_at DESC LIMIT 1;
-- expect: matched_count=0, value_drift_count=1, missing_in_target_count=1 (C001 counts as a
-- source_to_target "miss" in the aggregate -- see 07_reconciliation.md, value_drift_count is a
-- subset of missing_in_target_count), missing_in_source_count=0 (C001 is present on both sides,
-- so it is never MISSING_IN_SOURCE either)

-- reconciliation_mismatch_log -- see the flagged gap below for why this returns 0 rows as
-- literally configured
SELECT mismatch_type, match_key_values_json, differing_columns_json
FROM {catalog}.config.reconciliation_mismatch_log
WHERE reconciliation_id = 'recon_rec_002_customer_drift';

    This pass's actual verification status: see flowx_testing/TESTING_STATUS.md for whether this job was actually run against the live workspace and what the real result was -- this document describes what should happen structurally; the status tracker records what did happen, if anything, each time this scenario is executed. (Per this project's build convention, that tracker is updated centrally in a later phase, not by this build itself.)

    Build notes / judgment calls¶

    • New fixtures, not a reuse. No existing seeded fixture carries a customer_id/status baseline-vs-CDC pair drifted on a shared key (sample_data/sample_recon_customer_master_*.csv is the closest existing shape, but it's a poc-catalog test_specs/spec_09_* fixture using R00N keys and a different drifted record, R003, not C001 -- reusing it would not satisfy this TC's own literal C001 assertion). 2 small new CSV fixtures (1 row each) and 1 new dedicated seed notebook were added.
    • APPEND, not a CDC strategy, for both ingestion flows. Neither customer_baseline nor customer_cdc needs upsert/history semantics -- they are raw landing tables whose only purpose is to feed the reconciliation comparison, the same pattern scenario 002/003 already established for zerobus_bronze/autoload_bronze (see 02_cdc_load_strategies.md § APPEND).
    • Genuine framework gap: comparison_direction: "target_to_source" cannot produce the VALUE_DRIFT row TESTING_PLAN.md's own row asks to verify. This test case's own task description explicitly specifies comparison_direction: "target_to_source" "so nothing gets mutated," then asks to verify a VALUE_DRIFT row for C001 in reconciliation_mismatch_log. Tracing reconciliation/appender.py::run_target_reconciliation (the actual dispatch logic, not just the doc prose) shows these two expectations are mutually exclusive as the engine exists today:
    • evaluate_source_to_target = comparison_direction in ("source_to_target", "both") gates the only code path that ever adds MISSING_IN_TARGET/VALUE_DRIFT rows to mismatch_frames (appender.py lines ~522-527).
    • evaluate_target_to_source = comparison_direction in ("target_to_source", "both") gates a separate path that only ever adds MISSING_IN_SOURCE rows (line ~528-531).
    • So comparison_direction: "target_to_source" alone never writes a VALUE_DRIFT row to reconciliation_mismatch_log — only source_to_target/both do. And since C001 exists on both sides here (just with a drifted status, not an absence), this flow's target_to_source path also finds zero MISSING_IN_SOURCE records — meaning reconciliation_mismatch_log genuinely receives 0 rows for this reconciliation_id as configured, exactly as literally specified.
    • Flipping to comparison_direction: "both"/"source_to_target" would produce the VALUE_DRIFT mismatch-log row this TC wants to verify -- but evaluate_source_to_target unconditionally appends C001's corrected baseline row (status=SUSPENDED) into append_target_table the moment missing_in_target_count > 0 (which VALUE_DRIFT alone already satisfies, since it's a documented subset of that count) -- i.e. it would mutate customer_cdc (leaving it with two C001 rows, ACTIVE and SUSPENDED, append-only), which directly contradicts this same TC's own "so nothing gets mutated" requirement.
    • There is no reconciliation configuration today that audits VALUE_DRIFT into reconciliation_mismatch_log without also performing the self-healing append. This is a real gap in reconciliation/appender.py's design (an audit-only VALUE_DRIFT log without a mutating append is not expressible via any combination of documented fields), not a mistake in how this spec was authored. Per this build's own scope discipline, the spec was built exactly as literally instructed (target_to_source) rather than silently switching to "both" to fake a passing assertion; the reconciliation_run_log.value_drift_count=1 assertion above is the one that will actually pass live -- the reconciliation_mismatch_log row-level assertion, as this TC's own verification logic describes it, will not, until this gap is addressed (e.g. a future audit-only VALUE_DRIFT logging mode independent of the append action).
    • No run_observability_task. Same reasoning as every other TC-* build in this pass (see e.g. 42_tc_cdc_003.md's identical note) -- observability is opt-in via a spec's own observability[] array, not wired in by default.
