    Test Pipeline: Full Snapshot Diffing Without PK (TC-CDC-007)¶

    See also: Documentation index, metaflow_testing/TESTING_PLAN.md (Module 2, TC-CDC-007), metaflow_testing/TESTING_STATUS.md, 02_cdc_load_strategies.md § FULL_SNAPSHOT_CDC_NO_PK.

    Purpose¶

    Prove that target_config.cdc_load_strategy: "FULL_SNAPSHOT_CDC_NO_PK" correctly diffs successive full extracts from a source with no natural business key at all -- a classic legacy mainframe file dump. With no primary_keys configured, dq/quarantine.py:: _apply_hash_and_surrogate_key_columns generates __framework_surrogate_key (crypto/hashing.py::generate_surrogate_key_hash, a deterministic SHA-256 hash of every payload column) and cdc/snapshot.py::register_full_snapshot_cdc uses that hash -- not a user-supplied column -- as the apply_changes_from_snapshot diff key. A row that changes any field is therefore correctly tracked as a delete-of-the-old-row plus insert-of-a-new-row (the only possible interpretation when there is no stable identity to hang an "update" off of), a genuinely new row is inserted, and a row absent from the latest extract is removed.

    Responsibilities¶

    • Land a legacy mainframe customer/account extract in 2 successive full snapshots (Day-1, then Day-2) in the same landing Volume, so the pipeline's two triggered updates each diff one extract against the previous state:
    • Day-1 (sample_mainframe_customer_master_day1.csv, 10 rows): baseline snapshot, no natural key column present (customer_name, customer_city, customer_status only).
    • Day-2 (sample_mainframe_customer_master_day2.csv, 10 rows): John Smith's customer_status changes ACTIVE -> INACTIVE; Fatima Ali's customer_city changes Dallas -> Fort Worth; Wei Zhang is entirely absent (a delete); Noah Kim is a brand-new row (an insert). The other 7 rows are unchanged.
    • One ingestion_flow (df_cdc_007_mainframe_accounts_ingest) with source_type: "autoloader", plain CSV format, cdc_load_strategy: "FULL_SNAPSHOT_CDC_NO_PK", generate_surrogate_key: true (the strategy's own default -- set explicitly here for clarity), no primary_keys at all.

    Inputs¶

    • metaflow_testing/025_cdc_007_snapshot_nopk.json -- single-ingestion-flow onboarding spec (no transformation_flows/reconciliation_flows).
    • sample_data/sample_mainframe_customer_master_day1.csv (10 rows) / sample_mainframe_customer_master_day2.csv (10 rows) -- reused, not newly authored: these already exist, generated by sample_data/generate_sample_datasets.py:: generate_mainframe_snapshot_datasets specifically for a FULL_SNAPSHOT_CDC_NO_PK "two-day snapshot pair: 1 update, 1 delete, 1 insert" scenario -- an exact shape match for this test case, so no new fixture was written.
    • notebooks/00_seed_sample_data/03_seed_cdc_007_snapshot_nopk_data.py -- a new, dedicated seed notebook (kept separate from every other scenario's own seed notebook) that provisions the legacy schema and landing_mainframe/_schemas Volumes, then lands only the Day-1 extract in /Volumes/{{catalog}}/legacy/landing_mainframe/. The Day-2 extract is deliberately not landed by this notebook -- see "Main execution flow" below for the manual second step this scenario requires.

    Outputs¶

    • {{catalog}}.silver_legacy.mainframe_accounts_cdc -- after the Day-1 run: exactly 10 rows, one per Day-1 source row, each carrying a non-null __framework_surrogate_key. After the Day-2 run: still exactly 10 rows (the net Day-2 delta: -1 for Wei Zhang's removal, +1 for Noah Kim's insertion; John Smith's and Fatima Ali's changed rows each still count as exactly one present row, just under a new surrogate-key value).
    • __framework_surrogate_key present and non-null on every row (this strategy's defining column). __framework_hash_key is also present -- with no primary_keys configured, the generated surrogate key itself becomes the key hashed into __framework_hash_key (dq/quarantine.py::_apply_hash_and_surrogate_key_columns).

    Configuration¶

    metaflow_testing/025_cdc_007_snapshot_nopk.json's one ingestion_flows[] entry:

    "source_config": {
  "path": "/Volumes/{{catalog}}/legacy/landing_mainframe/",
  "format": "csv",
  "schema_location": "/Volumes/{{catalog}}/legacy/_schemas/mainframe_accounts_cdc/",
  "reader_options": {"header": "true", "cloudFiles.inferColumnTypes": "true"},
  "capture_technical_metadata": true
},
"target_config": {
  "cdc_load_strategy": "FULL_SNAPSHOT_CDC_NO_PK",
  "generate_surrogate_key": true,
  "storage_format": "delta"
},
"dq_config": {"rules": []}

    Target: {{catalog}}.silver_legacy.mainframe_accounts_cdc, target_type: "streaming_table" (every CDC-dispatched strategy -- including FULL_SNAPSHOT_CDC_NO_PK -- ends up backed by a genuine Lakeflow Streaming Table for its real storage regardless of the flow's declared target_type; see 02_cdc_load_strategies.md). No primary_keys field is set at all -- cdc/snapshot.py::register_full_snapshot_cdc unconditionally uses keys = ["__framework_surrogate_key"] whenever cdc_load_strategy == "FULL_SNAPSHOT_CDC_NO_PK", so one is never needed.

    Main execution flow¶

    databricks bundle deploy --target dev
databricks bundle run metaflow_test_cdc_007_snapshot_nopk_job --target dev

    Task chain: setup_control_tables -> seed_cdc_007_snapshot_nopk_data -> onboard_cdc_007 -> run_pipeline. This first job run lands and processes only the Day-1 extract -- confirm mainframe_accounts_cdc holds exactly 10 rows, each with a non-null __framework_surrogate_key, before moving on.

    Day-2 step (manual, by design -- this is the behavior the scenario exists to prove):

    1. Copy the Day-2 fixture into the same landing Volume, e.g. from a notebook attached to the same catalog: 
      dbutils.fs.cp(
    "file:/path/to/sample_data/sample_mainframe_customer_master_day2.csv",
    "/Volumes/metaflow/legacy/landing_mainframe/sample_mainframe_customer_master_day2.csv",
)
      (or databricks fs cp from the CLI against the same destination path).
    2. Re-run just the pipeline (no need to re-run the whole job -- setup_control_tables/seed_cdc_007_snapshot_nopk_data/onboard_cdc_007 are all a one-time/idempotent prerequisite, not part of the behavior under test here): 
      databricks bundle run metaflow_test_cdc_007_snapshot_nopk_pipeline --target dev
    3. Auto Loader picks up sample_mainframe_customer_master_day2.csv as a new file in its next triggered (availableNow) update; cdc/snapshot.py's _latest_snapshot callback hands the full Day-2 extract (with fresh __framework_surrogate_key values recomputed over every row) to apply_changes_from_snapshot as the new latest-snapshot version, which diffs it against the Day-1 version by surrogate key: John Smith's and Fatima Ali's old-hash rows are removed and their new-hash rows inserted (their real-world identity is the same row, but the framework has no way to know that without a natural key -- it only sees "an old hash disappeared, a new one appeared", which is the documented, correct behavior for this strategy), Wei Zhang's row is removed entirely (absent from Day-2), and Noah Kim's row is inserted (a hash never seen before).

    Expected results — simulation notes¶

    SQL assertions (after the Day-2 run, replace {catalog} with your actual target catalog):

    -- Every row has a surrogate key
SELECT count(*) AS rows_missing_surrogate_key
FROM {catalog}.silver_legacy.mainframe_accounts_cdc
WHERE __framework_surrogate_key IS NULL;
-- expect: 0

-- Row count reflects the net Day-2 delta (10 in, 10 out: -1 delete, +1 insert)
SELECT count(*) FROM {catalog}.silver_legacy.mainframe_accounts_cdc;
-- expect: 10

-- Wei Zhang was removed (present on Day-1, absent from Day-2)
SELECT count(*) FROM {catalog}.silver_legacy.mainframe_accounts_cdc
WHERE customer_name = 'Wei Zhang';
-- expect: 0

-- Noah Kim was inserted (new on Day-2)
SELECT customer_city, customer_status FROM {catalog}.silver_legacy.mainframe_accounts_cdc
WHERE customer_name = 'Noah Kim';
-- expect: San Jose, ACTIVE (1 row)

-- John Smith's status change landed under a new surrogate key, old value gone
SELECT customer_status FROM {catalog}.silver_legacy.mainframe_accounts_cdc
WHERE customer_name = 'John Smith';
-- expect: INACTIVE (1 row, not 2 -- the Day-1 ACTIVE-hash row is gone)

-- Fatima Ali's city change landed the same way
SELECT customer_city FROM {catalog}.silver_legacy.mainframe_accounts_cdc
WHERE customer_name = 'Fatima Ali';
-- expect: Fort Worth (1 row)

    This pass's actual verification status: see metaflow_testing/TESTING_STATUS.md for whether this job was actually run against the live workspace and what the real result was -- this document describes what should happen structurally; the status tracker records what did happen, if anything, each time this scenario is executed. (Per this project's build convention, that tracker is updated centrally in a later phase, not by this build itself.)

    Build notes / judgment calls¶

    • Reused existing fixtures, not new ones. sample_data/sample_mainframe_customer_master_ day1.csv/_day2.csv already existed, purpose-built by generate_sample_datasets.py:: generate_mainframe_snapshot_datasets for exactly this "no natural key, 1 update, 1 delete, 1 insert" shape -- per this project's own build convention (reuse a close-enough existing fixture over inventing a new one), these are read directly from their existing top-level sample_data/ location rather than copied into a new sample_data/metaflow_testing/<usecase>/ subdirectory.
    • Two-step execution is intentional, not a workaround -- the same convention already established by docs/42_tc_cdc_003.md's SCD1 Day-1/Day-2 scenario and 18_test_pipeline_scd1_wide_table_column_exclusion.md. Surrogate-key-based insert/update/delete diffing is only observable across two separate pipeline updates against the same target: a single job run landing both extracts at once would let Auto Loader's one triggered update see both files' rows together, which would not demonstrate a genuine "next full snapshot supersedes the previous one" diff. The job's own automated run therefore covers only Day-1 (a clean, idempotent, fully self-contained job execution); the Day-2 re-land-and-rerun step is documented above as a manual follow-up.
    • generate_surrogate_key: true is set explicitly even though it is this strategy's own documented default (dq/quarantine.py::_apply_hash_and_surrogate_key_columns: target_config.get("generate_surrogate_key", cdc_load_strategy == "FULL_SNAPSHOT_CDC_NO_PK")) -- for readability, matching the worked examples in onboarding_templates/onboarding_spec_full_reference.json and pipeline_onboarding_template.json, both of which set it explicitly too.
    • target_type: "streaming_table", matching every other ingestion flow in this repo. This field only controls whether the framework's internal quarantine-filtered "clean" view is read as a stream or a batch upstream of CDC dispatch (engine/flow_registration.py: is_streaming = flow_row.target_type == "streaming_table" for ingestion flows) -- the strategy's real published target table is always a genuine Streaming Table regardless (cdc/snapshot.py::register_full_snapshot_cdc always calls dlt.create_streaming_table), so this setting does not change the scenario's observable behavior; it is kept purely for consistency with every other ingestion flow already onboarded in this project.
    • No run_observability_task. TESTING_PLAN.md's own "Proposed Pipeline & Job Architecture" column names a second run_observability_task step, but per TESTING_STATUS.md's framing, TESTING_PLAN.md is a planned/aspirational matrix, not a literal build spec -- no other real scenario's job wires observability in by default (it's opt-in, added via a spec's own observability[] array plus a separate job). This build follows the real setup_control_tables -> seed -> onboard -> run_pipeline convention instead.
    • No DQ rules, no governance tags. This scenario is scoped to FULL_SNAPSHOT_CDC_NO_PK's own surrogate-key diffing behavior; DQ (TC-DQ-*) and governance (TC-GOV-*) are separate, already-tracked test modules with their own dedicated rows in TESTING_PLAN.md.
